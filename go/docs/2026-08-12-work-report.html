1. 요약

멘토링 지적 사항을 인프라에 반영하는 것이 이날의 목표였다. 결과적으로 세 가지를 했다 — 보안 통제를 실제로 배포했고, 검토 끝에 도입하지 않기로 결정한 것이 하나 있으며, 그 과정에서 운영을 위협하던 구조적 문제를 발견해 정리했다.

11배포한 보안 통제
5발견·수정한 실제 장애
1검토 후 미채택
0미해결 위험
이날 가장 값이 나간 산출물은 코드가 아니라 판단이다. “Log 계정이 안 해줘서 막혔다”고 적혀 있던 두 항목은 실제로는 우리 쪽 미적용이었고, AI 트리아지는 구현을 끝낸 뒤 도입하지 않는 것이 맞다고 결론 냈다. 근거는 모두 API 조회로 확인했다.

2. 배포한 것

항목내용확인

2-5. 크로스 계정 관측 연결 (OAM)

Log 계정이 모니터링 계정이 되어 워크로드 메트릭을 자기 것처럼 조회한다. 숫자 지표만 공유하고 로그 본문은 보내지 않는다 — 증적(로그)은 이미 불변 S3 + Athena 경로로 가고 있어 중복하면 비용과 복잡도만 는다.

서울     AWS/ApplicationELB · Gochuchamchi/ApplicationSecurity
버지니아  AWS/WAFV2
공유 범위 AWS::CloudWatch::Metric  # 로그·트레이스는 제외

서울 Link가 공유하는 Gochuchamchi/ApplicationSecurity가 이날 배포한 앱 보안 메트릭 필터의 네임스페이스라, 로그인 실패·5xx·권한 거부 신호가 Log 계정 대시보드로 흐른다. 메트릭 필터는 매칭 로그가 실제로 발생해야 데이터포인트를 만들므로 초기에는 그래프가 비어 있을 수 있다.

2-6. 팀 작업 병합·배포

같은 날 팀원이 올린 작업을 세 차례에 걸쳐 병합해 함께 배포했다. 겹치는 파일이 있었으나 변경 영역이 달라 충돌 없이 병합됐고, 매 병합 후 양쪽 기능 생존과 구문·validate를 확인했다.

  • 크로스 계정 보안 대시보드(Log 계정 측 Sink + 워크로드 측 Link)
  • 침해 대응 런북
  • 알림 등급화(P1~P4) 및 EKS 자동격리 보호
  • 중앙 Firehose 전송 상태 알람 — 워크로드 이벤트 버스에 Log 계정 PutEvents 권한 개방 (delivery-error P2 / delivery-delay·throttled-records P3)
  • RDS 감사 로그 Athena 쿼리 — 이날 시작한 rds-audit 중앙화 위에 얹힌 작업
적용 순서를 뒤집을 뻔했다. Firehose 알람은 Log 계정이 보내는 쪽, 워크로드가 받는 쪽이다. 받는 쪽 권한이 없으면 PutEvents가 AccessDenied로 조용히 유실되고, 반대로 워크로드만 먼저 열어두는 것은 무해하다. 처음엔 “팀원 쪽 순서가 있을 수 있다”고 판단했으나 의존 방향을 코드로 확인하니 워크로드가 선행이었다.

3. 검토 후 채택하지 않은 것 — GuardDuty AI 트리아지

멘토 지적(“GuardDuty는 오탐이 많아 현업에서 안 쓴다 / AI로 걸러내는 도구는 니즈가 있다. 단 전량 분석 시 토큰 비용이 관건”)에 대한 답으로 구현을 완료했으나, 도입하지 않기로 결정했다. 구현물은 feat/guardduty-ai-triage 브랜치에 보존돼 있다.

설계상 해결한 것

  • 원시 로그를 모델에 넣지 않는다 — 탐지는 GuardDuty가 끝내고 모델은 finding 1건만 판정
  • 비용 게이트 5중(타입 필터 · severity · 억제 룰 · 판정 캐시 · 일일 상한)
  • AI에게 억제 권한 없음 — 어떤 판정이든 알림은 발송
  • 프롬프트 인젝션 방어 4겹(화이트리스트 · 델리미터 · 구조화 출력 · 인젝션 탐지 시 등급 상향)
  • API 키 없음 — Bedrock IAM 인증만 사용

도입하지 않은 이유

  • 관문 3단 — 모델 액세스 자동화 이후에도 사용 사례 양식 + Marketplace 구독 계약이 필요
  • 데이터 반출 — 서울에서 4.6+ 세대는 전부 global.* 라우팅. APAC 최신은 deprecated 모델뿐
  • 코드가 adaptive thinking · effort · 구조화 출력 · 캐싱을 전제 → 구세대로 낮추면 인젝션 방어 한 축을 잃음
  • 운영비 대비 이득이 현 단계에서 불확실

검토 과정에서 확인한 실제 Bedrock 단가와 추정 비용이다. 발표에서 “토큰 비용” 질문에 대한 근거로 쓸 수 있다.

4. 운영 구조 정리

4-1. 작업 사본 일원화

같은 저장소의 사본이 둘 있었고 양방향으로 갈라져 있었다. 운영 도메인(kycj.click)은 비-git 사본에만, 그날 만든 신규 기능은 저장소에만 있었다. daily-up.ps1이 자기 위치 기준으로 apply하므로 어느 사본에서 돌리느냐로 결과가 갈리는 상태였다.

4-2. 문서 기준 변경

아키텍처 문서의 상태 표가 “Log 계정 대기 2건”으로 적고 있었으나 사실이 아니었다. Log 계정은 이미 apply를 마친 상태였고 막힌 쪽은 워크로드였다 — 해당 코드가 그날 아침 apply보다 늦게 커밋됐을 뿐이다. 표를 정정하고, 문서의 기준을 저장소가 아니라 실물 조회로 고정했다.

6. 남은 작업

당일 해소. 이 자리에는 원래 미해결 위험이 하나 있었다 — account-baseline state에 SSM 세션 로깅 리소스(ssm_sessions 로그 그룹, session_manager_prefs 문서)가 남아 있는데 어느 코드에도 선언이 없어 (전 스택 grep 0건, git 이력 0건) 그 스택을 apply하는 순간 삭제될 상태였다. SSH가 없는 이 환경에서 유일한 접속 감사 증적이고, OAM Link가 같은 스택이라 대시보드 연결을 하려다 로깅을 지울 뻔했다.

terraform state show로 읽은 실물을 그대로 코드로 옮겨 IaC 관리로 되돌렸다. terraform state rm은 쓰지 않았다 — 실물은 살아남아도 관리 대상 밖으로 밀려나 같은 사고가 반복된다. 결과적으로 plan에서 destroy가 사라진 뒤 OAM Link를 적용했다.

이후   2 to add, 0 to change, 0 to destroy

7. 발표에 쓸 만한 지점

“감시를 켜니 장애가 나왔다”

  • DML 감사 활성화 → 5분에 266건 INSERT 실패 발견
  • 앱은 200을 반환하고 있었다 — 관측이 없으면 영원히 몰랐을 고장
  • 보안 통제가 품질 문제를 잡아낸 사례

“심각도 숫자를 믿지 않는다”

  • 루트 자격증명 사용이 severity 2로 버려지고 있었다
  • 타입 기반으로 전환 — 벤더 점수가 아니라 우리 환경 기준
  • 멘토 지적(“의미 있는 필드값에만 경고”)에 대한 직접적인 답

“AI를 검토하고 안 쓰기로 했다”

  • 구현·비용 산정·데이터 반출 분석까지 끝낸 뒤의 결정
  • 월 $23~54, 하드 실링 $360 — 숫자로 답할 수 있다
  • “안 해봐서 모른다”가 아니라 “해보고 안 쓴다”

“책임을 잘못 귀속했던 것을 바로잡았다”

  • 문서엔 “Log 계정 대기”, 실제로는 우리 쪽 미적용
  • 실물 조회로 확인하고 문서 기준 자체를 바꿨다
  • 협업에서 “코드에 있음 ≠ 배포됨”
