반복 패턴 — 8일이 가르쳐준 것

1. destroy/재구축의 적은 "참조되지 않는 의존"이다. NAT 경로, 라우트 테이블, SG 규칙, kubeconfig, ECR 이미지, 수동 비밀번호 — 전부 Terraform 그래프나 state 밖에 있어서 깨졌다. 해법도 일관됨: 그래프에 넣거나(depends_on 모듈 전체), 코드화하거나, 절차를 자동화한다.

2. AWS API의 숨은 제약은 같은 유형이 반복된다. IAM description 한글 불가(7/30) → WAF description 한글 불가(8/3). Helm이 모르는 키 무시(7/29 hostname) → 조용한 실패는 로그·실물 검증으로만 잡힌다 (jar unzip, SHOW TABLES, aws-node 컨테이너 수).

3. 에러 문구 감별표가 쌓이면 해결이 빨라진다. no such host/타임아웃/Unauthorized (EKS), TIMED_OUT/reset/REFUSED (접속), 403 대신 404 (GitHub workflow 스코프) — 7/31 이후 같은 증상은 분 단위로 해결됨.

4. 두 번 재발하면 문서가 아니라 설계를 고친다. ECR 비움 503이 대표 사례 — 세 군데 문서화로도 못 막았고, 자동화/구조 변경이 답이었다. 8/4의 "반쪽 배포"도 같은 경로를 밟았다: 체크리스트가 못 막은 것을 배포 계약 검증·스모크 테스트로 강제화.

5. (8/4 신규) Terraform의 기록과 실제 상태는 다를 수 있다 — 양방향으로. 7/31엔 실패가 성공으로(실패를 삼키는 프로비저너), 8/4엔 성공이 실패로(Inspector2 tainted) 기록됐다. 판정 전에 항상 실상태를 조회하고(list/describe API), "코드 두 벌 + state 한 벌" 상황(폴더 복사, terraform·gitops 분리)을 만들지 말 것 — 뒤처진 코드의 apply는 삭제 명령이 된다.
