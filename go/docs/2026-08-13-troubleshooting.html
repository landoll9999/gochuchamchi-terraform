0. 이 문서를 읽는 법

8/12 기록과 마찬가지로 절반 이상이 실제 결함이 아니라 오진이다. 오늘은 특히 같은 사람이 같은 함정을 문서에 적어 놓고 코드에서 다시 밟은 사례가 두 건 있었다(§2-1, §4-4). 그래서 결함 목록이 아니라 “무엇을 보고 무엇을 잘못 믿었는가” 기준으로 묶는다.

분류뜻건수

오늘의 관통 주제 하나를 꼽으면 — “성공했다”는 신호를 믿을 수 있는가. 검증 스크립트가 통과를 냈는데 아무것도 증명하지 않았고(§2-1), 폴백 로직은 조건이 안 맞아 영원히 안 돌았으며(§2-2), 안전장치는 자기가 실패하면 조용히 사라졌다(§2-3).

1. 착시 — 도구가 만든 가짜 신호

1-1. 오래된 원격 참조가 “이 기능은 폐기됐다”는 정반대 결론을 만들었다

증상
적용 가이드가 지시한 브랜치 feat/guardduty-triage가 없었다. 대신 폐기된 Bedrock 구현(feat/guardduty-ai-triage)과 main의 62f142a chore: AI 트리아지 판정 렌더러 제거 (미채택 확정) 커밋이 있었다.
오진
“이 기능은 폐기됐고 가이드가 틀렸다”고 판단하고 작업을 중단했다. 존재하지 않는 브랜치 + “미채택 확정” 커밋이 맞물려 일관되고 그럴듯한 그림이 나왔다.
원인
git fetch를 하지 않은 상태의 참조로 판단했다. fetch하자 origin/feat/guardduty-triage가 나타났고 Bedrock 브랜치는 원격에서 삭제돼 prune됐다. Bedrock은 폐기됐고 Groq 구현으로 새로 만들어진 뒤였다.
조치
브랜치 상태를 근거로 판단하기 전에 git fetch --prune을 먼저 한다.
교훈. 증상이 “문서·가이드가 저장소와 전면적으로 안 맞는다”이면 가이드를 의심하기 전에 내 참조가 낡았는지부터 본다. 브랜치가 삭제·재생성된 경우 로컬 참조만으로는 정반대 결론이 나온다.

1-2. 중복 억제는 정상 동작했는데 검증이 “실패”라고 했다

증상
[주의] 중복 억제가 안 걸렸습니다. 그런데 출력된 응답 본문은 {"status":"filtered","reason":"중복 finding …"}으로 정상이었다.
원인
검증 스크립트가 Lambda 응답(UTF-8)을 Get-Content -Raw 기본값(CP949)으로 읽어 한글 reason이 깨졌고, -match "중복" 매칭이 실패했다.
조치
-Encoding UTF8 명시.
교훈. 동작은 정상인데 검증이 거짓 실패를 내는 것이 가장 위험하다 — 멀쩡한 것을 고치러 들어가게 만든다. 검증 로직이 한글 문자열을 매칭한다면 그 자체가 인코딩 의존점이다.

1-3. 인코딩 실패가 “알람 0개”로 보였다

증상
검증 스크립트가 CloudWatch 알람을 0개로 보고했다. 알람이 사라진 줄 알았다.
원인
describe-alarms가 'cp949' codec can't encode character '—'로 통째로 실패했다. 알람 설명 문구에 들어 있던 em-dash를 AWS CLI가 Windows 로캘로 인코딩하려다 죽은 것이다. 실패가 조회 대상의 문제처럼 보인다.
실패한 시도
PYTHONIOENCODING=utf-8 — 안 통함(CLI v2는 frozen 바이너리라 파이썬 환경변수를 안 본다). [Console]::OutputEncoding 변경 — 안 통함(죽는 쪽은 콘솔이 아니라 CLI 내부).
조치
--query로 필요한 필드만 뽑는다. 설명 필드를 애초에 출력에서 빼면 인코딩할 문자가 없다.
교훈. “조회 결과가 0개”와 “조회가 실패했다”를 스크립트가 구분하지 못하면 없어진 것으로 오진한다. 조회 실패는 0이 아니라 오류로 다룰 것.

1-4. 부하 테스트 403 30건 — WAF 차단인 줄 알았다

증상
동시 요청 30건이 전부 403. rate 기반 WAF 규칙에 걸려 IP가 차단된 줄 알았다.
판별
단일 요청은 200이었다. IP 차단이면 단일 요청도 막혀야 한다.
원인
User-Agent 헤더 부재. .NET HttpClient는 UA 기본값이 없고, WAF 관리형 규칙의 NoUserAgent_HEADER가 이를 막는다. UA를 붙이자 45건 전부 200.
교훈. WAF가 제대로 도는 증거였지 결함이 아니었다. 부하 도구가 403을 뱉으면 rate limit보다 User-Agent를 먼저 볼 것. 스크립트로 만든 요청은 브라우저가 자동으로 붙여 주는 헤더가 없다.

1-5. “알람에 액션이 없다” — 이 프로젝트의 설계였다

증상
새로 만든 검증 스크립트가 상시 알람 2개를 모두 실패로 판정했다. AlarmActions가 0개였다.
원인
sns.tf:146에 답이 있었다 — 이 프로젝트는 알람에 액션을 붙이지 않는다. EventBridge가 CloudWatch Alarm State Change 이벤트를 알람 이름 접두사 gochuchamchi-로 잡아 SNS로 넘긴다. 즉 액션 없음이 정상이다.
조치
검사를 뒤집었다. 이 설계에서 진짜 위험한 것은 접두사를 안 지킨 알람이 룰에 안 걸려 조용히 통보에서 빠지는 것이므로, 접두사 불일치와 룰 활성 상태를 보게 바꿨다.
교훈. 검사를 짜기 전에 왜 지금 이 모양인지를 코드에서 먼저 찾는다. 일반적인 베스트프랙티스를 기준으로 검사하면 의도된 설계를 결함으로 신고한다.

1-6. 존재하지 않는 S3 오류를 두 번 헛짚었다

증상
“daily-down에서 S3 오류가 뜬다”는 보고.
오진 1
force_destroy 누락으로 BucketNotEmpty가 나는 것으로 추정. 확인 결과 일일 계층 3버킷 전부 force_destroy = true였다.
오진 2
prevent_destroy가 걸려 destroy가 막히는 것으로 추정. 확인 결과 루트 어디에도 없었다.
실제
이미 해결된 문제였다. 5832f65가 CloudFront 로그 버킷을 상시 계층으로 옮겨 고쳤고, AWS에도 적용돼 있었다. 그 커밋은 로컬에 push되지 않은 채 남아 있다가 이날 함께 올라갔다.
교훈. 오류 문구를 확보하기 전에 원인을 추정하지 말 것. 두 번의 추정이 모두 빗나갔고, 그 시간에 persistent/cloudfront-logs.tf 머리말을 읽었으면 바로 나왔다 — 거기에 BucketNotEmpty 실패 사례와 해결 경위가 이미 적혀 있었다.

1-7. 이미 무효가 된 값을 지우려고 계획을 세웠다

증상
tfstate 버전 이력 142개에 CloudFront Origin 검증 헤더가 평문으로 남아 있으니, SSE-KMS 전환과 별도로 헤더 로테이션도 해야 한다고 판단했다.
원인
값의 수명을 확인하지 않고 저장 위치만 봤다. 그 random_password는 go/terraform(일일 계층)에 있어서 매일 밤 destroy되고 아침에 새로 만들어진다. terraform state list로 보니 destroy 직후 현재 state는 리소스 0개였다 — 이력에 남은 값들은 이미 그날로 무효다.
조치
로테이션 작업을 계획에서 뺐다. 대신 이 작업의 값어치를 다시 정의했다 — 평문 노출 제거가 아니라 방어선 이중화(s3:GetObject + kms:Decrypt)와 열람 감사(KMS Decrypt가 CloudTrail에 남는다)다.
교훈. “시크릿이 어디에 저장돼 있나”만큼 “그 값이 며칠짜리인가”가 중요하다. 매일 재생성되는 값은 이력에 남아도 이미 죽은 값이다. 대응 우선순위가 완전히 달라진다.

2. 은폐된 고장 — 성공처럼 보이던 실패

2-1. 검증이 “통과”했는데 아무것도 증명하지 않았다 오늘의 대표

증상
IAM 토큰 재발급 검증 스크립트가 통과를 냈다.
발견 경위
출력에 gochuchamchi_app_iam의 CONNECT 줄이 없었다. 최근 10분간 IAM 계정의 새 접속이 0건이라는 뜻인데 판정은 통과였다. 
CONNECT  rdsadmin                 16회
QUERY    gochuchamchi_app_iam     346회   ← CONNECT 는 0건
판정: 통과
원인
MariaDB는 접속을 맺을 때만 인증하고 그 뒤로는 재인증하지 않는다. IAM 토큰은 “접속 시점의 입장권”이지 세션을 계속 검사하는 값이 아니다. 따라서 이미 열린 커넥션 위의 QUERY는 몇 백 건이든 전부 첫 토큰의 결과이고, 토큰이 만료된 뒤에도 그 커넥션은 아무 일 없이 계속 돈다. 스크립트는 QUERY만 세고 있었으므로 재발급이 한 번도 안 일어나도 통과가 나온다.
조치
HikariCP maxLifetime(기본 30분)을 기다렸다. 커넥션이 폐기되고 새로 열릴 때 캐시가 만료된 뒤라 반드시 토큰을 새로 발급받는다. 14:43~14:45에 물리 커넥션 4개가 교체됐고 FAILED_CONNECT 0건.
실패한 시도
동시 요청 45건으로 풀을 키우려 했으나 새 CONNECT 0건. 응답이 빨라 파드당 커넥션 2개로 전부 처리됐다. maximumPoolSize=10은 필요할 때 늘어나는 한도이지 미리 여는 개수가 아니다.
교훈. 전날 문서에 “219건은 첫 토큰이라 증명이 아니다”라고 정확히 적어 놓고 정작 검사 조건은 같은 함정에 들어가 있었다. 문서로 아는 것과 코드가 검사하는 것은 별개다. QUERY는 “죽지 않았다”를, CONNECT는 “재발급이 됐다”를 증명한다 — 필요한 건 후자였다.

2-2. 폴백 로직이 조건이 안 맞아 영원히 안 돌고 있었다

증상
Gemini에 reasoning_effort=none을 보내자 3회 전부 400. 재시도 폴백이 걸리지 않았다.
원인
400을 받았을 때 오류 본문에 reasoning_effort라는 문자열이 있어야만 파라미터를 빼고 재시도하도록 돼 있었다. Groq은 어느 파라미터가 문제인지 본문에 적어 주지만 Gemini는 "Request contains an invalid argument."라고만 한다. Gemini에서는 이 폴백이 영원히 안 걸린다.
조치
본문 검사를 빼고, 보냈다면 일단 제거하고 한 번 재시도한다. 400의 가장 흔한 원인이고 재시도 비용은 호출 한 번이다.
교훈. provider 하나만 쓰는 동안에는 드러나지 않는 결함이 있다. 오류 메시지의 친절함에 의존한 분기는 다른 벤더에서 조용히 죽는다.

2-3. 안전장치가 자기가 실패하면 조용히 사라졌다

증상
없었다. daily-up.ps1의 코드 변경 게이트는 정상으로 보였다.
원인
게이트는 git으로 변경 여부를 판단한다. 그런데 git 호출이 실패하면 $head·$dirty가 비어 codeChanged=false가 되고, plan 확인을 조용히 건너뛰고 바로 apply로 갔다.
조치
git 정보를 못 읽으면 “변경 있음”으로 보고 plan을 띄워 승인을 받는다.
교훈. 안전장치를 짤 때는 “이 검사 자체가 실패하면 어느 쪽으로 기우는가”를 정해야 한다. 모르면 통과시키는 기본값은 안전장치가 아니다.

2-4. 저녁 종료가 stderr 한 줄에 죽는 상태였다

증상
아직 안 터졌다. 조건이 갖춰지면 daily-down.ps1이 1단계에서 RemoteException으로 죽는다.
원인
검역 SG 조회에 2>$null이 붙어 있었다. PS 5.1은 native 명령의 stderr를 리다이렉트할 때 각 줄을 ErrorRecord로 감싸고, 스크립트가 $ErrorActionPreference="Stop"이라 그 자리에서 죽는다. 버려도(2>$null) 마찬가지다 — 원인은 “리다이렉트했다”는 사실 자체다.
영향
AWS CLI가 stderr를 쓰는 가장 흔한 경우가 SSO 토큰 만료다. 즉 SSO가 만료된 저녁이면 종료가 실패하고 그날 과금이 그대로 간다.
실측
2>$null 붙임 → 사망 / 리다이렉트 없음 → 생존 (stdout·$LASTEXITCODE 모두 정상, 종료코드 128도 정상 감지).
조치
리다이렉트 제거 후 $LASTEXITCODE로 판정. 조회 실패 시 destroy로 넘어가지 않고 aws sso login 안내를 띄우고 멈춘다.
교훈. 같은 파일 33행은 이미 같은 이유로 리다이렉트를 피하고 있었는데 18행만 빠져 있었다. 교훈이 주석으로 남아도 코드 전체에 적용되지는 않는다 — 고칠 때 같은 패턴을 파일·저장소 전체에서 훑을 것.

2-5. 암호화를 바꿨는데 아무 일도 일어나지 않았다

증상
tfstate 버킷 기본 암호화를 SSE-KMS로 바꾸고 “전환 완료”로 넘어갈 뻔했다. 실물을 확인하니 state는 계속 AES256으로 저장되고 있었다.
원인
terraform S3 백엔드는 encrypt = true이고 kms_key_id가 없으면 AES256을 “명시적으로” 보낸다. 명시 지정이 버킷 기본값을 이긴다. 오류도 경고도 없다.
조치
워크로드 버킷을 쓰는 backend.tf 5개에 kms_key_id를 추가하고 각 루트를 재init했다. 키 ARN이 아니라 별칭 ARN을 써서 키를 재생성해도 backend를 안 고치게 했다.
교훈. 서버 측 “기본값”은 클라이언트가 아무것도 안 보낼 때만 적용된다. 도구가 무엇을 명시적으로 보내는지를 확인하지 않으면, 설정을 바꾸고도 바뀐 게 없다. 확인은 설정 조회가 아니라 head-object로 실제 객체를 봐야 한다.

3. 설계 구멍 — 동작하지만 보호가 안 되던 것

3-1. 오늘 없앤 것보다 훨씬 강한 자격증명이 남아 있었다

증상
없었다. 하루 종일 “상시 유효한 DB 자격증명을 없앤다”를 하고 있었다.
발견
“해커가 이걸 털려고 하면 어디로 오는가”를 실물 기준으로 점검하다 나왔다. terra-user — AdministratorAccess, 정적 키, 38일 로테이션 없음, MFA 없음. DB 계정은 DML만 되고 매일 사라지는데 이 키는 IAM·S3·EC2 전부에 무기한이었다.
원인
실작업은 7/30 구계정 철거가 마지막이었으나 그 뒤로도 계속 쓰이고 있었다. ~/.aws/credentials의 [default]가 이 키였기 때문이다 — --profile을 안 붙인 모든 명령이 전권 자격증명으로 돌고 있었다. “안 쓰는 키”가 아니라 “기본값이라 조용히 쓰이는 키”였다.
조치
사용처(terraform 루트·daily 스크립트·CI) 전부 확인 후 백업 → 비활성화 → 로컬 정리. 삭제가 아닌 이유는 공유 계정이라 팀원이 같은 키를 쓸 수 있어서다.
교훈. 보안 작업의 초점이 최근에 만진 것에 쏠린다. 오래돼서 잊힌 것이 더 위험하다. 그리고 프로필만 고치면 안 된다 — 환경변수(프로세스·사용자·시스템)에도 정적 키가 없는지 함께 확인해야 한다.

3-2. 안 쓰는 DB 비밀번호가 파드 환경변수에 남아 있었다

증상
없었다. 앱은 이미 IAM 토큰으로 DB에 붙고 있었고 정상 동작했다.
문제
envFrom의 secretRef: gochuchamchi-db-app이 남아 있어 쓰이지도 않는 DB_PASS가 계속 주입되고 있었다. 파드가 침해되면 그대로 읽히고, 15분이면 만료되는 토큰과 달리 이 값은 만료가 없다.

교훈. 전환을 “새 방식이 동작한다”에서 끝내면 옛 자격증명이 그대로 남는다. 토큰으로 바꾼 목적이 상시 자격증명 제거라면, 안 쓰는 값이 남아 있는 한 목적은 절반만 달성된 것이다.

3-3. Claude를 호환 레이어로 붙였으면 조용히 죽었을 것

상황

영향

조치
호환 레이어 경로를 탈락시키고 네이티브 Messages API로 구현. 코드 주석과 변수 설명 양쪽에 경고를 남겼다. 같은 이유로 Gemini 호환 레이어는 추측하지 않고 실측했다(동작함).
교훈. 호환 레이어는 “붙는다”와 “기능이 다 통한다”가 다르다. 내 코드가 의존하는 필드가 그 레이어에서 지원되는지를 도입 전에 확인할 것 — 무시되는 필드는 에러를 내지 않는다.

교훈. 규칙 기반 배선(이름·태그 매칭)은 배선 누락을 막아 주지만 규칙 위반을 알려주지는 않는다. 그 검사는 따로 만들어야 한다.

교훈. 계층을 나눈 인프라에서 data source는 계층 간 결합이다. “A 루트가 B 루트의 산출물을 읽는다”고 쓰는 순간, 자동화가 B를 도는지를 같이 확인해야 한다. 여기서는 매일 도는 자동화가 A만 돌고 있었다.

공통 원인

증상

조치
저장소의 .ps1 8개 전부 BOM 확보. 새로 추가한 파일만 빠져 있었다.
교훈. 일괄 점검은 앞 3바이트가 ef bb bf인지 보면 된다. 저장소 관례가 있는데 새 파일만 빠지는 전형적인 패턴이다.

4-3. AWS CLI는 file:// 인자를 로캘 인코딩으로 읽는다

증상
text contents could not be decoded. BOM을 없애도 계속 실패했다.
원인
BOM이 아니라 한글이 UTF-8 바이트로 들어간 것이 문제였다. CLI가 CP949로 읽어 디코드하지 못한다.
조치
비 ASCII를 JSON \uXXXX 이스케이프로 바꿔 순수 ASCII로 쓴다. JSON 규격상 동등하고 어떤 로캘에서도 안전하다.
교훈. 인코딩을 “맞추려” 하지 말고 인코딩 의존을 없애는 방향이 확실하다. ASCII로 표현 가능한 형식이 있으면 그것을 쓴다.

4-4. 2>$null도 리다이렉트다

배경
8/11 체크리스트에 2>$null 문제가 이미 적혀 있었고 해법으로 cmd /c "… 2>nul" 경유를 권했다.
실측
더 간단하고 확실한 해법은 리다이렉트를 아예 빼는 것이었다. 2>$null → 사망 / 없음 → 생존(stdout·종료코드 모두 정상).
조치
체크리스트 항목을 실측 결과로 정정. EAP를 Stop으로 올리지 않은 스크립트의 2>&1은 정상 패턴이니 건드리면 안 된다는 것도 함께 명시했다.
교훈. 체크리스트에 적힌 해법도 더 나은 답이 있을 수 있다. “이미 알려진 문제”라고 지나치지 말고, 다시 만났을 때 한 번 더 재볼 것.

4-5. 머지가 문서 때문에 막혔다 — 파일이 겹치지도 않는데

증상
git merge가 Your local changes to the following files would be overwritten으로 거부. 정작 브랜치는 go/docs/를 전혀 건드리지 않았다.
원인
작성 중이던 문서가 인덱스에 스테이징된 상태였다. fast-forward가 아닌 머지는 인덱스가 HEAD와 같아야 진행된다 — 파일이 겹치는지와 무관하다.
조치
git stash push -- <경로>로 잠시 빼고 머지한 뒤 git stash pop --index로 스테이징 상태까지 복원.
교훈. 머지 거부 메시지가 파일 이름을 대면 충돌로 읽히지만, “인덱스가 깨끗하지 않다”는 뜻일 수 있다.

4-6. 남의 계정 버킷을 내 자격증명으로 찾고 있었다

증상
ALB 액세스 로그 검증이 버킷을 못 찾았다.
원인
그 버킷은 gochuchamchi-alb-access-logs-<Log계정>이다. 다른 계정 소유라 워크로드 자격증명으로는 영원히 못 찾는다.
조치
ALB 속성(access_logs.s3.enabled, .bucket)을 보는 것으로 바꿨다. 워크로드에서 확인 가능한 것은 “그리로 쓰도록 설정돼 있는가”까지다.
교훈. 다계정 구조에서 검증을 짤 때는 “이 자격증명으로 확인 가능한 경계가 어디까지인가”를 먼저 정한다. 경계를 넘는 확인은 실패가 아니라 다른 담당자의 몫이다.

4-7. 백엔드를 바꾸면 다음 아침 자동화가 프롬프트에서 멈춘다

증상
(사전 차단) backend.tf를 고친 뒤 terraform init이 마이그레이션 여부를 대화형으로 묻는다.
원인
daily-up.ps1은 비대화형으로 init을 부른다. 프롬프트가 뜨면 거기서 멈추고, 증상은 백엔드와 아무 상관 없어 보인다 — “아침에 인프라가 안 올라온다”로만 보인다.
조치
변경 당일에 5개 루트 전부 terraform init -reconfigure를 돌려 로컬 백엔드 기록을 새 설정과 맞췄다. 그 뒤 평범한 init이 프롬프트 없이 exit 0인 것을 실측으로 확인했다.
교훈. 자동화가 부르는 명령의 대화형 분기를 항상 의식한다. 사람이 손으로 칠 때는 그냥 한 번 엔터인 것이, 자동화에서는 무한 대기다. 설정을 바꾼 날 안에 “자동화가 부르는 형태 그대로” 한 번 돌려 볼 것.

4-8. 계정 구조 때문에 만들 수 없는 자격증명이었다

증상
PR #7이 요구하는 fine-grained PAT 2개(읽기 전용 / 읽기+쓰기)를 발급하려는데 대상 저장소를 고를 수 없었다.
원인
저장소 소유자 landoll9999가 조직이 아니라 개인 계정이고, 작업자는 push만 있고 admin: false인 협업자다. fine-grained PAT의 Resource owner는 본인 계정이나 소속 조직만 고를 수 있다 — 다른 개인의 계정은 선택지에 없다.

Classic PAT로도 대체가 안 된다. private 저장소에 읽기 전용 스코프가 없어서 PR #7이 하려던 읽기/쓰기 분리가 원리적으로 불가능하다. GitHub App도 설치는 소유자 권한이라 마찬가지다.
조치
소유자에게 발급을 요청하는 절차를 문서화하고, 소유자가 어려울 때를 위한 임시 우회로(기존 PAT를 두 시크릿에 복사)를 함께 준비했다.
교훈. 자격증명 설계는 기술 요구사항 이전에 계정 소유 구조에 갇힌다. “최소 권한으로 쪼갠다”는 계획을 세우기 전에 그 토큰을 누가 발급할 수 있는가를 먼저 확인한다. 개인 계정 저장소는 협업자에게 이 선택지를 주지 않는다.

4-9. aws는 되는데 terraform만 죽었다 재발

증상
terraform plan이 No valid credential sources found + InvalidGrantException으로 죽는데, aws sts get-caller-identity는 멀쩡히 성공했다.
원인
캐시가 둘로 나뉘어 있다. AWS CLI는 ~/.aws/cli/cache의 역할 자격증명(수 시간)을 쓰고, terraform의 Go SDK는 ~/.aws/sso/cache의 SSO 토큰을 본다. SSO 토큰만 먼저 만료되면 CLI는 계속 되고 terraform만 실패한다. 실측: 토큰 만료 08:24:32Z, 실패 시각 08:29Z — 5분 차이.
조치
aws sso login --profile workload-admin. 만료 시각은 두 캐시 디렉터리의 JSON에서 expiresAt으로 확인할 수 있다(토큰 값은 출력하지 말 것).
교훈. 이미 알려진 함정인데 또 밟았다 — “한쪽 도구가 되니까 자격증명은 멀쩡하다”는 추론이 반사적으로 나온다. 도구마다 보는 캐시가 다르면 그 추론은 성립하지 않는다. terraform/백엔드 문제로 오진하지 말 것.

가장 값비싼 교훈 — §2-1. “통과”가 아무것도 증명하지 않을 수 있다. 전날 문서에 함정을 정확히 적어 놓고도 검사 조건은 그 함정 안에 있었다. 검증 스크립트를 쓸 때는 “이 검사가 통과했을 때 정확히 무엇이 참인가”를 한 문장으로 쓸 수 있어야 한다. 못 쓰면 그 검사는 아직 설계되지 않은 것이다.
두 번째 — §4-4, §2-4. 교훈이 문서·주석에 남아도 코드 전체에 적용되지는 않는다. 같은 파일 33행이 지키고 있던 규칙을 18행이 어기고 있었고, 체크리스트에 적힌 해법보다 더 나은 답이 있었다. 고칠 때 같은 패턴을 저장소 전체에서 훑는 습관이 문서보다 확실하다.
