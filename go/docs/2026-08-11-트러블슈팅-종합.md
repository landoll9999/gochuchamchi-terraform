## §1. 실행 정책 차단 — ZIP 배포의 Mark of the Web

**증상**: `.\scripts\bootstrap-state.ps1` 실행 즉시 "파일이 디지털 서명되지 않았습니다.
현재 시스템에서 이 스크립트를 실행할 수 없습니다" (`UnauthorizedAccess`).

**원인**: 저장소를 git clone이 아니라 **ZIP 다운로드**로 받음 → 전 파일에 인터넷 출처
표시(Zone.Identifier, Mark of the Web)가 붙음 → `RemoteSigned` 정책이 "인터넷에서 온
스크립트"로 취급해 서명을 요구.

**해결**: `Get-ChildItem -Recurse -File | Unblock-File`로 저장소만 차단 해제.
실행 정책 자체는 건드리지 않음(보안 기준 유지). 이후 작업 사본을 git clone으로
전환해 원천 차단 — clone한 파일에는 MotW가 붙지 않는다.

**교훈**: 팀 배포는 ZIP이 아니라 git clone으로. 8/5 §2에서 `-ExecutionPolicy Bypass`로
우회했던 것과 같은 계열인데, 저장소 단위 `Unblock-File`이 정책을 낮추지 않는 더 좁은 해법이다.

## §2. Windows PowerShell 5.1 비호환 3종 + 원본 버그 1종

**증상**(순서대로 드러남):
1. `aws s3api head-bucket … 2>$null` 줄에서 `NativeCommandError`로 스크립트 즉사.
2. 그다음엔 `Error parsing parameter '--public-access-block-configuration': Invalid JSON` —
   에러 메시지의 `JSON received: {PublicAccessBlockConfiguration:{…}}`에 **따옴표가 하나도 없음**.
3. 스크립트의 한글 출력이 전부 `湲곗〈 tfstate 踰꾪궥…`처럼 깨짐.

**원인**:
1. PS 5.1은 네이티브 명령의 stderr를 리다이렉트하면 ErrorRecord로 승격시키는데,
   스크립트가 `$ErrorActionPreference = "Stop"`이라 "버킷 없음(404)"이라는 **정상 분기가
   종결 오류**가 됨.
2. PS 5.1의 네이티브 인자 전달은 임베디드 큰따옴표를 이스케이프하지 않는다 —
   JSON을 인자로 직접 넘기면 aws.exe에 도달할 때 따옴표가 벗겨진다. (PS 7.3+에서 고쳐진 동작)
3. 스크립트가 BOM 없는 UTF-8 → PS 5.1이 CP949로 읽음. **8/5 §2에서 이미 기록된 함정의 재발.**
4. (환경 무관 원본 버그) `put-public-access-block` 인자를 API 요청 구조 이름인
   `PublicAccessBlockConfiguration` 키로 감쌌는데, CLI 파라미터는 그 구조 **자체**라
   감싸면 안 된다 — PS 7이었어도 `Unknown parameter`로 실패했을 코드.

**해결** (`scripts/bootstrap-state.ps1`을 5.1/7 양쪽 호환으로 수정):
- JSON 인자 → `Set-Content -Encoding Ascii`로 임시 파일에 쓰고 `file://` URI로 전달
  (따옴표 유실 원천 차단, 어떤 PS 버전에서도 동일 동작).
- head-bucket → `cmd /c "… 2>nul"` 경유 (stderr가 PS에 도달하지 않아 승격 자체가 없음.
  try/catch 방식은 `$LASTEXITCODE`가 이전 명령 값으로 남는 경합이 있어 배제).
- 래퍼 키 제거, 파일을 UTF-8(BOM)로 저장.

**검증**: 수정본을 PS 5.1에서 실행 — 기존 버킷 감지(멱등) · 4종 설정 적용 · 한글 정상.

**교훈**: **클러스터/AWS로 들어가는 JSON은 인자로 넘기지 말고 `file://`로** — PS 버전
불문 안전. `2>$null`은 PS 5.1에서 "정상 분기 죽이는 스위치"가 될 수 있다.
`.ps1`은 UTF-8 **BOM 포함**이 기본값이어야 한다(8/5 §2 재발 — pitfalls에 있었지만
새 스크립트가 또 BOM 없이 작성됨. 체크리스트는 새 파일에도 적용해야 한다).

## §3. ACM 검증 레코드 `already exists` — 잔재와의 충돌은 import로

**증상**: terraform 1차 apply가 218개 생성 후 중단 —
`Tried to create resource record set [name='_66…….kycj.click.', type='CNAME'] but it already exists` (apex·www 2건).
argocd·grafana용 검증 레코드는 충돌 없이 생성됨.

**원인**: 과거 이 계정에서 같은 도메인으로 ACM 인증서를 요청했던 잔재.
**ACM DNS 검증 레코드는 (계정, 도메인)당 이름·값이 고정**이라, 재요청하면 정확히 같은
CNAME을 다시 만들려고 한다. 잔재 인증서는 apex·www 2개 SAN뿐이라 argocd·grafana는 무사했던 것.

**해결**: 절차 §13 "이름 충돌은 삭제보다 import 먼저" 그대로 —
1. `terraform state show aws_acm_certificate.this`로 새 인증서가 요구하는 레코드 이름/값 추출.
2. 존의 기존 레코드와 대조 → **이름·값·TTL(60) 완전 일치** 확인.
3. `terraform import 'aws_route53_record.cert_validation["kycj.click"]'
   'Z009…__66…….kycj.click_CNAME'` 형식으로 2건 import.
4. 재plan에서 두 레코드가 무변경으로 수렴함을 확인 후 apply 재개.

**검증**: 이후 `aws_acm_certificate_validation` 정상 완료(NS 위임이 살아 있어 수 분 내 발급),
ALB·CloudFront 모두 신규 인증서로 TLS 종단.

**교훈**: 검증 레코드 충돌은 "지우고 다시"가 아니라 import가 정답 — 값이 같으므로
지울 이유가 없고, 지우면 검증 중인 다른 인증서까지 흔든다. import 전 **값 대조**가
안전핀(값이 다르면 다른 원인이다).

## §4. CI OIDC 실패 — 파일이 아니라 "저장소 Variables"가 구계정

**증상**: `deploy.yml` 수동 실행 → "Could not assume role with OIDC: The web identity
token provided could not be validated". 빌드 단계(gitleaks·Maven·Trivy)는 전부 통과하고
AWS 자격증명 단계에서만 실패.

**원인**: 워크플로는 계정값을 하드코딩하지 않고 `vars.*` 4개로 받는 구조인데,
그 **저장소 Variables가 전부 구계정(307223751140) 값**이었다.
- 판별 근거: 실행 커밋이 `a288da1`(구계정 시절 마지막 커밋) — 파일 수정 없이 돌렸다는 뜻이고,
  파일에는 애초에 계정값이 없다.
- 자동 동기화 장치(`ci-sync.tf`의 `sync_github_ci_variables`)가 있었지만 **이 PC에 gh CLI가
  없어 설계대로 조용히 건너뛰고** 수동 명령만 출력한 상태였다(apply 로그에 남아 있었음).
- 8/6 §1의 "GitHub 변수가 옛 KMS 키를 가리킴"과 같은 뿌리 — 재구축하면 GitHub 쪽 값이
  낡는다. 이번엔 키 하나가 아니라 4개 전부였다.

**해결**: Variables 4개를 신계정 값으로 교체(ECR URL / 빌드 역할 / 서명 역할 / KMS 키 ARN).
교체 전에 신계정 IAM에서 OIDC 프로바이더와 두 역할의 신뢰 정책을 사전 검증 —
sub 조건이 `repo:…:ref:refs/heads/main`(빌드), `repo:…:environment:production-signing`(서명)으로
정확히 준비돼 있어 "값만 바꾸면 통과"임을 확인하고 진행. 재실행 → build·sign 모두 성공.

**검증**: ECR에 `candidate-…` → `signed-a288da1…` → `sha256-….sig` 3종 확인.

**교훈**: **재구축 후 CI 실패는 워크플로 파일보다 저장소 Variables/Secrets부터** 본다.
실행 커밋 SHA가 "코드 문제인지 설정 문제인지"를 가르는 1차 판별 근거.
gh CLI를 설치·로그인해 두면 다음 재구축부터 apply가 자동 동기화한다(ci-sync.tf).

## §5. CI 성공 후에도 ImagePullBackOff — gitops 참조가 두 겹으로 낡음

**증상**: §4 해결로 서명 이미지가 ECR에 올라갔는데도 파드는 계속 `ImagePullBackOff`.

**원인**(두 겹):
1. gitops 매니페스트의 이미지 레지스트리가 구계정 `307223751140.dkr…` — 신계정 ECR에
   아무리 이미지를 밀어도 파드는 구계정에서 pull을 시도.
2. 레지스트리를 고친 뒤에도 태그가 임의 SHA(`a45e6d79…`) — 이 워크플로가 만드는 태그는
   `candidate-<sha>-<run>-<attempt>`와 `signed-<git SHA>`뿐이라 **그 태그의 이미지는 영원히
   생기지 않는다**. (spring main HEAD는 `a288da1` — 어디서 온 SHA인지 불명, 착오로 추정)
3. 태그를 자동으로 맞춰 줄 Image Updater는 §6으로 마비 상태 — 자동 복구 경로가 없었다.

**해결**: `kustomization.yaml`의 `images[].name`/`deployment.yml`의 image를
`828885965304.dkr…`로, `newTag`를 `signed-a288da1…`(CI가 실제로 만든 태그)로 교체.
§6 수복 후에는 Image Updater가 write-back으로 태그를 관리하므로 이 수동 개입은 최초 1회로 끝.

**검증**: ArgoCD Synced → 파드 2/2 Running(`signed-a288da1…`) → `https://kycj.click` 200.

**교훈**: 계정 이관 시 gitops는 **레지스트리와 태그가 별개의 낡음**이다 — 레지스트리만
고치면 "존재하지 않는 태그"로 증상이 그대로 이어져 "고쳤는데 그대로"(8/4 §1의 직렬
다중 원인 패턴) 함정에 빠진다. 태그는 손으로 지어내지 말고 **CI 태그 규칙에서 도출**할 것.

## §6. `fork/exec …: no such file or directory` — 파일은 있었다, 인터프리터가 없었다

오늘의 핵심. Image Updater가 2분마다:

```
Could not fetch credentials: error executing /scripts/ecr-auth.sh:
fork/exec /scripts/ecr-auth.sh: no such file or directory
```

**진단이 어려웠던 이유**: "파일이 없다"는 메시지와 달리 **전부 존재**했다 —
파드에 `/scripts` 마운트 ✓, `argocd-image-updater-authscripts` ConfigMap ✓, 키 `ecr-auth.sh` ✓.
분기점은 `fork/exec`의 ENOENT가 **두 가지를 가리킨다**는 것: 대상 파일 부재 **또는
셔뱅 인터프리터 부재**. ConfigMap 내용을 바이트로 찍자 정체가 드러났다:

```
#!/bin/sh<CR><LF>        ← 커널이 "/bin/sh\r"라는 인터프리터를 찾다 ENOENT
echo "AWS:$(aws ecr get-login-password …)"<CR><LF>
```

**근본 원인**: git clone(autocrlf=true)이 `.tf` 파일을 CRLF로 변환 →
`argocd.tf`의 heredoc 문자열에 CR이 그대로 들어감 → helm values → ConfigMap → 셔뱅 파괴.
구계정에서 정상이었던 이유는 그때가 **LF 체크아웃**이었기 때문(같은 코드, 다른 줄바꿈).
**8/5 §1에서 `.gitattributes`로 이 계열을 막았다가 §7에서 삭제(회귀)** — 그 대가가
문서 노이즈가 아니라 인프라 장애로 돌아온 첫 사례다.

**해결**: `argocd.tf`의 스크립트 heredoc을 `replace(…, "\r\n", "\n")`로 감싸
**체크아웃 설정과 무관하게 LF 보장**. plan 검토(helm_release in-place 1 + 상시 게이트 3 +
앱 타깃그룹 경보 2 신규 — 전부 예상 범위) 후 apply.

**검증**: 컨트롤러 로그 `images_updated=1, errors=0`. gitops에 write-back 커밋
(`build: automatic update of gochuchamchi`) 자동 생성 — 감지→커밋→sync→롤아웃 체인 완전 복구.
이 시점에 스모크 테스트 전 항목 PASS.

**교훈**:
- `fork/exec` ENOENT에서 파일이 존재하면 **다음 용의자는 셔뱅**(CRLF 또는 인터프리터 경로).
  판별은 ConfigMap/파일 내용을 `<CR>` 가시화해서 볼 것.
- **클러스터로 들어가는 셸 스크립트를 .tf/차트 heredoc에 둘 때는 줄바꿈을 코드에서 강제**
  (`replace`)하거나 `.gitattributes`(`*.tf text eol=lf`)로 저장소 차원에서 고정할 것.
  같은 위험이 다른 heredoc·차트 스크립트에도 잠재한다.
- 한 번 지운 가드(.gitattributes)는 "노이즈 감수"가 아니라 **장애 예약**이었다 — 재도입.
