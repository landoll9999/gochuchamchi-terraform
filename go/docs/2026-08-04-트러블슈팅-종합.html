§1. DB 전면 500 — "반쪽 배포"

증상: 정적 페이지 정상, DB를 타는 요청은 전부 500 (/api/health 500). 새 파드는 CreateContainerConfigError, 고장난 옛 파드가 계속 서빙.

근본 원인: 제로트러스트 전환은 terraform apply와 gitops 수정이 한 세트인데 gitops 쪽이 누락된 채 apply만 실행됨 — 이중 잠김 상태.

기존 파드
admin + 평문→ require_secure_transport=1
평문 거부→ 500 · 새 파드→ 삭제된 Secret 참조
시작 불가

해결: gitops secret 이름 교체 + redis secret 추가 + 연쇄 발견 4건(kubectl KUBECONFIG, helm 주석 {{ }}, PAT 주입, NetworkPolicy DNS) — 상세 2026-08-04.md §4.1~4.5. 검증: /api/health 500 → 302, 메인 200.

terraform 변경과 gitops 변경이 결합된 작업은 한 PR/한 사람이 원자적으로. "고쳤는데 그대로"면 같은 증상의 다른 원인을 의심할 것 (500의 원인이 5겹이었다).

§2. 진단 환경 제약 — 컴퓨터별 계정/자격증명 분리

증상: 이 컴퓨터에서 인프라 조회·수정 불가. 원인: 인프라·tfstate는 admin 프로파일 계정(옆컴퓨터에만 있음), 이 컴퓨터의 terra-user는 다른 계정 소속. gitops 저장소도 비공개.

대응: 코드·문서 기반 추론 + 외부 검증 신호 — curl(HTTP 상태), Resolve-DnsName(CloudFront 경유 여부), git 이력. 실행 조치는 전부 "옆컴퓨터에서 실행할 명령"으로 산출.

권한 없는 환경에서도 진단은 가능하다. 단 결론에 "확인한 것"과 "추정인 것"을 구분해 표기할 것.

§3. full-HA 13개 파일 소실 — 폴더 복사 버전 관리의 대가

증상: CloudFront/WAF가 계정에서 사라짐. 코드에도 없음.

타임라인
~8/3 오전
fin 라인: full-HA 13개 파일→ 8/4 10:53 first commit
13개 파일 없는 구버전 베이스→ 같은 tfstate에 apply
= state 잔여 리소스 삭제→ CloudFront/WAF 소멸

7/31에도 같은 유형("11개 수정 흔적 복원 불가") — git 없이 fin/찐막/go(final) 폴더 복사로 버전 관리한 구조적 결과.

해결: fin 사본에서 복원 + 8/4 제로트러스트와 3-way 병합 (terraform validate 통과). 병합 원칙:

8/4 코드 우선 (복원 안 함)

  • key_name (B2로 제거), argocd_git_pat (B3 ESO)
  • 배스천 ClusterAdmin → 네임스페이스 Edit 유지
  • DB 마스터 접속·구 elasticache — 제로트러스트 유지

대체·버그로 제외

  • network-policies → 8/4 k8s-network-policies.tf가 대체
  • sns-alerts → SNS 허브(§8)가 상위 호환
  • github-oidc → ecr.tf OIDC와 중복 (같은 URL provider는 계정당 1개 — fin 자체 버그)
후속: 복원 커밋 이후 waf-cdn.tf(611줄, edge.tf와 역할 중복)가 추가 커밋됐다가 origin 753f4f5에서 삭제되고 edge-logs.tf로 재구성됨 → apply 전 반드시 git pull (중복 CloudFront/WAF 생성 방지).
라인이 여러 갈래면 파일 몇 개의 존재/시각으로 최신을 판단하지 말고 전 파일 diff로 각 라인의 고유 변경을 식별해 병합할 것. tfstate를 공유하는 코드가 두 벌이면, 뒤처진 쪽의 apply는 곧 삭제 명령이 된다.

§4. 병합 시 파괴적 변경 식별 — plan에 replace가 뜨면 중단

항목적용 시 결과처리
RDS kms_key_id (CMK 전환)인스턴스 교체 → DB 데이터 소실보류 fin 스스로 경고했던 항목
EFS kms_key_id파일시스템 교체 → 파일 소실보류 efs.tf에 주석으로 위치 표시
로그 버킷 object_lock_enabled버킷 교체 (생성 시점에만 설정 가능)보류 대신 DenyObjectDeletion/DenyPolicyTampering으로 차선 방어

검사법: apply 전 plan에서 must be replaced를 반드시 훑는다. RDS·EFS·로그 버킷에 replace가 보이면 보류 항목이 새어 들어간 것 → 중단.

"보안 강화 설정"이라도 기존 스택에는 파괴적일 수 있다. 재생성 유발 속성(암호화 키, object lock, 서브넷)은 재구축 사이클에 모아서 반영한다.

§5. Cost Anomaly Monitor 거부 — AWS 선점 리소스와 한도 충돌

증상: Limit exceeded on dimensional spend monitor creation (400).

원인: Cost Explorer 최초 활성화 때 AWS가 Default-Services-Monitor (DIMENSIONAL/SERVICE)를 자동 생성해 두는데, 이 타입은 계정당 1개 한도 — 복원된 cost-monitoring.tf가 두 번째를 만들려다 거부.

해결: 새로 만들지 않고 기존 것을 import 후 이름만 in-place 변경 (재생성 없음):

aws ce get-anomaly-monitors --profile admin --region us-east-1 `
  --query "AnomalyMonitors[?MonitorType=='DIMENSIONAL'].MonitorArn" --output text
terraform import aws_ce_anomaly_monitor.services "<ARN>"
"계정당 N개" 한도 리소스는 AWS가 선점해뒀을 가능성을 list API로 먼저 확인. 콘솔을 한 번 연 것만으로 생기는 리소스들이 있다.

§6. Inspector2 타임아웃 — 성공이 실패로 기록됨

증상: aws_inspector2_enabler create 5분 타임아웃, 재시도해도 반복.

활성화 요청→ 5분 타임아웃
state: tainted→ AWS는 계속 진행
결국 ENABLED
다음 apply → tainted라 destroy
= Inspector 비활성화→ 재생성 → 같은 타임아웃 = 무한 루프

해결: 실제 상태 조회 → 성공 확인 → untaint + 타임아웃 연장:

aws inspector2 batch-get-account-status --profile admin   # ec2/ecr ENABLED 확인
terraform untaint aws_inspector2_enabler.this             # destroy 루프 차단
# + ecr.tf: timeouts { create = "15m" } (재구축 대비)
타임아웃 실패는 "실제 실패"와 "관측 실패"를 구분하라. 8/3 "실패를 삼키는 프로비저너" (실패→성공으로 기록)의 정반대 사례(성공→실패로 기록) — 양쪽 다 terraform의 기록과 실제 상태는 다를 수 있다는 같은 교훈.

§7. git 위생 — 커밋되면 안 되는 것들이 커밋됨

  • .gitignore에 stash 충돌 마커가 미해결 채 커밋 — 마커 줄은 무의미한 패턴으로 취급돼 우연히 동작 중이나 정리 필요. upstream 개선(**/.claude/settings.local.json만 제외해 skills 공유 가능)과 terraform 규칙 블록을 병합하면 됨
  • cloudwatch-discord.zip(빌드 산출물) 추적 중 — git rm --cached 필요
  • 정정 초기 리뷰의 ".gitignore 사실상 비어 있음" 판정은 go/.gitignore 미확인 오판 — 실제 갭은 *.tfvars 부재와 zip 추적뿐, 조치 완료
stash/pull 충돌은 그 자리에서 해결하고 커밋. 점검 시 중첩 .gitignore까지 확인.
