# 2026-08-05 작업 기록

## 1. 로그 아카이브 버킷이 또 state에서만 사라져 apply가 실패 — 8/4 §5.6의 3차 재발

### 작업 목적

apply를 돌려 인프라를 최신 코드에 맞추는 것. 특별한 변경 의도는 없었고, 직전 사이클에서
끊긴 부분을 마저 채우는 성격의 실행이었다.

### 문제가 발생한 지점

Kyverno 정책 차트까지는 정상 생성되고, 그 직후 S3 버킷 생성에서 멈췄다.

```
helm_release.kyverno_policies: Creation complete after 9s [id=kyverno-policies]
╷
│ Error: creating S3 Bucket (gochuchamchi-cloudwatch-log-archive-307223751140):
│ operation error S3: CreateBucket, https response error StatusCode: 409,
│ BucketAlreadyOwnedByYou: Your previous request to create the named bucket
│ succeeded and you already own it.
│
│   with aws_s3_bucket.cloudwatch_log_archive,
│   on cloudwatch-log-archive.tf line 27
╵
```

### 문제 원인

**`BucketAlreadyOwnedByYou`는 "남이 이름을 선점했다"가 아니라 "내 계정에 이미 있는데
Terraform은 모르고 있다"는 뜻이다.** state와 실물이 어긋났다는 신호다.

state를 확인하니 버킷과 그 하위 리소스가 통째로 빠져 있었다:

```powershell
terraform state list | Select-String "cloudwatch_log_archive"
# 로그 그룹 / 로그 스트림 / IAM Role 만 나옴
# aws_s3_bucket.* 은 하나도 없음
```

| 항목 | AWS 실물 | state |
|---|---|---|
| 버킷 자체 | 있음 (`head-bucket` exit 0) | **없음** |
| 버킷 정책 | 없음 (`NoSuchBucketPolicy`) | 없음 |
| Public Access Block | 없음 | 없음 |
| Lifecycle | 없음 | 없음 |
| 버전 관리 | Enabled | 없음 |
| 기본 암호화 | AES256 (S3 기본값) | 없음 |
| 객체 | **909개** | — |

이 어긋남의 출발점은 8/4 §5.5다. 그때 Object Lock COMPLIANCE 때문에 버킷을 삭제할 수
없어서 **`terraform state rm`으로 관리에서만 떼어냈다.** 그 뒤로 "실물은 있는데 state에는
없는" 상태가 구조적으로 굳어졌고, apply를 돌릴 때마다 같은 에러가 난다.
8/4 §5.6에서 한 번, §5.8(파일 되돌아감)에서 한 번, 그리고 오늘이 세 번째다.

**다만 오늘 걸린 버킷은 8/4의 그 버킷이 아니다.** 생성 시각이 `2026-08-05T00:32:33Z`로,
8/4 밤~8/5 새벽 재구축 사이클에서 새로 만들어진 것이다. 즉 8/4에 잠겨 있던 버킷은
정리됐고, **새 버킷에서 같은 어긋남이 다시 발생했다.** 재구축을 해도 이 패턴 자체는
사라지지 않는다는 뜻이다.

#### 미해결 의문 — 새 버킷인데 Object Lock이 켜져 있다

```powershell
aws s3api get-object-lock-configuration --bucket <bucket> --profile admin
# {"ObjectLockConfiguration": {"ObjectLockEnabled": "Enabled"}}
```

`cloudwatch-log-archive.tf`에는 `object_lock_enabled` 선언이 **없다**(81~85행 주석에
"복원 보류, 다음 재구축 사이클에서 반영할 것"이라고 적혀 있다). 코드에 없는데 실물에는
켜져 있는, 8/4 §5.5와 **완전히 같은 형태의 불일치**가 새 버킷에서 재현됐다.
어느 경로로 켜졌는지는 이번에 규명하지 못했다.

**다행히 이번에는 destroy를 막지 않는다.** 버킷 레벨 Object Lock은 켜져 있지만 기본
보존 규칙(Rule)이 없어서 개별 객체가 잠기지 않았다:

```powershell
aws s3api get-object-retention --bucket <bucket> --key <샘플키> --profile admin
# NoSuchObjectLockConfiguration: The specified object does not have a ObjectLock configuration
```

8/4를 교착시킨 것은 Object Lock "활성화"가 아니라 **COMPLIANCE 30일 보존 규칙**이었다.
지금은 그 규칙이 없으므로 같은 교착은 재발하지 않는다. 단, 규칙이 다시 붙으면
그 시점부터 쌓이는 객체는 또 잠긴다.

### 해결 방법

버킷을 지우지 않고 import로 흡수했다. 버킷 이름은 계정 전역 유일이라 이름을 바꿔
우회할 수도 없다.

```powershell
terraform import "aws_s3_bucket.cloudwatch_log_archive" "gochuchamchi-cloudwatch-log-archive-307223751140"
# Import successful!
```

import 후 plan으로 **교체가 계획되지 않는지 반드시 확인한다**(8/4 §5.6의 경고).
`object_lock_enabled`가 Optional+Computed라 코드에 없어도 diff가 생기지 않아
이번에도 교체 없이 통과했다:

```
Plan: 22 to add, 0 to change, 0 to destroy.
```

`0 to destroy`를 확인한 뒤 그 plan 파일로만 apply했다.

```
Apply complete! Resources: 22 added, 0 changed, 0 destroyed.
```

생성된 22개는 버킷 하위 설정(PAB·ownership·versioning·KMS 암호화·lifecycle·버킷 정책),
Firehose 파이프라인(스트림 2 + IAM 정책 2 + 구독 필터 2), 그리고 보안 로깅
(CloudTrail, VPC Flow Logs, Glue 테이블 2, Athena 쿼리 6)이다.

**재발 방지** — 버킷에 `prevent_destroy`를 걸었다. 이 어긋남은 항상 destroy에서
시작되므로, 그 지점을 plan 단계에서 막는 것이 가장 앞선 차단선이다.

```hcl
lifecycle {
  prevent_destroy = true
}
```

⚠️ 트레이드오프가 있다. 이게 걸려 있으면 `terraform destroy`가 이 버킷에서 멈춘다.
전체 재구축 시에는 블록을 잠시 주석 처리하거나 `state rm`으로 떼어낸 뒤 destroy하고,
재구축 후 위 import로 다시 붙인다. **`state rm` 후 import를 잊는 것이 바로 이 문제의
발생 경로이므로, 떼어냈다면 반드시 같은 세션 안에서 다시 붙일 것.**

### 검증 완료 사항

- `terraform import` 성공, 이어진 plan이 `0 to destroy` (교체 계획 없음)
- `terraform apply` 22개 생성, 에러 0건
- 버킷 객체 909개(`cloudtrail` 348 / `cloudwatch` 354 / `vpc-flow-logs` 207)가
  import 전후로 그대로 — import는 메타데이터만 다루므로 데이터에 영향 없음
- 버킷 정책이 새로 생성되어 `DenyObjectDeletion`·`DenyPolicyTampering`이 다시 활성화됨.
  이후 이 버킷 정책을 바꾸려면 **루트 계정으로 정책을 지우고 apply**해야 한다
  (`cloudwatch-log-archive.tf` 274~278행의 복구 경로)

#### 진단 중 실제로 잘못 읽은 것 — `KeyCount`가 null

객체 수를 처음 확인할 때 "0개"로 오독했다.

```powershell
aws s3api list-objects-v2 --bucket <bucket> --max-items 5 --profile admin --query "KeyCount"
# null   ← 0이 아니라 "필드가 없음"
```

**AWS CLI가 자동 페이지네이션을 하면 결합된 응답에서 `KeyCount`가 빠진다.**
`null`을 0으로 읽으면 "로그가 하나도 없으니 버려도 된다"는 정반대 판단으로 이어진다.
실제 개수는 `Contents`를 세어야 한다:

```powershell
aws s3api list-objects-v2 --bucket <bucket> --profile admin --query "Contents[].Key" --output text
aws s3api list-object-versions --bucket <bucket> --profile admin --query "length(Versions)"
```

이번엔 import 경로를 택해서 결과가 같았지만, "비었으니 지우자"로 갔다면 로그 909개를
날릴 뻔했다. 8/4 §5.5에서 `delete-objects`의 `Quiet` 응답을 버려 오진한 것과 같은
계열의 실수다 — **CLI 출력의 "없음"이 "0"인지 "필드 자체가 없음"인지 구분할 것.**

### 1.1 PowerShell이 `-out=tfplan.binary`를 점에서 잘라 plan이 실패

```powershell
terraform plan -out=tfplan.binary
# Error: Too many command line arguments
```

PowerShell이 따옴표 없는 인자를 `.`에서 쪼개 `-out=tfplan`과 `binary` 두 개로 넘긴다.
terraform은 두 번째를 위치 인자(작업 디렉토리)로 받아 "인자가 너무 많다"고 답한다.
에러 메시지가 원인과 전혀 안 닮아서 코드를 의심하기 쉽다.

```powershell
terraform plan "-out=tfplan.binary"   # 따옴표로 감싸면 통과
```

이미 알려진 함정인데(`-target=a.b`가 같은 이유로 잘림) plan 옵션에서 또 밟았다.
**terraform 인자에 `.`이나 `=`가 있으면 조건 없이 따옴표를 씌운다.**
Bash로 검증하면 재현되지 않으므로 PowerShell에서 직접 확인해야 한다.

### 1.2 plan 산출물이 `.gitignore`에 안 걸려 있었다

`.gitignore`에 `*.tfplan`은 있었지만 `plan -out`의 산출물 이름을 `tfplan.binary`처럼
붙이면 걸리지 않는다. plan 파일은 바이너리지만 **리소스 속성값이 그대로 들어 있어
state와 같은 급으로 다뤄야 한다.** 이름 기준 패턴을 추가했다:

```gitignore
tfplan
tfplan.*
```

## 2. ArgoCD를 도메인으로 직접 접속 — internal ALB → internet-facing + IP 허용목록

### 작업 목적

ArgoCD UI를 볼 때마다 SSM 포트포워딩 + `kubectl port-forward` 2단 터널을 띄우는 것이
번거로워, `argocd.gochuchamchi.shop`으로 바로 들어가게 한다.

### 문제가 발생한 지점

**도메인과 인증서는 이미 다 있었다.** 없는 것은 접근 경로뿐이었다.

```powershell
aws route53 list-resource-record-sets --hosted-zone-id <zone> --profile admin `
  --query "ResourceRecordSets[?contains(Name, 'argocd')]"
```

- `argocd.gochuchamchi.shop` A/AAAA 별칭 레코드 존재 (external-dns가 생성)
- ACM 검증용 CNAME도 존재
- 가리키는 대상: `internal-k8s-argocd-argocdse-...` — **Scheme이 `internal`**

internal ALB는 프라이빗 IP만 반환하므로, 퍼블릭 DNS로 이름이 풀려도 집에서는
그 IP로 라우팅되지 않는다. 그래서 포트포워딩이 유일한 경로였다.

### 문제 원인

원인이라기보다 **의도된 설계**였다. `argocd.tf` 주석에 근거가 남아 있다 —
ArgoCD는 클러스터 admin급 권한과 gitops write-back PAT를 함께 쥐고 있어, 탈취되면
"gitops 커밋 → 자동 배포"라는 공급망 경로가 열리는 최고가치 타겟이다. 그래서
인터넷 노출 대신 internal ALB를 택했다.

즉 이번 작업은 버그 수정이 아니라 **보안 결정을 운영 편의 쪽으로 다시 저울질한 것**이다.

### 해결 방법

노출 자체를 막는 대신 **노출 범위를 IP로 좁히는 방식**으로 바꿨다.
`argocd.tf`의 ingress 어노테이션 수정:

```hcl
"alb.ingress.kubernetes.io/scheme"        = "internet-facing"   # 기존: internal
"alb.ingress.kubernetes.io/inbound-cidrs" = join(",", var.endpoint_public_access_cidrs)
```

`inbound-cidrs`는 컨트롤러가 ALB 보안그룹 인바운드를 이 목록으로 한정하게 만든다.
허용 IP 밖에서는 로그인 화면조차 못 보고 TCP 연결 단계에서 끊긴다.

**IP 목록을 새로 만들지 않고 `endpoint_public_access_cidrs`를 재사용한 것이 핵심이다.**
EKS 퍼블릭 엔드포인트와 ArgoCD가 같은 변수를 공유하므로 접근 출발지가 한 곳에서
관리된다. 네트워크가 바뀌면 한 군데만 고치면 양쪽이 함께 열린다.

⚠️ 반대로 **stale한 `/32`를 남겨두면 위험이 두 배가 된다.** 유동 IP는 나중에 남에게
재할당되므로, 그 사람에게 EKS 엔드포인트와 ArgoCD UI가 동시에 열린다.
`variables.tf` 주석의 "안 쓰는 항목은 지울 것"이 이 변경으로 더 중요해졌다.

⚠️ 인터넷에 노출되는 만큼 **admin 비밀번호를 bcrypt로 고정하는 편이 좋다**
(백로그 B4, `TF_VAR_argocd_admin_password_bcrypt`). 미설정이면 `argocd-initial-admin-secret`
동작이라 재구축마다 초기 비밀번호로 회귀한다.

### 검증 완료 사항

(dev 브랜치 작업분 — apply 전 코드 검증 단계까지)

- public 서브넷에 `kubernetes.io/role/elb` 태그가 있어 internet-facing ALB 배치 가능
  (`main.tf` 63~65행) — internal에서 옮겨갈 자리가 준비돼 있음을 확인
- Route53 레코드·ACM 인증서는 이미 존재하므로 추가 리소스 불필요
- external-dns 정책이 `upsert-only`라 ALB 교체 시 기존 레코드를 **갱신**한다(삭제 아님)

- `terraform fmt -check` / `terraform validate` 통과
- plan 결과는 **`0 to add, 1 to change, 0 to destroy` — `helm_release.argocd` in-place 1건**뿐이다.

⚠️ **plan이 조용하다고 변경이 작은 게 아니다.** ingress 어노테이션은 helm values 안에
있으므로 Terraform에게는 릴리스 값 갱신 1건으로 보인다. 실제 ALB 교체는 apply 이후
**AWS LB Controller가 수행**한다 — `scheme`은 ALB의 불변 속성이라 컨트롤러가 기존
ALB를 지우고 새로 만든다. 즉 **plan의 `0 to destroy`가 무중단을 뜻하지 않는다.**

**미검증** — 새 ALB가 뜨고 external-dns가 레코드를 갱신하기까지 접속이 끊기며,
실제 도메인 접속 확인은 apply 이후로 남아 있다.
