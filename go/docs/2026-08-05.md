# 2026-08-05 작업 기록

## 1. 저장소 위생 정리 — fmt · 줄바꿈 정규화 · 8/4 작업분 커밋

### 작업 목적

전체 코드 점검("고칠 만한 것" 리뷰) 결과, 코드 자체보다 저장소 상태가 문제였다:

1. `contract.tf`가 `terraform fmt -check`에 걸림 — 8/4에 만든 CI(`terraform-ci.yml`)가
   fmt를 hard-fail로 검사하므로 이대로 커밋하면 첫 PR부터 CI가 실패한다.
2. `git status`에 **저장소 내 거의 모든 파일이 항상 modified로 표시** — 실제 변경
   10건이 100개 넘는 가짜 M에 묻혀 diff/status가 사실상 못 쓰는 상태.
3. 8/4 자동화·이미지 서명·edge-logs·CI 작업 결과물(신규 20건 + `waf-cdn.tf` 삭제)이
   전부 미커밋 — 디스크 유실 시 하루치 작업이 사라지는 상태.
4. 루트에 `_to_delete/probe-tmp` (내용 "test" 5바이트) 잔존.

### 문제 원인 (2번 — 전 파일 modified 노이즈)

`core.autocrlf=true`(전역 설정)인데 저장소에 `.gitattributes`가 없었다.
인덱스는 LF, 워킹트리는 CRLF로 어긋난 채 저장소 기준이 고정돼 있지 않아,
git이 모든 텍스트 파일에 "LF will be replaced by CRLF" 경고를 내며 M으로 표시했다.
개인 PC 설정(autocrlf)에 의존하는 한 다른 작업 PC에서도 같은 노이즈가 재발한다.

### 해결 방법

1. `terraform fmt -recursive` — `contract.tf` 1건 정렬 (다른 스택 2개는 통과).
2. 루트에 `.gitattributes` 신설(`* text=auto` + png/zip binary) 후
   `git add --renormalize .` 1회 실행. 이제 저장소 기준이 LF로 고정되어
   개인 PC의 autocrlf 설정과 무관하게 동작한다.
   - 함정: 워킹트리에 삭제된 추적 파일(`waf-cdn.tf`)이 있으면 renormalize가
     `unable to stat`으로 실패한다 → 삭제를 먼저 `git add`로 스테이징한 뒤 실행.
3. 8/4 작업분과 8/5 위생 정리를 커밋 2개로 분리해 기록 (아래 커밋 이력 참고).
4. `_to_delete/` 삭제 (내용 확인 후).

### 검증 완료 사항

- `terraform fmt -check -recursive` 3개 스택(terraform / cloudwatch-notifications /
  discord-notifications) 모두 통과.
- renormalize 후 `git status`가 실제 변경만 표시 (가짜 M 0건).
- push 전 시크릿 스캔(runbook 패턴: PAT/AKIA/PRIVATE KEY/webhook URL) 통과 —
  `SECURITY_AUDIT_REPORT.md`의 매치는 실제 토큰이 아니라 점검 명령 속 패턴 문자열.

## 2. 재구축 apply 3연속 실패 — 고아 리소스 · 실행 정책 · 인코딩

### 작업 목적

재구축(destroy → apply) 중 apply가 에러 3건을 내고 중단됐다. 세 건이 한 화면에 함께
떠서 같은 뿌리로 보였지만 실제로는 서로 무관한 세 가지 원인이었다.

### 2.1 이름 충돌 — `BucketAlreadyOwnedByYou` / `AlreadyExistsException`

#### 문제가 발생한 지점

```
Error: creating S3 Bucket (gochuchamchi-cloudwatch-log-archive-307223751140):
  BucketAlreadyOwnedByYou: Your previous request to create the named bucket succeeded
Error: creating KMS Alias (alias/gochuchamchi-logs):
  AlreadyExistsException: An alias with the name ... already exists
```

#### 문제 원인

state에는 없는데 AWS에는 살아있는 "고아" 리소스였다. 진단은 **state 버전 이력**으로 했다:

```powershell
aws s3api list-object-versions --bucket gochuchamchi-tfstate-307223751140 --prefix eks/terraform.tfstate
```

`03:16:03 UTC`에 state 크기가 **5,116바이트**로 급락한 지점이 있었다. 그 앞은 210KB,
그 뒤 `03:24`부터 다시 46만 → 186만으로 증가 — 즉 그 시각에 state가 비워지고(destroy 완료
처리) 재구축이 시작됐다는 뜻이다.

결정적 근거는 **KMS 키 `4892dcf2`가 `PendingDeletion`이 아니라 `Enabled`였다**는 점이다.
Terraform이 destroy를 시도했다면 `schedule-key-deletion`이 호출돼 삭제 예약 상태여야 한다.
Enabled로 남았다는 것은 그 리소스가 **destroy 그래프에 아예 없었다**는 뜻이고, destroy 교착을
풀면서 `state rm`으로 빼낸 것들이 실물로 남았을 가능성이 크다(8/4 §5.5에서 실제로 그 절차를
썼다). state의 `aws_kms_key.logs`는 새로 만든 `9613be9a`인데 alias는 옛 키를 가리키고 있어
키가 2개가 된 상태였다.

#### 해결 방법

두 리소스를 `terraform import`로 인수했다. alias는 in-place 업데이트로 새 키를 가리키게 됐다.
고아로 남은 옛 키(`4892dcf2`)는 alias가 떨어져 나가므로 별도 정리 대상으로 보고했다.

### 2.2 `local-exec`의 `.ps1` 실행이 서명 오류로 차단

#### 문제가 발생한 지점

```
File C:\terraform\go\scripts\smoke-test.ps1 cannot be loaded.
The file ... is not digitally signed.
```

#### 문제 원인

`CurrentUser` 실행 정책이 `RemoteSigned`인데, git/다운로드로 받은 파일에 `Zone.Identifier`
스트림(인터넷 출처 표시)이 붙어 있었다. 확인은 `Get-Item <파일> -Stream *`.

#### 해결 방법

`Unblock-File`은 파일을 다시 받으면 원상복구되므로 **호출하는 쪽**에서 우회했다.

```hcl
interpreter = ["PowerShell", "-ExecutionPolicy", "Bypass", "-Command"]
```

인라인 명령을 쓰는 `db-zero-trust.tf` · `rds-schema-init.tf`는 실행 정책 영향을 받지 않으므로
그대로 뒀다. 이 문제는 `.ps1` **파일**을 실행할 때만 발생한다.

### 2.3 스크립트 인코딩 — BOM 없는 UTF-8이 파싱을 깨뜨림

#### 문제가 발생한 지점

실행 정책을 푼 뒤 그 아래에서 새 에러가 드러났다.

```
Unexpected token '珥?' in expression or statement.
The string is missing the terminator: ".
Missing closing '}' in statement block or type definition.
```

#### 문제 원인

`scripts/*.ps1` 두 파일 모두 **BOM 없는 UTF-8**이었다. PowerShell 5.1은 BOM이 없으면
시스템 ANSI(CP949)로 읽으므로 한글이 깨지고(`?ㅻえ???뚯뒪??`), 그 깨진 바이트가 따옴표·괄호를
삼켜 **스크립트 전체가 파싱 실패**한다. 증상이 문법 오류로 나타나서 인코딩 문제로 보이지 않는다.

앞선 서명 차단이 이 문제를 가리고 있었다 — 아예 실행이 안 됐기 때문에 드러날 기회가 없었다.

#### 해결 방법

두 파일을 UTF-8 BOM으로 재저장했다. git은 BOM을 내용의 일부로 보존하므로 최초 저장이 유일한
기회다.

```powershell
[System.IO.File]::WriteAllText($p, $text, (New-Object System.Text.UTF8Encoding($true)))
```

### 검증 완료 사항

- `import` 2건 후 plan이 25 add / 1 change / 1 destroy로 정리되고, 삭제 대상은 tainted
  스모크 테스트뿐 — S3·KMS 재생성 없음을 확인.
- `[System.Management.Automation.PSParser]::Tokenize()`로 실행 없이 구문 검사 통과.
- 스크립트 실제 실행에서 한글 출력 정상.

## 3. 로그 버킷 불변성 정책 — 방어는 성립하지 않고 운영만 막던 문제

### 작업 목적

§2를 해결하고 apply를 재개하자 다음 에러가 나왔다.

```
Error: putting S3 Bucket Policy: AccessDenied: User: .../admin is not authorized to
perform: s3:PutBucketPolicy ... with an explicit deny in a resource-based policy
```

### 문제 원인

`cloudwatch-log-archive.tf`의 `DenyPolicyTampering`이 `s3:PutBucketPolicy`를 **조건 없이
전원 거부**하고 있었다. 의도는 "침해자가 admin 자격증명을 얻어도 증거 로그를 지우거나 정책을
풀 수 없게" 하는 것이었는데, 실제로는 정반대로 동작했다:

- Deny 대상이 `PutBucketPolicy` **뿐**이라 `s3:DeleteBucketPolicy`는 열려 있었다.
  공격자는 `delete-bucket-policy` 한 번으로 정책 전체를 지울 수 있고, 그러면
  `DenyObjectDeletion`까지 **함께 사라진다**. 즉 방어가 우회되는 게 아니라 통째로 제거된다.
- 반대로 정상 운영자인 Terraform은 정책 "수정"이 막혀 apply가 403으로 실패했다.

**공격자는 못 막고 운영만 막는 상태**였다.

코드 주석(옛 274~278줄)에는 "버킷 소유 계정의 루트 사용자만은 DeleteBucketPolicy를 항상
호출할 수 있다"고 적혀 있었지만, 그건 Delete까지 Deny했을 때의 이야기다. 당시 정책은
그렇지 않아 admin으로도 삭제됐다 — pitfalls 85번("주석을 실물의 근거로 삼지 말 것")과 같은
함정이 정책 문서에서 반복된 셈이다.

### 해결 방법

정책 수정은 막혀 있고 삭제는 가능했으므로, 현재 정책을 삭제한 뒤 apply로 다시 붙였다
(삭제 전 원본을 백업). 정책 자체는 다음과 같이 고쳤다:

1. `DeleteBucketPolicy`를 Deny에 추가해 우회 경로를 막았다.
2. 운영 주체는 `ArnNotLike aws:PrincipalArn` 조건으로 예외 처리했다. 예외 목록은
   `cloudwatch_log_archive_admin_arns` 변수로 뺐고, 비우면 apply 실행 주체가 들어간다.

부정형 연산자는 **조건 키가 없는 요청(서비스 주체)에 true로 평가**되므로 CloudTrail 등
서비스에는 Deny가 그대로 걸린다.

남는 한계는 주석에 명시했다 — 예외 주체의 자격증명이 탈취되면 이 방어는 무력하다. 같은 계정의
관리자를 그 계정 리소스로 막는 구조의 본질적 한계이므로, 운영 전환 시에는 로그 전용 계정
분리나 Object Lock으로 재설계해야 한다.

### 검증 완료 사항

적용된 실물 정책을 조회해 두 Deny 문에 `ArnNotLike` 조건과 `DeleteBucketPolicy`가 모두
들어간 것을 확인.

## 4. 사이트 503 `Backend service does not exist` — ArgoCD PAT 소실

### 작업 목적

apply가 성공한 뒤에도 `gochuchamchi.shop`이 계속 503이었다. **재구축할 때마다 반복**되는
증상이라, 즉시 복구뿐 아니라 "apply가 성공하면 바로 접속되는" 상태까지 만드는 것이 목표였다.

### 4.1 원인 사슬

원인은 하나였고 나머지는 전부 그 결과였다.

```
PAT 값 없음 → ExternalSecret SecretSyncedError
  → ArgoCD "authentication required: Repository not found"
  → Application Sync=Unknown → 앱 미배포 → Service 없음
  → ALB "Backend service does not exist" (pitfalls 72번)
```

`describe-secret`은 성공하는데 `get-secret-value`가
`ResourceNotFoundException ... for staging label: AWSCURRENT`를 냈다 — **컨테이너는 있고
값(버전)만 없는** 상태로, pitfalls 76번에 적힌 그대로였다.

근본 원인은 `eso.tf`의 `recovery_window_in_days = 0`이다. destroy 때 시크릿이 즉시 삭제되면서
주입해둔 PAT도 함께 사라지므로, 재구축하면 항상 빈 컨테이너만 생긴다. **시크릿 "값"은 인프라와
생애주기가 다르다**는 점에서 ECR 이미지(pitfalls 38번)와 같은 계열의 함정이다.

### 4.2 즉시 복구

GitOps 저장소(`landoll9999/gochuchamchi-gitops`)는 private이라 인증이 필수였다. gh CLI가
`repo` 스코프 토큰으로 로그인돼 있어 그 값으로 복구했다.

1. `gh auth token` → Secrets Manager 주입 (저장값 길이로 검증)
2. ESO는 `refreshInterval: 1h`이라 즉시 반영되지 않는다 →
   `kubectl annotate externalsecret ... force-sync=<ts> --overwrite`로 강제 동기화
3. ArgoCD `argocd.argoproj.io/refresh=hard` → Synced, Deployment·Service·HPA 생성
4. 옛 ReplicaSet 파드 2개가 `ImagePullBackOff`인 채 메모리를 점유해 새 파드가 `Pending`이었다
   → 삭제 후 롤아웃 완료 (노드도 2→3 스케일업)

**오진할 뻔한 지점** — 파드 이벤트만 보면 `:latest` 이미지가 ECR에 없어 실패하는 것처럼
보였고, ECR 실제 태그(`signed-41611c4f...`)·kustomization의 `newTag`(`a45e6d79...`)·파드가
요청한 `latest`가 **셋 다 달랐다**. 그러나 실제 Deployment는 Image Updater가 써둔
`.argocd-source-gochuchamchi.yaml`의 올바른 태그를 쓰고 있었다. `latest` 파드는 첫 sync
순간의 잔재였을 뿐 이미지 파이프라인은 정상이었다. **파드 이벤트가 아니라 Deployment의 실제
image를 봐야** 판별된다.

### 4.3 재발 방지 — 환경변수 자동 주입 (`null_resource.inject_git_pat`)

`$env:ARGOCD_GIT_PAT`를 **local-exec 안에서 셸이 직접 읽어** 주입한다. 값이 terraform 변수를
거치지 않으므로 state·plan 어디에도 PAT가 남지 않는다 — ESO 도입 취지(백로그 B3)를 지키면서
수동 단계만 없앤 것이다. `TF_VAR_`로 받았다면 평문이 state에 박힌다.

| 상황 | 동작 |
|---|---|
| 환경변수 없음 | 건너뛰고 수동 주입 명령 안내 (기존 워크플로 유지) |
| 값이 이미 있음 | 건너뜀 — 로테이션은 의도적으로 수동 |
| 값 없음 + 환경변수 있음 | 주입 (재구축 시나리오) |

`triggers`에 시크릿 ARN을 넣었다. 시크릿이 재생성되면 ARN 끝의 랜덤 접미사가 바뀌므로
재구축마다 다시 실행된다. 값이 있을 때 덮어쓰지 않는 이유는, 낡은 환경변수가 셸 세션에 남아
있다가 운영 중인 PAT를 조용히 옛 값으로 되돌리는 사고를 막기 위해서다.

`helm_release.eso_config`의 `depends_on`에 이 리소스를 넣어 **ExternalSecret CR이 뜨는
시점에 값이 이미 있도록** 순서를 고정했다. 값 없이 CR이 뜨면 `SecretSyncedError`가 되고
`refreshInterval: 1h` 탓에 나중에 값을 넣어도 최대 1시간을 기다리게 된다(4.2에서 force-sync로
재촉해야 했던 이유).

### 4.4 앱 Ready 대기 (`null_resource.wait_for_app_ready`)

apply는 "AWS 리소스를 다 만들었다"에서 끝나지만 앱은 ArgoCD가 배포하므로, apply 직후에는
아직 파드가 없어 503이 뜬다. Terraform이 이 Deployment를 만들지 않아 의존성으로 표현할 수
없으므로 두 단계로 처리한다.

1. ArgoCD가 Deployment를 만들 때까지 15초 간격 폴링
2. 나타나면 `kubectl rollout status`로 Ready까지 대기

기본은 **경고 모드**다. 재구축 직후에는 앱이 안 뜨는 게 정상인 경우가 있어 apply를 막지 않고
사유만 출력한다. 운영 중 변경에는 `TF_VAR_wait_for_app_ready_enforce=true`로 강제한다.
실패 시 원인 후보와 확인 명령을 함께 출력하며, 특히 **kubeconfig가 옛 클러스터를 가리키는
경우**를 별도로 감지해 `update-kubeconfig`를 안내한다(§6.3 참고).

### 검증 완료 사항

- 사이트 `/` 200, `/api/health` 200 회복. 파드 2/2 Running, ALB 타겟 healthy 3.
- 스모크 테스트 **실패 0 / 경고 0 / 전체 14**.
- `inject_git_pat`의 "값이 이미 있음 → 건너뜀" 경로를 apply에서 확인.
- 정작 중요한 "빈 시크릿 → 주입" 경로는 임시 시크릿(`gochuchamchi-inject-logic-test`)을
  값 없이 만들어 재구축 직후와 같은 상태를 재현해 검증하고 삭제.
- `wait_for_app_ready`가 롤아웃 대기 후 "앱 준비 완료"로 통과.

## 5. apply 사전 점검 자동화 — `scripts/preflight-check.ps1`

### 작업 목적

§2.1의 이름 충돌은 **이미 pitfalls 79·80번에 두 번 적혀 있었는데도 재발**했다. "사람이 매번
기억해야 하는 절차"는 재구축 압박 상황에서 가장 먼저 생략된다. 교훈을 문서에 한 줄 더 추가하는
방식으로는 막히지 않는다고 보고, 점검을 실행 가능한 스크립트로 옮겼다.

### 해결 방법

plan이 **순수 생성(create)**하겠다고 한 것만 골라 AWS에 이미 있는지 조회하고, 있으면
`terraform import` 명령을 출력한다(`-Fix`면 자동 실행). 리소스 목록을 손으로 관리하지 않으므로
코드가 늘어도 자동으로 따라온다. 검사기는 20종이며 새 타입은 `$Checkers` 해시에 한 줄 추가한다.

교체(replace)는 제외한다 — 이미 state에 있어 terraform이 삭제 후 생성하기 때문이다. 이름이
AWS 생성값인 리소스(VPC·EC2 등)는 애초에 충돌하지 않으므로 건너뛴다.

### 만드는 과정에서 잡은 것 2건

1. **낡은 plan 오탐** — 이미 적용한 plan으로 돌리면 "AWS에 있음"이 충돌로 잡혔다.
   `terraform state list`와 대조해 state에도 있으면 `[낡음]`(이미 적용된 plan)으로 분류하도록
   고쳤다.
2. **스크립트 자신이 PowerShell 인자 함정을 밟았다** — §6.1 참고.

### 검증 완료 사항

- 낡은 plan으로 실행 → `[낡음] 3건`으로 정확히 분류, 충돌 0.
- 신선한 plan 자동 생성 모드 → 충돌 0 / 검사 0(현재 인프라가 수렴 상태), 종료코드 0.

## 6. PowerShell 함정 2종과 스모크 테스트 오탐

### 6.1 `-out=$var`에서 변수가 확장되지 않는다

#### 문제가 발생한 지점

`preflight-check.ps1`이 plan을 만들지 못하고 "파일 없음"으로 죽었다. 그런데 terraform 출력에는
`Saved the plan to: $tp`라고 **리터럴 변수명**이 찍혀 있었다.

#### 문제 원인

이 환경의 PowerShell은 `-out=$PlanFile` 형태에서 변수를 확장하지 않고 리터럴 `$PlanFile`을
그대로 넘긴다. 그 결과 **현재 디렉토리에 `$PlanFile`이라는 이름의 파일이 생기고**(저장소 오염)
의도한 경로는 비어 있었다. 게다가 terraform은 **종료코드 0으로 성공**하므로 다음 단계에서야
엉뚱한 에러로 나타난다.

pitfalls 62번(따옴표 없는 `-target=a.b`가 점에서 잘림)과 같은 뿌리의 다른 증상이다.

#### 해결 방법

`"-out=$PlanFile"`로 큰따옴표를 씌우고, **종료코드와 별개로 결과물이 실제로 생겼는지
`Test-Path`로 확인**하는 방어를 넣었다. 오염 파일 2개(`$PlanFile`, `$tp`)는 삭제했다.

### 6.2 변수 뒤에 한글이 붙으면 변수명으로 먹힌다

#### 문제가 발생한 지점

`wait_for_app_ready`의 출력이 `롤아웃 대기 중 (최대 )...`로 숫자가 비어 나왔다.

#### 문제 원인

`"최대 $remain초"`는 `$remain` + "초"가 아니라 **`$remain초`라는 미정의 변수**로 해석된다
(PowerShell 변수명은 유니코드를 허용한다). 에러가 아니라 조용히 값만 사라지므로 출력이
이상해질 때까지 알아채기 어렵다.

일괄 점검(`rg '\$[A-Za-z_][A-Za-z0-9_]*[가-힣]'`)으로 `smoke-test.ps1:159`의
`재시작 $restarts회`도 찾았다 — 파드가 5회 이상 재시작했을 때 **횟수가 표시되지 않던** 버그로,
이번 작업과 무관하게 원래 있던 것이다.

#### 해결 방법

`$($remain)초` 형태로 끊었다. 조사·단위가 붙는 자리는 모두 이 패턴을 쓴다.

### 6.3 스모크 테스트 오탐 2건

#### TCP 검사가 매번 거짓 FAIL

컨테이너에 `bash`가 없어(`/bin/sh`만 존재) `/dev/tcp` probe가 불가능한데, 스크립트가
`'not found'` 패턴만 SKIP으로 분류해서 실제 메시지
(`timeout: failed to run command 'bash': No such file or directory`)를 FAIL로 떨어뜨렸다.
앱은 멀쩡히 DB에 붙어 있었다(로그에 `HikariPool-1 - Added connection`).

도구 부재와 진짜 차단을 구분하도록 고쳤고, RDS는 HikariPool 로그로 대체 검증해 검사
목적(SG·NetworkPolicy 회귀 감지)을 유지했다. Redis는 확정적 증거가 없어 SKIP으로 정직하게
표시한다.

#### `no such host`를 허용목록 문제로 오진

스모크 테스트 3번이 "EKS 퍼블릭 엔드포인트 `/32` 허용목록에 현재 IP가 있는지 확인"이라고
보고했지만, 실제 IP는 허용목록에 있었고(`112.221.246.164/32`) 원인은 **kubeconfig가 옛 클러스터
엔드포인트를 가리키는 것**이었다(`dial tcp: lookup ...: no such host`). 재구축으로 엔드포인트가
바뀌었는데 kubeconfig가 그대로였다.

DNS 해석 실패와 TCP 타임아웃은 원인이 다르므로 같은 메시지로 묶으면 멀쩡한 허용목록을 뒤지게
된다. `wait_for_app_ready`에는 이 구분을 반영해 접속 실패 시 `update-kubeconfig`를 안내한다.

### 6.4 output이 bash 전용이라 PowerShell에서 실패

`argocd_admin_password_command`가 `| base64 -d`로 끝나는데 PowerShell에는 `base64`가 없어
그대로 붙여넣으면 실패했다. .NET 변환으로 교체하고, 접속 방법 자체가 output에 없어 매번
찾아봐야 했던 문제도 `argocd_port_forward_command`를 신설해 해결했다.

`grafana.tf:55` 주석의 같은 패턴도 함께 고쳤다. 왜 이렇게 썼는지(주 셸이 PowerShell 5.1)를
주석으로 남겨 다음에 bash 형태로 되돌아가지 않게 했다.

### 검증 완료 사항

- 수정 후 스모크 테스트 **실패 0 / 경고 0 / 전체 14**.
- `(최대 599초)`로 정상 출력.
- `terraform output -raw argocd_admin_password_command`를 그대로 실행해 16자 조회 성공.

## 7. 저장소 위생 회귀 — `.gitattributes`가 삭제됨

### 문제가 발생한 지점

§1에서 해소한 "전 파일이 항상 modified" 노이즈가 되돌아왔다. `git status`에 100건 넘는 M이
뜨고 `git diff`마다 "LF will be replaced by CRLF" 경고가 쏟아진다. 실제 변경은 9개 파일뿐이다.

### 문제 원인

커밋 `33bc5d2 Delete .gitattributes`로 §1에서 신설한 파일이 지워졌다(같은 흐름에서
`10b172f Delete .github/workflows directory`도 있다). 저장소 기준이 다시 개인 PC의
`core.autocrlf` 설정에 떠 있는 상태다.

### 조치

이번 커밋은 **바뀐 파일을 명시적으로 add**해서 노이즈를 섞지 않았다. `.gitattributes` 복구는
CI(`.github/workflows`)와 함께 삭제된 것이라 의도적 결정일 수 있어 임의로 되돌리지 않고
사용자 판단에 남긴다 — 복구하려면 §1의 절차(`* text=auto` 선언 + `git add --renormalize .`)를
그대로 반복하면 된다.

### 참고 — 커밋하지 않은 untracked 항목

- `go/gochuchamchi-gitops/` — **별도 저장소의 클론**이 인프라 저장소 안에 들어와 있다.
  커밋되면 저장소가 중첩되므로 `.gitignore` 등재가 필요하다.
- `go/terraform/check-*.json`, `apply-and-restart.json` — 이전 세션의 임시 산출물로 보인다.
- `go/discord-notifications/.terraform.lock.hcl`
