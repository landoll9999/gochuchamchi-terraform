1. 개요 — 이 문서가 답하는 것

요청이 들어오는 지점부터 데이터에 닿기까지 무엇이 검문하는가, 무슨 일이 있었는지 어디에 남는가, 이상이 생기면 무엇이 자동으로 움직이는가. 세 질문에 대한 현재 구조를 정리한다.

2026-08-12 작업으로 제로트러스트의 두 축이 데이터 계층에서 모두 채워졌다 — 승인(누가 들어올 수 있는가)은 8/4에 구축돼 있었고, 이번에 감시(들어와서 무엇을 했는가)를 붙였다. 멘토링에서 지적된 "접근통제에 행위 감시를 더하면 완성도가 오른다"가 이 부분이다.

이 문서의 범위. 엣지(WAF/CloudFront) → 데이터 계층(RDS) → 관제(탐지·대응) → 증적(중앙 로그)의 보안 축만 다룬다. EKS·ArgoCD·CI 파이프라인 등 배포 구조는 architecture.md와 일자별 작업 기록을 참고한다.

2. 요청 경로와 검문소

외부 요청은 CloudFront와 WAF를 반드시 통과해야 애플리케이션에 닿는다. 문제는 ALB 주소를 알아낸 공격자가 WAF를 건너뛰고 직접 때리는 경로였다. 8/12에 검증 헤더를 추가해 두 겹으로 막았다.

4. 탐지에서 대응까지

관제의 핵심은 무엇을 올릴지 고르는 일이다. 심각도 숫자만으로 거르면 루트 계정 사용 같은 저심각도 신호를 놓치고, 포트 스캔 같은 배경소음은 그대로 통과한다. 8/12에 타입 기반 필터로 전환했다.

왜 심각도가 아니라 타입인가 (실측 근거). 현재 detector의 finding 3건이 전부 severity 2(Low)였고 그중 Policy:IAMUser/RootCredentialUsage(루트 사용)가 있었다. 기존 기준은 severity ≥ 4라 가장 중요한 신호가 통보에서 누락되고 있었다. 반대로 Medium 이상으로 올라오는 PortProbe·BruteForce는 공인 IP라면 항상 쏟아지는 배경소음이고, 배스천은 SSH/RDP 인바운드가 0개라 무차별 대입은 성공 자체가 불가능하다. aws events test-event-pattern으로 6개 시나리오를 검증했다.

복구를 자동화하지 않은 것은 의도다. "정말 오탐인가"의 판단은 사람이 해야 한다 — 자동 원복은 진짜 침해를 자동으로 풀어주는 역방향 위험이 된다. 대신 격리 시점에 각 ENI의 원래 SG를 태그(gochuchamchi:pre-quarantine-sgs)에 기록해두어, 사람이 판단한 뒤에는 한 번의 호출로 되돌릴 수 있게 했다.

5. 증적은 다른 계정에 남는다

침해된 계정이 자기 흔적을 지울 수 있으면 그건 감사가 아니다. 로그는 workload를 떠나 Log 계정의 불변 버킷에 쌓인다 — Object Lock COMPLIANCE라 workload 권한으로는 지울 수도 고칠 수도 없다.

workload → log 계정 (구독 필터 경유)
앱 로그 EKS 컨트롤플레인 WAF (us-east-1) RDS 감사
적용됨 → Log Destination → Firehose
GZIP · 5분 버퍼→ 중앙 S3
KMS CMK · Object Lock COMPLIANCE→ Athena
별도 경로
ALB 액세스 로그
enabled=true→ ALB 전용 버킷
SSE-S3 · Log 계정 VPC Flow Logs · CloudTrail
중앙 버킷 직행
ALB 로그만 버킷이 분리된 이유. AWS 문서상 ALB 액세스 로그는 SSE-S3만 지원해 KMS로 암호화된 중앙 버킷에 기록할 수 없다. 중앙 버킷의 암호화를 낮추면 CloudTrail·VPC Flow까지 보호 수준이 함께 떨어지므로, 버킷만 나누고 불변성(Object Lock COMPLIANCE + 버저닝)은 동일하게 유지한다. 중앙집중의 본질은 "Log 계정으로 모으는 것"이지 "버킷 한 개"가 아니다.

정정 (2026-08-12 재확인). 이 표는 원래 중앙 로그와 앱 보안 로그를 “Log 계정 대기”로 적고 있었다. 사실이 아니었다. AWS 실물을 조회해 보니 Log 계정은 go/log-archive를 이미 apply해 둔 상태였다 — 서울·버지니아 Destination 3개가 살아 있었고 ALB 로그 버킷도 존재했다. 막혀 있던 쪽은 워크로드였다. 두 기능의 코드가 그날 아침 daily-up이 돈 뒤에 커밋돼(09:47 배포 / 10:55·12:21 커밋) 인프라에 반영될 기회가 없었을 뿐이다. 그 상태에서 apply하니 두 건 모두 즉시 붙었다.

남은 교훈은 대기처를 잘못 지목했다는 것보다, “코드에 있음”을 “배포됨”으로 읽었다는 데 있다. 이 문서의 상태 표는 저장소가 아니라 describe-* 조회 결과를 기준으로 유지한다.

7. 설계에서 반복된 판단

증명의 층위를 구분한다

  • SG(prefix list)는 출처의 범위만 좁히고, 검증 헤더가 신원을 증명한다
  • 같은 논리로 IAM 정책 리소스 ARN에 DB 유저명까지 박아 "이 역할로는 이 유저만" 되게 했다

기록은 관측 대상 바깥에 남긴다

  • 감사 로그가 workload 안에만 있으면 침해 시 함께 사라진다
  • 격리 이력도 인스턴스 태그에만 두면 일일 destroy 때 증발하므로 별도 저장소에 남긴다

되돌릴 수 있는 대응을 고른다

  • 액세스키는 삭제가 아니라 비활성화 — IAM에 DeleteAccessKey를 주지 않았다
  • EC2는 종료가 아니라 네트워크만 차단 — EBS·메모리 포렌식이 가능하다

판단이 필요한 지점은 자동화하지 않는다

  • 격리는 자동, 복구는 수동 — 오탐 여부는 사람이 판단한다
  • 알림은 고른 것만 — 매시간 "이상 없음"은 보내지 않는다. 소음이 쌓이면 진짜 신호를 못 본다
