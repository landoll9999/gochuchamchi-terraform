# 2026-07-29 작업 기록

## 1. EKS+ArgoCD+Discord 재구축 트러블슈팅

### 작업 목적
- `gochuchamchi-eks(argo+discord)` 디렉토리로 EKS+ArgoCD(+Image Updater)+Discord 알림까지 처음부터 완전히 재구축 (VPC/EKS/ArgoCD/discord-notifications 전부 처음부터 apply)
- 배포 성공 후 ArgoCD/Image Updater/Discord 알림 파이프라인이 실제로 end-to-end 동작하는지 검증

### 1.1 `null_resource.apply_db_schema` PowerShell 따옴표 이스케이프 버그
- **증상**: `terraform apply` 중 local-exec 스크립트가 PowerShell 파싱 에러(`Unexpected token`)로 실패
- **원인**: `rds-schema-init.tf`의 local-exec가 `interpreter = ["PowerShell", "-Command"]`로 실행되는데, bash 쪽에 전달할 문자열(`SECRET_JSON=$(...)`, `mysql -p"$DB_PASS"`)을 PowerShell **큰따옴표** 문자열 안에 `\"`로 이스케이프하려 했음 — PowerShell 큰따옴표 문자열은 backtick(`` ` ``)만 이스케이프 문자로 인식하므로 `\"`는 그냥 문자열을 조기 종료시킴. 설령 고쳐도 `$(...)`가 PowerShell 서브표현식으로 **로컬에서** 실행돼버려 원래 의도(원격 SSM 명령으로 전달)와 어긋남
- **해결**: 해당 배열 원소들을 PowerShell **작은따옴표** 문자열로 교체(내부 작은따옴표는 `''`로 이스케이프) → PowerShell이 `$()`/`$VAR`를 전혀 해석하지 않고 완전히 리터럴로 취급, 그대로 SSM 원격 명령으로 전달됨

### 1.2 `terraform destroy`가 subnet/IGW 단계에서 영원히 막힘
- **증상**: destroy 도중 `Ingress ... still exists`, `Unable to uninstall Helm release argocd: context deadline exceeded`, `deleting EC2 Subnet: DependencyViolation`, `deleting EC2 Internet Gateway: has some mapped public address(es)` 동시 발생
- **원인 확인 과정**: ALB 컨트롤러 파드는 살아있는데(`Running`) 로그에 `dial tcp ...: i/o timeout`이 반복 — `aws ec2 describe-nat-gateways`/라우트 테이블 확인 결과 **NAT 인스턴스(EC2 기반, `module.nat_instance`)가 이미 삭제되고 기본 라우트도 사라진 상태**. `kubernetes_ingress_v1`/`helm_release.argocd`가 만든 ALB를 컨트롤러가 정리하는 도중, private subnet의 유일한 인터넷 경로였던 NAT가 먼저 destroy돼서 AWS API 호출이 전부 타임아웃 — 원인은 `module.nat_instance`/`aws_route.private_subnet`을 참조(depends_on)하는 리소스가 하나도 없어서 Terraform이 아무 때나 지워도 된다고 판단한 것
- **해결(설계 수정)**:
  - `eks-pod-identity.tf`: `helm_release.aws_load_balancer_controller`가 `module.nat_instance`, `aws_route.private_subnet`에 `depends_on`하도록 추가 → destroy 시 ALB 컨트롤러(및 이를 의존하는 external_dns/ingress/image_updater/argocd 전부)가 다 지워진 뒤에야 NAT가 지워지도록 순서 고정
  - `argocd.tf`: `helm_release.argocd`가 `helm_release.aws_load_balancer_controller`에 `depends_on`하도록 추가 (ArgoCD 자체 Ingress도 ALB를 만드는데 컨트롤러 대기 없이 병렬 생성/삭제되고 있었음 — external_dns와 같은 종류의 순서 누락 버그)
- **막힌 destroy를 그 자리에서 복구한 절차** (설계를 고쳐도 이미 꼬인 클러스터는 수동 개입 필요):
  1. `aws elbv2 describe-load-balancers`로 고아가 된 ALB 확인 → `aws elbv2 delete-load-balancer`로 수동 삭제 (ENI/EIP 해제)
  2. `kubectl get ingress -n <ns> <name> -o yaml`로 `deletionTimestamp`는 찍혔는데 `finalizers: [ingress.k8s.aws/resources]`가 안 없어진 것 확인
  3. `kubectl patch ingress <name> -n <ns> -p '{"metadata":{"finalizers":[]}}' --type=merge`로 강제 제거 → 즉시 삭제됨
  4. namespace가 `Terminating`에서 안 넘어가면 `kubectl get namespace <ns> -o yaml`의 `status.conditions`에서 원인 리소스 확인 (`TargetGroupBinding` 등 elbv2 관련 CR이 같은 이유로 finalizer 막혀있는 경우가 많음) → 그 리소스도 동일하게 finalizer patch

### 1.2-1 같은 교착이 다른 경로로 재발 — public 라우트 테이블
- **증상**: 위 수정(NAT/private 라우트 depends_on) 이후 다시 destroy했더니, NAT 인스턴스도 노드도 ALB 컨트롤러도 **전부 살아있는데** 컨트롤러 로그에 `dial tcp ...: i/o timeout`이 반복되며 Ingress 삭제가 20분 넘게 멈춤
- **원인**: `aws ec2 describe-route-tables`로 확인하니 private 라우트 테이블(→ NAT ENI)은 멀쩡한데 **public 라우트 테이블 자체가 이미 삭제된 상태**였음. NAT 인스턴스는 public subnet에 있는데 그 subnet의 IGW 경로가 사라져서 NAT가 인터넷으로 못 나감 → 결국 13.2와 같은 교착
- **왜 depends_on이 안 먹었나**: `helm_release.aws_load_balancer_controller`의 `set` 블록이 `module.vpc.vpc_id`를 참조하므로 **VPC 리소스 자체와는** 순서가 잡힘. 하지만 Terraform은 참조된 output이 의존하는 리소스까지만 따라가므로, **모듈 안의 public 라우트 테이블은 순서 밖**이라 병렬로 먼저 삭제됨
- **해결**: 컨트롤러의 depends_on에 `module.vpc`(모듈 전체)를 명시 → VPC 모듈의 모든 리소스가 컨트롤러보다 나중에 삭제됨
- **finalizer를 미리 비워두는 건 소용없음 (타이밍 함정)**:
  1. 컨트롤러가 살아있을 때 TGB finalizer를 비움 → 그땐 지워짐
  2. 이후 namespace 삭제가 TGB 삭제를 시도할 때 **아직 살아있던 컨트롤러가 finalizer를 다시 부착**
  3. 곧이어 terraform이 컨트롤러를 삭제 → finalizer를 떼어줄 주체가 영구 소멸 → 교착
  => 반드시 **ALB 컨트롤러가 삭제된 뒤에** finalizer를 제거할 것.
     권장 순서: ① ALB 수동 삭제 → ② destroy 진행해서 컨트롤러까지 지워지게 둠
                → ③ 남은 Ingress/TargetGroupBinding finalizer 일괄 제거 → ④ destroy 재실행
- **destroy 막바지의 `InvalidVpcID.NotFound`는 무해**: VPC는 실제로 삭제됐는데 Terraform의 삭제 요청이 경합에 걸려 받은 에러. destroy를 한 번 더 돌리면 refresh 후 state에서 정리됨
- **destroy 후 확인할 것**: 미사용 EIP(`aws ec2 describe-addresses`)는 남아있으면 계속 과금되므로 반드시 확인. ALB 컨트롤러가 만든 타겟그룹은 Terraform 관리 밖이라 고아로 남을 수 있음(`aws elbv2 describe-target-groups`)

### 1.2-2 3차 재발 — 이번엔 **보안 그룹 "규칙"**이 먼저 삭제됨
- **증상**: 보안 조치 apply 이후 다시 destroy했더니 또 같은 자리에서 멈춤
  ```
  kubernetes_ingress_v1.gochuchamchi_web: Still destroying... [19m50s elapsed]
  Error: Unable to uninstall Helm release argocd: … context deadline exceeded
  Error: Ingress (gochuchamchi/gochuchamchi-web-ingress) still exists
  ```
- **13.2 / 13.2-1과 달랐던 점 — 네트워크가 전부 멀쩡했음**: NAT 인스턴스 `running`, private 라우트 테이블 2개 모두 NAT ENI를 정상 지시, public 라우트 테이블의 IGW 경로도 존재, 노드 2대 `running`, ALB 컨트롤러 파드도 `Running` 2개. 눈에 보이는 건 다 정상이라 원인이 한참 안 잡혔음
- **결정적 단서는 컨트롤러 로그**였음:
  ```
  Reconciler error … EC2: DescribeSecurityGroups … dial tcp 43.202.71.241:443: i/o timeout
  Reconciler error … ElasticLoadBalancingv2: DescribeTargetHealth … i/o timeout
  ```
  구성요소는 살아있는데 **통신만 안 됨** → 경로가 아니라 필터(보안 그룹) 문제로 범위 좁힘
- **원인**: NAT 인스턴스의 보안 그룹(`module.nat_sg`) 규칙이 **0개**였음 (`add_node_sg`도 0개).
  보안 그룹 "그룹"은 실행 중인 인스턴스에 붙어 있어 삭제가 거부됐지만, **"규칙"은 별개 리소스**(`aws_vpc_security_group_ingress_rule` / `_egress_rule`)라 먼저 지워짐.
  인바운드가 없으니 노드가 보낸 트래픽을 NAT가 안 받고, 아웃바운드가 없으니 NAT가 인터넷으로 못 나감 → 컨트롤러의 AWS API 호출 전부 타임아웃 → ALB 정리 불가 → finalizer 영구 잔류
- **왜 기존 depends_on으로 안 막혔나 (13.2-1과 완전히 같은 함정)**:
  `module.eks`는 `module.add_node_sg.id`를, `module.nat_instance`는 `module.nat_sg.id`를 참조한다.
  하지만 그 `id`는 `aws_security_group` 리소스의 출력이라 **그 리소스 하나에만** 순서가 걸린다.
  같은 모듈 안의 규칙 리소스들은 **아무도 참조하지 않으므로** 그래프상 자유롭게 먼저 삭제된다.
  → `module.vpc`를 통째로 넣어야 했던 13.2-1과 원인·해법이 동일
- **해결(설계 수정)**: `eks-pod-identity.tf`의 컨트롤러 `depends_on`에 `module.nat_sg`, `module.add_node_sg`를 **모듈 전체로** 추가
- **막힌 destroy를 그 자리에서 복구한 절차** — 이번엔 ALB 수동 삭제/finalizer 강제 제거가 **불필요했음**:
  1. NAT 보안 그룹에 원래 규칙 2개를 수동 복구
     ```bash
     aws ec2 authorize-security-group-ingress --group-id <nat-sg> \
       --ip-permissions 'IpProtocol=-1,IpRanges=[{CidrIp=172.30.0.0/16}]'
     aws ec2 authorize-security-group-egress --group-id <nat-sg> \
       --ip-permissions 'IpProtocol=-1,IpRanges=[{CidrIp=0.0.0.0/0}]'
     ```
  2. 약 1분 뒤 컨트롤러가 스스로 정상 동작 재개 → **ALB 2개 자동 삭제 + Ingress finalizer 자동 해제** 확인
  3. `terraform destroy` 재실행
  => **통신만 되살려주면 컨트롤러가 알아서 정리한다.** finalizer를 강제로 뜯는 건 통신 복구가 불가능할 때의 최후 수단이고,
     가능하면 원인(경로/필터)을 고쳐서 컨트롤러가 정상 절차대로 끝내게 하는 편이 타겟그룹 고아 문제도 안 생겨서 낫다
- **수동 복구 규칙이 Terraform과 충돌하지 않는 이유**: 해당 규칙 리소스는 이미 state에서 제거된 상태라 Terraform이 모른다.
  이후 보안 그룹 자체가 삭제될 때 AWS가 그 안의 규칙을 함께 지우므로 잔재도 남지 않음
- **배스천이 이미 terminate된 뒤라 kubectl 경로가 없었음**: EKS 엔드포인트가 `/32`로 제한돼 있어도 **작업 PC가 그 허용 IP였으므로**,
  `aws eks get-token` + `curl`로 K8s REST API를 직접 호출해 파드 상태·로그·finalizer를 확인할 수 있었음
  ```bash
  EP=$(aws eks describe-cluster --name <c> --query cluster.endpoint --output text)
  TOK=$(aws eks get-token --cluster-name <c> --query status.token --output text)
  curl --ssl-no-revoke --cacert eks-ca.pem -H "Authorization: Bearer $TOK" \
    "$EP/api/v1/namespaces/kube-system/pods/<pod>/log?tailLines=25"
  ```
  (Windows Git Bash의 curl은 schannel을 써서 폐기목록 확인에 실패하므로 `--ssl-no-revoke` 필요)

### 1.3 ArgoCD 접속 주소가 `argocd.example.com`으로 나옴
- **원인**: `argocd.tf`의 `helm_release.argocd` values에서 `server.ingress.hosts = [...]`(list)를 썼는데, 현재 배포된 argo-cd 차트 버전은 `server.ingress.hostname`(단수 string)을 씀. Terraform/Helm은 차트가 모르는 키를 줘도 에러 없이 무시하므로 값이 조용히 버려지고 `global.domain` 기본값(`argocd.example.com`)이 그대로 적용됨
- **해결**: `hosts = [...]` → `hostname = "argocd.${var.domain_name}"`로 수정 (차트 GitHub 저장소의 실제 `values.yaml`을 직접 확인해서 정확한 키 이름 확정)

### 1.4 `discord-notifications` state가 `argocd-notifications-cm`/`-secret` 생성 시 `already exists`
- **원인**: 이 두 리소스는 argo-cd Helm 차트 자체가 기본으로 만들고 계속 소유함(`templates/argocd-configs/argocd-notifications-cm.yaml` 등, `notifications.cm.create`/`notifications.secret.create` 기본값 true) — 별도 state에서 새로 만들려니 충돌. `import`로 우회해도 다음 `helm_release.argocd` 업그레이드 때 차트가 빈 기본값으로 덮어써서 Discord 설정이 조용히 사라지는 문제가 있음
- **해결**: `argocd.tf`의 `helm_release.argocd` values에 `notifications.cm.create = false`, `notifications.secret.create = false` 추가 → 차트가 이 두 리소스를 아예 만들지/건드리지 않게 함 → `../terraform apply`로 기존 리소스가 지워진 뒤 `discord-notifications` state에서 충돌 없이 생성

### 1.5 Discord 알림이 전혀 발송 안 됨 (`service type 'discord' is not supported`)
- **원인**: `argocd-notifications-cm`의 `service.discord` 키는 애초에 존재하지 않는 서비스 타입이었음 — `notifications-engine`(`pkg/services/`) 소스를 직접 확인한 결과 discord 전용 구현이 없음(slack/teams/telegram/webhook 등만 존재)
- **해결**: `service.webhook.discord`(범용 webhook 서비스, Discord Webhook URL 직접 POST)로 교체. 기본 webhook 서비스는 GET+메시지원문을 보내는데 Discord Webhook은 POST+JSON(`{"content": "..."}`)만 허용하므로, `template.app-sync-succeeded`/`app-sync-failed`/`app-health-degraded`를 오버라이드해서 `webhook.discord.method: POST` + JSON body를 명시

### 1.6 위 수정 후에도 `trigger 'on-sync-succeeded' is not configured` 에러
- **원인**: `trigger.*` 정의(on-sync-succeeded 등)가 컨트롤러에 내장된 게 아니라, 원래는 argo-cd Helm 차트가 `argocd-notifications-cm`을 만들 때 기본값으로 같이 채워주던 것이었음. 13.4에서 차트의 CM 소유권을 완전히 가져오면서 그 기본 트리거 정의까지 같이 사라짐
- **해결**: `argoproj/argo-cd` 저장소의 `notifications_catalog/install.yaml`에서 `trigger.on-sync-succeeded`/`trigger.on-sync-failed`/`trigger.on-health-degraded` 정의를 그대로 가져와 `discord-notifications/notifications.tf`에 명시적으로 추가

### 1.7 `argocd-image-updater`가 write-back을 전혀 안 함 (annotation 무시됨)
- **증상**: Docker Hub에는 새 이미지가 올라와 있는데 `gochuchamchi-gitops` 저장소에 커밋이 전혀 안 생김. 컨트롤러 로그에 `"No ImageUpdater CRs to process"`만 반복
- **원인**: `helm_release.argocd_image_updater`가 버전 고정 없이 최신 차트를 받다 보니 `argocd-image-updater v1.2.2`가 설치됐는데, 이 버전부터 Application의 `argocd-image-updater.argoproj.io/*` annotation을 더 이상 자동으로 안 읽고, 새로 생긴 `ImageUpdater` CRD로 명시적으로 감시 대상을 지정해야만 동작함(`kubectl explain imageupdater.spec`으로 스키마 확인)
- **해결**: `charts/gochuchamchi-application/templates/imageupdater.yaml`을 추가해서 `ImageUpdater` CR을 생성, `applicationRefs[].useAnnotations: true`로 기존 annotation 설정을 그대로 재사용하도록 함. CRD가 먼저 설치돼야 하므로 `helm_release.gochuchamchi_application`이 `helm_release.argocd_image_updater`에 `depends_on`하도록 순서도 추가
- **추가로 걸린 함정**: 이 템플릿 파일을 추가한 뒤 `terraform apply`를 돌려도 반영이 안 됨 → `charts/gochuchamchi-application/Chart.yaml`의 `version`을 안 올려서 Terraform이 로컬 차트 내용 변경을 감지 못 한 것 (`pitfalls-checklist.md` 참고). `version: 0.1.0` → `0.2.0`으로 올리자 정상 반영됨
- **Image Updater의 실제 write-back 방식도 예상과 달랐음**: 기존 주석(`kustomization.yaml`의 `images.newTag`를 직접 커밋)과 달리, 실제로는 `.argocd-source-<app>.yaml`이라는 별도 오버라이드 파일을 새로 만들어 커밋하고, ArgoCD가 sync 시점에 이를 Kustomize 오버레이로 병합하는 방식이었음 — 베이스 `kustomization.yaml`은 그대로 두고 이 파일만 갱신됨

### 1.8 배스천 SSM 세션에서 `kubectl: command not found`
- **원인**: SSM Session Manager 기본 접속 사용자는 `ec2-user`가 아니라 `ssm-user`. `userdata.sh.tpl`이 kubectl을 `/home/ec2-user/bin/`에만 설치하는데, `/home/ec2-user` 홈 디렉토리 자체가 `700`(소유자 전용) 권한이라 다른 사용자는 PATH를 잡아줘도 애초에 그 디렉토리 트리에 진입 자체가 안 됨
- **해결**: `sudo su - ec2-user`로 로그인 셸 전환 (`-` 필수 — `.bash_profile`의 PATH 설정과 kubeconfig 소유권이 제대로 적용되려면 로그인 셸이어야 함)

### 검증 완료 사항
- Docker Hub 새 이미지 push → Image Updater 감지 → `gochuchamchi-gitops`에 write-back 커밋 → ArgoCD 자동 sync → Deployment 롤링 업데이트까지 전체 파이프라인 실제 동작 확인
- `gochuchamchi-gitops`에 테스트 리소스 추가/삭제 커밋으로 ArgoCD의 자동 배포(sync)와 자동 정리(prune) 양방향 모두 확인
- ArgoCD sync 성공 시 Discord 채널에 실제 알림 도착 확인

## 2. `gochuchamchi.shop` 접속 불가 (`DNS_PROBE_FINISHED_NXDOMAIN`)

### 증상
- 브라우저에서 `https://gochuchamchi.shop` 접속 시 `DNS_PROBE_FINISHED_NXDOMAIN` — 도메인 자체가 없는 것처럼 응답
- `www.gochuchamchi.shop`, `argocd.gochuchamchi.shop`은 정상 접속됨 (apex만 문제)

### 원인 확인 과정
1. `aws route53 list-resource-record-sets`로 확인한 apex(`gochuchamchi.shop.`) A/ALIAS 레코드가 가리키는 ALB DNS 이름(`...-842323760...`)이, `aws elbv2 describe-load-balancers`로 확인한 **현재 실제로 떠 있는 ALB의 DNS 이름(`...-1755434171...`)과 다름** — 삭제된 옛날 ALB를 계속 가리키는 낡은 레코드였음 (오늘 destroy/재생성을 여러 번 반복하면서 ALB가 재생성될 때마다 DNS 이름이 바뀌는데, apex 레코드만 갱신이 안 되고 있었음)
2. `www`는 이미 올바른 최신 ALB를 가리키고 있어서 정상 동작 — apex만 유독 안 바뀐 이유를 external-dns 쪽에서 조사
3. `kubectl delete pod -n external-dns -l app.kubernetes.io/name=external-dns`로 강제 재시작 후 로그의 `config:` 라인에서 `TXTPrefix:`가 **빈 문자열**임을 확인
4. 그런데 실제 Route53에 있는 TXT 소유권 레코드는 전부 `cname-www...`, `aaaa-www...`, `cname-argocd...` 처럼 **접두사가 붙어있었음** → 이건 예전(이전 세션 또는 이전 버전) external-dns가 다른 `--txt-prefix` 설정으로 만들어 놓은 흔적이고, 지금 떠 있는(접두사 없는 설정의) external-dns는 이 TXT 레코드들을 자기 소유로 인식하지 못함
5. `policy: upsert-only`라 소유권(TXT)이 확인 안 되는 레코드는 값이 틀려도 절대 건드리지 않도록 설계되어 있어서, apex는 물론 사실 `www`/`argocd`도 (지금 우연히 값이 맞아서 티가 안 났을 뿐) 전부 "고아" 상태였음 — Route53 호스티드존이 `data` 소스라 여러 세션에 걸쳐 재사용되면서, 그 사이 컨트롤러 버전/설정이 바뀔 때마다 TXT 소유권 형식이 어긋나기 시작한 것으로 추정

### 해결
1. **즉시 복구**: `aws route53 change-resource-record-sets`로 apex A/ALIAS 레코드를 현재 ALB DNS 이름으로 수동 UPSERT → 바로 접속 정상화
2. **재발 방지**: 현재 external-dns 설정(무접두사)에 맞는 TXT 소유권 레코드를 `gochuchamchi.shop`/`www.gochuchamchi.shop`/`argocd.gochuchamchi.shop` 3개 전부에 새로 생성(`CREATE`) — 이제 external-dns가 이 셋을 진짜 자기 소유로 인식하므로, 다음에 ALB가 재생성돼도 자동으로 갱신됨 (수동 개입 불필요)
3. 재시작된 external-dns 로그에서 `"All records are already up to date"`로 에러 없이 안정화 확인

### 교훈 (체크리스트 추가)
- [ ] Route53 존을 `data` 소스로 재사용하는 구조에서는, destroy/apply를 반복하거나 external-dns 버전/설정이 바뀔 때 **TXT 소유권 레코드 형식(prefix 유무 등)이 과거 흔적과 어긋나면서 특정 레코드가 "고아" 상태로 방치될 수 있음** — 사이트가 갑자기 NXDOMAIN/엉뚱한 곳으로 뜨면, external-dns 로그의 `config:` 라인에서 `TXTPrefix` 값과 실제 Route53의 TXT 레코드 이름 패턴이 일치하는지부터 확인할 것
- [ ] ALB가 재생성되는 이벤트(수동 삭제, destroy/apply 재반복 등) 이후에는 관련 도메인이 실제로 최신 ALB를 가리키는지 `aws route53 list-resource-record-sets` vs `aws elbv2 describe-load-balancers`로 교차 확인하는 습관 필요

## 3. 컨테이너 레지스트리 Docker Hub → Amazon ECR 마이그레이션

### 작업 목적 / 전환을 권장한 이유
- 기존: `gochuchamchi-spring`의 GitHub Actions가 Docker Hub(`dnjstjr504/gochuchamchi`, **public**)로 push → Image Updater가 감시
- 전환 근거:
  1. Cluster Autoscaler로 노드가 늘어날 때마다 각 노드가 이미지를 새로 pull하는데, Docker Hub **익명 pull은 6시간당 100회 제한**이 있어 스케일 아웃 시 실패 위험
  2. Docker Hub 저장소가 public이었음 → ECR은 기본 private
  3. 같은 리전(ap-northeast-2) 내 pull이라 더 빠르고, **외부 서비스 의존성이 하나 줄어듦**
  4. GitHub Actions ↔ AWS 인증을 OIDC로 바꾸면 정적 액세스키를 GitHub Secret에 둘 필요가 없어짐
- 실현 가능성 사전 확인: EKS 노드 IAM 역할에 이미 `AmazonEC2ContainerRegistryReadOnly`가 붙어있어(terraform-aws-modules/eks 기본값) **파드 pull에는 `imagePullSecrets`가 아예 불필요**했음

### 변경한 것
- `terraform/ecr.tf`(신규): `aws_ecr_repository`(scan_on_push) + lifecycle policy(최근 10개만 유지) + GitHub Actions용 OIDC Provider + push 전용 IAM Role(신뢰 정책을 `repo:<owner>/gochuchamchi-spring:ref:refs/heads/main`으로 제한)
- `terraform/eks-pod-identity.tf`: Image Updater가 ECR 토큰을 발급받을 Pod Identity 추가(`additional_policy_arns`로 `AmazonEC2ContainerRegistryReadOnly` 부착)
- `terraform/argocd.tf`: Image Updater에 ECR 레지스트리 커스텀 등록 + `authScripts`로 인증 스크립트 마운트, 앱 이미지 참조를 ECR로 교체
- `charts/gochuchamchi-application`: `dockerhubImage` → `appImage`로 이름 변경(Chart version 0.2.0 → 0.3.0)
- `gochuchamchi-spring/.github/workflows/deploy.yml`: Docker Hub 로그인/push → OIDC + `amazon-ecr-login` + ECR push (`workflow_dispatch`도 추가해 코드 변경 없이 수동 트리거 가능하게 함)
- `gochuchamchi-gitops`: `deployment.yml`/`kustomization.yaml`의 이미지 참조를 ECR로, stale해진 `.argocd-source-gochuchamchi.yaml`(Docker Hub 오버라이드)은 삭제

### 3.1 Image Updater 파드가 `Init:CreateContainerConfigError`로 뜨지 않고 helm이 10분 타임아웃
- **증상**: `helm_release.argocd_image_updater`가 `Upgrade failed: context deadline exceeded`로 실패. 파드는 `Init:CreateContainerConfigError` 상태로 10분간 정지
- **원인**: ECR 인증 스크립트가 `aws` CLI를 필요로 한다고 판단해서 `amazon/aws-cli` 이미지를 initContainer로 붙였는데, 이 이미지는 root로 실행됨. 반면 argocd-image-updater 차트의 podSecurityContext는 `runAsNonRoot: true` → kubelet이 컨테이너 생성 자체를 거부 (`container has runAsNonRoot and image will run as root`)
- **해결(설계 자체를 제거)**: `argocd-image-updater` 이미지의 Dockerfile을 확인해보니 **alpine 기반에 `apk add ... aws-cli ...`로 aws CLI가 이미 설치되어 있고**(배포된 v1.2.2 태그에서도 확인) UID 1000으로 실행됨 → initContainer/volumes를 전부 걷어내고 스크립트에서 `aws`를 바로 호출
- **교훈**: 컨테이너에 도구가 없다고 가정하고 사이드카/initContainer를 붙이기 전에, **해당 이미지의 Dockerfile을 먼저 확인**할 것

### 3.2 위를 고쳤는데도 두 번째 apply가 같은 자리에서 또 10분 타임아웃
- **증상**: 수정본을 apply해도 `Upgrade failed: context deadline exceeded` 반복. 확인해보니 클러스터의 deployment에는 **여전히 예전 broken spec(initContainer)이 그대로** 남아있어서 수정본이 반영조차 안 된 상태였음
- **원인**: helm 릴리즈가 v2, v3 연속 `failed`. `cleanup_on_fail = true`가 **실패한 upgrade에서 "새로 생성된" 리소스를 롤백으로 삭제**하는데, 이때 `argocd-image-updater-authscripts` ConfigMap이 지워짐. 그런데 deployment는 그 ConfigMap을 필수 마운트(`Optional: false`)로 참조하고 있어서 새 파드가 `MountVolume.SetUp failed ... configmap not found`로 못 뜸 → 다음 upgrade도 rollout 대기에서 계속 타임아웃되는 교착
- **수동 복구 절차**:
  1. `kubectl patch deployment argocd-image-updater-controller -n argocd --type=json -p '[{"op":"remove","path":"/spec/template/spec/initContainers"}]'` — broken initContainer 제거
  2. 누락된 `argocd-image-updater-authscripts` ConfigMap을 직접 생성하되, **helm이 다음 upgrade에서 인수(adopt)하도록 소유권 메타데이터를 반드시 포함**:
     ```yaml
     labels:
       app.kubernetes.io/managed-by: Helm
     annotations:
       meta.helm.sh/release-name: argocd-image-updater
       meta.helm.sh/release-namespace: argocd
     ```
     (이 메타데이터 없이 만들면 §1.4처럼 다음 upgrade에서 `already exists` 충돌이 남)
  3. 파드가 `1/1 Running`이 된 뒤 `terraform apply` 재실행 → helm v4 `deployed`

### 3.3 registries.conf의 `api_url`에 저장소 경로까지 들어간 버그
- **원인**: `aws_ecr_repository.repository_url`은 `<account>.dkr.ecr.<region>.amazonaws.com/<repo>` 형태인데 이걸 그대로 `api_url`에 넣어서 `https://....amazonaws.com/gochuchamchi`가 됨. 레지스트리 API 엔드포인트는 **호스트까지만**이어야 하고, 저장소 이름은 이미지 참조 쪽에 들어가는 값
- **해결**: `local.ecr_registry_host = split("/", ...repository_url)[0]`로 분리해서 `api_url`/`prefix` 모두 호스트만 사용
- **검증 방법**: `kubectl get cm argocd-image-updater-config -n argocd -o jsonpath='{.data.registries\.conf}'`로 실제 생성된 설정을 눈으로 확인

### 3.4 `gh`로 워크플로 파일을 push할 때 404
- **증상**: 저장소 권한은 `admin: true`인데 `.github/workflows/deploy.yml` PUT이 404
- **원인**: `gh` 토큰 스코프가 `gist, read:org, repo`뿐이었음. GitHub은 `.github/workflows/` 아래 파일 생성/수정에 **`workflow` 스코프를 별도로 요구**하고, 없으면 403이 아니라 **404를 반환**해서 원인이 잘 안 드러남
- **해결**: `gh auth refresh -h github.com -s workflow` (device flow 인증)

### 3.5 마이그레이션 순서 — ECR이 비어있는 상태에서 gitops를 먼저 바꾸면 서비스가 죽음
- 새로 만든 ECR은 당연히 비어있으므로, **gitops 매니페스트를 ECR로 먼저 바꾸면 `ImagePullBackOff`로 사이트가 즉시 다운됨**
- 안전한 순서(실제로 이 순서로 진행함):
  1. CI 워크플로를 ECR push로 교체
  2. `workflow_dispatch`로 수동 실행해서 **ECR에 첫 이미지 적재** (여기까지는 운영 중인 사이트가 기존 Docker Hub 이미지로 계속 서비스)
  3. gitops 매니페스트를 ECR 참조로 교체 → ArgoCD 자동 배포
  4. 파드가 ECR 이미지로 정상 기동 + 사이트 200 확인
  5. 그 다음에야 Docker Hub 저장소 삭제
- 참고: 워크플로 파일을 push하면 `push` 트리거와 `workflow_dispatch` 트리거가 **동시에 2번 실행**됨. 같은 커밋이라 태그가 겹쳐서 먼저 끝난 쪽 이미지가 untagged로 남는데, lifecycle policy가 정리하므로 무해

### 3.6 전환 직후 사이트가 일시적으로 502
- 파드 교체(롤아웃) 중 ALB 타겟 등록/헬스체크 통과 전이라 나는 **일시적 현상**이었고, 롤아웃 완료 후 5회 연속 HTTP 200으로 정상 확인됨
- 이때 롤아웃이 두 번 일어난 이유: gitops 커밋으로 SHA 태그 배포 → 곧이어 Image Updater가 ECR을 스캔해 `latest` 태그로 write-back(커밋 `build: automatic update of gochuchamchi`) → 두 번째 롤아웃. 동일 이미지라 내용 변화는 없음

### 검증 완료 사항
- GitHub Actions → OIDC로 AWS assume → ECR push 성공 (정적 키 없이)
- EKS 노드가 `imagePullSecrets` 없이 ECR pull 성공 (노드 역할의 `AmazonEC2ContainerRegistryReadOnly`만으로 동작)
- 파드 내부에서 Pod Identity 환경변수 주입 + `/scripts/ecr-auth.sh` 실행 → ECR 토큰 정상 발급 확인
- Image Updater가 ECR을 감시해서 `gochuchamchi-gitops`에 write-back 커밋 생성 확인
- ArgoCD 동기화 → 파드가 ECR 이미지로 교체 → `https://gochuchamchi.shop` HTTP 200

### 마이그레이션 후 정리
- `gochuchamchi-spring`의 불필요해진 GitHub Secret 6개 삭제: `DOCKERHUB_TOKEN`, `DOCKERHUB_USERNAME`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_REGION`, `EC2_INSTANCE_ID`
  - 주의: **GitHub Secret을 지워도 AWS 쪽 실제 IAM 액세스 키는 그대로 살아있음**. 별도로 IAM에서 비활성화/삭제해야 함 (이번엔 계정의 활성 키가 `admin`(로컬 terraform용, 유지 필요)과 `kim`(한 번도 사용된 적 없고 연결 정책도 없는 팀원 계정)뿐이라 건드리지 않음)
- Docker Hub 저장소(`dnjstjr504/gochuchamchi`) 삭제는 Docker Hub 웹 UI에서 수동으로 수행 (Settings → Delete repository)
