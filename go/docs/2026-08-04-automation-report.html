1. 왜 자동화인가 — 장애 5건의 공통점

지금까지 겪은 장애를 원인별로 세어보면 결론이 하나로 모인다.

날짜장애진짜 원인
8/3회원가입 500schema.sql이 실행되지 않았는데 프로비저너가 Status를 검사하지 않아 terraform이 성공으로 기록
8/3사이트 503ECR이 비어 ImagePullBackOff — apply는 성공
8/4사이트 503PAT 미주입으로 ArgoCD가 저장소에 못 붙음 — apply는 성공
8/4앱 전체 500NetworkPolicy가 서비스 CIDR을 안 열어 DNS 전면 차단 — apply는 성공
8/4이중 잠김terraform은 Secret 이름을 바꿨는데 gitops는 옛 이름 참조 — apply는 성공
공통점. “terraform apply 성공”이 “서비스 정상”을 전혀 보장하지 않는데, 그 간극을 사람이 매번 손으로 메우고 있었다. 8/4 회고에 적어둔 교훈 — “체크리스트가 문서에 있어도 강제 장치가 없으면 누락된다” — 을 코드로 옮기는 것이 이번 작업이다.

자동화 이전 / 이후

이전 — 검증이 전부 사람 몫
terraform apply→ 성공→ 사람이 runbook 보고 수동 확인(누락 가능)→ 장애를 사용자가 먼저 발견
이후 — 계약 + 자동 검증이 파이프라인 안에
terraform apply→ 계약 검증(이름·키)→ 스모크 테스트 12종→ PASS / FAIL + 다음 행동 출력
상시 — Terraform 밖의 변경 감지
콘솔 클릭 / IAM 변경 / 루트 사용→ CloudTrail→ EventBridge 룰 3종→ SNS 허브→ Discord + 이메일

2. 자동화 ① 배포 계약 (Deployment Contract)

신규terraform/contract.tf · scripts/verify-contract.ps1

terraform이 만드는 Secret/ConfigMap 이름과 gitops가 참조하는 이름은 두 저장소 사이의 인터페이스인데, 지금까지 어디에도 명시돼 있지 않았다. 그래서 한쪽만 바꿔도 아무도 못 막았다. 이제 output "deployment_contract" 하나가 그 계약서 역할을 한다.

계약 항목어긋나면 생기는 일
ConfigMap 이름·키앱이 DB 호스트/유저를 못 받음 → 기동 실패
Secret 이름·키새 파드가 CreateContainerConfigError로 못 뜸 (8/4 장애)
forbidden_refs
(삭제된 이름)		옛 문서를 보고 gochuchamchi-db-secret을 되살리는 것을 차단
Service 이름/포트Ingress 백엔드가 안 잡혀 ALB 타겟 미등록 → 503
파드 라벨NetworkPolicy가 아무 파드에도 안 걸리고 default-deny만 남아 앱 전체 차단
계약에 값(비밀)은 절대 넣지 않는다. 넣는 순간 output이 tfstate·CLI에 그대로 노출되어 db-zero-trust.tf/eso.tf로 없앤 경로가 부활한다. 실제로 kubernetes_secret_v1.data는 provider가 sensitive로 표시하므로 keys()로 뽑으면 output 자체가 거부된다 — 그래서 Secret의 키는 의도적으로 문자열 리터럴로 적었다.

검증 스크립트가 보는 것

정적 — gitops YAML

  • 참조 이름이 계약에 없으면 FAIL
  • 삭제된 이름을 참조하면 FAIL
  • 계약에 있는데 아무도 안 쓰면 WARN
  • kustomization.yaml에 등재 안 된 잔재 매니페스트 적발 8/4 §4.5
  • Service 이름·파드 라벨 일치

라이브 — 클러스터 실측

  • Secret/ConfigMap이 실제로 존재하고 키까지 맞는가
  • 배포된 Deployment의 참조가 전부 해석되는가
  • gochuchamchi-db-app은 배스천이 런타임에 만드는 Secret이라 “apply 성공”이 존재를 보장하지 않는다 → 실측이 필수

3. 자동화 ② apply 후 스모크 테스트

신규terraform/smoke-test.tf · scripts/smoke-test.ps1

겪은 장애를 하나씩 검사 항목으로 옮겼다. 각 항목은 실패 시 다음 행동을 함께 출력한다.

#검사대응 사고 / 실패 시 안내
2kubectl 컨텍스트가 지금 클러스터인가8/3 옛 클러스터 kubeconfig(no such host) → aws eks update-kubeconfig 명령 출력
3노드 Ready 수API 접속 실패 시 endpoint_public_access_cidrs에 현재 IP 확인 안내
4배포 계약 (위 스크립트 위임)8/4 CreateContainerConfigError
5파드 상태 + waiting reason + 재시작 횟수8/3 ImagePullBackOff(빈 ECR) → “앱 CI 재실행” 안내
6ExternalSecret Ready8/4 PAT 미주입 → argocd_git_pat_inject_command 안내
7ArgoCD Application Synced/HealthyGitOps 동기화 실패
8파드에서 DNS 해석 getent hosts <RDS>8/4 NetworkPolicy DNS 전면 차단 → 서비스 CIDR 확인 + delete netpol --all 롤백
9파드에서 3306 / 6379 TCP 도달SG(참조 규칙)·netpol egress 회귀
10Ingress ALB 주소 할당LB 컨트롤러 실패
11/ 200, /api/health 302사용자 관점 최종 확인 (302 = 로그인 리다이렉트 = 정상, 8/4 복구 검증 기준)
12ALB 타겟 헬스파드는 Running인데 타겟이 unhealthy인 구간 — 503의 직접 원인
기본은 경고 모드다. 재구축 직후에는 PAT 수동 주입 전이라 앱이 안 떠 있는 게 정상이고, 여기서 apply를 실패시키면 재구축 자체가 막힌다. 정상 가동 중 변경 apply에서는 $env:TF_VAR_smoke_test_enforce = "true"로 올려서 “서비스를 깨는 apply는 실패로 기록”되게 하는 것이 목표 상태.
왜 계약을 인자로 넘기나. apply 도중에는 state가 아직 확정 전이라, 스크립트가 terraform output을 호출하면 옛 값을 읽거나 실패한다. 그래서 null_resource가 계약 JSON을 명령 인자로 직접 전달한다(단독 실행 시에만 output 조회).

4. 자동화 ③ 수동 변경(드리프트) 감지

신규cloudwatch-notifications/drift-detection.tf · 수정sns.tf, lambda_function.py

룰무엇을 잡나 / 노이즈 대책
gochuchamchi-console-mutation CloudTrail의 sessionCredentialFromConsole=true + readOnly=false — 사람이 브라우저에서 클릭한 변경만. Terraform·CLI·클러스터 컨트롤러(ALB controller, ExternalDNS)는 이 필드가 없어 자동으로 걸러지므로 제외 목록 없이도 노이즈가 거의 없다.
gochuchamchi-iam-mutation aws.iam 비읽기 호출 중 Terraform 실행 주체를 제외한 전부 (anything-but + data.aws_caller_identity.current.arn). 제외하지 않으면 apply마다 수십 건이 울린다.
gochuchamchi-root-activity 루트 계정 사용(로그인 포함). MFA 강제 그룹으로도 통제 못 하는 유일한 주체라, 쓰였다는 사실 자체가 신호.

왜 terraform plan 방식이 아닌가 — 트레이드오프

정석은 “하루 1회 plan -detailed-exitcode → 종료코드 2면 알림”이다. 그런데 이 스택은 kubernetes/helm 프로바이더를 쓰고 EKS 퍼블릭 엔드포인트가 /32 허용목록으로 잠겨 있어, GitHub 호스티드 러너에서는 plan이 refresh 단계에서 타임아웃난다. 즉 plan 방식은 self-hosted runner 결정이 선행돼야 한다.

plan 기반 (미도입)

  • 모든 드리프트를 잡음
  • 러너 인프라 필요, 사후 감지(최대 1일 지연)

이벤트 기반 (이번 도입)

  • 콘솔 변경을 즉시 감지, 비용 0, 러너 불필요
  • CLI/SDK로 낸 수동 변경은 못 잡음

두 방식은 대체재가 아니라 보완재다. 러너가 생기면 plan 룰을 추가로 붙인다.

함정 2개를 주석으로 남겼다.
① SNS 토픽 정책의 ArnEquals에 새 룰 ARN을 등록하지 않으면 발행이 조용히 거부된다 — 룰 지표는 정상(TriggeredRules 증가)인데 알림만 안 오는, 원인 찾기 어려운 유형.
② input_transformer로 이메일용 예쁜 문자열을 만들면, 같은 토픽을 구독하는 Lambda가 받는 Message가 JSON이 아니게 되어 json.loads에서 터지고 → SNS 재시도 → DLQ로 간다. 그래서 원본 JSON을 보내고 사람이 읽는 형태로 바꾸는 일은 Lambda가 담당한다.

6. 알려진 한계

항목한계판단
스모크 테스트가 매 apply 실행plan에 항상 1개 변경으로 뜸“코드가 바뀔 때”가 아니라 “인프라를 건드릴 때마다” 돌아야 의미 → 감수
경고 모드가 기본실패해도 apply 통과재구축 시나리오를 막지 않기 위함. 정상 가동 중에는 enforce로 승격
수동 변경 감지가 콘솔 한정CLI/SDK 수동 변경은 미검출완전 커버는 plan 기반 필요 → 러너 결정 선행
계약 정적 검증이 정규식 기반특이한 YAML 형식은 놓칠 수 있음라이브 검증이 2차 방어. Helm 템플릿 gitops로 가면 재설계 필요
이메일 구독자는 원본 JSON 수신읽기 불편Discord = 사람이 읽는 채널, 이메일 = “파이프라인 고장” 백업 경로라는 원래 역할대로

7. 남은 작업 — 러너 결정이 병목

다음 결정 1개가 아래 3개를 막고 있다. EKS 퍼블릭 엔드포인트가 /32 허용목록이라 GitHub 호스티드 러너는 kubernetes/helm 프로바이더 refresh에서 타임아웃 난다.
  (a) CI는 lint·보안스캔·계약 정적검증까지만 + apply는 로컬  /  (b) 배스천에 self-hosted runner
상태항목
대기Terraform CI — PR에 fmt/validate/tflint/checkov + plan 코멘트, main 머지 시 승인 후 apply. OIDC provider는 ecr.tf에 이미 있으므로 plan용(ReadOnly)·apply용 역할 2개만 추가
대기plan -detailed-exitcode 기반 드리프트(하루 1회) — 이번 이벤트 감지와 보완 관계
대기gitops PR에서 계약 검증 실행 — 진짜 “머지 차단”은 여기서 완성됨
백로그이미지 태그 자동화 — gitops kustomize화 + CI가 태그 커밋 → ArgoCD PAT를 read-only로 강등 + ECR IMMUTABLE 전환 가능 (백로그 2건 동시 해소)
백로그야간·주말 노드그룹 스케일다운(EventBridge Scheduler) — 비용 절감, ArgoCD/ESO 기동 순서 설계 필요

8. 면접 설명

“장애 5건을 사후 분석해보니 전부 ‘apply는 성공했는데 서비스는 죽어 있는’ 유형이었고, 공통 원인은 절차가 문서에만 있고 강제 장치가 없다는 것이었습니다. 그래서 두 저장소 사이의 인터페이스를 Terraform output으로 선언해 계약으로 만들고(삭제된 이름까지 금지 목록으로 명시), apply 파이프라인 안에서 계약 일치·DNS·TCP·ALB 타겟·HTTP까지 12개를 자동 검증하게 했습니다. 재구축을 막지 않으려고 기본은 경고 모드로 두고 운영 상태에서는 강제 모드로 올리는 구조입니다. 드리프트는 CloudTrail의 콘솔 세션 플래그로 ‘사람이 콘솔에서 만진 변경’만 골라 알림을 붙였는데, 이건 EKS 엔드포인트를 /32로 잠가둔 탓에 CI 러너에서 terraform plan을 못 돌리는 제약을 우회한 선택이고, self-hosted runner를 붙이면 plan 기반 감지를 추가할 계획입니다.”
