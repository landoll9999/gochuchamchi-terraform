**네 건 모두 "재시도하면 되겠지"로 넘어가면 안 되는, 원인이 따로 있는 문제**였습니다.

## 1. `terraform apply`가 `Error locating chart`로 두 번 중단됨

### 문제가 발생한 지점

apply 도중 `helm_release`만 골라서 실패했습니다. 1차는 `aws_load_balancer_controller`, 재실행 후 2차는 `argocd`였습니다.

```
Error: Error locating chart

  with helm_release.argocd,
  on argocd.tf line 16, in resource "helm_release" "argocd":

Unable to locate chart argo-cd: looks like "https://argoproj.github.io/argo-helm" is not a valid
chart repository or cannot be reached: read tcp 192.168.31.51:55946->185.199.109.153:443:
wsarecv: A connection attempt failed because the connected party did not properly respond after
a period of time, or established connection failed because connected host has failed to respond.
```

### 오진했던 경로

처음에는 **일시적 네트워크 장애로 판단하고 재실행을 권했습니다. 이건 틀린 진단이었습니다.**
근거로 삼았던 것은 단독 테스트가 전부 통과했다는 사실이었습니다.

```
aws.github.io            -> 185.199.111.153  TcpTestSucceeded=True
kubernetes-sigs.github.io-> 185.199.108.153  TcpTestSucceeded=True
kubernetes.github.io     -> 185.199.111.153  TcpTestSucceeded=True

index.yaml 5회 연속 fetch -> 5/5 성공 (1556KB, 평균 580ms)
```

**단독 테스트가 통과한다는 것이 곧 문제 없음을 뜻하지 않습니다.** 두 번째 발생(`argocd`)이 있고 나서야 재현되는 문제임이 확정됐습니다.

### 문제 원인 — PMTUD 블랙홀

TCP 4개 IP 전부 `ok=4/4`, 평균 3~13ms로 정상인데도 실패한다는 점이 단서였습니다. **연결은 되는데 읽기에서 죽는다**(`wsarecv`)는 것은 경로 MTU 문제의 전형적인 형태입니다.

```
payload 1472 (1500 total) -> SILENT DROP (블랙홀)
payload 1464 (1492 total) -> ok
payload 1452 (1480 total) -> ok
payload 1444 (1472 total) -> ok
```

- 회선의 실제 경로 MTU는 **1492**(PPPoE 전형값)인데 이더넷 어댑터는 **1500**
- 1500바이트 패킷이 드롭될 때 라우터가 ICMP `fragmentation needed`를 **돌려주지 않고 그냥 버림**
- → OS가 MSS를 낮춰야 한다는 사실을 영영 알지 못함

증상이 정확히 맞아떨어집니다:

| 단계 | 패킷 크기 | 결과 |
|---|---|---|
| TCP 3-way handshake | 작음 | 성공 (`Test-NetConnection` 통과) |
| TLS handshake 초반 | 작음 | 성공 |
| `index.yaml` 본문 전송 | **풀사이즈 1500** | **증발** → 재전송 반복 → 읽기 타임아웃 |

**간헐적으로 보이는 이유**는 Windows의 블랙홀 탐지가 재전송 몇 번 후 MSS를 낮추는 데 가끔 성공하기 때문입니다. 그래서 단독 테스트(연결 1개)는 통과하고, apply처럼 연결이 여러 개 몰릴 때 실패합니다.

### 해결 방법

관리자 권한 PowerShell:

```powershell
netsh interface ipv4 set subinterface "이더넷" mtu=1492 store=persistent
netsh interface ipv4 show subinterfaces      # 확인
```

재부팅 불필요. 되돌리려면 `mtu=1500`.

> **이 조치는 아직 적용하지 않았습니다.** 세션이 비관리자라 실행할 수 없었습니다. 다음 apply 전에 반드시 적용할 것.

### 검증 완료 사항

- 진단 근거는 `ping -f`(DF 비트) 응답 유무로 확정 — `Packet needs to be fragmented` 메시지조차 없는 **무응답**이라 블랙홀 확정
- GitHub Pages 고유 문제가 아님. 큰 응답을 주는 모든 호스트에 해당하며 EKS API 호출·ECR 푸시도 같이 영향받음
- 차선책 `terraform apply -parallelism=1`은 동시 연결 수를 줄여 확률만 낮출 뿐 근본 해결이 아님

### 남은 개선 여지

`helm_release` 3개(`aws-load-balancer-controller`, `external-dns`, `cluster-autoscaler`)에 `version`이 없어 매 apply마다 최신 차트를 받습니다. 버전 고정을 제안했으나 **최신 자동 추적을 유지하기로 결정**했습니다(의도된 선택).

## 2. `kubectl`이 전부 `no such host`

### 문제가 발생한 지점

```
Unable to connect to the server: dial tcp: lookup
3DA886DFAF5BB769939FDEAE60FA1466.gr7.ap-northeast-2.eks.amazonaws.com: no such host
```

### 문제 원인

kubeconfig가 **destroy로 삭제된 옛 클러스터의 엔드포인트**를 가리키고 있었습니다. EKS 엔드포인트 해시는 클러스터를 재생성하면 바뀝니다.

| | 엔드포인트 해시 |
|---|---|
| kubeconfig에 있던 값 | `3DA886DFAF5BB769939FDEAE60FA1466` |
| 실제 클러스터 (09:07 생성) | `174CD61B2C3BE4885459797D0D170A65` |

### 해결 방법

```powershell
aws eks update-kubeconfig --name gochuchamchi-eks --region ap-northeast-2 --profile admin
```

### 검증 완료 사항

- `Unauthorized`(토큰·권한)나 TCP 타임아웃(엔드포인트 허용목록)과 **증상이 명확히 다릅니다.** `no such host`는 DNS 해석 실패이므로 kubeconfig 문제로 바로 좁힐 수 있습니다
- destroy/apply를 반복하는 구조이므로 **apply 직후 이 명령을 습관적으로 실행**하는 것이 맞습니다 (runbook §1.1)

## 3. 회원가입 500 — `schema.sql`이 한 번도 실행되지 않음

이번 재구축에서 가장 찾기 어려웠던 문제입니다.

### 문제가 발생한 지점

사이트는 200으로 정상 응답하는데 회원가입만 500이 났습니다. 앱 로그:

```
ERROR 1 --- [nio-8080-exec-4] o.a.c.c.C.[.[.[/].[dispatcherServlet] :
  Servlet.service() ... threw exception [Request processing failed:
  org.springframework.jdbc.BadSqlGrammarException:
### Error querying database.  Cause: java.sql.SQLSyntaxErrorException:
    (conn=67) Table 'gochuchamchi.users' doesn't exist
```

### 왜 정상처럼 보였는가

배스천에서 확인하니 **데이터베이스는 존재하는데 테이블만 0개**였습니다.

```
SHOW DATABASES;              ->  gochuchamchi ✓ 존재
USE gochuchamchi; SHOW TABLES;  ->  (출력 없음)
```

`gochuchamchi` 데이터베이스는 `schema.sql`이 만든 것이 아니라 **RDS 인스턴스의 `DBName` 설정이 만든 빈 껍데기**였습니다 (`aws rds describe-db-instances --query 'DBInstances[0].DBName'` → `gochuchamchi`).

즉 `schema.sql`은 **단 한 줄도 실행되지 않았습니다.** `USE`가 성공하기 때문에 얕게 보면 정상으로 착각하기 쉽습니다.

### 문제 원인 — 경합 + 실패를 삼키는 프로비저너

배스천의 `schema.sql` 파일 타임스탬프가 결정적 단서였습니다.

| 시각 (UTC) | 사건 |
|---|---|
| `00:07` | `schema.sql`이 S3 → 배스천으로 복사됨 (6294 bytes) |
| `00:11:50` | **RDS 인스턴스 생성 완료** |

mysql 접속이 RDS 준비보다 **약 5분 먼저** 실행되어 실패했습니다. 그런데 그 실패가 **두 군데에서 조용히 삼켜졌습니다.**

**① 종료코드가 `rm`의 것으로 덮임** (`rds-schema-init.tf`)

```powershell
'mysql --defaults-extra-file=/home/ec2-user/.my.cnf < /home/ec2-user/schema.sql; rm -f /home/ec2-user/.my.cnf'
```

`;`로 이어져 있어 이 줄의 종료코드는 항상 성공하는 `rm`의 것입니다. → **SSM이 `Success`로 끝납니다.**

**② 프로비저너가 Status를 검사하지 않음**

```powershell
$cmdId = aws ssm send-command ... --query "Command.CommandId" --output text
Start-Sleep -Seconds 30
aws ssm get-command-invocation --command-id $cmdId ...    # 출력만 하고 검사 안 함
```

결과를 **출력만** 하므로 PowerShell은 exit 0으로 끝나고 → **terraform이 `null_resource.apply_db_schema`를 생성 완료로 기록합니다.**

**③ 그래서 재시도도 되지 않음**

트리거가 `filemd5(schema.sql)` + `rds_id`뿐이라, `schema.sql`을 고치지 않는 한 **apply를 몇 번 다시 돌려도 재실행되지 않습니다.** "state에는 있는데 실물은 없는" 상태가 계속 남습니다.

> `depends_on = [module.rds, ...]`가 있었지만 이것은 **리소스 생성 순서만 보장**할 뿐, RDS가 **접속 가능한 상태**가 될 때까지 기다려주지 않습니다. 배스천 SSM 온라인 대기 루프는 있었는데 정작 RDS 준비 대기가 없었던 것이 근본 설계 누락입니다.

### 해결 방법

**즉시 조치** — 배스천에서 스키마 수동 적용 (`CREATE TABLE IF NOT EXISTS` 기반이라 재실행 안전, 당시 테이블 0개라 데이터 손실 위험 없음):

```bash
aws s3 cp s3://gochuchamchi-k8s-manifests-307223751140/db/schema.sql ~/schema.sql --region ap-northeast-2
DB_HOST=$(kubectl -n gochuchamchi get cm gochuchamchi-config -o jsonpath='{.data.DB_HOST}')
DB_PASS=$(kubectl -n gochuchamchi get secret gochuchamchi-db-secret -o jsonpath='{.data.DB_PASS}' | base64 -d)
MYSQL_PWD="$DB_PASS" mysql -h "$DB_HOST" -u admin < ~/schema.sql
```

**재발 방지** — `rds-schema-init.tf` 3곳 수정:

| 위치 | 변경 |
|---|---|
| 배스천 SSM 대기 루프 뒤 | **RDS `available` 대기 루프 추가** (15초 × 40회 = 최대 10분) |
| mysql 실행 줄 | `rc=$?`로 **종료코드 보존** 후 `exit $rc` — rm이 실패를 가리지 못하게 |
| `send-command` 이후 | 고정 `Sleep 30` → **완료까지 폴링 + `Status -ne "Success"`면 stderr 출력 후 `exit 1`** |

### 검증 완료 사항

```
--- SCHEMA APPLIED, VERIFYING ---
Tables_in_gochuchamchi        id  username    role
notices                       1   superadmin  superadmin
product_sizes
products
users
```

- 테이블 4개 생성 확인 (`schema.sql`의 `CREATE TABLE`은 5개로 보이지만 1개는 주석 줄)
- 기본 `superadmin` 계정 시드 확인
- 앱 로그에 신규 에러 없음, 사이트 200 유지
- **파드 재시작 불필요** — 커넥션 풀은 그대로고 테이블만 생기면 즉시 반영됨
- `terraform validate` 통과 (`plan`은 `TF_VAR_argocd_git_pat` 필요로 미실행)
- 수정된 프로비저너는 **지금 재실행되지 않습니다.** 트리거가 그대로라 terraform이 아무것도 하지 않으며, 스키마가 이미 적용됐으므로 그것이 올바른 동작입니다. 다음 destroy/apply부터 효과가 납니다

## 4. 사이트 503 / ArgoCD 접속 불가 — 둘 다 "없어서"였음

### 4.1 사이트 503 — ECR 비어 있음 + kubelet 백오프

destroy가 ECR 이미지까지 지웠고(`force_delete = true`), CI를 아직 안 돌린 상태였습니다.

```
aws ecr list-images --repository-name gochuchamchi
{ "imageIds": [] }
```

연쇄 반응:

```
ECR 이미지 없음 → 파드 ImagePullBackOff → Service endpoints 0개 → ALB 타겟 0개 → 503
```

엔드포인트별 실측:

| URL | 결과 |
|---|---|
| `http://gochuchamchi.shop` | 301 → HTTPS (정상) |
| `https://gochuchamchi.shop` | **503** |
| `https://grafana.gochuchamchi.shop` | 302 → `/login` (정상) |
| `https://argocd.gochuchamchi.shop` | 타임아웃 (internal ALB, 의도된 설계) |

DNS·ACM·리다이렉트·external-dns 레코드는 전부 정상이었고 **앱 이미지만 없었습니다.**

**함정** — CI가 `09:44:24`에 이미지를 푸시한 뒤에도 파드는 계속 `ImagePullBackOff`였습니다. kubelet 백오프 간격이 실패할수록 늘어나 최대 5분까지 벌어지기 때문입니다. **이미지가 없어서가 아니라 다시 시도할 때까지 기다리는 상태**였습니다.

```powershell
kubectl -n gochuchamchi delete pod -l app=gochuchamchi-web
```

파드를 지우니 즉시 새 이미지를 당겨왔습니다. `rollout restart`가 아니라 **파드 삭제**를 쓴 이유는 GitOps 관리 리소스라 Deployment template에 annotation을 추가하면 ArgoCD 드리프트가 생기기 때문입니다.

결과:

| 단계 | 결과 |
|---|---|
| 파드 | `2/2 Running` |
| Service endpoints | `172.30.40.128:8080`, `172.30.41.225:8080` |
| ALB 응답 | 503 → **200** (0.12s) |

### 4.2 ArgoCD `localhost:8080` 접속 불가

ArgoCD 자체는 정상이었습니다 (`argocd-server` 파드 `1/1 Running`, endpoints 정상).

```
8080에 리스닝 중인 프로세스 없음
실행 중인 kubectl 프로세스 없음
```

재구축 과정에서 **port-forward 프로세스가 죽었고 다시 띄우지 않은 상태**였습니다. ArgoCD ALB는 internal이라 터널 없이는 접근 경로가 아예 없습니다.

```powershell
kubectl port-forward -n argocd svc/argocd-server 8080:80
```

→ `http://localhost:8080` 200 확인.

### 4.3 `ak121231` 계정 admin 권한 부여

회원가입 정상화 확인 후 요청에 따라 권한을 변경했습니다.

```sql
UPDATE users SET role='admin' WHERE username='ak121231';
```

```
--- BEFORE ---          --- AFTER ---
id  username   role     id  username    role
2   ak121231   user     1   superadmin  superadmin
                        2   ak121231    admin
```

- **재로그인 필요** — Spring Security는 로그인 시점에 `CustomUserDetailsService`가 권한을 만들어 세션에 담으므로, 기존 세션에는 여전히 `ROLE_USER`가 들어 있습니다
- 이 변경은 **DB에만 있어 다음 destroy/apply 때 사라집니다** (runbook §5 체크리스트 항목)
