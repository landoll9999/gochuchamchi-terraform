# 2026-08-06 작업 기록

## 1. 재구축 직후 사이트 503 — 원인이 5중이었던 건

### 작업 목적

전날(8/5) 커밋한 재구축 apply가 **에러 없이 한 번에 성공**했는데도 브라우저로 `gochuchamchi.shop`에 접속하면 백엔드 에러가 뜨는 상태였다. 원인을 찾아 사이트를 복구한다.

이 프로젝트의 대표적 실패 유형인 **"apply는 성공했는데 서비스는 죽어 있음"**의 다섯 번째 반복이다(8/3 ECR 빈 상태, 8/4 PAT 미주입·NetworkPolicy DNS, 8/5 PAT 값 증발에 이어).

### 문제가 발생한 지점

`https://gochuchamchi.shop` → **HTTP 503**.

진단의 출발점부터 막혔다. `kubectl get nodes`가 이렇게 실패했다:

```
dial tcp: lookup 6FDE62BEAE056B8C4AF7FC528CE4B92B.gr7.ap-northeast-2.eks.amazonaws.com: no such host
```

### 문제 원인

**원인이 하나가 아니라 다섯이었고, 앞의 것을 고쳐야 다음 것이 드러나는 직렬 구조였다.** 각각을 §1.1~§1.5로 나눠 적는다.

가장 큰 함정은 **각 단계의 최종 증상이 전부 똑같은 503**이라는 점이다. 증상만 보고는 몇 개가 겹쳐 있는지 알 수 없어서, 하나를 고칠 때마다 "이제 됐겠지" 하고 확인하면 여전히 503이었다.

### 해결 방법 / 검증 완료 사항

§1.1~§1.5 각 항목에 적는다. 최종 상태:

| 항목 | 결과 |
|---|---|
| `gochuchamchi.shop` / `www` | **HTTP 200** |
| 앱 파드 | 2/2 Running, **재시작 0회** |
| 노드 | t3.medium 2대 (t3.small 정리 완료) |
| ArgoCD | Synced, Image Updater 자동 태그 갱신 동작 |
| 스모크 테스트 | 실패 0 / 경고 0 / 전체 14 |

### 1.1 kubeconfig가 삭제된 옛 클러스터를 가리킴

**증상이 인증 실패가 아니라 DNS 실패(`no such host`)라 원인을 오해하기 쉽다.** 8/3(§3)에도 같은 건이 있었고 그때 runbook에 적어 뒀는데, 이번에도 진단 첫 단계에서 그대로 걸렸다.

```powershell
aws eks update-kubeconfig --name gochuchamchi-eks --region ap-northeast-2 --profile admin
```

**문서에 적어 두는 것으로는 재발이 막히지 않는다**는 게 8/5 §5(사전 점검 자동화)에서 이미 나온 결론이었다. 이번에는 apply가 직접 갱신하도록 코드로 옮겼다(§3 `null_resource.sync_kubeconfig`).

한 가지 더 — **AWS 자격증명 자체가 기본 프로필에 없었다.** `aws eks list-clusters`가 `Unable to locate credentials`로 실패했는데, 이 저장소는 `admin` 프로필을 쓴다. 매 명령에 `$env:AWS_PROFILE="admin"`이 필요하다(PowerShell은 호출 간 셸 상태가 유지되지 않는다).

### 1.2 GitHub Actions 변수가 "삭제 대기 중인" 옛 KMS 키를 가리킴

kubectl이 붙자마자 드러난 사실: **`gochuchamchi` 네임스페이스에 Deployment도 Service도 없었다.** Ingress만 있었다. 그래서 ALB에 타겟그룹이 아예 생성되지 않았고(웹 ALB에 붙은 타겟그룹 0개), ALB는 503을 반환할 수밖에 없었다.

ECR을 보니 **이미지가 0개**였다. `force_delete = true` 때문에 destroy가 이미지까지 지운 것으로, 8/3·8/5에 이어 세 번째다. 복구 방법은 문서대로 CI 재실행인데 — **직전 CI 실행(8/5)이 이미 실패 상태**였다.

```
Could not assume role with OIDC: The web identity token provided could not be validated.
```

OIDC provider와 trust policy를 확인했으나 **둘 다 정상**이었다(`aud`, `sub` 조건 일치). 그럼 왜 실패했나 — 진짜 원인은 그 다음 잡에 있었다:

```
IMAGE_SIGNING_KMS_KEY_ARN = arn:...key/7324ccfa-...   ← GitHub 변수
$ aws kms describe-key --key-id 7324ccfa-...
  "State": "PendingDeletion"                          ← 재구축으로 삭제 대기 중
$ aws kms describe-key --key-id alias/gochuchamchi-image-signing
  "State": "Enabled"     key/fae648d5-...             ← 실제 새 키
```

**재구축이 KMS 키를 새로 만들면 옛 키는 30일 삭제 대기로 들어가는데, GitHub 변수는 수동 관리라 옛 키를 그대로 가리킨다.** 그 상태로 CI를 돌리면 서명 잡이 PendingDeletion 키로 서명을 시도해 실패하고 → ECR에 이미지가 안 올라가고 → 앱이 배포되지 않아 503이 유지된다.

**원인이 세 단계 떨어져 있다**(503 ← 앱 미배포 ← 이미지 없음 ← CI 실패 ← 변수 불일치). 사이트를 보고 KMS 키를 의심하기까지의 거리가 이 건의 난이도였다.

```powershell
gh variable set IMAGE_SIGNING_KMS_KEY_ARN --repo landoll9999/gochuchamchi-spring `
  --body "arn:aws:kms:ap-northeast-2:307223751140:key/fae648d5-a6ef-4570-b8a3-da575271c6d6"
gh workflow run "Build and sign release image" --repo landoll9999/gochuchamchi-spring
```

빌드·서명 모두 성공해 `signed-b53166d9…` 태그가 ECR에 올라갔다.

> 참고 — 8/5 실패 로그의 표면 메시지는 OIDC assume 실패였다. 그 실행 시점의 계정 상태는 지금과 다르므로 그때의 직접 원인은 확정할 수 없지만, **오늘 시점에 CI를 막고 있던 것은 KMS 변수 불일치**였고 그것을 고치자 통과했다.

### 1.3 t3.small 메모리 고갈 → ArgoCD가 크래시루프

이미지가 생겼는데도 앱이 안 떴다. ArgoCD Application이 `Unknown`이었다:

```
Failed to load target state: ... dial tcp 10.100.161.164:8081: connect: connection refused
```

repo-server가 죽어 있었다. 파드를 보니 ArgoCD 대부분과 external-dns, metrics-server, cluster-autoscaler가 **동시에 재시작을 반복**하고 있었다.

```
$ kubectl top nodes
ip-172-30-41-39    940m  48%   1353Mi  94%     ← t3.small (2GB)
ip-172-30-61-163    98m   5%   1137Mi  79%
```

노드 하나가 **메모리 94%**, limits는 **182% 오버커밋**. 커널 메모리 압박으로 프로세스가 멈추자 liveness probe가 줄줄이 타임아웃했고, kubelet이 파드를 죽이는 연쇄가 일어났다. `Node is not ready` 이벤트까지 떴다.

t3.small 2대(각 allocatable 약 1.4GB)에 CloudWatch Observability, fluent-bit, Kyverno, ESO, ArgoCD 7종, Grafana, EFS CSI 등이 전부 올라가 있었다. **앱은 2 replica × 512Mi를 요구하는데 들어갈 자리가 없었다** — 설령 ArgoCD가 정상이었어도 파드는 Pending이었을 것이다.

`variables.tf`의 `node_instance_types`를 `t3.medium`으로 올려 apply했다(노드그룹 replace → 롤링 교체).

**apply 대기를 줄이려 옛 노드를 직접 비웠다.** terraform은 `create_before_destroy`라 새 노드그룹을 만든 뒤 다른 리소스를 처리하고 마지막에 옛 것을 지우는데, 그 사이 ArgoCD는 계속 과부하 노드 위에 있었다:

```powershell
kubectl cordon <t3.small 2대>
kubectl drain <41-39> --ignore-daemonsets --delete-emptydir-data --force --disable-eviction
```

파드가 t3.medium으로 옮겨가자 ArgoCD가 곧바로 안정됐다. 교체 후 노드 사용률은 23% / 23%.

### 1.4 PAT 미주입 — ArgoCD가 private 저장소 인증 실패

ArgoCD가 살아나자 **또 다른 에러**로 바뀌었다:

```
Failed to load target state: ... failed to list refs: authentication required: Repository not found.
```

`Repository not found`라 저장소 경로 문제로 보이지만, 실제로는 **private 저장소에 인증 없이 접근했을 때 GitHub가 주는 응답**이다.

```
$ kubectl get externalsecret -n argocd
gochuchamchi-gitops-repo-creds   SecretSyncedError   False
  err: Secret does not exist

$ aws secretsmanager describe-secret --secret-id gochuchamchi/argocd/git-pat
  "Versions": null        ← 컨테이너만 있고 값이 한 번도 들어간 적 없음
```

8/5 §4에서 만든 자동 주입(`$env:ARGOCD_GIT_PAT`)은 **환경변수가 있을 때만** 동작한다. 재구축 apply를 돌린 셸에 그 값이 없었으므로 조용히 건너뛰었고, 시크릿은 빈 컨테이너로 남았다.

`gh auth token`(repo 스코프 보유)을 주입하고 ESO를 강제 동기화했다:

```powershell
$tok = (gh auth token).Trim()
aws secretsmanager put-secret-value --secret-id gochuchamchi/argocd/git-pat --secret-string $tok --region ap-northeast-2
kubectl -n argocd annotate externalsecret gochuchamchi-gitops-repo-creds force-sync=$(date +%s) --overwrite
```

`SecretSynced True`로 바뀌자 ArgoCD가 저장소를 읽고 Deployment/Service/HPA를 만들었다.

> ⚠️ 현재 PAT는 **`gh` CLI 토큰**이다. 만료되면 같은 증상이 재발하므로 전용 fine-grained PAT로 교체하는 편이 좋다. 교체는 위 `put-secret-value` 한 번이면 되고, §2 이후로는 재구축해도 값이 유지된다.

#### 오진 경로 — Image Updater의 "not supported source type"

이 단계에서 Image Updater 로그에 계속 이런 경고가 찍혔다:

```
skipping app 'argocd/gochuchamchi' of type '' because it's not of supported source type
```

Image Updater 설정 문제로 보였지만 아니었다. **`type ''`(빈 값)이 신호다** — repo-server가 죽어 manifest를 생성하지 못하니 Application의 `status.sourceType`이 확정되지 않았고, Image Updater는 타입을 모르는 앱을 건너뛴 것이다. §1.3·§1.4가 풀리자 `sourceType=Kustomize`가 되면서 경고도 사라졌다.

#### 이미지 태그 불일치 — 사람이 고치기 전에 Image Updater가 고쳤다

앱이 배포됐지만 `ImagePullBackOff`였다. 원격 gitops의 `.argocd-source-gochuchamchi.yaml`이 8/5에 write-back된 `signed-41611c4f…`를 가리키는데, 그 이미지는 ECR과 함께 삭제된 뒤였다.

로컬에서 새 태그로 고쳐 push하려 했으나 **거부됐다** — 원격이 앞서 있었다. 확인해 보니 정상화된 Image Updater가 스스로 갱신한 커밋이었다:

```
a8f76da build: automatic update of gochuchamchi
  updates image gochuchamchi tag 'signed-41611c4f...' to 'signed-b53166d9...'
```

**자동화가 이미 한 일을 손으로 덮어쓰지 않도록** 로컬 커밋을 버리고 `git reset --hard origin/main`으로 되돌렸다. GitOps 저장소에서 수동 개입 전에 원격 상태를 먼저 확인해야 하는 이유다.

### 1.5 liveness가 "기동 중"인 파드를 죽이고 있었음

파드가 뜨긴 했는데 **두 개 모두 재시작 1회**를 기록했다. 종료 사유는 `Error exit=143`(SIGTERM).

```
Started GochuchamchiApplication in 48.014 seconds (process running for 79.582)
```

**앱의 실제 기동 시간은 약 80초**다(Spring 컨텍스트 48초 + OTel 자동계측 에이전트 부착). 그런데 `livenessProbe`가 `initialDelaySeconds: 40`부터 검사를 시작하니, 아직 부팅 중인 컨테이너를 죽였다.

`deployment.yml`에 `startupProbe`를 추가해 **"기동 중"과 "죽음"을 분리**했다:

```yaml
startupProbe:
  httpGet: { path: /, port: 8080 }
  periodSeconds: 10
  failureThreshold: 24      # 240초 예산 = 실측 80초의 3배
```

startupProbe가 통과할 때까지 readiness/liveness는 아예 돌지 않으므로 두 probe의 `initialDelaySeconds`는 제거했다. 적용 후 파드 2개 모두 **재시작 0회**.

이건 노드가 느리거나 이미지 pull이 길어지면 기동↔강제종료를 무한 반복하는 크래시루프가 될 수 있었다. t3.small에서 이미 그 문턱에 있었다.

## 2. 재발 방지 (1/2) — 영속 state 분리 (`go/persistent`)

### 작업 목적

§1의 원인 중 **1.2(KMS 키)와 1.4(PAT)**, 그리고 이미지 소실은 전부 같은 구조에서 나온다: **재구축과 생애주기가 달라야 하는 것이 메인 state에 묶여 함께 삭제된다.**

`docs/ecr-state-separation.txt`에 2026-07-31자 계획서가 있었으나 **미실행 상태**였고, 그 사이 8/3·8/5·8/6에 같은 사고가 반복됐다. 이번에 실행한다.

### 문제 원인

| 사라지는 것 | 결과 |
|---|---|
| ECR 이미지 (`force_delete = true`) | ImagePullBackOff → 503 |
| 서명 KMS 키 | ARN 변경 → GitHub 변수 불일치 → CI 서명 실패 → 이미지 갱신 불가 |
| GitHub OIDC provider·IAM 역할 | CI가 AWS를 assume 못 함 |
| ArgoCD PAT 시크릿 (`recovery_window_in_days = 0`) | ArgoCD 인증 실패 → 앱 미배포 → 503 |

**넷 중 하나만 살려서는 소용이 없다.** 이미지를 보존해도 CI를 못 돌리면 갱신할 수 없고, CI가 돌아도 PAT가 없으면 배포되지 않는다. 그래서 계획서의 5개가 아니라 **10개를 한 묶음**으로 옮겼다.

### 해결 방법

`go/persistent/` 신설 (state key `persistent/terraform.tfstate`). 전 리소스에 `prevent_destroy`.

```
aws_ecr_repository / aws_ecr_lifecycle_policy
aws_iam_openid_connect_provider.github_actions
aws_iam_role(_policy).github_actions_ecr_push
aws_kms_key / aws_kms_alias .image_signing
aws_iam_role(_policy).github_actions_image_signer
aws_secretsmanager_secret.argocd_git_pat
```

**계획서의 `state mv` 대신 "persistent에서 `import` → 메인에서 `state rm`" 순서를 썼다.** 두 state에 잠시 동시 존재할 뿐 apply를 하지 않으므로, 순서를 잘못 밟아 ECR이 파괴될 위험이 구조적으로 없다. 계획서 6장이 경고하던 바로 그 위험을 절차 자체로 제거한 셈이다.

메인에는 `persistent-data.tf`를 두고 **data source로 조회**한다(remote state 참조가 아니라 — 전부 이름이 고정된 리소스라 결합도가 낮고 apply 순서에도 덜 민감하다). KMS는 별칭으로 조회해서 키를 교체해도 참조가 깨지지 않게 했다.

### 검증 완료 사항

- persistent import 후 plan: `0 to add, 2 to change, 0 to destroy` — 변경 2건은 `force_delete`·`deletion_window_in_days`처럼 **AWS API로 읽을 수 없는 Terraform 전용 속성**이라 state에만 기록됨(실제 리소스 무변경)
- 메인 `state rm` 후 plan: **`0 to change`, 실제 인프라 destroy 0건**. 삭제로 잡힌 3건은 `timestamp()` trigger로 매번 재생성되는 `null_resource`뿐
- apply 결과: 스모크 테스트 **실패 0 / 경고 0 / 전체 14**, `앱 준비 완료`
- **`terraform plan -destroy` 검증**: destroy 대상 327건 중 영속 리소스 **0건**(매칭된 것은 전부 `data.` 읽기 로그)

### 2.1 push 직전에 드러난 원격 PR과의 통합

커밋 후 push가 non-fast-forward로 거부됐다. 원격에 **PR #5 `feat/ecr-tag-immutability`**가 머지돼 있었고, 하필 내가 `persistent`로 옮긴 바로 그 `aws_ecr_repository`를 수정한 PR이었다:

- `image_tag_mutability`를 `IMMUTABLE_WITH_EXCLUSION`으로 + Cosign 아티팩트 3종(`sha256-*.sig|att|sbom`) 예외 필터
- lifecycle을 3단계로(signed 20개 보존 / candidate 7일 / untagged 7일)

게다가 같은 PR이 이 계획서에 **경고**를 달아 뒀었다:

> 주의 (2026-08-05) … state 분리는 팀 합의 후 현재 ecr.tf의 서명·Lifecycle 구성을 **함께 옮기는 방식으로 재설계할 것**

내 작업이 그 요구(서명 KMS·역할을 함께 이관)를 이미 충족했지만, **불변 태그와 lifecycle 구성은 반영하지 못한 상태**였다 — base로 삼은 로컬 `ecr.tf`가 PR 이전 버전이었기 때문이다. 경고가 우려한 "구성이 되돌아감"이 그대로 일어날 뻔했다.

**여기서 중요한 사실 하나** — `terraform` 코드는 머지됐지만 **apply되지 않은 상태**였다:

```
$ aws ecr describe-repositories ...
  "imageTagMutability": "MUTABLE"      ← 실물은 그대로
$ lifecycle 규칙 수: 1
```

그래서 내 `import`가 실물(MUTABLE + 1규칙)을 기준으로 잡혔고 plan이 no-change로 통과했던 것이다. **"코드에 있다"와 "인프라에 있다"가 다를 수 있다**는 걸 import 기준값이 그대로 드러냈다.

처리:

1. `git rebase origin/main` — 충돌 2건
2. `terraform/ecr.tf`는 **내 버전 채택**(`git checkout --theirs` — rebase에서는 `theirs`가 적용 중인 내 커밋이다). ECR 리소스는 이미 `persistent`로 갔으므로 여기 남으면 안 된다
3. **PR #5의 불변 태그·lifecycle 구성을 `persistent/ecr.tf`로 이관** — 이게 핵심이다. 코드만 합치고 이 단계를 건너뛰면 경고가 예언한 대로 공급망 보안 구성이 조용히 사라진다
4. 계획서 충돌은 양쪽을 살려 통합(경고 + 해소 내역)
5. `persistent` apply — `image_tag_mutability`는 **in-place**, lifecycle 정책만 교체(둘 다 `prevent_destroy`에 걸리지 않음)

검증에서 한 번 더 걸린 것 — `aws ecr describe-repositories` 응답에 **예외 필터가 안 보였다.** 설정이 안 된 줄 알았으나 `aws-cli/2.13.0`이 `imageTagMutabilityExclusionFilters` 필드를 모르는 것이었다. **판별은 terraform으로** 했다: refresh 후 `plan`이 `No changes`(exit 0)면 provider가 실물을 읽어 config와 일치함을 확인한 것이다. **CLI 출력에 없다고 설정이 없는 게 아니다** — 필드가 없으면 그건 CLI 버전 문제일 수 있다.

### 함정 — state lock이 고아로 남음

import를 PowerShell 루프로 돌리면서 출력을 `| Select-Object -First 1`로 잘랐더니, **첫 import 이후 전부 `Error acquiring the state lock`**이 났다. 파이프를 조기에 끊으면 terraform이 락을 해제하기 전에 끝나 버린다.

```powershell
terraform force-unlock -force <ID>
# 이후: 파이프로 자르지 말고 $out = (terraform import ... 2>&1) -join "`n" 으로 받아서 판정
```

`aws_secretsmanager_secret`은 **이름이 아니라 ARN으로만 import**된다(`could not parse import ID ... as ARN`).

## 3. 재발 방지 (2/2) — apply 파이프라인에 진단·동기화 편입 (`ci-sync.tf`)

### 작업 목적

§2가 "사라지지 않게" 만든다면, 이쪽은 **그래도 어긋났을 때 apply가 즉시 알려주게** 만든다. §1에서 사람이 손으로 메운 단계들이 대상이다.

### 해결 방법

`terraform/ci-sync.tf` 신설 — 셋 다 **경고 모드**(apply를 실패시키지 않음). 재구축 도중에는 "아직 안 된 상태"가 정상이므로, `smoke-test.tf`가 세운 원칙을 따랐다.

| 리소스 | 하는 일 | §1 대응 |
|---|---|---|
| `sync_kubeconfig` | apply한 클러스터로 kubeconfig 갱신 | 1.1 |
| `sync_github_ci_variables` | GitHub 변수 4개를 실제 ARN으로 덮어씀 | 1.2 |
| `verify_ecr_has_image` | `signed-` 태그 개수를 세고, 없으면 복구 명령 출력 | 1.2 |

GitHub 변수 동기화에 **provider가 아니라 `gh` CLI를 쓴 이유** — `integrations/github` provider는 PAT를 terraform 변수로 받아야 한다. 이 저장소는 이미 ArgoCD PAT를 Secrets Manager로 옮겨 "terraform 변수에 토큰을 두지 않는" 방향을 잡았고(8/4 백로그 B3), 같은 목적에 두 번째 토큰 경로를 만들고 싶지 않았다. `gh`는 운영자가 이미 로그인해 둔 자격증명을 쓰므로 새 비밀이 늘지 않는다. `gh`가 없거나 로그인이 안 됐으면 수동 명령을 그대로 출력한다.

`verify_ecr_has_image`가 **candidate가 아니라 `signed-`를 세는 이유** — Image Updater가 감시하는 대상이 정확히 `^signed-[0-9a-f]{40}$`(argocd.tf의 `web.allow-tags`)라서, candidate만 있으면 배포는 일어나지 않는다.

`smoke-test.tf`의 `wait_for_app_ready`도 손봤다. Deployment가 안 나타날 때 기존 메시지는 **PAT만 지목**했는데, 이번에는 ECR 빈 상태와 노드 리소스 부족이 겹쳐 있어서 그 안내가 오히려 진단을 늦췄다. 원인 3가지를 **확인 순서와 함께** 출력하도록 바꿨다.

### 검증 완료 사항

- apply 로그에서 `GitHub Actions 변수 4개를 현재 인프라 값으로 동기화했습니다` 확인, 실제 GitHub 변수 4개의 갱신 시각이 apply 시각과 일치
- `ECR에 배포 가능한 서명 이미지 1개가 있습니다` 출력 확인
- `앱 준비 완료 — deployment.apps/gochuchamchi-web`
