# 2026-08-13 작업 기록

## 1. GuardDuty AI 트리아지 적용 — 시작부터 오진했던 것

### 작업 목적

`GUARDDUTY-TRIAGE-WORKLOAD-APPLY-GUIDE.md`에 따라 Workload 계정(828885965304)에
트리아지를 적용한다. 통보 경로를 `EventBridge → SNS 직결`에서
`EventBridge → 트리아지 Lambda → SNS`로 바꾸는 작업이다.

### 문제가 발생한 지점

가이드와 저장소가 전면적으로 어긋나 보였다. 가이드는 브랜치 `feat/guardduty-triage`,
`triage/check-groq.py`, Groq API 키를 말하는데 로컬에는 그런 브랜치가 없고
`feat/guardduty-ai-triage`(Bedrock 구현)만 있었다. main에는
`62f142a chore: AI 트리아지 판정 렌더러 제거 (미채택 확정)`까지 있었다.

가이드가 잘못됐거나 다른 저장소의 것이라고 판단하고 작업을 중단했다.

### 문제 원인

**`git fetch`를 하지 않은 상태의 원격 참조를 근거로 판단했다.** fetch하자
`origin/feat/guardduty-triage`가 나타났고 `feat/guardduty-ai-triage`는 원격에서
삭제돼 prune됐다. 즉 Bedrock 구현은 폐기됐고 Groq 구현으로 새로 만들어진 뒤였다.

진단이 어려웠던 이유는 **오래된 참조가 그럴듯한 반대 결론을 만들어냈다**는 것이다.
"미채택 확정" 커밋과 존재하지 않는 브랜치가 맞물려 "이 기능은 폐기됐다"는 일관된
그림이 나왔고, 그 그림이 틀렸다는 신호가 없었다.

### 해결 방법

브랜치 얘기가 나오면 판단 전에 `git fetch --prune`을 먼저 한다. 이번처럼 원격에서
브랜치가 삭제·재생성된 경우 로컬 참조만으로는 정반대 결론이 나온다.

### 검증 완료 사항

- `terraform plan` = `11 to add, 1 to change, 1 to destroy` — 가이드 예고와 일치
- 가이드에 빠져 있던 것 발견: 이 루트는 `alert_emails` 기본값이 `[]`라
  `TF_VAR_alert_emails` 없이 plan하면 **이메일 구독 삭제가 딸려 나온다**. 주입 후 진행
- `apply` = `11 added, 1 changed, 1 destroyed`
- 격리 Lambda(`guardduty-isolation`)·`aws_sns_topic.alerts`·격리용 EventBridge 룰
  **무변경** 확인 — 가이드가 "보이면 중단"이라 한 항목 없음

## 2. verify-deployment.ps1이 Windows PowerShell 5.1에서 실행 자체가 불가능했던 것

### 작업 목적

배포 검증 스크립트로 정책 표 6개 조합과 중복 억제를 확인한다.

### 문제가 발생한 지점

인코딩 문제 **3중**으로 세 번 연속 실패했다.

1. 스크립트가 파싱조차 안 됨 — `Unexpected token`, 한글이 `?먭꺽利앸챸`로 깨짐
2. payload 파일을 AWS CLI가 못 읽음 — `text contents could not be decoded`
3. 중복 억제가 정상 동작하는데 `[주의] 중복 억제가 안 걸렸습니다`로 오판

### 문제 원인

세 개가 모두 다른 원인이었다.

- **(1)** 이 파일만 BOM이 없었다. 저장소의 다른 `.ps1` 두 개(`daily-up`,
  `bootstrap-state`)는 BOM이 있고 `.gitattributes`에도 `*.ps1 text eol=crlf`가
  잡혀 있는데 이 파일만 빠져 있었다. BOM이 없으면 PS 5.1이 CP949로 읽어 한글이
  깨지고 파서가 죽는다.
- **(2)** `Out-File -Encoding utf8`이 PS 5.1에서는 BOM을 붙인다(pwsh 7은 안 붙임).
  BOM을 없애도 여전히 실패했는데, 진짜 원인은 **AWS CLI가 Windows에서 `file://`
  파라미터를 로캘 인코딩(CP949)으로 읽기** 때문이었다. 한글이 UTF-8 바이트로
  들어가면 디코드하지 못한다.
- **(3)** `Get-Content -Raw`가 Lambda 응답(UTF-8)을 CP949로 읽어 한글 `reason`이
  깨졌고, 그 탓에 `-match "중복"` 매칭이 실패했다. **동작은 정상인데 검증이
  거짓 실패를 냈다** — 가장 위험한 형태다.

### 해결 방법

- payload를 비 ASCII → `\uXXXX` 이스케이프한 **순수 ASCII**로 쓴다. JSON 규격상
  동등하면서 어떤 로캘에서도 안전하다.
- Lambda 응답을 `Get-Content -Raw -Encoding UTF8`로 읽는다.
- 파일에 BOM을 붙인다(§6에서 처리).

### 검증 완료 사항

- 배선 2건 OK, 정책 표 6개 조합 전부 기대와 일치
- **루트 사용(severity 2) → `tier=HIGH` 승격** — 가장 중요한 확인
- LOW 소음은 모델 호출 없이 `filtered`, CRITICAL은 판정 무관 `urgent`
- 중복 억제 OK (인코딩 수정 후)
- 실제 샘플 finding(`CryptoCurrency:EC2/BitcoinTool.B!DNS`, sev 8)이 EventBridge를
  거쳐 도달 → `TRUE_POSITIVE`(0.85)/`urgent`. 격리 Lambda는 `skipped`
  (인스턴스 없음 — 매일 destroy 환경에서 정상), 부작용 0

## 3. Groq 무료 티어 TPM 한계 — 가이드에 없던 운영 사실

### 문제가 발생한 지점

검증 중 429가 12회 발생했다.

### 문제 원인

무료 티어가 **8000 TPM**인데 finding 1건이 입력 2,100~2,400 토큰을 쓴다.
**분당 3건을 넘으면 걸린다.** 검증이 6건을 연속으로 쏘면서 바로 벽에 부딪혔다.

### 해결 방법

구조적으로는 문제가 없다. 429가 나면 `verdict=null → UNCERTAIN`으로 떨어지고
정책 표대로 통보되므로 **탐지 공백은 없고 소음만 는다.**

다만 판정이 자꾸 `UNCERTAIN`으로 보이면 모델 성능이 아니라 레이트리밋을 먼저
의심해야 한다. 로그의 `unavailable_reason`에 사유가 남는다.

## 5. 판정 provider 추상화 — Claude를 OpenAI 호환 레이어로 부르면 안 되는 이유

### 작업 목적

Groq 무료 티어 TPM 벽과 키 관리 부담 때문에 대안을 시험할 수 있어야 했다.
재배포 없이 provider를 바꿔 비교할 수 있게 만든다.

### 진행 내용과 판단 근거

`judge.py`의 provider 차이를 `_build_payload` / `_extract_content` /
`_extract_usage` 세 함수에만 가뒀다. `judge()`는 provider를 모른다.

| | groq / openai / gemini | anthropic |
|---|---|---|
| 규격 | OpenAI Chat Completions | Messages API |
| system | `messages` 안의 role | **최상위 필드** |
| max_tokens | 선택 | **필수** |
| 구조화 출력 | `response_format: json_object` | `output_config.format`의 json_schema |
| 응답 | `choices[0].message.content` | **`content` 블록 배열** |
| temperature | `0` 전송 | **안 보냄** |

anthropic 경로에서 `temperature`를 보내지 않는 이유: Claude 최신 계열(Opus 5/4.8/4.7,
Sonnet 5, Fable 5)은 이 파라미터를 **제거**해서 보내면 400이다. `reasoning_effort`도
Anthropic에 없는 개념이라 뺐다.

응답 파싱에서 주의할 점 두 가지 — thinking 블록이 앞에 붙을 수 있어 **첫 원소를
집으면 안 되고**, `stop_reason`이 `refusal`/`max_tokens`면 HTTP 200인데도 판정을
꺼낼 수 없어 따로 처리해야 한다(`_ResponseError`).

### 문제가 발생한 지점 — 검토했다가 탈락시킨 경로

**Claude를 OpenAI 호환 레이어(`base_url=api.anthropic.com/v1/`)로 부르는 방법**을
검토했다. 코드 무수정으로 붙어서 매력적이었다.

공식 문서 확인 결과 **`response_format`을 무시한다.** 우리 판정은 구조화 출력이
계약의 근간이라(judge.py docstring ④), 무시되는 순간 모델이 산문으로 답하고
`_validate`가 전부 떨어뜨려 **모든 finding이 조용히 "판정 없음"이 된다.** 에러가
아니라 침묵이라 몇 주가 갈 수 있다.

Anthropic 문서 자체가 이 레이어를 "모델 성능을 테스트·비교하기 위한 것이며 대부분의
경우 장기·운영용 해법으로 보지 않는다"고 명시한다. **Claude를 쓰려면 반드시
네이티브 Messages API(`provider="anthropic"`)로 간다.**

### 검증 완료 사항

- 분기 24개 항목 로컬 통과 — 엔드포인트·모델 해석, 오타 provider 폴백, 페이로드 모양,
  thinking 블록 건너뛰기, refusal/잘림 처리, usage 정규화, 옛 `GROQ_*` 이름 폴백
- `terraform fmt` / `validate` 통과, 잘못된 provider는 validation이 차단
- plan은 Lambda 1개 in-place 갱신뿐

## 6. Gemini 실측 — 후보로 추가하고 재본 결과

### 작업 목적

무료 티어가 있고 결제 등록도 필요 없어 Groq의 8000 TPM 벽을 대체할 후보가 된다.
OpenAI 호환 엔드포인트가 있어 `judge.py`가 무수정으로 붙는다.

### 문제가 발생한 지점

구글 문서가 **`response_format` 지원 여부를 명시하지 않는다.** 호환 레이어가 베타이고
"새로 쓰는 거면 Gemini API를 직접 부르라"고 권한다. Anthropic 호환 레이어를
탈락시킨 바로 그 지점이라 추측하지 않고 실측했다.

### 검증 완료 사항 (`gemini-3.6-flash`, 같은 표본 3회씩)

| `reasoning_effort` | 1회 | 2회 | 3회 | 최대 | 편차 |
|---|---|---|---|---|---|
| `none` | 400 | 400 | 400 | — | 미지원 |
| `minimal` | 18.95 | 9.31 | 15.27 | **18.95초** | **9.6초** |
| **`low`** | 9.12 | 9.81 | 9.94 | **9.94초** | **0.8초** |

- **`response_format`이 작동한다** — 유효한 구조화 판정이 나와 `_validate` 통과
- **`low`가 `minimal`보다 빠르고 안정적이다(반직관적).** 편차가 0.8초 대 9.6초.
  판정 품질도 `low`가 최고(위험도 90, 근거에 해외 IP 명시). **기본값이 이미 최적**
- **인젝션 감지에서 Groq보다 낫다** — 같은 표본에서 Groq(gpt-oss-120b)은
  "감지 아니오", Gemini는 "감지 예". 판정 자체는 둘 다 TRUE_POSITIVE로 맞췄다
- 속도는 Groq 압승(1.17초 대 9.94초). 다만 finding 1건당 Lambda 1회 호출이고 서로
  병렬이라 **판정 시간은 누적되지 않는다** — 20초 판정 타임아웃에만 걸리는 문제다

### 결론

**Groq 유지.** Gemini는 코드에 선택지로만 남긴다. 전환하려면 무료 티어 실제 TPM을
`aistudio.google.com/rate-limit`에서 먼저 확인해야 한다 — Groq의 8000 TPM 벽이 전환
동기였으므로 그보다 빡빡하면 의미가 없다. 전환 시 판정 타임아웃 20→30초 권장.

## 7. `reasoning_effort` 폴백이 Gemini에서 발동하지 않던 버그

### 문제가 발생한 지점

`reasoning_effort=none`으로 3회 전부 400이 났는데 **재시도 폴백이 걸리지 않았다.**

### 문제 원인

400을 받았을 때 **오류 본문에 `reasoning_effort`라는 문자열이 있어야만** 파라미터를
빼고 재시도하도록 돼 있었다. Groq은 어느 파라미터가 문제인지 본문에 적어 주지만
Gemini는 `"Request contains an invalid argument."`라고만 하고 알려주지 않는다.
그래서 **Gemini에서는 이 폴백이 영원히 걸리지 않았다.**

Groq만 쓰던 동안에는 드러나지 않던 종류의 결함이다.

### 해결 방법

본문 검사를 빼고, `reasoning_effort`를 보냈다면 일단 제거하고 한 번 재시도한다.
400의 원인으로 가장 흔한 후보이고 재시도 비용은 호출 한 번이다. 다른 이유의 400이면
재시도도 실패하고 그 사유가 그대로 남는다.

## 8. daily 스크립트가 stderr 한 줄에 죽던 것 — 저녁 종료 실패의 원인

### 작업 목적

`daily-up.ps1` / `daily-down.ps1`이 제대로 되어 있는지 점검한다.

### 진행 내용과 판단 근거

멀쩡한 것부터 확인했다. `Select-Object -First` 함정(2026-08-12 수정)도, destroy
게이트의 속성값 오탐(2026-08-12 수정)도 이미 정확히 고쳐져 있었고 근거까지 주석에
남아 있었다. `domain_name`은 `variables.tf` 기본값이 이미 `kycj.click`이라 주입이
더는 필요 없다(과거 기록이 낡았다).

### 문제가 발생한 지점

`daily-down.ps1` 18~20행이 **이 스크립트가 30~32행에 자기 손으로 적어둔 교훈을
어기고 있었다.**

```powershell
$sg = aws ec2 describe-security-groups ... --output text 2>$null
```

### 문제 원인

PS 5.1은 native 명령의 stderr를 **리다이렉트할 때** 각 줄을 ErrorRecord로 감싼다.
두 스크립트 모두 `$ErrorActionPreference="Stop"`이라 aws/git이 경고 한 줄만 뱉어도
그 자리에서 죽는다. **`2>$null`로 버려도 마찬가지다** — 죽는 원인은 "stderr를
리다이렉트했다"는 사실 자체다.

실측으로 확정했다.

| | 결과 |
|---|---|
| `2>$null` 붙임 | **RemoteException으로 사망** |
| 리다이렉트 없음 | **생존**, stdout·종료코드 모두 정상 |
| 리다이렉트 없음 + 종료코드 128 | **생존**, 종료코드도 정상 감지 |

AWS CLI가 stderr를 쓰는 가장 흔한 경우가 **SSO 토큰 만료**다. 즉 SSO가 만료된 저녁에
daily-down이 1단계에서 정체불명의 `RemoteException`으로 죽고, **종료를 못 하면 그날
과금이 그대로 간다.**

### 해결 방법

리다이렉트를 빼고 `$LASTEXITCODE`로 판정한다. 조회에 실패하면 destroy로 넘어가지
않고 `aws sso login` 안내를 띄우고 멈춘다 — 검역 SG가 남아 있는지 확인하지 못한 채
지우면 VPC 삭제가 막혀 반쯤 지워진 상태로 멈춘다.

## 13. IAM 토큰 재발급 검증 · DB 비밀번호 제거 완료 — "통과"가 아무것도 증명하지 않았던 것

### 작업 목적

§12에서 남긴 것을 끝낸다. 토큰 재발급 구간을 검증하고, 통과하면 2 → 3 순서로 머지한다.

### 문제가 발생한 지점

§12에서 만들어 둔 `verify-iam-token.ps1`을 돌렸고 **통과가 나왔다.**

```
[3] RDS 감사 로그 — 최근 10분 (토큰 캐시 만료 이후 구간)
    CONNECT  rdsadmin                 16회
    QUERY    gochuchamchi_app_iam     346회
판정: 통과 — IAM 토큰 재발급 구간을 넘겨 DB 접속이 유지됐다.
```

그런데 출력에 `gochuchamchi_app_iam`의 **CONNECT 줄이 없다.** 최근 10분간 IAM 계정의
새 접속이 0건이라는 뜻이다. 스크립트는 통과라는데 재발급 증거가 없었다.

### 문제 원인

**MariaDB는 접속을 맺을 때만 인증하고, 그 뒤로는 재인증하지 않는다.** IAM 토큰은
"접속 시점의 입장권"이지 세션을 계속 검사하는 값이 아니다. 따라서 **이미 열려 있는
커넥션 위에서 도는 QUERY는 몇 백 건이든 전부 첫 토큰의 결과**이고, 토큰이 만료된
뒤에도 그 커넥션은 아무 일 없이 계속 돈다.

스크립트 `[3]`은 QUERY 건수만 세고 있었다. 그래서 **재발급이 한 번도 안 일어난
상태에서도 통과가 나온다.** §12에서 "219건은 첫 토큰이라 증명이 아니다"라고 정확히
적어 놓고, 정작 검사 조건은 같은 함정에 들어가 있었다.

감사 로그에서 CONNECT 시각만 뽑아 보니 분명했다.

| 시각 | 계정 | 이벤트 |
|---|---|---|
| 14:19:07 ~ 14:20:28 | `gochuchamchi_app_iam` | CONNECT 5건 |
| 이후 | — | **없음** |

파드 기동 시각뿐이다. 플러그인 캐시(10분)는 14:29:50에 만료됐는데, 그 뒤로 새 커넥션이
필요한 일이 없었으니 토큰을 다시 발급받을 이유도 없었던 것이다.

### 해결 방법

증명하려면 **캐시 만료 이후에 새 물리 커넥션이 열리는 순간**을 잡아야 한다.

**실패한 시도 — 동시 요청으로 풀을 키우기.** 커넥션 풀이 커지면 새 물리 커넥션이
생기므로, 동시 요청 45건(15건씩 3라운드)을 몰아쳤다. **새 CONNECT는 0건이었다.**
응답이 빨라서 파드당 커넥션 2개로 전부 처리됐다. 앱에 Hikari 설정이 없어 전부
기본값(`maximumPoolSize=10`)인데, 최대치는 "필요할 때 늘어나는 한도"이지 미리 여는
개수가 아니다.

> **곁다리로 밟은 오진** — 첫 시도에서 30건이 **전부 403**이었다. rate 기반 WAF 규칙에
> 걸린 줄 알고 IP 차단을 의심했는데, 단일 요청은 200이었다. 원인은 **User-Agent 헤더가
> 없는 것**이었다 — .NET `HttpClient`는 UA 기본값이 없고, WAF 관리형 규칙의
> `NoUserAgent_HEADER`가 이를 막는다. UA를 붙이자 45건 전부 200. **WAF가 제대로 도는
> 증거였지 결함이 아니었다.** 부하 도구가 403을 뱉으면 rate limit보다 UA를 먼저 볼 것.

**통한 방법 — HikariCP `maxLifetime`(기본 30분)을 기다린다.** 커넥션은 수명이 다하면
폐기되고 곧바로 새로 열린다. 그 새 커넥션은 캐시가 만료된 뒤라 **반드시 토큰을 새로
발급받아야** 한다. 14:20에 열린 커넥션이므로 14:50 전후를 보면 된다.

### 검증 완료 사항

14:43 ~ 14:45, 감사 로그에 정확히 그 교체가 찍혔다.

| 시각 | 이벤트 | 커넥션 ID |
|---|---|---|
| 14:43:11 | DISCONNECT | 32 (14:20 생성) |
| 14:43:12 | **CONNECT** | **72** |
| 14:44:32 | DISCONNECT / **CONNECT** | 30 → **74** |
| 14:44:35 | DISCONNECT / **CONNECT** | 31 → **75** |
| 14:45:02 | DISCONNECT / **CONNECT** | 33 → **77** |

**`FAILED_CONNECT` 0건.** 첫 토큰이 아니라 재발급된 토큰으로 물리 커넥션 4개가 새로
맺어졌다. 이것이 §12가 남긴 "아직 한 번도 안 돌아본 경로"의 실증이다.

재실행한 스크립트도 이제 CONNECT를 잡는다 — 최근 10분 `gochuchamchi_app_iam`
CONNECT 3회 / QUERY 355회, 파드 재시작 0, 로그에 DB 오류 없음, 사이트 200.

> **스크립트에 남은 구멍** — `[3]`의 판정 조건은 여전히 QUERY 기준이다. 다음에 같은
> 검증을 할 때는 **CONNECT 0건이면 통과로 보지 말 것.** QUERY는 "죽지 않았다"를,
> CONNECT는 "재발급이 됐다"를 증명한다. 필요한 건 후자다.

### 머지 — 2 → 3 순서

**2. gitops `853a6a4` (fast-forward, push 완료).** ArgoCD가 자동 동기화(prune·selfHeal)라

**apply는 하지 않았고 할 필요도 없다.** 밤 `daily-down`이 런타임 루트를 통째로
destroy하므로 시크릿과 K8s Secret이 그때 사라지고, 다음 `daily-up`부터는 코드에
없으니 재생성되지 않는다. DB 계정도 인스턴스가 매일 재생성되므로 `DROP USER`로
쫓아다닐 잔재가 없다.

> **되돌리는 방법이 바뀌었다.** 머지 전에는 ConfigMap의 `DB_USER`를 `gochuchamchi_app`,
> URL을 `?sslMode=trust`로 되돌리면 즉시 복귀할 수 있었다. **이제는 비밀번호 계정
> 자체가 만들어지지 않으므로 `dbae59c`를 revert해야 한다.**

### 곁다리 — 머지가 문서 때문에 막혔던 것

`git merge`가 `Your local changes to the following files would be overwritten`으로
거부했는데, 정작 브랜치는 `go/docs/`를 전혀 건드리지 않았다. 원인은 **작성 중이던 이
문서가 인덱스에 스테이징된 상태**였던 것 — fast-forward가 아닌 머지는 인덱스가 HEAD와
같아야 진행된다. 파일이 겹치는지와 무관하다. 커밋해 버리면 작성 중인 문서가 어중간하게
남으므로 `git stash push -- <경로>`로 잠시 빼고 머지한 뒤 `git stash pop --index`로
스테이징 상태까지 그대로 복원했다.

### 런북 갱신 (§1.4 RDS 접속)

절차가 바뀌었으므로 `runbook.md`의 DB 접속 항목을 현재 상태로 고쳤다. **옛 절차를 그대로
따라가면 존재하지 않는 Secret을 찾다가 막힌다.**

- ③ 앱 계정 접속을 `kubectl get secret ... DB_PASS` → `aws rds generate-db-auth-token`으로
  교체. `TOKEN_LEN=0` 판별과 "토큰은 접속 시점에만 검사된다(세션은 안 끊기지만 재접속은
  재발급 필요)"를 함께 적었다
- ⑤ SSM 포트포워딩 경로 신규 — GUI 도구용. **토큰은 실제 엔드포인트로 발급해야 하고,
  `127.0.0.1`로 붙으면 TLS 호스트명 검증이 실패**한다는 두 함정을 명시
- 트러블슈팅 표의 `Access denied`를 "비밀번호 불일치 → `gochuchamchi-db-app` 확인"에서
  "토큰 만료·호스트명 불일치·계정 부재" 세 갈래로 교체
- 고정 값 참조표의 "RDS 앱 계정 비밀번호" 행을 **"없음 — 저장된 비밀값이 존재하지 않음"**으로
- 곁다리 정정: `max_connections=30`에 대해 "HikariCP가 파드당 5개"라고 적혀 있었으나
  앱에 Hikari 설정이 없어 **전부 기본값(`maximumPoolSize=10`)**이다. 파드 2개가 한계까지
  쓰면 20개라 여유가 생각보다 없다

## 14. 검증 스크립트 5종 — 만들자마자 오검사 2건을 스스로 잡았다

### 작업 목적

검증이 매번 "그때그때 명령어를 조합해서" 이뤄지고 있었다. 그래서 무엇을 확인했고
무엇을 빠뜨렸는지가 기억에만 남는다. WAF 가이드 8~11번은 그렇게 몇 주째 미실행으로
남아 있었다. 확인해야 할 것들을 스크립트로 고정한다.

### 진행 내용

`go/scripts/`에 5개를 추가했다. 저장소 관례대로 BOM·PS 5.1 호환이다.

| 스크립트 | 보는 것 |
|---|---|
| `verify-db-iam-only.ps1` | 비밀번호 잔재 부재, 파드 `DB_PASS` 부재, 토큰 재발급 |
| `verify-waf.ps1` | ALB 우회 차단(8번), SQLi 차단(9번), WAF 로그(10번), 알람·구독 |
| `verify-notifications.ps1` | SNS 구독 확인 상태, 알람→EventBridge→SNS 배선, 시크릿 값 유무 |
| `verify-log-pipeline.ps1` | 구독 필터 존재·목적지 계정, 로그 유입, ALB 액세스 로그 설정 |
| `verify-all.ps1` | 위 전부 + 기존 smoke-test·verify-contract·verify-schema-sync 요약 |

**판정을 통과/미결/실패 3단계로 나눴다(종료 코드 0/2/1).** 토큰 재발급처럼 시간이
지나야 관찰되는 항목을 "실패"로 부르면 아침마다 헛경보가 난다. "아직 모른다"가
정확한 답인 경우가 있고, 그건 고칠 것이 있다는 뜻이 아니다.

### 문제가 발생한 지점 — 스크립트가 자기 오검사를 잡았다

돌려 보자마자 두 가지가 드러났다. **둘 다 스크립트를 안 만들었으면 내일 아침에
"고장"으로 오진했을 것들이다.**

**① `'cp949' codec can't encode character '—'`**

`describe-alarms`가 통째로 실패했다. 알람 설명에 em-dash(—)가 들어 있는데 AWS CLI가
Windows 로캘로 출력을 인코딩하려다 죽는 것이다. 실패가 조회 대상의 문제처럼
보인다는 게 고약하다 — 화면에는 **"알람 0개"**로 나온다. 알람이 사라진 줄 안다.

`PYTHONIOENCODING=utf-8`은 듣지 않았다(실측). AWS CLI v2는 frozen 바이너리라
파이썬 환경변수를 안 본다. `[Console]::OutputEncoding` 변경도 소용없었다 — 죽는
쪽은 콘솔이 아니라 CLI 내부다.

해법은 **`--query`로 필요한 필드만 뽑는 것**이다. 설명 필드를 애초에 출력에서
빼면 인코딩할 문자가 없다.

```powershell
aws cloudwatch describe-alarms --region $rg `
  --query "MetricAlarms[].{Name:AlarmName,State:StateValue}" --output json
```

**② "알람에 액션이 없다"는 오검사**

처음엔 `AlarmActions`가 비면 실패로 판정하게 짰다. 실제로 상시 알람 2개가 전부
액션 0개로 나왔다. 그런데 `sns.tf:146`에 답이 있었다 — **이 프로젝트는 알람에
액션을 붙이지 않는다.** EventBridge가 `CloudWatch Alarm State Change` 이벤트를
**알람 이름 접두사 `gochuchamchi-`로 잡아** SNS로 넘긴다.

즉 액션 없음이 정상이고, 이 설계에서 진짜 위험한 것은 따로 있다. **접두사를 안
지킨 알람은 룰에 안 걸려 조용히 통보에서 빠진다** — 알람은 멀쩡히 ALARM으로
바뀌는데 아무도 모른다. 검사를 그쪽으로 바꿨다(접두사 불일치 + 룰 활성 상태).

`us-east-1` WAF 알람도 같은 구조다(`gochuchamchi-waf-alarm-state-change`가 서울로
중계). 여기도 액션을 요구하면 안 된다.

**③ ALB 액세스 로그를 워크로드 S3에서 찾고 있었다**

`k8s-deploy.tf:222`가 가리키는 버킷은 `gochuchamchi-alb-access-logs-<Log계정>`이다.
**남의 계정 버킷이라 워크로드 자격증명으로는 영원히 못 찾는다.** ALB 속성
(`access_logs.s3.enabled`, `.bucket`)을 보는 것으로 바꿨다 — 워크로드에서 확인
가능한 것은 "그리로 쓰도록 설정돼 있는가"까지다.

### 검증 완료 사항

- 5개 전부 BOM·구문 검사 통과, 인프라가 내려간 상태에서 크래시 없이 정상 판정
- `verify-notifications.ps1`은 상시 계층 대상이라 지금도 실제 검증이 된다:
  SNS 구독 2건 확인됨(이메일·Discord Lambda, PendingConfirmation 없음),

  "비밀번호 계정이 더 이상 태어나지 않는다"의 증거가 된다
