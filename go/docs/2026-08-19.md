## 2. 침해 방어 분석 — NAT · assume-breach · 악성코드 주입

**코드 변경 없는 분석.** 사용자 질문 3연속에 대한 코드 실측 기반 답변.

### 2.1 NAT로 외부 침투 가능한가 → 불가
NAT는 퍼블릭 서브넷·공인 IP를 갖지만 `nat_sg` 인바운드가 **VPC CIDR로만** 제한(`securitygroups.tf`), 리스닝 서비스 없음(`nat_install.tpl`은 iptables MASQUERADE뿐), SSM 전용·IMDSv2. 인터넷發 인바운드는 SG에서 전부 드롭. 방어심층화 관점 개선점: 퍼블릭 서브넷 NACL이 기본 전체허용이라 SG 단일 계층 / NAT egress `0.0.0.0/0`이 exfil 통로(다만 "나가는" 문제).

### 2.2 assume-breach — 앱 파드 침해 시 → 반경 매우 좁음
NetworkPolicy `default-deny-all` + 앱 파드 egress를 DNS/RDS/Redis/443/Pod-Identity로만 제한(리버스쉘 임의 포트 차단), `add_node_sg` VPC-전체 인그레스 제거로 kubelet/NodePort 측면이동 차단, 앱 IAM 역할은 `s3:PutObject` 한 prefix + `rds-db:connect`뿐(계정 장악 불가), IMDSv2 hop_limit 1. GuardDuty EKS Audit/S3/EBS Malware·FlowLog·RDS Audit·CloudTrail 상시 + sev≥7 자동격리.

### 2.3 악성코드 주입 → 이미지는 막힘, in-container 런타임 탐지가 약점
Kyverno 서명검증 `Deny`(미서명 이미지 admit 거부)로 악성 **이미지 배포**는 차단. 다만 **이미 뜬 컨테이너 안 프로세스**는 GuardDuty Runtime Monitoring이 기본 OFF라 실시간 미탐지, PSA restricted가 Audit 모드(차단 아님). 완화: ResourceQuota·NetworkPolicy. → 강화 후보로 정리(런타임 모니터링 ON, PSA Enforce 승격).

## 5. 04 Athena 크로스계정 — `sts:TagSession` 버그 (양쪽 수정)

### 작업 목적
04 대시보드가 Log 계정 `security_events` 뷰를 조회하려면 grafana 파드가 Log 계정 reader 역할을 assume해야 함. `grafana_athena_reader_role_arn`의 프로젝트 기본값을 `arn:aws:iam::564186750363:role/gochuchamchi-grafana-athena-reader`로 고정해 Athena 데이터소스를 등록한다. 이 값은 비밀정보가 아니므로 Git에서 제외되는 로컬 `terraform.tfvars`에 의존하지 않는다.

### 문제가 발생한 지점
데이터소스는 등록됐으나 04 패널들이 빨간 에러. grafana 파드 로그:
```
AccessDenied: ...grafana-cloudwatch/... is not authorized to perform: sts:TagSession
on resource: arn:aws:iam::564186750363:role/gochuchamchi-grafana-athena-reader
```

### 문제 원인
`grafana-athena-datasource` 플러그인이 AssumeRole에 **세션 태그를 붙인다**. 크로스계정 태그 assume는 caller·target **양쪽**이 `sts:TagSession`을 허용해야 하는데, 초기 코드는 양쪽 다 `sts:AssumeRole`만 있었다(작성자가 플러그인의 세션 태깅을 몰랐음 — Log 파일 주석에도 "AssumeRole만 필요"라 적혀 있었음). 진단이 어려웠던 건 AssumeRole은 통과하고 **그 다음 단계 TagSession에서 403**이라, "역할 전환 실패"로 오인하기 쉬웠던 것.

### 해결 방법
양쪽에 `sts:TagSession` 추가(`075353a`):
- Workload caller: `terraform/module/grafana/main.tf`의 `AssumeLogAccountReaderRole` statement
- Log target trust: `log-archive/grafana-athena-access.tf`의 `grafana_reader` 신뢰 정책

세션 태그의 용도: Log 계정 CloudTrail에서 "누가 reader 역할을 assume했나" 귀속 + ABAC 여지.

### 검증 완료 사항
Workload 쪽 apply 완료(grafana IAM 정책만 갱신, 파드 재시작 없이 즉시 반영). **Log 쪽(`log-archive`)은 Log 계정 프로필이 필요**한데 사용자 `~/.aws`엔 `workload-admin`만 있어 apply 불가 → **팀원이 `20260819.01` pull 후 `go/log-archive`를 Log 프로필로 apply**해야 04에 데이터가 뜬다. 코드는 push 완료.

## 6. 05 실시간 대시보드 — DB 패널 CWLI 쿼리 버그

### 작업 목적
05의 `DB — 접속 이벤트` 패널이 "No data"가 아니라 **빨간 에러 아이콘**(쿼리 실패)이었다. 원인 규명·수정.

### 문제가 발생한 지점·진단
grafana 로그에 `POST /api/ds/query status=400` 반복. 패널의 CWLI 쿼리를 `aws logs start-query`로 그대로 재현하니:
```
MalformedQueryException: Ephemeral field is already defined: dbuser
```

### 문제 원인
`parse @message "*,..." as ..., dbuser, ...`로 필드를 만든 뒤 `| fields @timestamp, dbuser, ...`로 **같은 필드를 재나열**해 "중복 정의" 에러. RDS 감사 로그엔 데이터가 충분히 있었고(24h 2,100여 건) 쿼리 문법만 틀린 것 — "No data"가 아니라 에러였다는 게 진단의 출발점.

### 해결 방법
`fields` → `display`로 투영(재정의 없이 컬럼만 선택), sort/limit 뒤로 이동. `start-query` 재현으로 수정 쿼리가 100행 반환 확인 후 코드 반영(`562dc0e`).

### 검증 완료 사항
수정 쿼리 실측 통과(rdsadmin의 localhost CONNECT/DISCONNECT 15초 주기 헬스체크가 정상 표시). apply 반영됨.

## 7. 제로트러스트 DB 가드레일 알람 구축

### 작업 목적
DB 감시를 "실시간 패널"이 아니라 **"제로트러스트 선을 넘을 때만 Discord로 알리는" 이벤트 방식**으로 구축(`terraform/db-audit-monitoring.tf`, `562dc0e`). 감사 로그는 rdsadmin 헬스체크·앱 INSERT로 노이즈가 커(24h 2,100여 건) 실시간 패널은 소음만 크기 때문. 앱 계정은 파드 대역에서 DML만 하는 것이 정상이라, 그 밖은 정상 운영에서 절대 안 나온다 = 뜨면 사건.

### 해결 방법 — 가드레일 2종
- **① 앱 계정 DDL/DCL 시도** (SEC/P1): `gochuchamchi_app_iam` × {DROP,ALTER,CREATE,GRANT,REVOKE,TRUNCATE} 필터 6개 → 단일 지표 `AppAccountDdlDclAttempt`, 임계 1. DML 전용이라 절대 불가.
- **② FAILED_CONNECT** (SEC/P2): 무차별 대입·IAM 토큰 우회·프로빙, 임계 5/5분(변수화).
- 메트릭 필터 → 알람(`gochuchamchi-` 접두사) → 기존 `cloudwatch-notifications` EventBridge→SNS→Discord.

### 문제가 발생한 지점·해결
앱 로그는 JSON(`{ $.f = v }`) 패턴이지만 **RDS 감사 로그는 CSV**라 그 문법을 못 쓴다. 텍스트 매칭(공백=AND, `"..."`=정확)으로 전환하고 **`aws logs test-metric-filter`로 오탐 검증**: `"gochuchamchi_app_iam" DROP`은 DROP행만 잡고 정상 INSERT행은 제외됨을 실증(패턴 A `FAILED_CONNECT`는 1행만). CREATE 등은 데이터 리터럴에 그 단어가 들어가면 오탐 가능(감사는 SELECT 제외 DML만 기록, 앱 데이터가 구조적이라 위험 낮음)이라 주석에 튜닝 방법 명시.

### 검증 완료 사항
apply 후 알람 2개 `State=OK`(위반 없음=정상), 메트릭 필터 7개 생성. **파이프라인 실증**: 알람 생성 시 `INSUFFICIENT_DATA → OK` 상태변화가 Discord까지 도달(EventBridge→SNS→Lambda→Discord 정상).

## 8. 알람 이름 정리 + `classify_alarm` 등록

### 8.1 알람 이름 중복 `db-db-` 제거 (`1616fe1`)
알람 key에 `db-` 접두사가 붙어 resource 접두사 `gochuchamchi-db-`와 겹쳐 `gochuchamchi-db-db-...`로 중복됐다(필터는 단일 `db-`). key에서 `db-`를 빼 정합. 사용자 apply 완료 — 실측 `gochuchamchi-db-app-account-ddl-dcl`·`gochuchamchi-db-failed-connect`.

### 8.2 `classify_alarm()` 등록 (`c51e707`)
Discord 알림이 `[UNCLASSIFIED][P3]`로 뜬 이유: 알림 Lambda `cloudwatch-notifications/lambda_function.py`의 `classify_alarm()`(알람 이름→domain/tier 매핑)에 DB 알람이 없어 기본값으로 떨어진 것. 등록: `app-account-ddl-dcl`→**SEC/P1**(제로트러스트 breach 최상위), `db-failed-connect`→**SEC/P2**. 마커가 rename 전/후 이름 다 매칭. **검증**: 배포된 Lambda 코드(`get-function` → 다운로드 → grep)에 두 규칙 실존 확인.
