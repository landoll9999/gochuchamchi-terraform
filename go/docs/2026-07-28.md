# 2026-07-28 작업 기록

## 1. 메인 페이지 텍스처 배경 미노출 트러블슈팅

### 작업 목적
- 메인 페이지(`index.html`)의 `<main>` 영역에 배경 텍스처 이미지(`texture.png`, S3 저장)를 표시
- 애플리케이션 코드 수정 → GitHub Actions 재빌드 → Docker Hub 재푸시 → K8s 재배포까지 전체 파이프라인으로 반영

### 문제가 발생한 지점
- 브라우저에서 `https://gochuchamchi.shop` 메인 화면 진입 시, `<main>` 안의 `<div class="bg-texture">` 요소는 DOM에 존재하지만 텍스처가 전혀 보이지 않음
- F12 Network 탭에 `texture.png` 요청 자체가 아예 나타나지 않음 (요청이 발생하지 않음)
- Elements → Computed 탭 확인 결과 `.bg-texture` 요소의 실제 `height: 0px` (width만 일부 존재)

### 문제 원인 (단계적으로 3가지가 겹쳐서 발생)

1. **1차 원인 — 버킷 이름 불일치 (404)**
   - `index.html`의 `<style>` 블록에 `background-image` URL이 `https://gochuchamchi-images.s3.ap-northeast-2.amazonaws.com/texture.png`로 하드코딩되어 있었음
   - 실제 S3 버킷 이름은 계정 ID가 붙은 `gochuchamchi-images-307223751140`이라 존재하지 않는 호스트로 요청 → `404 Not Found`
   - (S3 버킷 자체나 `S3Service.java`의 업로드 로직 코드는 정상이었음 — `@Value("${cloud.aws.s3.bucket}")`로 버킷명을 프로퍼티에서 읽어오는 방식이라 문제 없었고, 문제는 `index.html`에 별도로 하드코딩된 텍스처 URL 한 줄뿐이었음)

2. **2차 원인 — `application.yml`에 `cloud.aws.s3.bucket` 프로퍼티 자체가 없었음**
   - (버킷 이름 문제와는 별개로 확인된 잠재 이슈) `application.yml`에 `cloud:` 섹션이 아예 없어서 `@Value("${cloud.aws.s3.bucket}")`가 값을 못 받을 수 있는 상태였음
   - `cloud.aws.s3.bucket`, `cloud.aws.region.static`을 환경변수(`CLOUD_AWS_S3_BUCKET`, `CLOUD_AWS_REGION_STATIC`) 매핑과 함께 명시적으로 추가

3. **3차 원인 — CSS 규칙 문법 파괴 (근본 원인, height:0의 직접적 원인)**
   - GitHub 웹 편집기로 URL을 고치는 과정에서 `.bg-texture{` 셀렉터와 여는 중괄호 `{`가 실수로 삭제되고, 선언부(`background-image:...;`)만 덩그러니 남음:
     ```css
     main{...}
     background-image:url('...');   /* 셀렉터 없이 홀로 남은 선언 — 유효하지 않은 CSS */
     ```
   - 브라우저 CSS 파서가 셀렉터 없는 선언 블록을 통째로 무시 → `.bg-texture` 클래스에 대한 CSS 규칙이 전혀 적용되지 않음
   - Elements → Styles 탭에서 확인 시 `.bg-texture`에 매치되는 규칙이 하나도 없고(`*`, `div`, `body` 상속 규칙만 존재) `position:absolute`도 적용되지 않아 요소가 일반 빈 `<div>`처럼 동작 → `height:0px`

### 해결 방법
1. `index.html`의 `<style>` 블록에서 깨진 CSS를 원래 형태로 복원:
   ```css
   .bg-texture{
     position:absolute;
     inset:0;
     background-image:url('https://gochuchamchi-images-307223751140.s3.ap-northeast-2.amazonaws.com/texture.png');
     background-size:cover;
     background-position:center;
     background-attachment:fixed;
     opacity:1;
     mix-blend-mode:multiply;
   }
   ```
   (버킷 URL을 계정 ID 포함한 정확한 값으로 교체 + 셀렉터/중괄호 복원을 동시에 처리)
2. `application.yml`에 `cloud.aws.s3.bucket` / `cloud.aws.region.static` 명시적 추가
3. GitHub 커밋 → Actions 자동 빌드/푸시 → 새 이미지 태그로 `03-deployment-web.yml` 갱신 → `terraform apply` → 배스천에서 `aws s3 sync --exact-timestamps` + `kubectl apply -f` → 파드 재기동 확인 후 브라우저에서 텍스처 정상 노출 확인 완료

### 디버깅 과정에서 유효했던 접근법 (재사용 가치 높음)
- **Network 탭 Initiator 체인** 확인 → 요청이 어느 문서/스크립트에서 발생했는지 역추적 (`gochuchamchi.shop → index.html` 인라인 스타일로 확인됨)
- **Elements → Computed 탭**으로 실제 렌더링된 `height`/`position` 등 계산값 확인 → "요소는 있는데 안 보인다"를 "레이아웃 문제"로 좁힘
- **Elements → Styles 탭**으로 해당 요소에 매치되는 CSS 규칙 목록 확인 → 클래스에 대한 규칙이 아예 없다는 것으로 "CSS 자체가 안 먹고 있다"를 확정
- **배포된 jar 내부를 직접 unzip해서 확인**: `kubectl exec ... unzip -p /app/app.jar BOOT-INF/classes/templates/index.html | grep texture` — 실제 컨테이너 안에 어떤 코드가 반영됐는지 배포 파이프라인을 신뢰하지 않고 직접 검증

## 2. 상품 등록 이미지 업로드 413 에러

### 작업 목적
- 상품 등록 화면에서 이미지 파일을 첨부하여 정상적으로 상품 데이터 + 이미지를 등록

### 문제가 발생한 지점
- 상품 등록 시 이미지 파일을 첨부하고 제출하면 **413 에러** 발생 (요청이 서버에 거부됨)

### 문제 원인
- 파드 로그 확인 결과:
  ```
  WARN ... DefaultHandlerExceptionResolver : Resolved [org.springframework.web.multipart.MaxUploadSizeExceededException: Maximum upload size exceeded]
  ```
- `application.yml`에 `spring.servlet.multipart.max-file-size`/`max-request-size` 설정이 없어서 Spring Boot 기본값(**1MB**)이 적용되고 있었음
- 업로드하려던 이미지 파일이 이 기본 한도를 초과 → ALB나 다른 프록시가 아니라 **애플리케이션(Tomcat/Spring) 레벨에서 차단**된 것으로 확인됨

### 해결 방법
- `application.yml`의 `spring:` 블록에 아래 설정 추가:
  ```yaml
  spring:
    servlet:
      multipart:
        max-file-size: 10MB
        max-request-size: 10MB
  ```
  (`server.servlet.encoding`/`server.servlet.session`과는 별개의 키이므로 혼동 주의 — `spring.servlet.multipart`와 `server.servlet.*`는 각자 다른 최상위 블록 아래에 존재해야 함)
- GitHub 커밋 → Actions 빌드/푸시 → 새 이미지 태그(`b2bb4609b591e8000d410fca4774c3a1b7d06f33`)로 `03-deployment-web.yml` 갱신 → `terraform apply` → 배스천 재동기화 + `kubectl apply` → 재배포 후 이미지 첨부 상품 등록 정상 동작 확인 완료

### 참고
- 413 에러가 다시 발생한다면, 이번엔 애플리케이션이 아니라 **ALB의 요청 크기 제한**이나 별도 프록시(Nginx 등) 레벨일 수 있으니 로그에서 어느 레이어의 에러인지 먼저 구분할 것 (Spring이 던진 `MaxUploadSizeExceededException`인지, ALB가 아예 애플리케이션까지 요청을 전달하지 않고 자체적으로 끊은 것인지)
