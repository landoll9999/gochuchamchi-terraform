04 Grafana SIEM 대시보드 04·05 배포

증상

terraform plan이 EKS refresh에서 i/o timeout, helm_release를 "생성 예정"으로 오표시(상태엔 12개 존재).

05 04 Athena — sts:TagSession 버그 Log는 팀원 대기

배경

04는 Log 계정 security_events 뷰를 보려고 grafana 파드가 Log 계정 reader 역할을 assume한다. 먼저 grafana_athena_reader_role_arn(로컬 tfvars)로 데이터소스 등록 — 빈값이면 모듈이 아예 미등록.

증상

데이터소스는 등록됐는데 04 패널들이 빨간 에러. grafana 파드 로그:

AccessDenied: ...grafana-cloudwatch/... is not authorized
to perform: sts:TagSession on resource:
arn:aws:iam::564186750363:role/gochuchamchi-grafana-athena-reader
원인

플러그인이 AssumeRole에 세션 태그를 붙인다. 크로스계정 태그 assume는 caller·target 양쪽이 sts:TagSession을 허용해야 하는데 초기 코드는 양쪽 다 sts:AssumeRole만 있었다. AssumeRole은 통과하고 다음 단계 TagSession에서 403이라 "역할 전환 실패"로 오인하기 쉬웠다.

해결

양쪽에 sts:TagSession 추가(075353a): Workload caller(module/grafana/main.tf) + Log target trust(log-archive/grafana-athena-access.tf). 세션 태그는 Log 계정 CloudTrail 귀속·ABAC 용도.

상태

Workload apply 완료(파드 재시작 없이 즉시). Log 쪽은 Log 계정 프로필 필요 → 팀원이 go/log-archive apply해야 04 데이터가 뜬다. 코드는 push 완료.

06 05 DB 패널 — CWLI 쿼리 버그

증상

DB — 접속 이벤트 패널이 "No data"가 아니라 빨간 에러. grafana 로그에 status=400 반복.

원인

쿼리를 start-query로 재현하니:

MalformedQueryException: Ephemeral field is already defined: dbuser

parse ... as ..., dbuser, ...로 만든 필드를 | fields ..., dbuser, ...로 재나열해 중복 정의. 데이터는 24h 2,100여 건 있었고 문법만 틀렸다.

해결

fields → display(재정의 없이 투영), sort/limit 뒤로. 재현으로 100행 반환 확인 후 반영(562dc0e).

제로트러스트 DB 가드레일

07 DB 감시를 "패널"에서 "알림"으로

감사 로그는 rdsadmin 헬스체크·앱 INSERT로 24h 2,100여 건 — 실시간 패널로는 소음만 크다. 앱 계정은 파드 대역에서 DML만 하는 것이 정상이라, 그 밖은 정상 운영에서 절대 안 나온다 = 뜨면 곧 사건. 그래서 "선을 넘을 때만" Discord로 알리는 이벤트 가드레일로 재설계.

RDS 감사 로그 → 메트릭 필터 → 알람(gochuchamchi-) → EventBridge → SNS → Lambda → Discord
가드레일등급조건 · 의미
앱 계정 DDL/DCL 시도SEC P1gochuchamchi_app_iam × {DROP·ALTER·CREATE·GRANT·REVOKE·TRUNCATE}. DML 전용이라 절대 불가 → 임계 1
FAILED_CONNECTSEC P2무차별 대입·IAM 토큰 우회·프로빙 → 임계 5/5분(변수화)
함정

앱 로그는 JSON 패턴이지만 RDS 감사 로그는 CSV라 그 문법을 못 쓴다. 텍스트 매칭(공백=AND, "..."=정확)으로 전환하고 test-metric-filter로 오탐 검증: "gochuchamchi_app_iam" DROP은 DROP행만 잡고 정상 INSERT는 제외됨을 실증.

검증

알람 2개 State=OK(위반 없음), 필터 7개 생성. 파이프라인 실증: 알람 생성 시 INSUFFICIENT_DATA → OK가 Discord까지 도달.

08 알람 이름 정리 + classify_alarm 등록

이름

알람 key에 db-가 겹쳐 gochuchamchi-db-db-*로 중복 → key에서 제거(1616fe1). 실측 gochuchamchi-db-app-account-ddl-dcl·...failed-connect.

분류

Discord가 [UNCLASSIFIED][P3]로 뜬 이유 = 알림 Lambda classify_alarm()에 DB 알람이 없어 기본값. 등록(c51e707): DDL/DCL→SEC/P1, FAILED_CONNECT→SEC/P2. 배포된 Lambda 코드 다운로드로 반영 확인.
