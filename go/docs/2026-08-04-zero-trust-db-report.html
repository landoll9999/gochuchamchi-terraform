제로트러스트 DB 하드닝 보고서

작성일 2026-08-04 · gochuchamchi EKS · 대상: RDS MariaDB + ElastiCache Redis · 코드 완료 / apply 전 상태

1. 개요 — 무엇을, 왜

데이터 계층에 남아 있던 마지막 신뢰 가정을 제거했다. 지금까지는 "VPC 안이면, SG를 통과했으면 믿는다"가 전제였다. 네트워크(SG 참조 좁히기, 감사보고서 #5)는 이미 조치됐지만, 접속 계정·전송 암호화·접근 기록은 비어 있었다. 이번 작업으로 제로트러스트 3원칙을 DB 계층에 적용했다: 최소권한(앱 전용 DML 계정), 명시적 검증(TLS 이중 강제 + AUTH), 침해 가정(자격증명의 state 격리 + 감사 로그).

작업 중 발견한 기존 리스크: k8s-deploy.tf가 RDS 마스터 비밀번호를 data 소스로 읽어 K8s Secret을 만들면서 tfstate에 평문으로 저장하고 있었다. 감사보고서 #1이 "state에 secret_string이 다시 들어가는 시점 = ESO 도입 트리거"로 정의해 둔 바로 그 상태가 이미 발동돼 있었던 것. 이번 구조 변경으로 마스터/앱 DB 비밀번호 모두 state에서 완전히 제거됐다.

2. Before → After

BEFORE — 네트워크 위치만 믿는 구조
앱 파드→ admin (마스터)
DDL/DCL 전부 가능→ 평문 3306→ RDS
접속 기록 없음
Terraform→ 마스터 비번 조회
tfstate 평문 저장 · 앱 파드→ 평문 · 무인증 6379→ Redis
AFTER — 매 접속을 검증하는 구조
앱 파드→ gochuchamchi_app
DML만 · REQUIRE SSL→ TLS 강제
require_secure_transport=1→ RDS
감사 플러그인 → CloudWatch
배스천(SSM)→ 비번 생성 · Secrets Manager 저장
DB 계정 생성 · K8s Secret 주입 · 앱 파드→ TLS + AUTH 토큰→ Redis (replication_group)

핵심: Terraform은 이제 비밀 "컨테이너"만 만들고 값은 모른다. 값의 생성·저장·주입은 전부 배스천 런타임에서 일어나므로 tfstate·SSM 커맨드 로그 어디에도 비밀번호가 남지 않는다. (예외 1건: Redis auth_token은 리소스 인자라 state 경유 불가피 — §6 트레이드오프)

3. 기존 상태의 갭 4개

#갭리스크 (침해 시나리오)
1앱이 DB 마스터(admin)로 접속 (DB_USER=admin) SQL 인젝션·의존성 취약점 하나로 즉시 DBA 권한 — DROP TABLE, GRANT, 타 DB 생성까지 전부 가능
2마스터 비밀번호가 tfstate에 평문 저장 state 파일 접근 = DB 전체 장악. 감사보고서 #1의 ESO 트리거가 이미 발동된 상태였음
3전송 암호화 미강제 (앱·배스천 모두 평문 3306) "같은 VPC = 안전" 가정. VPC 내 다른 자원(NAT 등) 침해 시 트래픽 스니핑 가능
4DB 접속 기록 없음 + Redis 평문·무인증 (#14 잔여) 무단 접속 시도를 볼 수단이 없음. 세션 스토어는 SG 하나 넘으면 로그인 세션 탈취

4. 변경 상세 (파일별)

파일구분변경 내용
db-zero-trust.tf신규 이번 작업의 핵심. ① 앱 전용 계정 gochuchamchi_app — gochuchamchi.*에 SELECT/INSERT/UPDATE/DELETE만, REQUIRE SSL이라 TLS 없이는 로그인 불가. ② 비번 생성 → Secrets Manager(gochuchamchi/app/db-credentials) → DB 계정 생성 → K8s Secret(gochuchamchi-db-app) 주입을 전부 배스천 SSM에서 실행. ③ 멱등(재실행 시 비번 재사용) + Status 검사로 실패를 삼키지 않음(8/3 교훈 반영). 재시도: terraform taint null_resource.provision_app_db_user
rds.tf수정 ① require_secure_transport=1 — 평문 접속은 핸드셰이크에서 거부. ② MARIADB_AUDIT_PLUGIN — 접속(실패 포함)/DDL/DCL 기록, CloudWatch /aws/rds/instance/gochuchamchi-db/audit로 export. ③ SG egress 전면 제거(DB는 아웃바운드를 시작할 일 없음). ④ storage_encrypted=true 명시. ⑤ IAM DB 인증은 MariaDB 미지원이라 제외(주석 기록)
redis.tf수정 aws_elasticache_cluster(암호화/AUTH 미지원) → aws_elasticache_replication_group 단일 노드 교체. 전송/저장 암호화 + AUTH 토큰. 1노드 유지라 비용 동일. SG egress 제거. 감사보고서 #14 잔여과제 이행
k8s-deploy.tf수정 ① ConfigMap: DB_USER=gochuchamchi_app, SPRING_DATASOURCE_URL=...?sslMode=trust(env가 application.yml보다 우선 — 앱 리빌드 불필요), Redis 엔드포인트를 primary_endpoint_address로, SPRING_DATA_REDIS_SSL_ENABLED=true. ② 마스터 비번을 읽던 data 소스 + K8s Secret gochuchamchi-db-secret 삭제 → state에서 마스터 비번 제거. ③ Redis AUTH용 gochuchamchi-redis-secret 추가(키 = SPRING_DATA_REDIS_PASSWORD)
iamRole.tf / eks-pod-identity.tf수정 rds!* 와일드카드("리전 내 모든 RDS 마스터 시크릿" 조회 가능) 2곳 제거 → 배스천: 마스터 1개(Get) + 앱 시크릿 1개(Get/Put/Describe), 앱 Pod Identity: 앱 시크릿 1개만. 배스천·앱이 털려도 폭발 반경이 시크릿 단위로 제한됨
rds-schema-init.tf수정 배스천 mysql [client]에 ssl 추가 — TLS 강제 후에도 스키마 초기화 동작
main.tf수정 random 프로바이더 추가(Redis AUTH 토큰) → terraform init 1회 필요
cloudwatch-managed-metrics.tf수정 Redis 알람 디멘션을 RG 멤버 클러스터 ID(gochuchamchi-redis-001)로 변경 — 참조 깨짐 방지

5. 적용 절차 (다음 apply 체크리스트)

미적용 주의: 위 변경은 코드·문서 완료 상태다. 아래 순서대로 실행해야 AWS에 반영된다. 특히 1번(gitops)을 apply보다 먼저 해야 파드가 새 Secret 이름을 찾는다.
순서작업
1gitops 저장소 03-deployment-web.yml — secret 이름 gochuchamchi-db-secret → gochuchamchi-db-app 교체(키 DB_PASS 동일) + gochuchamchi-redis-secret envFrom 한 줄 추가
2MTU 1492 적용(8/3 잔여 — 안 하면 Error locating chart 재발 가능): 관리자 PowerShell에서 netsh interface ipv4 set subinterface "이더넷" mtu=1492 store=persistent
3terraform init(random 프로바이더) → terraform validate → terraform plan
4plan 확인: destroy = elasticache_cluster, 구 K8s Secret · create = replication_group, random_password, app 시크릿, null_resource, redis 시크릿 · update = RDS(파라미터/옵션/로그), SG, ConfigMap, IAM 2건. 중단 조건 RDS가 replace로 뜨면 진행 금지(기존 인스턴스가 비암호화였다는 뜻 — 스냅샷 경유 전환 필요)
5terraform apply — 앱 파드가 잠깐 CreateContainerConfigError여도 정상 (프로비저너가 Secret을 만들면 kubelet이 자동 재시도)
6ConfigMap/Secret은 파드 시작 시 주입되므로 마지막에 kubectl -n gochuchamchi delete pod -l app=gochuchamchi-web (GitOps 드리프트 없는 재기동)

이미 떠 있는 인스턴스에 적용하는 경우: RDS 파라미터가 pending-reboot로 남으면 aws rds reboot-db-instance 1회(1~2분) · ElastiCache 교체 중 5~10분 세션 공백(재로그인) · admin 계정은 전환 기간에도 유효하므로 순서만 지키면 서비스 다운타임 없음.

6. 검증 방법 (apply 후)

# 1) TLS 강제 — 평문이 "거부"되면 성공
mysql -h <RDS엔드포인트> -u admin -p --skip-ssl -e "SELECT 1"    # -> ERROR (secure transport required)
mysql -h <RDS엔드포인트> -u admin -p --ssl -e "SHOW STATUS LIKE 'Ssl_cipher';"

# 2) 앱 계정 최소권한 — DML만 보이고, DROP은 거부돼야 함
mysql -h <RDS> -u gochuchamchi_app -p --ssl -e "SHOW GRANTS FOR CURRENT_USER;"
mysql -h <RDS> -u gochuchamchi_app -p --ssl -e "DROP TABLE gochuchamchi.users;"   # -> DENIED

# 3) 감사 로그 스트림 확인
aws logs describe-log-streams --log-group-name /aws/rds/instance/gochuchamchi-db/audit --region ap-northeast-2

# 4) Redis AUTH+TLS — 무인증이 거부되면 성공
redis6-cli -h <Redis> -p 6379 --tls ping             # -> NOAUTH Authentication required
redis6-cli -h <Redis> -p 6379 --tls -a '<토큰>' ping  # -> PONG

# 5) (로컬) 마스터 비번이 state에서 사라졌는지
terraform state pull | Select-String "password"

이번 세션에서 완료된 사전 검증: HCL 파서로 13개 파일 구문 통과 · 구(舊) 리소스 참조 0건 · 배스천 스크립트의 SQL/JSON 생성 로직 시뮬레이션(600 권한, 인용부호 안전성) 통과. terraform validate는 로컬에서 실행할 것.

7. 트레이드오프 · 설계 판단

채택한 것

  • 배스천 런타임 프로비저닝 — ESO 없이도 "비밀이 state에 없는" 목표를 지금 달성. 기존 rds-schema-init 패턴 재사용이라 학습 비용 최소
  • sslMode=trust (1단계) — 암호화 즉시 확보, 앱 리빌드 불필요. 인증서 검증(verify-full)은 CA 번들 배포가 필요해 2단계로
  • 감사 이벤트 CONNECT+DDL/DCL만 — 전체 쿼리 로깅은 비용·성능 부담. 접속 추적 + 구조 변경 감사가 우선
  • Redis 1노드 유지 — 보안(TLS+AUTH)과 가용성(다중화)을 분리, 비용 동일 유지

남긴 한계 (사유 문서화)

  • IAM DB 인증 미적용 — MariaDB 엔진 미지원. MySQL/PG였다면 15분 IAM 토큰 인증까지 가능
  • Redis auth_token은 state에 남음 — 리소스 인자라 불가피. S3 암호화+잠금 뒤라 등급은 낮고, ESO 도입 시 최우선 이관
  • 앱 비번 자동 로테이션 없음 — 운영 기준은 rotation Lambda/ESO. 현재는 taint 재실행으로 수동 로테이션 가능 구조까지만
  • 비용 증가 ≈ $0 — 감사 로그 CloudWatch 수집만 소액(트래픽 소량 기준 $1 미만)

8. 면접 핵심 스토리 (한 문단)

"DB 계층을 제로트러스트로 재구성했습니다. 앱은 마스터가 아니라 DML 전용 계정으로 접속하고, 그 계정은 REQUIRE SSL과 서버측 require_secure_transport로 TLS를 이중 강제했습니다. 자격증명은 배스천 런타임에서 생성해 Secrets Manager와 K8s Secret으로 직접 주입하므로 Terraform state에 비밀번호가 남지 않고 — 실제로 기존 구조에서 마스터 비밀번호가 state에 평문으로 들어가 있던 것을 발견해 제거했습니다. 접근 기록은 MariaDB 감사 플러그인을 CloudWatch로 내보내 확보했고, 세션 스토어(Redis)도 전송 암호화와 AUTH로 전환해 'VPC 내부라서 신뢰한다'는 가정을 데이터 계층 전체에서 제거했습니다. IAM DB 인증은 MariaDB 엔진 제약으로 제외했다는 것, 남은 state 내 시크릿(Redis 토큰)은 ESO 도입 시 이관한다는 것까지 한계와 다음 단계를 함께 관리하고 있습니다."
