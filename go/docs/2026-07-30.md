## 2. `terraform apply` 중 kubernetes/helm 리소스 전부 TCP 타임아웃

### 문제가 발생한 지점
`terraform apply` 도중 클러스터 API를 호출하는 리소스만 골라서 전부 실패:

```
Error: Post "https://<id>.gr7.ap-northeast-2.eks.amazonaws.com/apis/storage.k8s.io/v1/storageclasses":
  dial tcp 43.202.175.103:443: connectex: A connection attempt failed because the connected party
  did not properly respond after a period of time ...
Error: installation failed — Kubernetes cluster unreachable (helm_release.aws_load_balancer_controller)
Error: installation failed — Kubernetes cluster unreachable (helm_release.cluster_autoscaler)
Error: Post ".../api/v1/namespaces" (kubernetes_namespace_v1.gochuchamchi)
```

- 실패한 것: `kubernetes_*` / `helm_release.*` (= 클러스터 엔드포인트로 직접 붙는 프로바이더)
- **성공한 것**: `null_resource.apply_db_schema` (`Creation complete after 1m3s`) — SSM `send-command` 경유라 엔드포인트를 안 씀
- → **apply가 절반만 성공한 상태**로 끝남

### 문제 원인
`main.tf`의 `endpoint_public_access_cidrs`가 집 공인 IP `/32` **하나로 하드코딩**되어 있었고, 이날 다른 네트워크에서 apply를 실행했음.

| | 값 |
|---|---|
| 실행 시점 공인 IP (`curl checkip.amazonaws.com`) | `112.221.246.164` |
| 클러스터에 적용된 허용목록 (`aws eks describe-cluster`) | `116.122.154.177/32` |

허용목록 밖의 IP는 EKS가 패킷을 **블랙홀 처리**하므로, 인증 실패(`Unauthorized`)가 아니라 **TCP 타임아웃**으로 나타난다. 이 증상 차이가 원인 판별의 핵심 단서였음 — 자격증명/토큰 문제로 오해하기 쉬움.

### 해결 방법
1. `variables.tf`에 `endpoint_public_access_cidrs` 변수 신규 추가 (`list(string)`), 집 IP와 작업 네트워크 IP 둘 다 등재
2. `main.tf`의 하드코딩된 `["116.122.154.177/32"]` → `var.endpoint_public_access_cidrs`
3. `terraform validate` 통과 확인
4. 엔드포인트를 먼저 열어야 프로바이더가 붙으므로 **2단계로 apply**:
   ```powershell
   terraform apply -target=module.eks   # 허용목록만 갱신 (클러스터 UPDATING, 2~5분)
   terraform apply                       # 나머지 전체
   ```

### 남은 주의사항
- **유동 IP의 stale `/32`는 지울 것** — ISP가 그 IP를 타인에게 재할당하면 허용목록에 남은 항목이 그 사람에게 엔드포인트 접근을 열어주는 셈이 된다. 변수 주석에도 명시해둠
- 이 사고는 [배스천 유지 근거](#참고--배스천-관련)와 직접 연결됨 (아래)

### 검증 완료 사항
- 원인 확정 — 현재 IP(`curl checkip.amazonaws.com`) vs 클러스터 허용목록(`aws eks describe-cluster`) 실측 대조
- 코드 수정 후 `terraform validate` 통과
- **2단계 apply 성공** (`-target=module.eks` → 전체). 클러스터 허용목록에 두 IP 모두 반영 확인:
  ```
  aws eks describe-cluster --name gochuchamchi-eks \
    --query "cluster.{status:status,cidrs:resourcesVpcConfig.publicAccessCidrs}"
  → status: ACTIVE, cidrs: ["112.221.246.164/32", "116.122.154.177/32"]
  ```
- 앞서 실패했던 리소스 13개가 전부 state에 생성됨 (`terraform state list`):
  - `helm_release` 6개 — `argocd`, `argocd_image_updater`, `aws_load_balancer_controller`, `cluster_autoscaler`, `external_dns`, `gochuchamchi_application`
  - `kubernetes_*` 7개 — `namespace_v1`, `service_account_v1`, `config_map_v1`, `secret_v1`(db/gitops), `ingress_v1`, `storage_class_v1.efs`
- ALB 컨트롤러가 ALB 2개 생성 (앱용 external, ArgoCD용 internal)
- **Route 53 레코드가 신규 ALB와 일치함** — 7/29 §2의 TXT 소유권 조치가 유지되어 external-dns가 자동 갱신에 성공했음을 확인 (수동 개입 불필요했음):

  | 레코드 | ALIAS 대상 |
  |---|---|
  | `gochuchamchi.shop.` | `k8s-gochucha-gochucha-ca3220929d-...` (현재 external ALB) |
  | `www.gochuchamchi.shop.` | 동일 |
  | `argocd.gochuchamchi.shop.` | `internal-k8s-argocd-argocdse-...` (현재 internal ALB) |

### 남은 문제
- apply 자체는 성공했지만 `https://gochuchamchi.shop`이 **503** — 원인은 별개 이슈이므로 §3에 분리 기록

### 참고 — 배스천 관련
배스천 제거 가능 여부를 검토하던 중 이 사고가 발생했고, 결과적으로 배스천 유지 근거를 실증한 사례가 됐다.

현재 코드에서 배스천에 남은 의존성:
- **필수**: `rds-schema-init.tf:5` `null_resource.apply_db_schema` — RDS가 `publicly_accessible = false` + `database_subnets`에 있어 VPC 내부에서 mysql 클라이언트를 실행할 주체가 필요
- **부수적**: `rds.tf:23` RDS SG 인그레스, `iamRole.tf:37` Secrets Manager 읽기 권한, `main.tf:129` EKS access entry(cluster admin)
- **운영상 가치**: 엔드포인트가 `/32`로 묶여 있는 한, 허용목록 밖에서는 배스천이 SSM 경유로 붙을 수 있는 **유일한 경로** (이번 사고에서 실제로 배스천 경유 작업만 성공했음)

반면 배스천의 **원래 주 임무였던 배포 경로는 이미 사라진 상태**:
- `eks-pod-identity.tf:22` 주석 — "k8s 오브젝트를 배스천 없이 로컬에서 직접 적용하기 위한 프로바이더"
- k8s 오브젝트는 `kubernetes` 프로바이더, helm 릴리즈는 `helm` 프로바이더가 로컬에서 직접 처리
- 앱 배포는 ArgoCD GitOps로 이관
- 옛 `S3 → SSM → 배스천 kubectl apply` 파이프라인은 `k8s-deploy.tf`에서 제거됨

결론: 배스천은 "아키텍처상 필수"가 아니라 **월 10달러대의 값싼 보험**. 제거하려면 (1) 스키마 초기화를 K8s Job으로 전환(SSM/PowerShell 이스케이프 문제도 같이 해소 — 2026-07-29 §1.1 참고), (2) 엔드포인트를 단일 `/32`에 묶어두는 구조 정리가 선행돼야 한다.

## 3. apply 성공 후에도 사이트 503 — ECR이 destroy로 비워져 `ImagePullBackOff`

### 문제가 발생한 지점
- §2의 2단계 apply가 성공하고 리소스 13개가 모두 생성됐는데도 `https://gochuchamchi.shop`이 **HTTP 503 지속** (3회 연속, 시간이 지나도 그대로)

### 원인 확인 과정 (오진 → 정정)
1. **처음엔 일시적 현상으로 오판했음.** 타겟 상태가 `initial` / `Reason: Elb.RegistrationInProgress`로 보여서 7/29 §3.6의 롤아웃 중 502와 같은 성격이라고 판단
2. 잠시 후 재확인하니 타겟이 `healthy`인데도 **503이 그대로** → 일시적 현상이 아님을 확인
3. **오판의 원인: 타겟그룹을 잘못 짚었음.** `TargetGroups[0]`로 조회한 그룹이 앱이 아니라 **ArgoCD 것**이었음. 타겟그룹은 반드시 이름/소속 ALB를 함께 확인해야 함

   | 타겟그룹 | 소속 ALB | 타겟 수 |
   |---|---|---|
   | `k8s-argocd-argocdse-...` | ArgoCD (internal) | 1개 `healthy` |
   | `k8s-gochucha-gochucha-...` | 앱 (external, `gochuchamchi.shop`) | **0개** |

4. 앱 타겟그룹이 비어있는 이유를 파드에서 확인:
   ```
   kubectl -n gochuchamchi get pods
   gochuchamchi-web-6cc8968bf5-6n2vx   0/1   ImagePullBackOff
   gochuchamchi-web-6cc8968bf5-dzmqn   0/1   ImagePullBackOff
   → deployment 0/2 available, endpoints 비어있음 → ALB에 등록할 타겟 자체가 없음
   ```

### 문제 원인
파드가 참조하는 이미지가 ECR에 **존재하지 않음**:

```
참조 이미지 : 307223751140.dkr.ecr.ap-northeast-2.amazonaws.com/gochuchamchi:latest
ECR 생성시각: 2026-07-30T09:29:55  ← 오늘 apply로 새로 만들어짐
ECR 이미지  : []                    ← 비어 있음
```

`ecr.tf:17`의 **`force_delete = true`** 때문에 `terraform destroy`가 저장소를 **이미지째로** 삭제했고, apply가 빈 저장소를 다시 만들었다. GitOps 매니페스트는 여전히 ECR 이미지를 참조하므로 pull 실패.

**7/29에 이미 기록해둔 함정이 다른 리소스에서 재발한 것**:
- 기존 체크리스트: *"Terraform이 만든 S3 버킷은 '버킷'만 관리 대상이고 '내용물'은 아님"*
- ECR도 **동일** — Terraform은 저장소만 관리하고 이미지는 관리 대상이 아니다. 게다가 `force_delete = true`는 그 내용물을 destroy 때 **적극적으로 삭제**한다
- 7/29 §3.5에 적어둔 *"ECR이 비어있는 상태에서 gitops를 먼저 바꾸면 서비스가 죽음"*과 결과가 같지만 경로가 다름 — 그때는 마이그레이션 순서 문제였고, 이번은 **destroy/apply 사이클이 저장소를 비운 것**

### 해결 방법
`gochuchamchi-spring`의 GitHub Actions 워크플로(`Deploy to Amazon ECR`, `workflow_dispatch` 지원)를 수동 실행해서 ECR에 이미지를 다시 적재한다. 그러면 kubelet이 pull에 성공하고 ArgoCD/파드가 정상 기동한다.

```bash
gh workflow run "Deploy to Amazon ECR" --repo landoll9999/gochuchamchi-spring
gh run watch --repo landoll9999/gochuchamchi-spring
```

- OIDC push 역할(`gochuchamchi-github-actions-ecr-push`)은 apply로 재생성됐지만 **이름 기반 ARN이 동일**해서 워크플로 수정은 불필요

**이미지를 올린 뒤 파드가 자동 회복되지 않았음 — 막힌 파드는 지워야 함**
- 이미지 push 완료 후에도 파드가 계속 `ImagePullBackOff` 상태였음 (파드 생성 후 10분 경과)
- 원인: kubelet의 이미지 pull 재시도 백오프가 **최대 5분까지 늘어나** 있어서, 이미지가 생긴 직후에도 바로 재시도하지 않음
- 조치: 막힌 파드를 삭제해 즉시 재시도시킴. ReplicaSet이 바로 재생성하며, **deployment 스펙을 건드리지 않으므로 ArgoCD와 충돌하지 않음**
  ```bash
  kubectl -n gochuchamchi delete pod -l app=gochuchamchi-web
  kubectl -n gochuchamchi rollout status deploy/gochuchamchi-web --timeout=180s
  ```
- `rollout restart`도 되지만 template에 annotation을 추가하므로 GitOps 관리 리소스에는 **파드 삭제가 더 깔끔함**
- 교훈: "백오프라서 알아서 회복된다"는 말은 맞지만 **최대 5분을 기다려야 한다**. 복구 상황에서는 기다리지 말고 파드를 지울 것

### 재발 방지 (선택지)
- **destroy/apply를 반복하는 개발 단계**에서는 apply 후 워크플로 수동 실행을 절차에 포함시킨다
- **근본 해결**: 운영 전환 시 `ecr.tf`의 `force_delete = true`를 끄고 ECR을 별도 state 또는 `prevent_destroy`로 분리한다. 이미지는 인프라와 생애주기가 다르므로 같은 destroy에 묶이면 안 된다
- 참고: 이 판단은 S3 이미지 버킷에 대해 이미 체크리스트에 적어둔 것과 동일한 결론

### 검증 완료 사항
- 원인 확정 — ECR 이미지 목록 비어있음 + 파드 `ImagePullBackOff` + 저장소 생성 시각 대조
- **CI 워크플로 성공** (`workflow_dispatch`, run `30504364101`, `conclusion: success`, 약 2분)
- **ECR에 이미지 적재 확인** — `latest` + 커밋 SHA 태그 동시 부여:
  ```
  aws ecr describe-images --repository-name gochuchamchi
  → Tags: ["a45e6d791a007872996fd0f1c3b6d24c13939f2a", "latest"]
    Pushed: 2026-07-30T10:01:50+09:00, 약 117MB
  ```
- **파드 정상 기동** — 막힌 파드 삭제 후 `2/2 Running` (`rollout status` 정상 완료)
- **ALB 앱 타겟그룹에 타겟 2개 등록 + 전부 `healthy`** (이번에는 `TargetGroupName`으로 필터해서 앱 그룹임을 확인):
  ```
  k8s-gochucha-... : 172.30.40.130:8080 healthy / 172.30.61.234:8080 healthy
  ```
- **사이트 정상화** — `https://gochuchamchi.shop` **HTTP 200 × 5회 연속**, `https://www.gochuchamchi.shop` **HTTP 200**

### 근본 조치 (미이행 — 판단 필요)
`ecr.tf:17`의 `force_delete = true`는 **그대로 둠**. 지금은 destroy/apply를 반복하는 개발 단계라 끄면 destroy가 이미지 때문에 막히므로 켜두는 게 편하다. 운영 전환 시 껐다가 ECR을 별도 state 또는 `prevent_destroy`로 분리할 것.

그때까지의 운영 절차: **destroy/apply 사이클 후에는 `aws ecr list-images`로 비어있는지 확인하고, 비었으면 CI 워크플로를 수동 실행**한다.

## 4. ArgoCD 접속 불가 — internal ALB 전환의 결과(정상) + port-forward 프로토콜 함정

### 작업 목적
- 재구축 후 `https://argocd.gochuchamchi.shop` 접속이 안 되는 원인 확인 및 접속 경로 확립

### 증상
- 브라우저에서 `argocd.gochuchamchi.shop` 접속 시 `ERR_CONNECTION_TIMED_OUT`
- "도메인이 바뀐 것 아닌가" 의심했으나 **도메인·레코드 모두 정상**이었음

### 원인 (설정 의도대로 동작한 것 — 장애 아님)
7/29 보안 조치(`SECURITY_AUDIT_REPORT.md` #7)로 ArgoCD ALB를 **internal로 전환**해 인터넷 노출을 없앤 상태.

```
argocd.gochuchamchi.shop → 172.30.41.21, 172.30.60.112   ← VPC 사설 IP
ALB scheme               → internal      (앱 ALB만 internet-facing)
argocd.tf:44             → alb.ingress.kubernetes.io/scheme = "internal"
```

사설 IP는 인터넷에서 도달 불가 → 브라우저가 타임아웃. ArgoCD는 클러스터 admin 권한 + GitOps write-back PAT를 가진 최고 가치 타겟이라 의도적으로 닫아둔 것이며, **되돌리면 안 된다.**

배스천에서 ALB까지의 경로는 정상임을 SSM으로 실측 확인:
```
DNS      : 172.30.41.21 / 172.30.60.112 정상 해석
HTTPS 443: http_code=404  connect=0.0023s   ← 2ms 연결 성공
```
(404는 `Host` 헤더가 없어 ALB 기본 동작으로 떨어진 것. 인그레스가 호스트 기반 라우팅이므로 정상)

### 4.1 `kubectl port-forward`가 `connection reset by peer`로 끊김

- **증상**:
  ```
  kubectl port-forward -n argocd svc/argocd-server 8080:443
  Forwarding from 127.0.0.1:8080 -> 8080
  Handling connection for 8080
  E... an error occurred forwarding 8080 -> 8080: ... read: connection reset by peer
  error: lost connection to pod
  ```
- **원인**: **ALB가 TLS를 종료하는 구성이라 ArgoCD 서버는 평문으로 뜬다.** 여기에 `https://`로 붙어서 평문 리스너에 TLS 핸드셰이크를 보냈고, 서버가 연결을 리셋함
  ```
  argocd-cmd-params-cm : server.insecure = "true"
  argocd-server 컨테이너: ["argocd-server","--port=8080","--metrics-port=8083"]   ← 평문 8080
  svc/argocd-server    : http 80→8080, https 443→8080   (둘 다 같은 평문 타겟)
  ```
  → 서비스 포트 `443`은 **ALB가 TLS를 벗겨서 넘겨줄 때 쓰는 입구**일 뿐, 파드가 TLS를 처리하는 게 아님
- **해결**: 서비스 포트 `80`으로 붙고 **`http`** 로 접속
  ```powershell
  kubectl port-forward -n argocd svc/argocd-server 8080:80
  # → http://localhost:8080   (https 아님)
  ```
- 실측 검증: `http_code=200` + `<title>Argo CD</title>` 로그인 페이지 정상 응답 확인

### 4.2 에러 코드로 원인을 즉시 가르는 표 (재사용 가치 높음)

세 가지 실패가 전부 "접속 안 됨"으로 보이지만 원인이 완전히 다르다.

| 브라우저 에러 | 의미 | 조치 |
|---|---|---|
| `ERR_CONNECTION_TIMED_OUT` | 패킷이 어디에도 안 닿음 = **사설 IP로 직접 접속** | 터널을 먼저 띄울 것 |
| `ERR_SSL_PROTOCOL_ERROR` / `connection reset` | 평문 리스너에 TLS 시도 | `https` → `http` |
| `ERR_CONNECTION_REFUSED` | **로컬에 리스너가 없음** = port-forward가 죽었거나 안 띄움 | port-forward 재실행 후 창을 열어둘 것 |

- 실제로 이번에 세 가지를 순서대로 다 겪었음: 도메인 직접 접속(TIMED_OUT) → `https`로 port-forward(reset) → 죽은 터널에 재접속(REFUSED)
- `netstat -ano | findstr :8080`으로 LISTENING 여부를 보면 REFUSED 여부가 바로 판별됨
- **port-forward는 실행 중인 창을 닫으면 즉시 죽는다** — 별도 창에 띄워두고 브라우저는 다른 창에서 열 것

### 4.3 배스천 접속 (SSM)
배스천이 오늘 재생성되어 **인스턴스 ID가 바뀜** (`i-0094d7f58cf6b6b50`, 공인 IP `3.36.78.108`).

```powershell
aws ssm start-session --target i-0094d7f58cf6b6b50 --region ap-northeast-2 --profile admin
```
- 공인 IP로 직접 SSH는 불가 — SG 인바운드가 0개(`securitygroups.tf:59`)이며 모든 접속이 SSM 경유
- 접속 후 반드시 `sudo su - ec2-user` (7/29 §1.8 — SSM 기본 사용자는 `ssm-user`이고 `/home/ec2-user`가 700이라 kubectl 접근 불가)
- VS Code Remote-SSH를 쓰면 `~/.ssh/config`의 `HostName`을 새 인스턴스 ID로 갱신해야 함 (재생성마다 반복되는 작업)

### 4.4 재구축으로 되돌아간 보안 조치 — admin 비밀번호
- 7/29 #7의 "즉시 조치"였던 **ArgoCD admin 비밀번호 변경이 초기화됨**
  ```
  argocd-initial-admin-secret  생성: 2026-07-30T00:50:50Z   ← 오늘 apply로 재생성, 여전히 존재
  admin.passwordMtime          2026-07-30T00:50:49Z         ← 설치 시각 그대로 = 변경 이력 없음
  ```
- **원인**: `internal` ALB 전환은 `argocd.tf` 코드에 있어 재구축에도 유지됐지만, **비밀번호 변경은 클러스터 안에서 수동으로 한 작업이라 Terraform state에 없어 사라졌다**
- 위험도 자체는 낮음(초기 비밀번호는 랜덤 생성값 + ALB가 internal) 이지만 조치 항목으로는 미이행 상태로 되돌아간 것
- **일반화된 교훈**: 코드에 없는 수동 보안 조치는 destroy/apply마다 사라진다. 조치는 코드에 넣거나, 못 넣으면 재구축 절차서에 명시해야 한다
- 조치 방법 (미실행 — 계정 자격증명 변경이라 사용자 판단 영역):
  ```powershell
  # 로그인용 초기 비밀번호 확인
  kubectl -n argocd get secret argocd-initial-admin-secret -o jsonpath='{.data.password}' | base64 -d
  # 변경 후 초기 시크릿 삭제
  kubectl -n argocd delete secret argocd-initial-admin-secret
  ```

### 검증 완료 사항
- ArgoCD ALB `scheme: internal` 및 도메인이 사설 IP로 해석되는 것 확인 (`describe-load-balancers`, `nslookup`)
- 배스천 → internal ALB 443 연결 성공 (SSM `send-command`로 실측, connect 2ms)
- `kubectl port-forward ... 8080:80` + `http://` 로 **ArgoCD 로그인 페이지 HTTP 200 응답 확인**
- 사용자 브라우저에서 실제 접속 성공
- 부수 확인: IAM 사용자 `admin`은 소속 그룹 없음 → 7/29 §4.2의 `DenySensitiveServices` explicit deny 재발 아님. session-manager-plugin 1.2.835.0 설치됨

## 5. 회원 계정을 관리자로 승격 (`users.role`)

### 작업 목적
- 재구축 후 가입한 계정(`dnjstjr504`)의 등급을 관리자로 변경

### 확인한 것
- `users` 테이블에 `role varchar(20) DEFAULT 'user'` 컬럼이 존재 (`k8s/gochuchamchi/schema.sql:23`)
- RDS는 `publicly_accessible = false`라 **배스천 경유 접속만 가능**
  → 접속 절차는 `architecture.md` §6 "RDS(MariaDB) 접속 — 배스천 경유"에 정리(재사용용)

### 실행한 SQL
```sql
UPDATE users SET role='admin' WHERE username='dnjstjr504';
SELECT id, username, role FROM users WHERE username='dnjstjr504';
```

### 주의사항
- **role 문자열이 앱 기대값과 일치해야 한다** — 스키마 기본값이 소문자 `'user'`이므로 `'admin'`이 맞을 가능성이 높지만, `'ADMIN'`/`'ROLE_ADMIN'`을 기대하는 구현이라면 값이 조용히 안 먹는다. 관리자 기능이 안 보이면 `gochuchamchi-spring`의 role 비교 코드를 확인할 것
- **role은 보통 로그인 시점에 세션에 담긴다** → 변경 후 **로그아웃 → 재로그인** 필요
- `users.role`은 애플리케이션 데이터이므로 **Terraform 관리 밖**이다. `schema.sql`은 `IF NOT EXISTS`로 테이블만 만들고 데이터는 건드리지 않으므로, **destroy/apply로 RDS가 재생성되면 이 변경도 사라진다** (§3의 ECR, §4.4의 ArgoCD 비밀번호와 같은 성격 — 코드 밖의 상태는 재구축에서 살아남지 못함)

### 검증 상태
- 스키마에 `role` 컬럼 존재 및 접속 경로 확인: **완료**
- UPDATE 실행 결과 및 앱에서 관리자 기능 노출 확인: **미확인** (사용자가 mysql 세션에서 직접 실행)

## 7. 단일 apply 불가 — `data.aws_lb`와 IngressGroup의 순환

### 문제가 발생한 지점
전체 `terraform plan`이 시작하자마자 실패:

```
Error: Search returned 0 results, please revise so only one is returned
  with data.aws_lb.gochuchamchi_web,
  on cloudwatch-managed-metrics.tf line 15
```

### 문제 원인
- `cloudwatch-managed-metrics.tf`가 태그 `ingress.k8s.aws/stack = gochuchamchi-web`으로 ALB를 조회
- 당시 운영 ALB의 실제 태그는 `gochuchamchi/gochuchamchi-web-ingress` (암묵 그룹)
- **새 태그를 붙이는 건 apply인데 그 태그를 찾는 건 plan** → 순환
- `aws_lb` 데이터 소스는 0건이면 에러를 낸다(빈 결과가 아니라 실패)

### 해결 방법 — 2단계 apply

```powershell
# 1단계: Ingress만 (CloudWatch 데이터 소스가 그래프에서 빠짐)
terraform apply '-target=kubernetes_ingress_v1.gochuchamchi_web'

# 2단계: 새 ALB 태그 1건 확인 후
terraform apply
```

### PowerShell 인자 함정

```
terraform apply -target=kubernetes_ingress_v1.gochuchamchi_web
→ Error: Invalid target "kubernetes_ingress_v1"
```

**PowerShell 5.1은 따옴표 없는 `-target=a.b`를 `.` 앞에서 잘라버린다.**
Bash에서는 정상 동작해서 검증 시 놓치기 쉽다.

되는 형태:
- `terraform apply '-target=kubernetes_ingress_v1.gochuchamchi_web'`
- `terraform apply -target "kubernetes_ingress_v1.gochuchamchi_web"`

같은 이유로 `--dimensions "Name=DeliveryStreamName,Value=..."` 도 반드시 큰따옴표로 감쌀 것.

## 8. IngressGroup 전환 시 옛 ALB 스택이 자동 정리되지 않음

### 문제가 발생한 지점
1단계 apply 후 서비스는 정상(200)인데 **internet-facing ALB가 2개**가 됨.
컨트롤러 로그에 새 스택 생성 기록만 있고 **옛 스택 삭제 기록이 없음**.

### 문제 원인
Ingress finalizer가 바뀌면서 컨트롤러가 옛 스택 삭제 이벤트를 받지 못함:

```
ingress.k8s.aws/resources                   (암묵 그룹)
  → group.ingress.k8s.aws/gochuchamchi-web  (명시 그룹)
```

2026-07-29 §13.2의 고아 ALB와 같은 계열이지만 **원인이 다르다** — 그쪽은 NAT 소실로
컨트롤러가 AWS API를 못 부른 것이고, 이번은 컨트롤러가 멀쩡한데 이벤트 자체가 안 온 것.

### 해결 방법 — 수동 삭제 (순서 중요)

```powershell
# 삭제 전 안전 확인: 이 ALB를 가리키는 Route53 레코드가 없어야 함
aws route53 list-resource-record-sets --profile admin --hosted-zone-id Z09871632JXCAV3R6Z65M `
  --query "ResourceRecordSets[?AliasTarget.DNSName=='<옛ALB DNS>.'].[Name]" --output text

aws elbv2 delete-load-balancer  --profile admin --region ap-northeast-2 --load-balancer-arn <옛ALB ARN>
aws elbv2 delete-target-group   --profile admin --region ap-northeast-2 --target-group-arn <옛TG ARN>
aws ec2   delete-security-group --profile admin --region ap-northeast-2 --group-id <옛 관리SG>
```

**주의: 보안그룹 2개 중 하나만 지울 것.**
- `k8s-gochucha-gochucha-...` (Managed SecurityGroup for LoadBalancer) → 삭제 대상
- `k8s-traffic-gochuchamchieks-...` (Shared Backend SecurityGroup) → **새 ALB도 사용, 삭제 금지**

### 잔여 자원 일괄 확인

```powershell
aws resourcegroupstaggingapi get-resources --profile admin --region ap-northeast-2 `
  --tag-filters "Key=ingress.k8s.aws/stack,Values=gochuchamchi/gochuchamchi-web-ingress" `
  --query "ResourceTagMappingList[].ResourceARN" --output text
```

비면 정리 완료.

### 검증 완료 사항
- 옛 ALB/타겟그룹/관리SG 삭제 완료, 잔여 태그 자원 **0건**
- ALB 2개 유지(웹 + ArgoCD internal) — Grafana가 새 ALB를 만들지 않고 웹 ALB에 합류
- `gochuchamchi-web` 스택 타겟그룹 2개(웹 + Grafana), 각각 healthy

## 9. ACM 인증서 deposed 객체 — `destroy 5` 예상이 `4`로 나온 이유

### 증상
1단계 plan은 `5 to destroy`였는데 apply 결과는 `4 destroyed`.

### 원인
`create_before_destroy` 인증서에서 신규 생성 후 **옛 인증서 삭제가 완료되지 않아
deposed 상태로 state에 남았다.** 다음 plan에 이렇게 나타난다:

```
# aws_acm_certificate.this (deposed object 626c3bae) will be destroyed
# (left over from a partially-failed replacement of this instance)
```

옛 인증서를 **ArgoCD ALB가 아직 사용 중**이었기 때문이다. 1단계는 `-target`으로 Ingress만
잡아서 `helm_release.argocd`가 갱신되지 않았고, ArgoCD 리스너는 옛 인증서를 물고 있었다.
이 상태에서 수동 `acm delete-certificate`를 시도하면:

```
ResourceInUseException: Certificate ... is in use.
```

### 해결
전체 apply에서 `helm_release.argocd`가 새 인증서 ARN으로 갱신되면 자동으로 풀린다.
Terraform이 **의존 리소스 갱신 → deposed 삭제** 순서를 지키므로 별도 조치 불필요했다.

### 교훈
`-target`으로 부분 apply하면 그 리소스를 참조하는 다른 리소스는 옛 값을 유지한다.
인증서처럼 "사용 중이면 삭제 불가"인 자원은 이 때문에 deposed로 남을 수 있다.
**수동으로 지우지 말고 전체 apply를 기다릴 것** (Terraform이 아직 추적 중이므로).

## 10. Grafana IAM Role 생성 실패 — description에 한글

### 문제가 발생한 지점

```
Error: creating IAM Role (gochuchamchi-eks-grafana-cloudwatch):
  ValidationError: Value at 'description' failed to satisfy constraint:
  Member must satisfy regular expression pattern: [\u0009\u000A\u000D\u0020-\u007E\u00A1-\u00FF]*
```

### 문제 원인
**IAM `description`은 ASCII + Latin-1만 허용한다.** 한글(U+AC00~)은 범위 밖.

**IAM만 예외**라는 점을 기억할 것.

### 해결 방법
`module/grafana/main.tf`의 `aws_iam_role.grafana` description을 영문으로 변경.

### 사전 점검 방법
새 IAM 리소스를 추가할 때:

```bash
grep -rn --include=*.tf -A5 'resource "aws_iam_role"' . | grep -P 'description.*[^\x00-\xFF]'
```

## 11. Kinesis 계열이 계정 단위로 차단 — `SubscriptionRequiredException`

### 문제가 발생한 지점

```
Error: creating Kinesis Firehose Delivery Stream (gochuchamchi-application-log-archive):
  SubscriptionRequiredException: The AWS Access Key Id needs a subscription for the service
```

### 진단 — IAM 문제가 아님을 가르는 법
Terraform 없이 단순 조회로도 재현되면 계정/서비스 문제다:

```powershell
aws firehose list-delivery-streams --profile admin --region ap-northeast-2
```

범위를 좁히는 3가지 축:

| 축 | 결과 | 의미 |
|---|---|---|
| 리전 (ap-northeast-2 / us-east-1 / ap-northeast-1) | 전부 실패 | 리전 문제 아님 → 계정 단위 |
| 같은 계열 (`aws kinesis list-streams`) | 동일 실패 | Firehose만의 문제 아님 → Kinesis 계열 전체 |
| 인접 서비스 (SNS/SQS/Lambda/Glue) | 전부 정상 | 계정 가입 자체는 정상 |

→ **Kinesis 서비스 계열만 미구독** 상태로 확정.

### 오진했던 것 (기록용)
LB 컨트롤러 로그의 AWS Shield `SubscriptionRequiredException`을 같은 원인으로 묶었으나 **오판**.
Shield Advanced는 유료 구독이라 **모든 정상 계정에서 나오는 정상 메시지**다. 무관한 증상이었다.
`SubscriptionRequiredException`을 보면 **그 서비스가 원래 구독제인지부터** 확인할 것.

### 해결 방법
계정을 유료 플랜으로 업그레이드 → 즉시 해소.

```powershell
aws firehose list-delivery-streams --profile admin --region ap-northeast-2
# {"DeliveryStreamNames": [], ...}  ← 정상 응답
```

이후 `terraform apply` 한 번으로 나머지 5개 리소스(스트림 2, 구독 필터 2, IAM 정책 1) 생성 완료.

### 참고 — 막혔을 때의 대안 (미사용)
`aws logs create-export-task`는 이 계정에서 동작했으므로, Kinesis를 못 쓰는 상황이면
EventBridge Scheduler + Lambda로 CloudWatch Logs → S3 배치 내보내기가 가능하다.
S3 버킷/수명주기/Athena는 그대로 재사용되고 **넣는 경로만 바뀐다**(실시간 → 일 배치).

## 14. AWS Config / Security Hub 모듈 연결 및 적용

### 작업 목적
- 다른 PC에서 틀만 만들어 온 `aws-config` / `security-hub` 모듈을 기존 인프라의 실제 값과 연결하고 적용
- CloudTrail(누가 무엇을 했나)에 더해 Config(리소스가 어떤 상태인가) + Security Hub(보안 표준 평가)로 감사 체계를 완성

### 변경 내용

**모듈 위치 이동** — 프로젝트 관례(`terraform/module/<name>`, grafana·cloudwatch-managed-metrics와 동일)에 맞춤

| 이동 전 | 이동 후 |
|---|---|
| `aws-config/` (리포 루트) | `terraform/module/aws-config/` |
| `security-hub/` (리포 루트) | `terraform/module/security-hub/` |

- 모듈 README의 예시 `source = "./aws-config"`는 실제 경로 `./module/aws-config`로 갱신
- 딸려온 `security-hub/.terraform/` 프로바이더 캐시 859MB 삭제. 다른 PC에서 모듈 폴더 자체를 `terraform init`한 흔적이며, 자식 모듈에는 불필요

**신규 파일**
- `terraform/aws-config.tf` — CloudTrail과 **같은 중앙 로그 버킷** 재사용, prefix만 `config/`로 분리
  - `s3_bucket_name` / `s3_bucket_arn` → `aws_s3_bucket.cloudwatch_log_archive`
  - `tags` → `local.cloudwatch_log_archive_tags`
  - `depends_on` → 버킷 정책 / 암호화 / 버저닝 (cloudtrail.tf와 동일한 이유)
- `terraform/security-hub.tf` — `depends_on = [module.aws_config]`

**루트 변수 추가** (`terraform/variables.tf`)
- `aws_config_snapshot_delivery_frequency` — 기본 `Six_Hours`
- `security_hub_enable_cis_benchmark_v3` — 기본 `false` (FSBP만 활성)

### 문제가 발생한 지점 — 전체 apply를 하면 안 되는 이유

`terraform plan` 첫 시도가 변수 누락으로 실패:

```
Error: No value for required variable
  on variables.tf line 81:
  81: variable "argocd_git_pat" {
```

`argocd_git_pat`은 `TF_VAR_argocd_git_pat` 환경변수로 주입하는 시크릿이라 세션에 없었다.

**여기서 더미 값을 넣고 전체 apply를 하면 안 된다.** 이 변수는 `argocd.tf:84`의
Argo CD git 자격증명 Secret(`password`)에 그대로 들어가므로, 더미 값으로 apply하면
Argo CD의 GitOps 저장소 접근이 끊긴다.

### 해결 방법 — 타겟 apply로 범위 격리

```bash
# 1) 계획을 파일로 저장 (더미 PAT는 타겟 범위 밖이라 사용되지 않음)
TF_VAR_argocd_git_pat="unused-placeholder-not-in-target-scope" \
terraform plan -input=false -out=tfplan-secops.bin \
  -target=module.aws_config -target=module.security_hub

# 2) 저장된 계획 그대로 적용 (변수 재입력 불필요)
terraform apply -input=false tfplan-secops.bin
```

- `-target` 범위에 Argo CD Secret이 포함되지 않음을 **plan 출력으로 먼저 확인**한 뒤 적용
- `-out`으로 계획을 고정해 plan과 apply 사이의 차이를 제거
- 적용 후 `tfplan-secops.bin` 삭제. 변수 값이 들어있는데 `.gitignore`에 `tfplan*` 항목이 없다

결과: **8 added, 0 changed, 0 destroyed** — 기존 리소스 무변경

자동 생성한 **서비스 연결 규칙**이다.

- 우리 `aws-config` 모듈은 Config 규칙을 하나도 만들지 않는다 (Security Hub와 중복 방지)
- **Terraform으로 import·삭제 금지.** 소유권이 Security Hub에 있어 지워도 다시 생성된다
- 335개 중 상당수는 Neptune·FSx·SageMaker·Beanstalk 등 **안 쓰는 서비스** 규칙이라 평가 대상이 없다

**Config / CloudTrail 역할 구분** (헷갈리기 쉬움)

| | CloudTrail | AWS Config |
|---|---|---|
| 기록 | 누가 · 언제 · 무엇을 했나 (API 호출) | 리소스가 지금 어떤 상태인가 + 변경 이력 |
| 질문 | 누가 그랬어? | 지금 뭐가 잘못돼 있어? |

접속·조작 주체 추적은 **CloudTrail**이다. 실무 흐름은
Security Hub Finding으로 *"보안그룹 22번 열림"* 확인 → Athena `03-write-events`로
*"누가 언제 열었나"* 추적. Config 변경 이력에는 원인이 된 CloudTrail 이벤트 ID(`relatedEvents`)가 붙는다.

### 남은 주의사항

- **전체 plan 미확인.** 타겟 apply라 다른 리소스의 미적용 drift는 확인되지 않았다.
  `TF_VAR_argocd_git_pat`를 넣고 전체 `terraform plan`을 한 번 돌려볼 것.
  이번에 만든 8개는 state에 있으므로 no-op으로 나온다.
- **비용** — Config 요금의 주 발생원은 규칙 평가다. 규칙 335개 × 리소스 수로 평가가 돌고,
  프리티어는 월 2,000건 평가라 이 규모면 금방 초과한다.
  프로젝트 종료 시 `terraform/security-hub.tf`의 module 블록을 제거하고 apply하면 규칙 335개도 함께 정리된다.
- Security Hub 보안 점수·Finding은 Config 기록이 쌓여야 나온다. **활성화 후 2~12시간** 소요.
  직후에 콘솔이 비어 보이는 것은 정상이다.
- S3 수명주기(30일 `STANDARD_IA` → 90일 `GLACIER` → 365일 만료)는 `config/` prefix에도 동일 적용된다.
