## §1. DB 전면 500 — "반쪽 배포" (apply는 성공, 사이트는 고장)

**증상**: 정적 페이지 정상, DB를 타는 요청은 전부 HTTP 500 (`/api/health` 500).
새 파드는 `CreateContainerConfigError`, 기존 파드가 고장난 채 계속 서빙.

**근본 원인**: 제로트러스트 전환은 terraform apply와 gitops 수정이 **한 세트**인
작업인데 gitops 쪽이 누락된 채 apply만 실행됨. 그 결과 이중 잠김:

- 기존 파드 → 옛 설정(admin+평문)인데 DB가 `require_secure_transport=1`로 평문 거부 → 500
- 새 파드 → 삭제된 `gochuchamchi-db-secret` 참조 → 시작 불가

**해결**: gitops secret 이름 교체(`gochuchamchi-db-app`) + redis secret 추가 +
연쇄 발견된 4건(kubectl KUBECONFIG, helm 주석 `{{ }}`, PAT 주입, NetworkPolicy
DNS) 동시 수정 — 개별 상세는 `2026-08-04.md` §4.1~4.5.

**검증**: `/api/health` 500 → 302(로그인 리다이렉트), 메인 200.

**교훈**: 문서의 "apply 전 체크리스트"는 강제 장치가 아니다. **terraform 변경과
gitops 변경이 결합된 작업은 한 PR/한 사람이 원자적으로** 처리할 것. 부분 원인만
고치면 다음 원인이 이어서 드러난다(500의 원인이 secret → DNS 차단으로 5겹) —
"고쳤는데 그대로"면 같은 증상의 **다른 원인**을 의심할 것.

## §2. 진단 환경 제약 — 컴퓨터별 계정/자격증명 분리

**증상**: 이 컴퓨터에서 인프라 조회·수정 불가 (`admin` 프로파일 없음).

**원인**: 인프라·tfstate는 계정 307223751140(`admin` 프로파일, 옆컴퓨터에만 있음),
이 컴퓨터의 유효 프로파일 `terra-user`는 **다른 계정**(828885965304) 소속.
gitops 저장소도 비공개라 접근 불가.

**대응**: 코드·문서 기반 추론 + 외부에서 검증 가능한 신호 활용 —
`curl`(HTTP 상태), `Resolve-DnsName`(CloudFront 경유 여부), git 이력.
실행이 필요한 조치는 전부 "옆컴퓨터에서 실행할 명령" 형태로 산출.

**교훈**: 권한 없는 환경에서도 장애 진단은 가능하다. 단, 결론에 "확인한 것"과
"추정인 것"을 구분해 표기할 것.

## §3. full-HA 13개 파일 소실 — 폴더 복사 버전 관리의 대가

**증상**: CloudFront/WAF가 계정에서 사라짐. 코드에도 없음.

**원인 타임라인**:

1. ~8/3 오전: `fin` 라인에 full-HA 보안 강화 13개 파일 존재
   (edge/kms/nacl/vpc-endpoints/flow-logs/iam-security/dr/cost-monitoring/
   kyverno/resource-limits/sns-alerts/network-policies/github-oidc)
2. 8/4 10:53: git 저장소 "first commit"이 **13개 파일이 없는 구버전 베이스**로 생성
3. 그 코드로 같은 tfstate에 apply → state에 있던 해당 리소스들 삭제

7/31에도 같은 유형 사고("11개 수정 흔적 복원 불가")가 있었음 — git 없이
`fin`/`찐막`/`go(final)` 폴더 복사로 버전 관리한 구조적 결과.

**해결**: `fin` 사본에서 복원 + 8/4 제로트러스트와 3-way 병합. 원칙:

- **8/4 코드 우선** — key_name(B2 제거), argocd_git_pat(B3 ESO), 배스천
  ClusterAdmin(네임스페이스 Edit로 축소됨), DB 마스터 접속, 구 elasticache는 복원 안 함
- **대체된 것 제외** — network-policies(→k8s-network-policies), sns-alerts(→SNS 허브)
- **fin 자체 버그 제외** — github-oidc.tf는 ecr.tf의 OIDC와 리소스 중복
  (같은 URL의 OIDC provider는 계정당 1개)
- `terraform validate` 통과 확인

**후속 이슈**: 복원 커밋 이후 `waf-cdn.tf`(611줄, edge.tf와 역할 중복)가 추가로
커밋됐다가 origin `753f4f5`에서 삭제되고 `edge-logs.tf`(WAF/CloudFront 로그)로
재구성됨. → **apply 전 반드시 pull** (중복 CloudFront/WAF 생성 방지).

**교훈**: 저장소를 뒤늦게 만들 때 "어느 폴더가 최신인가"를 파일 몇 개의
존재/수정시각으로 판단하지 말 것 — 라인이 여러 갈래면 **전 파일 diff로 각
라인의 고유 변경을 식별**한 뒤 병합해야 한다. 그리고 tfstate를 공유하는 코드가
두 벌 존재하는 순간, 뒤처진 쪽의 apply는 곧 **삭제 명령**이 된다.

## §4. 병합 시 파괴적 변경 식별 — plan에 replace가 뜨면 중단

**리스크**: fin의 일부 변경은 기존 리소스 위에 그대로 적용하면 **재생성(데이터
소실)** 을 유발. 복원 때 다음을 의도적으로 보류함:

| 항목 | 적용 시 결과 | 처리 |
|---|---|---|
| RDS `kms_key_id`(CMK 전환) | 인스턴스 교체 → DB 데이터 소실 | 보류 (fin 스스로 경고했던 항목) |
| EFS `kms_key_id` | 파일시스템 교체 → 파일 소실 | 보류, efs.tf에 주석으로 위치 표시 |
| 로그 버킷 `object_lock_enabled` | 버킷 교체 (생성 시점에만 설정 가능) | 보류, 대신 DenyObjectDeletion/DenyPolicyTampering 버킷 정책으로 차선 방어 |

**검사법**: apply 전 plan에서 `must be replaced` 항목을 반드시 훑을 것.
RDS·EFS·로그 버킷에 replace가 보이면 보류 항목이 새어 들어간 것 → 중단.

**교훈**: "보안 강화 설정"이라도 기존 스택에는 파괴적일 수 있다. 재생성 유발
속성(암호화 키, object lock, 서브넷 등)은 **재구축 사이클에 모아서** 반영한다.

## §5. Cost Anomaly Monitor 생성 거부 — AWS 기본 리소스와의 충돌

**증상**: `aws_ce_anomaly_monitor` 생성이
`Limit exceeded on dimensional spend monitor creation` (400)으로 실패.

**원인**: Cost Explorer를 처음 활성화하는 순간 AWS가 `Default-Services-Monitor`
(DIMENSIONAL/SERVICE)를 **자동 생성**해 두는데, 이 타입은 **계정당 1개 한도**.
우리 코드(복원된 `cost-monitoring.tf`)가 두 번째를 만들려다 거부됨.

**해결**: 새로 만들지 않고 기존 것을 import 후 이름만 in-place 변경:

```powershell
aws ce get-anomaly-monitors --profile admin --region us-east-1 `
  --query "AnomalyMonitors[?MonitorType=='DIMENSIONAL'].MonitorArn" --output text
terraform import aws_ce_anomaly_monitor.services "<ARN>"
# plan: name이 ForceNew가 아니라 update in-place로 처리됨 (재생성 없음)
```

**교훈**: "계정당 N개" 한도가 있는 리소스는 **AWS가 선점해뒀을 가능성**을 먼저
확인(list API)할 것. 콘솔을 한 번 연 것만으로 생기는 리소스들이 있다.

## §6. Inspector2 활성화 타임아웃 — 성공했는데 실패로 기록됨

**증상**: `aws_inspector2_enabler` create가 5분 타임아웃으로 실패. 재시도해도 반복.

**원인**: EC2+ECR 동시 활성화는 계정 최초 1회에 5분(프로바이더 기본 타임아웃)을
넘기는 일이 잦다. **AWS 쪽 활성화는 백그라운드로 계속 진행돼 결국 ENABLED가
됐지만**, state에는 tainted로 남아 다음 apply가 destroy(=Inspector 비활성화)→
재생성을 돌려 같은 타임아웃을 반복하는 루프.

**해결**:

```powershell
aws inspector2 batch-get-account-status --profile admin   # ec2/ecr ENABLED 확인
terraform untaint aws_inspector2_enabler.this             # destroy 루프 차단
```

+ `ecr.tf`에 `timeouts { create = "15m" }` 추가 (재구축 대비).

**교훈**: 타임아웃 실패는 "실제 실패"와 "관측 실패"를 구분해야 한다. **실제 AWS
상태를 조회**해서 성공해 있으면 untaint가 정답 — 그냥 재apply하면 tainted 리소스는
destroy부터 돌아서 멀쩡한 것을 부순다. (8/3 "실패를 삼키는 프로비저너"의 정반대
사례: 그때는 실패가 성공으로, 이번엔 성공이 실패로 기록됨. 양쪽 다 "terraform의
기록과 실제 상태는 다를 수 있다"는 같은 교훈)

## §7. git 위생 — 커밋되면 안 되는 것들이 커밋됨

**발견된 문제들**:

1. **`.gitignore`에 stash 충돌 마커가 해결 안 된 채 커밋됨**
   (`<<<<<<< Updated upstream` / `=======` / `>>>>>>> Stashed changes`).
   충돌 마커 줄은 무의미한 패턴으로 취급돼 양쪽 규칙이 우연히 다 동작하지만,
   반드시 정리 필요 — upstream 쪽 개선(`.claude/` 통째 대신
   `**/.claude/settings.local.json`만 제외해 skills 공유 가능)과 terraform 규칙
   블록을 합치면 됨.
2. **`cloudwatch-discord.zip`(Lambda 빌드 산출물)이 추적 중** —
   `git rm --cached go/cloudwatch-notifications/cloudwatch-discord.zip` 필요.
3. (정정 기록) 초기 보안 리뷰에서 ".gitignore가 사실상 비어 있음"으로 판정했으나
   **`go/.gitignore`에 tfstate/.terraform 규칙이 이미 있었음** — 루트 파일만 보고
   내린 오판. 실제 갭은 `*.tfvars` 부재와 zip 추적뿐이었고 조치 완료.

**교훈**: stash pop/pull 충돌은 그 자리에서 해결하고 커밋할 것. 그리고 점검할 땐
**중첩된 .gitignore**(루트뿐 아니라 하위 디렉토리)까지 확인할 것.

## §8. (개선) 알림 파이프라인 SPOF 제거 — SNS 허브

장애는 아니지만 이번에 함께 개편한 구조 변화 기록:

- 기존: `EventBridge → Lambda → Discord` 직결 — Lambda/Discord가 죽으면 알림이
  흔적 없이 유실, 채널 추가 시 Lambda 수정 필요
- 개편: `EventBridge → SNS(gochuchamchi-alerts) → {Lambda→Discord, 이메일}` +
  SQS DLQ(14일) + **DLQ 감시 알람** — 알람 이름이 `gochuchamchi-` prefix라 기존
  EventBridge 룰에 자동 포착되어, Discord가 죽어도 이메일로 "파이프라인 자체의
  고장"이 통보되는 자기 감시 루프
- 운영 절차: `$env:TF_VAR_alert_emails = '["<주소>"]'` 주입, apply 후 확인 메일
  Confirm 클릭(3일 내), 실패분은 DLQ에서 원문 확인 가능
