# 재발 방지 체크리스트 (누적)

> 특정 날짜에 묶이지 않고 계속 누적되는 함정 목록입니다. 새 트러블슈팅에서 얻은 교훈은 해당 날짜 파일에 적고, 재사용 가치가 있으면 이 파일에도 한 줄 추가하세요.

---

- [ ] EC2 모듈에서 `root_block_device`는 버전마다 스키마가 다름 — 반드시 `.terraform/modules/.../variables.tf`에서 실제 필드명 확인
- [ ] `user_data_replace_on_change`가 있어도 EC2가 **완전 종료(terminate) 후 재생성**되어야 cloud-init이 처음부터 실행됨 (in-place 업데이트로는 userdata 재실행 안 됨)
- [ ] `al2023-ami-minimal` 계열 AMI는 SSM Agent 미포함 — userdata에서 명시적 설치 필요
- [ ] PowerShell `Out-File -Encoding utf8`은 BOM을 붙여서 AWS CLI가 파일을 못 읽음 → `Set-Content -Encoding ascii` 사용
- [ ] bash에서 `!`(느낌표)가 포함된 ARN 등은 반드시 **작은따옴표**로 감싸야 함 (히스토리 확장 방지)
- [ ] Ingress `certificate-arn`, ConfigMap `DB_HOST`/`REDIS_HOST` 같은 플레이스홀더는 재배포할 때마다 실제 값으로 채워졌는지 재확인 필요
- [ ] 애플리케이션이 특정 기능(Redis 세션 등)을 쓰려면 인프라 설정뿐 아니라 **jar 안에 관련 의존성이 실제로 포함됐는지** 먼저 확인 (`unzip -l app.jar | grep ...`)
- [ ] GitHub 웹 편집기로 CSS/코드를 부분 수정할 때는 **셀렉터와 중괄호 짝이 맞는지 반드시 재확인** — 브라우저는 문법이 깨진 CSS 규칙을 에러 없이 조용히 무시하므로, "요소는 있는데 안 보인다"는 증상만으로는 원인을 알 수 없고 Elements→Styles 탭으로 규칙 적용 여부를 직접 확인해야 함
- [ ] 파일 업로드 기능이 있다면 `spring.servlet.multipart.max-file-size`/`max-request-size`를 처음부터 명시적으로 설정 — Spring Boot 기본값(1MB)은 이미지 업로드조차 쉽게 초과함
- [ ] `helm_release`가 로컬 차트 경로(`path.module/charts/...`)를 참조할 때, 템플릿 파일 내용만 바꾸면 Terraform이 변경을 감지 못 함 — `Chart.yaml`의 `version`을 같이 올려야 재적용됨
- [ ] Helm 차트가 기본으로 만드는 리소스(예: `argocd-notifications-cm`/`-secret`)를 별도 Terraform state에서 관리하려면, 차트 쪽 값(`xxx.create = false`)으로 소유권을 먼저 넘겨받아야 함 — 안 그러면 `already exists` 충돌 + 다음 helm upgrade 때 조용히 덮어써짐
- [ ] destroy 전에 ALB Ingress Controller가 만든 ALB/타겟그룹이 다 정리될 때까지, NAT(인스턴스든 Gateway든)와 그 라우트가 먼저 지워지지 않도록 `depends_on`으로 순서를 강제해야 함 — 안 그러면 private subnet 노드가 AWS API 경로를 잃어서 ALB 정리가 영원히 멈추고 subnet/IGW 삭제도 막힘
- [ ] **`module.X.어떤_output`을 참조하는 것으로는 그 모듈 "전체"에 순서가 걸리지 않는다** — output을 만들어내는 리소스 하나에만 걸린다. 모듈 안의 나머지 리소스(라우트 테이블, **보안 그룹 규칙** 등)는 아무도 참조하지 않으면 그래프상 자유롭게 먼저 삭제된다. destroy 중 살아있어야 하는 컨트롤러가 있다면, 그 컨트롤러의 `depends_on`에 네트워크 관련 모듈을 **모듈 이름 통째로** 넣을 것 (`module.vpc`, `module.nat_sg`, `module.add_node_sg`). 2026-07-29 2차·3차 교착이 정확히 이 함정이었음
- [ ] **보안 그룹은 "그룹"과 "규칙"이 별개 리소스**라는 걸 항상 의식할 것 — 그룹은 실행 중인 인스턴스에 붙어 있으면 삭제가 거부되지만 규칙은 그 보호를 못 받고 먼저 사라진다. "자원은 다 살아있는데 통신만 안 된다"면 라우팅보다 **SG 규칙이 비어있는지**를 먼저 의심 (`aws ec2 describe-security-group-rules --filters Name=group-id,Values=<sg>`)
- [ ] destroy 교착 시 **finalizer를 강제로 뜯기 전에 "통신 복구"로 풀리는지 먼저 확인** — 컨트롤러가 살아있다면 경로/필터만 되살려주면 ALB·타겟그룹·finalizer를 정상 절차대로 알아서 정리한다. 강제 제거는 타겟그룹이 고아로 남으므로 통신 복구가 불가능할 때의 최후 수단
- [ ] 배스천이 이미 지워져 kubectl 경로가 없어도, **작업 PC가 EKS 엔드포인트 허용 CIDR 안이면** `aws eks get-token` + `curl`로 K8s REST API를 직접 호출해 진단할 수 있음 (Windows Git Bash curl은 `--ssl-no-revoke` 필요). 배스천 재생성보다 훨씬 빠름
- [ ] AWS Load Balancer Controller의 mutating webhook은 클러스터 전역 Service 생성을 가로채므로, 그 컨트롤러보다 먼저(또는 병렬로) Service/Ingress를 만드는 다른 helm_release/kubernetes 리소스가 있으면 반드시 `depends_on`으로 순서를 고정할 것
- [ ] 오픈소스 Helm 차트의 `values.yaml` 스키마는 버전이 바뀌면서 키 이름이 종종 바뀜(예: `server.ingress.hosts`(list) → `hostname`(string)) — Terraform이 모르는 키를 줘도 에러 없이 조용히 무시되고 차트 기본값이 적용되니, 값이 반영 안 되면 배포된 차트 버전의 실제 `values.yaml`을 직접 확인할 것
- [ ] SSM Session Manager는 기본적으로 `ec2-user`가 아니라 `ssm-user`로 접속됨 — `ec2-user` 홈 디렉토리가 700 권한이면 그 안의 kubectl/kubeconfig에 아예 접근이 안 되니 `sudo su - ec2-user`로 전환 필요
- [ ] 컨테이너에 특정 CLI가 없다고 가정하고 사이드카/initContainer로 주입하기 전에 **그 이미지의 Dockerfile을 먼저 확인** — 이미 들어있는 경우가 많고, 불필요한 initContainer는 `runAsNonRoot` 같은 securityContext와 충돌해서 파드 전체를 못 뜨게 만듦
- [ ] `cleanup_on_fail = true`인 helm_release가 실패하면 **그 upgrade에서 새로 만들어진 ConfigMap/Secret이 롤백으로 삭제**되는데, Deployment가 그걸 필수 마운트로 참조하면 파드가 못 떠서 다음 upgrade도 계속 타임아웃되는 교착이 생김 — 이때는 누락 리소스를 helm 소유권 메타데이터(`app.kubernetes.io/managed-by: Helm` + `meta.helm.sh/release-*`)와 함께 수동 생성해서 교착을 먼저 푼 뒤 apply할 것
- [ ] 레지스트리 API 엔드포인트(`api_url`)에는 **호스트까지만** 넣어야 함 — `aws_ecr_repository.repository_url`은 `<host>/<repo>` 형태라 그대로 쓰면 저장소 경로가 섞여 들어감
- [ ] `gh`로 `.github/workflows/` 아래 파일을 수정하려면 토큰에 **`workflow` 스코프**가 필요 — 없으면 권한 문제인데도 403이 아니라 **404**가 떠서 원인 파악이 어려움 (`gh auth refresh -h github.com -s workflow`)
- [ ] 레지스트리를 옮길 때는 **새 레지스트리에 이미지를 먼저 올린 뒤** 배포 매니페스트를 전환할 것 — 순서를 뒤집으면 `ImagePullBackOff`로 서비스가 즉시 중단됨
- [ ] GitHub Secret을 지워도 **AWS의 실제 IAM 액세스 키는 무효화되지 않음** — 정적 키를 정리할 땐 IAM에서도 별도로 비활성화/삭제해야 함
- [ ] ALB ingress에 `alb.ingress.kubernetes.io/ssl-policy`를 명시하지 않으면 기본값 `ELBSecurityPolicy-2016-08`이 적용되어 **이미 deprecated된 TLS 1.0/1.1이 열리고 TLS 1.3은 못 씀** (2026-07-29에 실제로 그 상태였음). `ELBSecurityPolicy-TLS13-1-2-2021-06`으로 고정하면 TLS 1.2/1.3만 허용됨. 리스너 속성만 바뀌므로 파드 재시작/다운타임 없음. 검증은 `curl --tlsv1.0 --tls-max 1.0 https://<host>` 식으로 버전별로 직접 찔러볼 것
- [ ] **Terraform이 만든 S3 버킷은 "버킷"만 관리 대상이고 "내용물"은 아님** — destroy/apply로 재생성하면 안에 있던 정적 자산이 사라져 참조하던 페이지가 깨짐(실제로 `index.html`의 배경 `texture.png`가 403이 났음). 재생성 후에도 유지돼야 하는 파일은 `aws_s3_object` 리소스로 코드에 넣을 것 (`source` + `etag = filemd5(...)`로 하면 파일이 바뀔 때 자동 재업로드됨)
- [ ] **S3 버킷에 `force_destroy = true`가 없으면 destroy가 `BucketNotEmpty`로 막힘** — 객체가 하나라도 남아있으면 버킷 삭제가 거부됨. destroy/apply를 반복하는 개발 단계에서는 켜두는 게 편함. 단 **destroy 시 버킷 내용물이 전부 삭제**되므로, 사용자 업로드물이 쌓이는 버킷(예: 상품 이미지)은 운영 전환 시 반드시 다시 끄고 `prevent_destroy`나 별도 state로 분리할 것

- [ ] **EKS `endpoint_public_access_cidrs`를 단일 `/32`로 하드코딩하지 말 것** — 허용목록 밖 네트워크에서 apply하면 `kubernetes`/`helm` 프로바이더가 인증 에러가 아니라 **TCP 타임아웃**(`connectex ... did not properly respond`)으로 실패한다. AWS API만 쓰는 리소스(EKS/RDS/`null_resource`+SSM)는 정상 진행되므로 **apply가 절반만 성공한 상태**로 끝나 원인을 자격증명 문제로 오해하기 쉬움. `curl checkip.amazonaws.com` vs `aws eks describe-cluster --query resourcesVpcConfig.publicAccessCidrs` 대조로 즉시 판별. 변수(`list(string)`)로 빼고 쓰는 네트워크를 등재해둘 것
- [ ] 위 허용목록의 **안 쓰는 `/32`는 반드시 지울 것** — 유동 IP는 나중에 타인에게 재할당되므로 stale 항목이 그 사람에게 엔드포인트 접근을 열어준다
- [ ] **ECR도 S3처럼 "저장소"만 Terraform 관리 대상이고 "이미지"는 아니다** — 게다가 `force_delete = true`면 destroy가 이미지까지 **적극적으로 삭제**한다. destroy/apply 사이클 후 저장소가 비어 파드가 `ImagePullBackOff`로 안 뜨고 사이트가 503이 된다. apply 후 `aws ecr list-images`로 비어있는지 확인하고, 비었으면 CI 워크플로를 수동 실행(`gh workflow run`)해서 이미지를 다시 적재할 것. 운영 전환 시에는 `force_delete`를 끄고 ECR을 별도 state/`prevent_destroy`로 분리 — 이미지는 인프라와 생애주기가 다르다
- [ ] **타겟그룹을 `TargetGroups[0]` 같은 인덱스로 조회하지 말 것** — 클러스터에 ALB가 여러 개면(앱 external + ArgoCD internal 등) 엉뚱한 그룹을 보게 되고, 남의 `healthy` 타겟을 보며 "정상인데 왜 503이지"로 헤매게 된다. 반드시 `TargetGroupName`과 `LoadBalancerArns`를 함께 출력해서 어느 ALB 것인지 확인할 것
- [ ] **503이 지속되면 ALB가 아니라 백엔드가 없는 것** — 타겟 수가 0이면 파드부터 본다(`kubectl get pods` → `ImagePullBackOff`/`CrashLoopBackOff`). 타겟 상태 `initial`(=등록 중)은 일시적이지만, **시간이 지나도 안 변하면 일시적 현상으로 단정하지 말 것**
- [ ] **`ImagePullBackOff`는 이미지를 올려놓아도 즉시 회복되지 않는다** — kubelet의 pull 재시도 백오프가 최대 5분까지 늘어나므로, 이미지를 적재한 뒤 "알아서 회복될 것"이라 기다리지 말고 막힌 파드를 지워 즉시 재시도시킬 것(`kubectl delete pod -l <selector>`). GitOps(ArgoCD) 관리 리소스라면 `rollout restart`(template에 annotation 추가)보다 **파드 삭제**가 스펙을 안 건드려서 깔끔하다
- [ ] **코드에 없는 수동 보안 조치는 destroy/apply마다 사라진다** — 클러스터 안에서 손으로 한 조치(ArgoCD admin 비밀번호 변경 등)는 Terraform state에 없어서 재구축 시 초기화된다. 반면 코드에 있는 조치(`argocd.tf`의 `scheme = internal`)는 유지된다. 조치는 가능하면 코드에 넣고, 못 넣으면 재구축 절차서에 명시할 것. 재구축 후에는 보안 보고서의 "조치완료" 항목이 실제로 살아있는지 재확인해야 한다
- [ ] **ALB가 TLS를 종료하는 구성에서 파드는 평문으로 뜬다** — ArgoCD는 `server.insecure=true`로 8080 평문에서 동작하고 `svc`의 443 포트도 같은 평문 타겟(8080)을 가리킨다. 따라서 `kubectl port-forward`로 붙을 때 `https://`를 쓰면 `connection reset by peer` / `lost connection to pod`가 난다. `svc/...` **80 포트로 붙고 `http://`로 접속**할 것. 서비스의 443 포트는 "ALB가 TLS를 벗겨 넘겨줄 때의 입구"일 뿐이다
- [ ] **"접속 안 됨"은 에러 코드로 즉시 원인이 갈린다** — `ERR_CONNECTION_TIMED_OUT`=사설 IP로 직접 접속(터널 없음) / `ERR_SSL_PROTOCOL_ERROR`·`connection reset`=평문 리스너에 TLS 시도 / `ERR_CONNECTION_REFUSED`=로컬 리스너 없음(port-forward 죽음). REFUSED는 `netstat -ano | findstr :<port>`의 LISTENING 유무로 바로 확정된다. **port-forward는 실행 창을 닫으면 즉시 죽는다**
- [ ] **internal ALB로 전환한 서비스는 도메인이 정상이어도 브라우저에서 안 열린다** — 레코드가 사설 IP를 가리키므로 정상 동작이다. "도메인이 바뀌었나" 의심하기 전에 `describe-load-balancers`의 `Scheme`과 `nslookup` 결과가 사설 IP인지 확인할 것
- [ ] **DB에 직접 넣은 데이터 변경(회원 role 승격 등)은 재구축에서 사라진다** — `schema.sql`은 `IF NOT EXISTS`로 테이블만 만들고 데이터는 관리하지 않으므로, destroy/apply로 RDS가 재생성되면 원복된다. 또한 role 같은 권한 값은 **로그인 시점에 세션에 담기므로 변경 후 재로그인이 필요**하고, 앱이 기대하는 문자열(`admin` vs `ADMIN` vs `ROLE_ADMIN`)이 다르면 에러 없이 조용히 안 먹는다

- [ ] **시크릿 변수가 필수인 프로젝트에서 전체 `apply`를 습관적으로 돌리지 말 것** — `argocd_git_pat`처럼 `TF_VAR_`로 주입하는 시크릿은 세션에 없으면 plan이 아예 실패한다. 여기서 더미 값을 채워 전체 apply하면 그 값이 실제 Secret 리소스(`argocd.tf`의 git 자격증명 `password`)에 그대로 기록돼 **운영 중인 연동이 조용히 끊긴다**. 시크릿을 모르는 상태에서 일부만 적용해야 한다면 `-target`으로 범위를 격리하고, **plan 출력에 그 Secret이 없음을 눈으로 확인한 뒤** 적용할 것
- [ ] **`plan -out`으로 계획을 고정한 뒤 그 파일로 apply할 것** — plan과 apply 사이에 상태가 바뀌어도 적용 내용이 흔들리지 않고, 변수를 다시 넣을 필요도 없다. 단 **plan 파일에는 변수 값이 들어있으므로 적용 후 삭제**할 것. 현재 `.gitignore`에 `tfplan*` 항목이 없어 커밋 사고가 날 수 있다
