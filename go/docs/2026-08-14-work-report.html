1. 탐지 확대 — Log 계정 log-archive, 룰 4 → 10개

탐지는 전부 Log 계정(564186750363)의 log-archive 쪽에서 늘렸다. 세 갈래(DB 감사 · EKS 제어평면 · 앱 행위)에서 룰을 2개씩, 총 6개를 추가했다.

DB 감사 — 정규화 뷰에 편입, 룰 2개

RDS 감사를 정규화 뷰(security-events-view.tf)에 편입했다. 원문 message가 MariaDB audit CSV라서 split으로 필드를 파싱하는 뷰를 만들고 탐지 뷰에 얹었다.

룰보는 것 · 판별 근거
db-auth-failure DB 인증 실패의 폭증. 무차별 대입·오설정을 초기에 잡는다.
db-unexpected-principal 예상 밖 DB 계정 접속. 구 비밀번호 계정 gochuchamchi_app의 접속을 상시 자동 감지한다 — 어제까지 verify-db-iam-only.ps1로 수동 검증하던 "비밀번호 계정이 더는 안 태어나는가"를 탐지 룰이 대체했다.

EKS 제어평면 — 조회조차 안 되던 로그를 살렸다, 룰 2개

control-plane 로그는 중앙 S3로 수집은 되고 있었으나 Glue 테이블이 없어 조회조차 안 됐다. eks-control-plane-analytics.tf로 원문 message 테이블을 신설하고, 뷰·룰에서는 audit JSON만 json_extract로 파싱한다. 탐지 뷰가 원본을 그대로 스캔하지 않게 원본 테이블을 직접 조회해 스캔량을 보호했다 — vpc_flow와 동일한 처리다.

eks-forbidden-burst K8s 403(Forbidden)의 폭증. 권한 밖 리소스를 훑는 정찰 신호.

2. 대응 강화 — workload, 격리 Lambda 1종 → 8종

대응은 전부 workload 계정의 격리 Lambda에서 늘렸다. 기존 2종(EC2 격리 — ENI의 SG를 검역 SG로 교체 · IAM 정적키 비활성화) 위에 오늘 6종을 추가했다.

WAF IP 자동 차단

  • persistent/waf-blocklist.tf에 us-east-1 CLOUDFRONT IP set 생성, ignore_changes=[addresses]로 Lambda가 넣는 IP를 terraform이 되돌리지 않게 함
  • terraform/edge.tf가 data.aws_wafv2_ip_set로 참조 + block rule(priority 3)
  • Lambda의 block_remote_ip(격리·키 비활성화와 병행) / sweep_expired_waf_blocks — 24h 자동 만료, audit 경로가 청소

침해 파드 K8s 격리

  • Lambda가 EKS 프라이빗 API에 직접 붙지 않고 배스천 SSM+kubectl로 deny-all NetworkPolicy 적용 — 파드를 살려 포렌식
  • gochuchamchi ns 한정, k8s 이름 정규식으로 인젝션 검증
  • Lambda timeout 60 → 120(SSM 왕복 시간 확보)

IAM 주체 격리

  • 키 비활성화가 못 잡는 AssumedRole / SSO 세션에 deny-all 인라인 정책 부착
  • 이 계정이 SSO라 실질적 갭이었다 — 정적 키가 아니면 비활성화가 무의미
  • recover-iam 복구, protected_iam_principals 보호목록 필수(자기 발을 쏘지 않게)

S3 버킷 퍼블릭 차단

  • S3 대상 finding 시 PublicAccessBlock 4개 항목을 전부 true로 강제
  • 버킷을 지우지 않고 노출만 닫는다

위험 SG 규칙 제거

  • 원본 SG에서 0.0.0.0/0 민감포트(22/3389/DB/K8s API)· 광범위 인그레스만 골라 revoke
  • SG 전체가 아니라 위험 규칙만 떼어 부수효과를 줄임

격리 시 EBS 포렌식 스냅샷

  • 격리하는 김에 create_snapshots로 증거 보존
  • 읽기 전용 — 대응이 원본을 훼손하기 전에 상태를 떠 둔다

4. GuardDuty 런타임 점검 — account-baseline/guardduty.tf

대응을 파드 런타임까지 연결하려면 GuardDuty가 그 신호를 내야 한다. 점검해 보니 대부분 이미 켜져 있었다.

기능상태
EKS_AUDIT_LOGSENABLED 이미 켜짐
S3_DATA_EVENTSENABLED 이미 켜짐
EBS_MALWARE_PROTECTIONENABLED 이미 켜짐
RUNTIME_MONITORING 변수 게이트 enable_guardduty_runtime_monitoring(기본 OFF) — t3.small 메모리 부담 때문
대응 편입은 severity 기반이라 이미 자동이다. 즉 RUNTIME_MONITORING을 켜기만 하면 파드 런타임 finding이 별도 배선 없이 파드 격리로 흐른다 — 주석에 그렇게 명시해 뒀다. 런타임 감시는 비용 판단만 남았고, 배선은 이미 준비돼 있다.

5. 보안 하드닝 패치 2건 — 별도 브랜치로 분리

주제가 자동 탐지·대응과 달라 별도 브랜치로 분리했다. 워크로드에 뚫린 구멍 두 개를 막는다.

WAF 로그인 rate limit — COUNT → BLOCK

  • terraform/variables.tf의 waf_login_rate_limit_action 기본값을 COUNT에서 BLOCK으로
  • 로그인 무차별 대입을 관찰만 하던 것을 실제 차단으로 — 임계 50회 / 5분

S3 업로드 콘텐츠 검증 — gochuchamchi-spring

  • S3Service.upload에 크기 10MB 제한
  • MIME 화이트리스트(jpg/png/webp/gif) — SVG는 스크립트 XSS 벡터라 제외
  • 매직바이트 위조 검증, 확장자·Content-Type을 검증된 값으로 강제
S3 검증이 막는 실제 경로 — 이미지인 척하는 HTML/SVG를 신뢰 도메인(CloudFront)에 올려 XSS·피싱에 쓰는 것이다. 확장자만 보고 통과시키면 브라우저는 실제 콘텐츠로 렌더하므로, 매직바이트까지 봐야 위조를 잡는다.
