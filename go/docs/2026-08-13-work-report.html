1. DB 비밀번호 제거 — 제로 트러스트 완결

8/12에 앱을 IAM 토큰 방식으로 전환해 두었으나, 쓰이지도 않는 DB_PASS가 파드 환경변수에 계속 남아 있었다. 파드가 침해되면 그대로 읽히고, 15분이면 만료되는 토큰과 달리 이 값은 만료가 없다. 토큰으로 바꾼 목적 자체가 "상시 유효한 자격증명을 없애는 것"이므로 안 쓰는 자격증명이 남아 있으면 그 목적이 반감된다.

이전 (8/4 ~ 8/12)
파드→ DB_PASS (만료 없음)→ RDS ＋ IAM 토큰 (15분)
현재
파드→ IAM 토큰만 (15분, 접속마다 재발급)→ RDS

순서가 전부였다 — 뒤집으면 장애

저장소 두 개가 순서로 묶여 있었고, gitops 커밋 메시지가 직접 경고하고 있었다.

단계내용결과
1IAM 토큰 접속을 재발급 구간까지 검증완료
2gitops 853a6a4 머지 → ArgoCD 배포 → 파드에서 DB_PASS 제거완료
3terraform dbae59c 머지 → 다음 apply부터 Secret·DB 계정 미생성완료
3이 2보다 먼저 가면 Secret은 없는데 참조만 남아 파드가 CreateContainerConfigError로 뜨지 못한다. 2026-08-04에 정확히 같은 방식으로 장애가 났다(terraform이 Secret 이름을 바꿨는데 gitops가 옛 이름을 계속 참조). 그래서 두 브랜치를 push만 해두고 검증이 끝날 때까지 머지하지 않았다 — 실패해도 비밀번호 계정이 살아 있어 되돌릴 수 있는 상태를 유지하기 위해서다.

검증이 "통과"했는데 아무것도 증명하지 않았던 것

전날 만들어 둔 검증 스크립트가 통과를 냈다. 그런데 출력에 gochuchamchi_app_iam의 CONNECT 줄이 없었다. 

[3] RDS 감사 로그 — 최근 10분 (토큰 캐시 만료 이후 구간)
    CONNECT  rdsadmin                 16회
    QUERY    gochuchamchi_app_iam     346회      ← CONNECT 는 0건
판정: 통과 — IAM 토큰 재발급 구간을 넘겨 DB 접속이 유지됐다.

MariaDB는 접속을 맺을 때만 인증하고 그 뒤로는 재인증하지 않는다. IAM 토큰은 "접속 시점의 입장권"이지 세션을 계속 검사하는 값이 아니다. 따라서 이미 열린 커넥션 위의 QUERY는 몇 백 건이든 전부 첫 토큰의 결과이고, 토큰이 만료된 뒤에도 그 커넥션은 아무 일 없이 계속 돈다. 스크립트는 QUERY만 세고 있었으므로 재발급이 한 번도 안 일어난 상태에서도 통과가 나온다.

전날 문서에 "219건은 첫 토큰이라 증명이 아니다"라고 정확히 적어 놓고, 정작 검사 조건은 같은 함정에 들어가 있었다. 문서로 아는 것과 코드가 검사하는 것은 별개다.

실패한 시도 — 동시 요청으로 풀을 키우기

커넥션 풀이 커지면 새 물리 커넥션이 생기므로 동시 요청 45건을 몰아쳤다. 새 CONNECT는 0건이었다. 응답이 빨라 파드당 커넥션 2개로 전부 처리됐다. maximumPoolSize=10은 "필요할 때 늘어나는 한도"이지 미리 여는 개수가 아니다.

곁다리로 밟은 오진 — 첫 시도에서 30건이 전부 403이었다. rate 기반 WAF 규칙에 걸린 줄 알았으나 단일 요청은 200이었다. 원인은 User-Agent 헤더 부재 — .NET HttpClient는 UA 기본값이 없고 WAF 관리형 규칙의 NoUserAgent_HEADER가 이를 막는다. WAF가 제대로 도는 증거였지 결함이 아니었다. 부하 도구가 403을 뱉으면 rate limit보다 UA를 먼저 볼 것.

통한 방법 — HikariCP maxLifetime(기본 30분)을 기다린다

커넥션은 수명이 다하면 폐기되고 곧바로 새로 열린다. 그 새 커넥션은 캐시가 만료된 뒤라 반드시 토큰을 새로 발급받아야 한다. 14:20에 열린 커넥션이므로 14:50 전후를 보면 된다.

"안 쓰는 키"가 아니라 "기본값이라 조용히 쓰이는 키"였다

CloudTrail 90일 이력상 실작업은 2026-07-30 구계정 철거가 마지막이었다. 그런데 그 뒤로도 GetCallerIdentity가 계속 찍혔다. 원인은 로컬 설정이었다. 

~/.aws/credentials
  [default]     -> AKIA4B7L…   (terra-user)
  [terra-user]  -> AKIA4B7L…   (같은 키)

--profile을 안 붙인 모든 AWS 명령이 이 전권 자격증명으로 돌고 있었다. 습관적으로 치는 aws sts get-caller-identity가 그대로 기록에 남은 것이다.

조치 — 삭제가 아니라 비활성화

terraform 루트 6개·daily 스크립트는 전부 workload-admin, CI는 OIDC 역할을 쓴다는 것을 먼저 확인한 뒤, 백업 → 비활성화 → 로컬 정리 순으로 진행했다. 삭제가 아닌 이유는 terra-user가 공유 계정의 IAM 사용자라 팀원 중 누가 같은 키를 쓰고 있을 수 있어서다. 비활성화는 되돌릴 수 있고 삭제는 못 되돌린다.

  • --profile 없이 get-caller-identity → SSO 역할 ARN 반환
  • ~/.aws/credentials에 aws_access_key_id 0건
  • 환경변수(프로세스·사용자·시스템)에도 정적 키 없음 — 프로필만 고쳐서는 소용없는 경우가 있어 같이 확인

3. GuardDuty AI 트리아지 — 적용하고, 검증하고, 철회했다

가이드에 따라 트리아지를 배포했다. 통보 경로에 판정 계층을 끼워 넣는 작업이다. 11 added, 1 changed, 1 destroyed로 plan·apply 모두 예고와 일치했고 검증도 전부 통과했다.

검증 통과 항목

  • 루트 사용(severity 2) → tier=HIGH 승격 — 가장 중요한 확인
  • LOW 소음은 모델 호출 없이 filtered
  • CRITICAL은 판정 무관 urgent
  • 중복 억제 동작
  • 실제 샘플 finding이 EventBridge 거쳐 도달 → TRUE_POSITIVE(0.85)
  • 격리 Lambda skipped, 부작용 0

그럼에도 껐다

  • Groq 무료 티어 8000 TPM — finding 1건이 2,100~2,400 토큰이라 분당 3건 넘으면 429. 검증 중 12회 발생
  • API 키가 대화 중 평문 노출 — 재발급 필요
  • 판정 provider를 다시 검토하기로 결정
429가 나도 탐지 공백은 없다. verdict=null → UNCERTAIN으로 떨어지고 정책 표대로 통보되므로 소음만 늘 뿐이다. 다만 판정이 자꾸 UNCERTAIN이면 모델 성능이 아니라 레이트리밋을 먼저 의심할 것 — 로그의 unavailable_reason에 사유가 남는다.

하마터면 terraform destroy를 칠 뻔했다

"매일 오후에 지운다"는 것은 맞지만 루트가 다르다. daily-down.ps1은 go/terraform(런타임 계층, 약 235개)만 destroy하고, 트리아지가 있는 cloudwatch-notifications는 손대지 않는 상시 계층이다. 그 루트에는 SNS 허브·격리 Lambda·Discord Lambda·IAM 활동 감시 등 40개 넘는 인프라가 들어 있다. enable_triage=false apply로 배선만 되돌렸다 — 알림 끊김 구간 없음.

5. 운영 스크립트 — 저녁 종료가 실패할 수 있던 버그

daily-down.ps1이 stderr 한 줄에 죽는 상태였다. AWS CLI가 stderr를 쓰는 가장 흔한 경우가 SSO 토큰 만료다. 즉 SSO가 만료된 저녁이면 1단계에서 정체불명의 RemoteException으로 죽고, 종료를 못 하면 그날 과금이 그대로 간다.

PS 5.1은 native 명령의 stderr를 리다이렉트할 때 각 줄을 ErrorRecord로 감싼다. 스크립트가 $ErrorActionPreference="Stop"이라 경고 한 줄에도 죽는다. 2>$null로 버려도 마찬가지다 — 원인은 "버렸다"가 아니라 "리다이렉트했다"는 사실 자체다.

방식결과
2>$null 붙임RemoteException 사망
리다이렉트 없음생존 — stdout·$LASTEXITCODE 모두 정상
리다이렉트 없음 + 종료코드 128생존 — 종료코드도 정상 감지
같은 파일 33행은 이미 같은 이유로 리다이렉트를 피하고 있었는데 18행만 빠져 있었다. 교훈이 주석으로는 남아 있었지만 코드 전체에 적용되지는 않은 상태였다.

daily-up.ps1의 git 두 줄도 같은 문제였고, 고치면서 게이트 로직의 구멍도 발견했다 — git이 실패하면 codeChanged=false가 되어 plan 확인을 조용히 건너뛰고 바로 apply로 갔다. 안전장치가 실패하면 안전장치가 없어지는 구조였다. 이제 git을 못 읽으면 "변경 있음"으로 보고 승인을 받는다.

검증이 매번 "그때그때 명령어를 조합해서" 이뤄지고 있었다. 그래서 무엇을 확인했고 무엇을 빠뜨렸는지가 기억에만 남는다. WAF 가이드 8~11번은 그렇게 몇 주째 미실행으로 남아 있었다. 확인해야 할 것들을 코드로 고정했다.

돌려 보자마자 드러난 오검사 — 둘 다 내일 아침에 "고장"으로 오진했을 것들

① 인코딩으로 "알람 0개"

  • 화면에는 "알람 0개"로 나온다 — 알람이 사라진 줄 안다

② "알람에 액션이 없다"

  • 상시 알람 2개가 전부 AlarmActions 0개 — 처음엔 실패로 판정
  • 그런데 이 프로젝트는 알람에 액션을 붙이지 않는다. EventBridge가 이름 접두사 gochuchamchi-로 잡아 SNS로 넘긴다
  • 진짜 위험은 따로 있다 — 접두사를 안 지킨 알람은 룰에 안 걸려 조용히 통보에서 빠진다
  • 검사를 그쪽으로 바꿨다(접두사 불일치 + 룰 활성 상태)
내일 아침 핵심 확인점 — verify-db-iam-only.ps1에서 gochuchamchi_app CONNECT가 0건이어야 한다. 오늘은 아침 프로비저닝 흔적 1건이 잡혔고, 그게 0이 되는 것이 "비밀번호 계정이 더는 태어나지 않는다"의 증거가 된다.

10. tfstate SSE-KMS 전환 — 진단이 절반 틀렸던 것

보안 점검 3번. tfstate가 SSE-S3라 버킷을 읽을 수 있으면 곧 복호화인 상태였다. CloudFront Origin 검증 헤더가 거기 평문으로 들어 있고, 그 값을 알면 자기 CloudFront 배포로 ALB를 오리진 삼아 WAF를 통째로 우회할 수 있다 — SG의 prefix list는 "CloudFront IP 대역에서 왔다"까지만 검증하므로 그 관문은 통과한다.

먼저, 틀린 진단부터

"버전 이력에 남은 평문 때문에 헤더 로테이션도 함께 필요하다"고 판단했다. 뒤쪽이 틀렸다. state에 들어가는 민감값을 전수 확인했더니 둘뿐이었고, 둘 다 매일 재생성되는 계층에 있었다.

값루트수명
random_password.cloudfront_origin_verifygo/terraform매일 재생성
random_password.redis_authgo/terraform매일 재생성
RDS 마스터manage_master_user_passwordstate에 없음
ArgoCD PAT · Grafana 비밀번호8/4에 state 밖으로 이미 뺐음state에 없음

terraform state list로 확인하니 destroy 직후 현재 state는 리소스 0개였다. 142개 버전에 남은 값들은 이미 무효다. 별도 로테이션 작업은 할 필요가 없었다. 장기 루트에는 평문 시크릿이 아예 없다 — 8/4 리뷰에서 이미 정리한 결과다.

그래서 이 작업의 값어치는 "평문 노출 제거"가 아니라 두 가지로 재정의된다 — 방어선이 하나에서 둘로(s3:GetObject만으로는 못 읽고 kms:Decrypt도 필요), 그리고 누가 state를 읽었는지 남는다(KMS Decrypt는 관리 이벤트라 S3 데이터 이벤트를 켜지 않아도 CloudTrail에 기록된다 — 실측 확인).

버킷만 바꾸면 아무 일도 안 일어난다

terraform S3 백엔드는 encrypt = true이고 kms_key_id가 없으면 AES256을 "명시적으로" 보낸다. 명시 지정이 버킷 기본값을 이기므로, 버킷 설정만 바꿔 놓으면 state는 계속 SSE-S3로 저장된다. 조용히 아무 일도 안 일어나는 종류의 실패다.

버킷만 KMS로 바꿨을 때
terraform→ x-amz-sse: AES256
명시 지정→ 버킷 기본값(KMS)→ SSE-S3로 저장
전환 실패
backend.tf에 kms_key_id를 넣었을 때
terraform→ x-amz-sse: aws:kms
키 지정→ SSE-KMS로 저장

키를 terraform이 아니라 부트스트랩 계층에 둔 이유

이 키로 암호화되는 것이 terraform 자신의 state다. terraform이 키를 관리하면 "키가 사라지면 state를 못 읽고, state를 못 읽으니 키를 되살릴 수도 없는" 순환이 생긴다. 버킷과 같은 계층(scripts/bootstrap-state.ps1)에 둬서 그 고리를 끊었다.

항목내용
KMS 키별칭 alias/gochuchamchi-tfstate, 기본 키 정책(계정 루트 위임), 연 1회 자동 로테이션
버킷 암호화aws:kms + BucketKeyEnabled=true — state는 작은 파일을 자주 쓰는 패턴이라 이게 없으면 KMS 요청 비용·지연이 그대로 붙는다
backend.tf 5개별칭 ARN으로 kms_key_id 추가 — 키를 재생성해도 값이 안 바뀌게
건드리지 않은 것log-archive, management/* — 다른 계정 버킷이라 이 키가 없다. 그 계정들은 각자 부트스트랩을 돌려야 한다
수명주기 신규버전 298개·138MB가 무한정 쌓이고 있었다. 30일 만료 + NewerNoncurrentVersions=10

검증

  • persistent state를 실제로 다시 써서 확인 — ServerSideEncryption=aws:kms, 키 fb00273a…, BucketKeyEnabled=true
  • CloudTrail에 Decrypt 이벤트 기록 확인 — 감사 이점이 말뿐이 아님을 실측
  • 평범한 terraform init이 프롬프트 없이 exit 0
이 확인을 빠뜨렸으면 내일 아침 daily-up이 멈췄을 것이다. 백엔드 설정이 바뀌면 다음 terraform init이 마이그레이션 여부를 대화형으로 묻는다. daily-up.ps1은 비대화형으로 init을 부르므로 그 프롬프트에서 멈추고, 증상은 백엔드와 무관해 보인다. 5개 루트에 init -reconfigure를 미리 돌려 뒀다.

11. PR #7 충돌 — 내일 아침 daily-up을 막는 것을 발견

SSE-KMS 작업을 push하려는데 거부됐다. 다른 사람이 agent/security-hardening 브랜치를 PR #7로 main에 머지한 것이다(b936f32). 파일이 겹치지 않아 rebase는 깔끔했지만, 그 내용이 내일 아침을 막는다.

무슨 일이 일어나는가

PR #7은 ArgoCD의 공용 PAT 하나를 읽기 전용 / 쓰기 두 개로 분리했다. 방향은 옳다. 문제는 배선이다.

내일 아침 daily-up
daily-up.ps1→ go/terraform만 apply→ data source가
없는 시크릿 참조→ plan 단계에서 실패
시작조차 못 함
그릇을 만드는 쪽
go/persistent/secrets.tf→ daily-up이 안 건드림

go/terraform/persistent-data.tf에 data "aws_secretsmanager_secret" 두 개가 추가됐는데, 그 시크릿을 만드는 코드는 go/persistent에 있다. daily-up.ps1은 go/terraform 루트만 apply한다(26행). data source는 대상이 없으면 plan에서 즉시 실패한다.

그 뒤에 숨은 두 번째 함정

그릇을 만들어도 값이 없으면 끝이 아니다. eso.tf의 주입 로직은 환경변수가 없으면 조용히 건너뛴다.

if (-not $env:ARGOCD_GITOPS_READ_PAT) { Write-Host "...skipping read PAT injection."; exit 0 }

그리고 ESO는 이제 옛 git-pat이 아니라 새 시크릿 두 개를 바라본다. 값이 비면 ExternalSecret이 실패하고 ArgoCD가 gitops에 인증하지 못한다 — 8/4 장애와 정확히 같은 실패 방식(authentication required: Repository not found)이다.

조치

go/persistent를 apply해 그릇을 만들었다(7 added, 0 changed, 0 destroyed). 시크릿 2개 외에 CloudFront 로그 버킷 하드닝 5개가 딸려 있었는데, 코드에만 있고 한 번도 apply되지 않았던 것들이다 — CloudFront가 destroy된 지금이 적용하기 가장 안전한 시점이었다.

남은 것 — 그리고 계정 구조가 만든 벽

값 주입이 남았는데, 여기서 GitHub 계정 구조가 걸린다.

확인 사항결과
gitops 저장소 소유자landoll9999 — 개인 계정(조직 아님)
작업자 계정wherekyj — 협업자
저장소 권한push: true, admin: false
Fine-grained PAT는 Resource owner로 본인 계정이나 소속 조직만 고를 수 있다. 다른 개인의 계정은 선택할 수 없으므로, 작업자는 이 저장소를 대상으로 하는 fine-grained PAT를 만들 수 없다. Classic PAT는 private 저장소에 읽기 전용 스코프가 없어 읽기/쓰기 분리가 원리적으로 불가능하다. GitHub App(장기 해법)도 설치는 소유자만 가능하다 — admin: false이므로 마찬가지다.

즉 저장소 소유자의 협조가 필요하다. 소유자가 당장 어려우면 기존 PAT 값을 새 시크릿 두 개에 복사해 두면 내일 아침은 안전하다 — 읽기/쓰기 분리는 안 되지만 오늘과 같은 수준이지 나빠지지 않는다.

12. 현재 상태와 남은 것

완료 현재 상태

  • DB 비밀번호 제거 완료 — 파드에 DB_PASS 없음
  • 정적 관리자 키 비활성화 — 로컬 [default]도 SSO로
  • tfstate SSE-KMS 전환 완료 — 수명주기 30일, 5개 루트 재init
  • GitHub 시크릿 점검 완료 — 세 저장소 모두 정적 AWS 키 0건, CI는 순수 OIDC

  • 저녁 daily-down 완료 — 278개 destroy, 상시 3버킷만 잔존

긴급 내일 아침 전에

  • ArgoCD PAT 2개 값 주입 — 안 하면 daily-up이 plan 단계에서 실패한다. 그릇은 만들어 뒀고 값만 없다
  • fine-grained PAT는 저장소 소유자만 만들 수 있다. 소유자가 어려우면 기존 PAT를 두 시크릿에 복사해 두면 내일은 안전하다

남은 것

  • Groq 키 재발급 — 노출됨. 트리아지 재가동 전 필수
  • terra-user 키 삭제 — 팀원 사용 여부 며칠 관찰 후
  • ArgoCD PAT → GitHub App 교체 — 설치가 소유자 권한이라 협조 필요
  • Log 계정 S3/Athena 적재 확인 · SIEM 상관 탐지 apply — log-admin 몫
  • eks 등 4개 루트의 state 객체는 아직 AES256 — 다음 apply 때 자동 전환

알고 있을 것

  • PR #7이 WAF에 IP 평판 목록을 BLOCK으로 추가했다 — 내일 자동 적용되고 VPN 경유 접속이 막힐 수 있다(익명 IP·로그인 rate limit은 COUNT라 관찰만)
