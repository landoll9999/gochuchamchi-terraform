# 2026-08-04 작업 기록

## 1. 제로트러스트 DB 하드닝 (RDS + Redis)

### 작업 목적

SECURITY_AUDIT_REPORT의 잔여 과제 중 데이터 계층을 제로트러스트 원칙(최소권한 ·
명시적 검증 · 침해 가정)으로 마감. 네트워크(SG 참조, #5)는 이미 조치돼 있었으므로
이번에는 **계정 · 암호화 · 감사** 축을 채웠다.

### 문제가 발생한 지점 (기존 상태의 갭 4개)

| # | 갭 | 리스크 |
|---|---|---|
| 1 | 앱 파드가 DB **마스터(admin)** 계정으로 접속 (`DB_USER=admin`) | SQL 인젝션/앱 침해 = 즉시 DBA 권한. DROP TABLE, GRANT, 타 DB 생성까지 가능 |
| 2 | `k8s-deploy.tf`가 마스터 비밀번호를 data 소스로 읽어 K8s Secret 생성 → **tfstate에 평문 저장** | 감사보고서 #1이 정의한 "state에 secret_string이 다시 들어가는 시점"(ESO 트리거)이 **이미 발동된 상태였음** |
| 3 | 전송 암호화 미강제 — 앱/배스천 모두 평문 3306 | "같은 VPC니까 안전"이라는 네트워크 위치 신뢰. VPC 내 다른 자원 침해 시 스니핑 가능 |
| 4 | DB 접속/변경 기록 없음 + Redis 평문·무인증 (#14 잔여) | 무단 접속 시도를 볼 수단이 없음. 세션 스토어는 SG 하나 뚫리면 끝 |

### 해결 방법 — 파일별 변경 내역

**`db-zero-trust.tf` (신규)** — 핵심.

- 앱 전용 계정 `gochuchamchi_app`: `gochuchamchi.*`에 DML(SELECT/INSERT/UPDATE/DELETE)만.
  DDL/DCL 불가. `REQUIRE SSL`이라 이 계정은 TLS 없이는 로그인 자체가 안 됨.
- 비밀번호 생성 → Secrets Manager(`gochuchamchi/app/db-credentials`) 저장 → DB 계정
  생성 → K8s Secret(`gochuchamchi-db-app`, 키 `DB_PASS`) 주입까지 **전부 배스천 SSM
  런타임에서 실행**. Terraform은 빈 Secret 컨테이너만 관리 → **앱 DB 비밀번호가
  state에 단 한 번도 안 들어감.** 비밀값은 SSM 커맨드 로그에도 안 남음(#13과 같은
  defaults-extra-file/600/즉시삭제 원칙).
- 멱등: 재실행 시 기존 비밀번호 재사용(CREATE IF NOT EXISTS + ALTER 수렴), K8s Secret은
  `--dry-run=client -o yaml | kubectl apply` 업서트. 실패 시 Status 검사로 반드시 실패 처리
  (8/3 "실패를 삼키는 프로비저너" 교훈 반영). 재시도: `terraform taint null_resource.provision_app_db_user`

**`rds.tf`**

- `require_secure_transport=1` 파라미터 — 평문 접속은 핸드셰이크에서 거부(전역 TLS 강제).
- `MARIADB_AUDIT_PLUGIN` 옵션 — CONNECT(실패 포함)/DDL/DCL 기록,
  `enabled_cloudwatch_logs_exports`에 `audit` 추가 → `/aws/rds/instance/gochuchamchi-db/audit`.
  QUERY 전체는 로그량·비용 때문에 제외(운영 전환 시 QUERY_DML 검토).
- `rds_sg` egress 전면 제거 — DB는 아웃바운드를 시작할 일이 없음(응답은 stateful 자동 허용).
- `storage_encrypted = true` 명시(모듈 기본값이지만 리뷰 가시성).
- IAM DB 인증은 **MariaDB 미지원이라 제외** — MySQL/PG였으면 15분 IAM 토큰 인증까지 가능(면접 포인트).

**`redis.tf`** — #14 잔여과제 이행

- `aws_elasticache_cluster`(암호화/AUTH 미지원) → `aws_elasticache_replication_group`
  단일 노드로 교체. `transit_encryption` + `at_rest_encryption` + `auth_token`.
  1노드 유지라 비용 동일. **교체 시 캐시 재생성 → 기존 로그인 세션 초기화(재로그인).**
- `redis_sg` egress 제거(동일 논리).
- auth_token은 리소스 인자라 state 경유가 불가피 → ESO 도입 시 최우선 이관 대상으로 주석 명시.

**`k8s-deploy.tf`**

- ConfigMap: `DB_USER=gochuchamchi_app`, `SPRING_DATASOURCE_URL=...?sslMode=trust`
  (환경변수가 application.yml보다 우선이라 **앱 리빌드 없이** JDBC TLS 적용.
  2단계는 RDS CA 번들 넣고 `verify-full`), `SPRING_DATA_REDIS_HOST`를
  `primary_endpoint_address`로, `SPRING_DATA_REDIS_SSL_ENABLED=true`.
- **마스터 비밀번호를 읽던 `data.aws_secretsmanager_secret_version` + K8s Secret
  `gochuchamchi-db-secret` 삭제** → 마스터 자격증명이 state에서 완전히 사라짐.
- Redis AUTH 주입용 K8s Secret `gochuchamchi-redis-secret`
  (키 = `SPRING_DATA_REDIS_PASSWORD`, envFrom 한 줄로 끝나게 env명 그대로).

**`iamRole.tf` / `eks-pod-identity.tf`** — 시크릿 권한 와일드카드 제거

- 배스천: `rds!*`(리전 내 모든 RDS 마스터 시크릿) → 이 스택의 마스터 1개(Get) +
  앱 시크릿 1개(Get/Put/Describe) 정확한 ARN으로 축소.
- 앱 Pod Identity: `rds!*` → 앱 시크릿 ARN 1개. 앱은 이제 마스터 시크릿에 접근 불가.

**`rds-schema-init.tf`** — 배스천 mysql `[client]`에 `ssl` 추가(TLS 강제 후에도 동작).

**`main.tf`** — `random` 프로바이더 추가(Redis AUTH 토큰 생성용) → **`terraform init` 1회 필요.**

**`cloudwatch-managed-metrics.tf`** — Redis 알람 디멘션을 RG 멤버 클러스터 ID
(`gochuchamchi-redis-001`)로 변경(참조 깨짐 방지).

### 적용 순서 (다음 apply 전 체크리스트)

1. **gitops 저장소(`gochuchamchi-gitops`) `03-deployment-web.yml` 수정 — 코드보다 먼저:**

   ```yaml
   # 기존: gochuchamchi-db-secret 참조 부분을 이름만 교체 (키 DB_PASS 동일)
   - secretRef:
       name: gochuchamchi-db-app        # <- gochuchamchi-db-secret 에서 변경
   # Redis AUTH 추가 (envFrom 목록에 한 줄)
   - secretRef:
       name: gochuchamchi-redis-secret  # SPRING_DATA_REDIS_PASSWORD 주입
   ```
   (valueFrom.secretKeyRef 방식이면 `name:`만 동일하게 교체 + redis는 키
   `SPRING_DATA_REDIS_PASSWORD`로 추가)

2. `terraform init` (random 프로바이더 설치) → `terraform validate`
3. `terraform plan` 확인 포인트:
   - destroy: `aws_elasticache_cluster.this`, `kubernetes_secret_v1.gochuchamchi_db_secret`
   - create: `aws_elasticache_replication_group.this`, `random_password.redis_auth`,
     `aws_secretsmanager_secret.app_db`, `null_resource.provision_app_db_user`,
     `kubernetes_secret_v1.gochuchamchi_redis_secret`
   - update(in-place): `module.rds`(파라미터/옵션/로그 export), SG 규칙, ConfigMap,
     배스천/앱 IAM 정책
   - **`storage_encrypted` 변경으로 RDS가 replace로 뜨면 중단**(기존 인스턴스가
     비암호화였다는 뜻 — 스냅샷 경유 전환 필요)
4. `terraform apply` — 앱 파드는 새 Secret이 생길 때까지 잠깐
   `CreateContainerConfigError`가 정상(프로비저너가 만들면 kubelet이 자동 재시도)
5. ConfigMap/Secret은 파드 시작 시점에 주입되므로 마지막에
   `kubectl -n gochuchamchi delete pod -l app=gochuchamchi-web` (GitOps 드리프트 없는 재기동)

**이미 떠 있는 인스턴스에 적용하는 경우 추가 주의:**
- RDS 파라미터는 동적이지만 `ParameterApplyStatus`가 `pending-reboot`면
  `aws rds reboot-db-instance --db-instance-identifier gochuchamchi-db` 1회(1~2분).
- ElastiCache는 교체라 약 5~10분 세션 스토어 공백(로그인 유지 안 됨) 발생.
- 앱이 admin으로 붙어 있는 동안에도 admin 계정은 계속 유효하므로, gitops 수정 →
  apply → 파드 재기동 순서면 다운타임 없이 전환됨.

### 검증 완료 사항 / 검증 명령

- 이 세션(클라우드)에서는 HCL 파서(hcl2)로 13개 파일 전부 구문 통과 + 참조 무결성
  (elasticache/secret 구 참조 0건) 확인. hashicorp 배포 서버가 막힌 환경이라
  `terraform validate`는 **로컬에서 실행할 것** (init 포함).
- 배스천 스크립트의 SQL/JSON 생성 로직은 동일 셸 로직으로 시뮬레이션 검증
  (600 권한, 인용부호 안전성 포함).

apply 후 검증 (배스천):

```bash
# 1) TLS 강제 — 평문 접속이 "거부"되면 성공
mysql -h <RDS엔드포인트> -u admin -p --skip-ssl -e "SELECT 1"   # -> ERROR (secure transport required)
mysql -h <RDS엔드포인트> -u admin -p --ssl -e "SHOW STATUS LIKE 'Ssl_cipher';"  # -> 암호명 표시

# 2) 앱 계정 최소권한 — DML만 보이면 성공, DROP 시도는 거부돼야 함
mysql -h <RDS엔드포인트> -u gochuchamchi_app -p --ssl -e "SHOW GRANTS FOR CURRENT_USER;"
mysql -h <RDS엔드포인트> -u gochuchamchi_app -p --ssl -e "DROP TABLE gochuchamchi.users;"  # -> DENIED

# 3) 감사 로그 스트림 생성 확인
aws logs describe-log-streams --log-group-name /aws/rds/instance/gochuchamchi-db/audit --region ap-northeast-2

# 4) Redis AUTH+TLS — 무인증 접근이 거부되면 성공
sudo dnf install -y redis6
redis6-cli -h <Redis엔드포인트> -p 6379 --tls ping          # -> NOAUTH Authentication required
redis6-cli -h <Redis엔드포인트> -p 6379 --tls -a '<토큰>' ping  # -> PONG
```

로컬(PowerShell) — 마스터 비밀번호가 state에서 사라졌는지:

```powershell
terraform state pull | Select-String "password"
# rds 마스터 값이 안 나와야 함 (redis auth_token은 남는 게 정상 — ESO 이관 대상)
```

### 면접 설명 (한 줄)

> "DB 계층을 제로트러스트로 재구성했습니다. 앱은 마스터가 아니라 DML 전용 계정으로,
> 그 계정은 REQUIRE SSL + 서버측 require_secure_transport로 TLS를 이중 강제하고,
> 자격증명은 배스천 런타임에서 생성·주입해 Terraform state에 남지 않습니다. 접근
> 기록은 MariaDB 감사 플러그인을 CloudWatch로 내보내 확보했고, 세션 스토어(Redis)도
> 전송 암호화+AUTH로 전환해 'VPC 내부 = 신뢰'라는 가정을 데이터 계층에서 제거했습니다.
> IAM DB 인증은 MariaDB 엔진 제약으로 제외했고, 남은 한 개의 state 내 시크릿(Redis
> auth_token)은 ESO 도입 시 이관할 계획까지 잡아뒀습니다."

## 2. 후속 하드닝 (같은 날 2차 — 리뷰 지적사항 반영)

**`main.tf`** — 배스천 EKS access entry를 `AmazonEKSClusterAdminPolicy`(cluster) →
`AmazonEKSEditPolicy`(namespace: `gochuchamchi`)로 축소. 배스천이 클러스터에 하는 일은
앱 Secret 업서트와 runbook §1.4의 cm/secret 조회뿐인데 cluster-admin이었음 — 배스천
침해 시 전 네임스페이스 Secret이 열리는 잔여 구멍. **이후 배스천에서 kube-system/argocd
등 타 네임스페이스 kubectl은 안 됨** → 로컬 kubectl 경로(runbook §1.1) 사용.

**`db-zero-trust.tf`**

- triggers에 `namespace_uid` 추가 — 네임스페이스만 단독 재생성되면 K8s Secret은
  증발하는데 트리거가 그대로라 프로비저너가 안 도는 갭을 자동 복구로 전환.
  (`script_version` v2로 상향 — 다음 apply 때 1회 재실행됨, 비밀번호는 재사용이라 안전)
- ps 순간 노출 제거: python `sys.argv` → `os.environ`, kubectl `--from-literal` →
  `--from-file`(600 파일). 외부 프로세스 argv에 비밀값이 실리는 경로 전부 폐쇄.
- mysql 인증을 `.my.cnf`(defaults-extra-file) → `MYSQL_PWD` env로 교체 — 옵션 파일은
  비밀번호에 `#`이 있으면 주석으로 잘려 **조용히 실패**하는 함정(runbook §1.4에 이미
  문서화된 것과 동일). RDS 관리형 마스터 비밀번호는 `#` 포함 가능해서 실제 발동 가능했음.

**`rds-schema-init.tf`** — 같은 `#` 함정 제거(MYSQL_PWD로 통일). 트리거 불변이라
기존 인프라에는 영향 없음. 내려받은 schema.sql도 종료코드 보존하며 정리하도록 변경.

**`terraform/.gitignore` (신규)** — state/plan + SSM 산출물 json(`*-params.json` 등,
계정 ID·시크릿 ARN 포함) git 제외 준비.

**`docs/runbook.md`** — §1.4/§1.5/§5.1/치트시트 현행화: 삭제된 `gochuchamchi-db-secret`
참조 제거, 앱 계정(`gochuchamchi-db-app`) 접속 절차와 마스터(Secrets Manager 경유) 분리,
`--ssl`/`--tls`+`REDISCLI_AUTH` 필수 반영.

**`docs/DB_SECRET_SETUP.md`** — 수동 생성 가이드 폐기, 자동 주입 구조 설명으로 재작성.

## 3. 보안 백로그 B1~B6 이행 (같은 날 3차)

전체 재점검(SECURITY_BACKLOG.md)에서 나온 잔여 과제를 코드로 이행. 상세·apply 절차·
검증 명령은 백로그 문서에 있고, 여기는 변경 파일 요약만.

- **B1** `securitygroups.tf` — `add_node_sg`의 "VPC 전체 전 포트" 인그레스 제거(빈 SG로
  유지 — destroy 순서 의존 때문), `add_cluster_sg` 소스를 VPC CIDR → 배스천 SG 참조로.
  노드 통신은 EKS 모듈 자체 SG가 전부 커버(ALB→파드 규칙은 LB 컨트롤러가 동적 관리).
- **B2** `main.tf`/`variables.tf` — `key_name` 전면 제거(노드그룹·NAT). 접속은 SSM만.
  **apply 시 노드 롤링 + NAT 재생성** 발생. `SETUP-NEW-WORKER.txt`의 키페어 절차 삭제.
- **B3** `eso.tf`(신규) + `charts/eso-config`(신규) — External Secrets Operator 도입.
  PAT는 Secrets Manager 컨테이너(값은 CLI 1회 주입, **재발급해서** 넣을 것)를 ESO가
  동기화. `argocd.tf`의 `kubernetes_secret_v1.gitops_repo_creds`와
  `var.argocd_git_pat` 삭제 → **PAT의 state 경유 자체가 소멸** (감사 #1 ESO 트리거 해소).
  ESO IAM은 이 스택 시크릿 2개 ARN만(Get/Describe). Redis auth_token은 리소스 인자라
  ESO로도 못 빼는 구조적 한계 — eso.tf 주석에 명시.
- **B4** `variables.tf`/`argocd.tf` — `argocd_admin_password_bcrypt`(해시만 허용하는
  validation) → 차트 `configs.secret.argocdServerAdminPassword` 조건부 주입.
  재구축해도 admin 비밀번호 유지. 미설정 시 기존 동작.
- **B5** `main.tf`(vpc-cni `enableNetworkPolicy=true`) + `k8s-network-policies.tf`(신규) —
  gochuchamchi ns 기본 거부 + 웹앱은 VPC→8080 인그레스, DNS/3306/6379/443/
  pod-identity-agent(169.254.170.23:80) 이그레스만. 시스템 ns는 의도적 제외.
  **apply 후 사이트 기능 검증 필수**, 문제 시 `kubectl -n gochuchamchi delete netpol --all`.
- **B6** `guardduty.tf`(신규) — 기본 탐지 활성(30일 무료). S3 OAC·verify-full·ECR
  IMMUTABLE·앱 계층은 이 저장소 단독으로 조치 불가 → 백로그에 보류 사유 명시.

검증: `terraform get` + `terraform validate` 통과. plan/apply는 미실행 (§2의 변경분과
함께 다음 apply에 일괄 반영 — 백로그 문서의 "apply 절차" 참고).
