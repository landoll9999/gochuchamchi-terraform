# GuardDuty AI 트리아지 — 구현 및 배포 런북

**작성일** 2026-08-12 · **대상 스택** `go/cloudwatch-notifications` · **상태** 코드 완료, **apply 전**

---

## 1. 왜 만들었나

멘토 피드백:

> GuardDuty는 오탐이 너무 많아 현업에서 잘 활용하지 못한다. 로그는 쏟아지는데
> 실질 활용이 어려워 안 쓰는 곳이 대부분이다. 제대로 쓰려면 들어오는 필드값을
> 다 쪼개서 **의미 있는 보안 필드값에만 경고를 올리도록 커스텀**해야 하는데,
> 클라우드 변화가 너무 빨라 그 커스텀을 유지하는 게 힘든 게 현실이다.
>
> (AI × 보안) 쏟아지는 로그를 AI가 자동 분석해 "이건 진짜 위협"만 알려주는
> 도구는 니즈가 있다. **단, 전량 분석 시 토큰 비용(운영비)이 관건이다.**

이 구현이 그 두 문장에 대한 답이다.

- **커스텀 룰의 유지보수 문제** → 룰 테이블 대신 [`ai-triage/context.md`](../cloudwatch-notifications/ai-triage/context.md)
  한 장을 최신으로 유지한다. 인프라가 바뀌면 문서를 고치지, 조건문을 고치지 않는다.
- **토큰 비용 문제** → 애초에 원시 로그를 모델에 넣지 않는다. 탐지는 GuardDuty가
  끝내고(하루 수십만 건), 모델은 **finding 1건의 판단만** 한다(하루 수십 건).
  그 위에 게이트를 5중으로 걸었다(§5).

[2026-08-11 handoff](2026-08-11-log-account-handoff.md) §5의 설계를 Workload 계정에
먼저 구현한 것이다. Log 계정 위임이 끝나면 같은 구조를 그쪽으로 옮긴다.

## 2. 배선

```
GuardDuty finding
   │
   ├─ Rule 1 (타입 기반 필터) ─→ [AI 트리아지 Lambda] ─→ SNS 허브 ─→ Discord / 이메일
   │    (A) 루트·자격증명·백도어…      판정만 붙인다
   │        = severity 무관 통과
   │    (B) 그 외 severity>=4,
   │        소음 타입 제외
   │
   └─ Rule 2 (severity >= 7) ─→ [격리 Lambda] ─→ ENI 검역 SG 교체 / 액세스키 비활성화
                                  AI를 기다리지 않는다
```

**필터와 판단은 층이 다르다.** Rule 1의 타입 필터가 "무엇을 알릴지"를 EventBridge
에서 공짜로 정하고, 트리아지는 살아남은 것에 대해서만 "그중 무엇이 진짜 위협인지"를
붙인다. 소음 제거를 모델에 시키면 그게 곧 토큰 낭비다.

**두 경로는 EventBridge에서 갈라져 서로를 모른다.** 대응(격리)이 모델 지연·장애·
오판에 걸리면 안 되기 때문이다. 이번 변경은 통보 경로에만 끼어들었다.

### 3-1. 같이 고친 기존 버그 2건

트리아지 렌더러를 붙이면서 같은 Lambda에서 발견한 것들. 트리아지와 무관하게
독립적으로 존재하던 문제다.

**🔴 IAM 활동 알림이 Discord에서 조용히 실패하고 있었다.**
`iam-activity.tf`의 `input_transformer`는 이메일 가독성을 위해 **평문 여러 줄**을
SNS로 보내는데, Discord Lambda의 `unwrap_events()`는 모든 메시지에 `json.loads`를
걸고 있었다 → `JSONDecodeError` → SNS 3회 재시도 → DLQ 적재 → DLQ 알람.
**이메일 구독자는 멀쩡히 받으므로 알아채기 어려운 형태의 고장이다.**
수정: JSON 파싱 실패 시 평문 전용 렌더러(`handle_plaintext_event`)로 넘긴다.
정규식으로 필드를 뽑지 않는다 — 발행자 템플릿이 바뀔 때마다 조용히 깨진다.

**🟡 자동대응 3종 확장의 신규 action에 렌더러가 없었다.**
`isolation_function.py`가 `recovered` / `manual-required` / `key-disabled` /
`stale-quarantine` / `audit-clean`을 내보내는데 `action_render` 맵이 그대로여서
`❓ key-disabled` 회색으로 떴다 — **가장 강한 대응인 자격증명 무효화가 가장
눈에 안 띄는 알림**이 되는 상태. 5종 전부 전용 문구/색을 붙였고, 자격증명 경로는
대상이 인스턴스가 아니라 키이므로 제목이 `사용자 / 액세스키`로 나오게 했다.

## 4. 배포 절차

### 4-1. ⚠️ 먼저: Bedrock 모델 액세스 승인 (Terraform 밖)

IAM 권한이 있어도 **콘솔에서 모델 액세스를 따로 켜야** 호출이 된다. 안 켜면
`AccessDeniedException`이 뜨는데, IAM 문제로 착각하기 쉬우니 순서를 지킬 것.

> Bedrock 콘솔 (`ap-northeast-2`) → Model access → Anthropic Claude 계열 승인

이때 **해당 리전에서 `anthropic.claude-opus-5`가 목록에 있는지** 확인한다. 없으면
`ai_triage_bedrock_region`을 서빙되는 리전으로 바꾼다 — 다만 그 순간부터 finding
내용이 그 리전으로 나가므로 데이터 반출 정책을 먼저 확인할 것.

### 4-2. apply

```powershell
cd C:\terraform\go\cloudwatch-notifications
terraform init
terraform plan
terraform apply
```

레이어(Anthropic SDK)는 apply 중 `build-layer.ps1`이 자동으로 빌드한다.
python3 + pip + PyPI 접근이 필요하다. **Windows PowerShell 전제**이므로 Linux CI로
옮길 때는 같은 내용의 sh 스크립트를 추가하고 `ai-triage.tf`의 `interpreter`에서 분기할 것.

### 4-3. 첫 호출 검증 — 여기서 실제로 확인해야 할 것

```powershell
# 테스트 finding 생성. Rule 1의 (A) 갈래(항상 통보)에 걸리는 타입을 골라야
# 필터에서 안 막힌다 — CryptoCurrency: 접두사는 기본 목록에 있다.
aws guardduty create-sample-findings `
  --detector-id (terraform -chdir=..\account-baseline output -raw guardduty_detector_id) `
  --finding-types "CryptoCurrency:EC2/BitcoinTool.B!DNS" `
  --region ap-northeast-2 --profile workload-admin

# 로그 추적
aws logs tail /aws/lambda/gochuchamchi-ai-triage --follow --region ap-northeast-2 --profile workload-admin
```

확인 순서:

1. **Bedrock 호출이 성공하는가** — `AccessDeniedException`이면 4-1(모델 액세스)
   또는 `ai-triage.tf`의 `InvokeTriageModel` 스테이트먼트 리소스 ARN을 점검한다.
   Mantle 엔드포인트의 정확한 IAM 액션/리소스 형태는 이번에 **실호출로 검증되지
   않았다** — 첫 호출이 이 설계에서 유일하게 확실치 않은 지점이다.
2. **Discord에 판정이 붙어 오는가** — 제목이 `🔴/🟡/⚪ + 한 줄 요약`이고,
   "판정 근거 출처" 필드에 `모델 판정 (anthropic.claude-opus-5)`이 찍혀야 한다.
3. **토큰 사용량이 보이는가** — CloudWatch > Metrics > `Gochuchamchi/AITriage`에
   `InputTokens` / `OutputTokens` / `CacheReadTokens` / `EstimatedCostUsd`.
4. **같은 finding을 한 번 더 쏴 본다** — 두 번째는 `판정 근거 출처`가
   `이전 동일 finding 판정 재사용`으로 바뀌고 모델 호출이 없어야 한다.
5. **저심각도 회귀 확인** — `Policy:IAMUser/RootCredentialUsage`(severity 2)를
   쏴서 `gate-severity`가 아니라 **모델 판정**이 붙는지 본다. 여기서 판정이 없으면
   `ALWAYS_TRIAGE_TYPE_PREFIXES` 환경변수가 비어 있는 것이다.
6. **IAM 활동 알림이 Discord에 뜨는지** (§3-1 버그 수정 확인) — 이메일만 오고
   Discord가 조용하면서 DLQ 알람이 뜨면 수정이 안 반영된 것이다.

## 5. 비용 통제 — 5중 게이트

멘토가 지적한 "전량 분석 시 토큰 비용"에 대한 직접적인 답. 순서대로 통과해야만
모델이 호출된다.

| # | 게이트 | 변수 | 기본값 |
|---|---|---|---|
| 0 | **타입 기반 통보 필터** (EventBridge) | `guardduty_notify_noise_types` | 소음 4종 |
| 1 | severity 하한 (**"항상 통보" 타입은 예외**) | `guardduty_notify_min_severity` + `guardduty_always_notify_type_prefixes` — Rule 1과 **같은 변수 공유** | 4 (Medium) |
| 2 | 결정적 억제 룰 | `ai_triage_suppress_finding_types` | `[]` |
| 3 | 판정 캐시 (타입 × 리소스) | `ai_triage_cache_ttl_hours` | 6시간 |
| 4 | 일일 호출 상한 | `ai_triage_daily_call_limit` | 200 |
| 5 | 프롬프트 캐싱 (**버스트에서만 유효** — 아래) | (`context.md` 블록에 breakpoint) | 자동 |

게이트 0이 가장 싸다 — EventBridge에서 걸리면 Lambda 호출조차 없다.

**게이트 5는 상시 절감 수단이 아니다.** `ephemeral` 캐시의 기본 TTL은 5분인데
이 환경의 finding은 몇 시간씩 벌어져 들어온다. 평상시에는 거의 매번 캐시 미스이고,
미스면 캐시 **쓰기**(정가 1.25배)를 물어 캐싱을 안 걸었을 때(1.0배)보다 25% 비싸다.
손익분기가 5분 안에 2건이라, 실제로 이득이 나는 건 finding이 쏟아질 때 —
즉 게이트 4(일일 상한)를 태우는 바로 그 상황이다. **버스트 보험으로 이해할 것.**
프리픽스가 4천 토큰 남짓이라 평상시 손해는 건당 +$0.005(월 $5 미만) 수준이므로
그대로 두었다. 며칠 뒤 `CacheReadTokens`가 계속 0이면 떼어낼지 판단한다.
`ttl: "1h"`로 늘리는 건 쓰기가 2배가 되어 더 나쁘다.

**게이트 1에 전용 변수를 두지 않은 이유** (2026-08-12 개편 반영): Rule 1의 (A)
갈래는 severity와 무관하게 루트 사용·자격증명 탈취 등을 통과시킨다. 트리아지가
자기 하한을 따로 들고 있으면 그 finding들이 Lambda에서 `gate-severity`로 걸려
**가장 중요한 것만 AI 판정을 못 받는다.** 실제로 이 환경의 finding은 전부
severity 2였다. 같은 변수를 공유해 두 값이 어긋날 여지를 없앴다.

**운영 튜닝 순서**: 며칠 돌려 보고 `Verdict_likely_benign`이 같은 타입에서 반복되면
→ 완전 소음이면 `guardduty_notify_noise_types`(게이트 0, 알림 자체를 끔),
알림은 받되 판정만 아끼려면 `ai_triage_suppress_finding_types`(게이트 2).

`EstimatedCostUsd`는 1st-party 정가 기준 **추정치**다(Bedrock 파트너 단가는 다를
수 있음). 실제 청구는 Cost Explorer에서 확인할 것 — 이 지표는 "오늘 얼마나
태웠나"를 대시보드에서 감으로 잡는 용도다. 캐시 토큰은 정가로 과금되지 않으므로
(읽기 0.1배 / 쓰기 1.25배) 그 배율을 반영해 계산한다.

### 5-1. 실측 기준 비용

배포 전 파일 크기 기준 추정. 첫 호출 후 `InputTokens` / `OutputTokens` 지표로
실제 값으로 대체할 것.

| 구성 | 크기 | 추정 토큰 |
|---|---|---|
| `TRIAGE_RULES` | 약 4.3KB | ~1,500 |
| `context.md` | 6,874 B | ~2,300 |
| finding JSON (화이트리스트 투영 후) | 보통 1~3KB, 상한 20,000자 | ~500–1,000 (최대 6,000) |
| CloudTrail 보강 (`MaxResults=15`) | — | ~300–800 |
| **입력 합계** | | **~4,500–5,500** |
| 출력 (adaptive thinking + verdict, `max_tokens=4096`) | | **~1,000–2,500** |

1st-party 정가($5/$25 per MTok) 기준 **1건당 약 $0.06**. 비용의 60% 이상이 출력
쪽인데, 그 대부분이 thinking 토큰이다 — **건당 비용을 줄이는 가장 큰 레버는
게이트가 아니라 `ai_triage_effort`다.** 트리아지는 3분류 판정에 가까워
`low`로 내려도 품질이 유지될 여지가 크다. `medium`으로 며칠 돌려 판정 품질을
확인한 뒤 비교할 것.

- 평상시(하루 30건 가정): $1.8/일 → **월 $50~60**
- 일일 상한(200건) 도달: $12/일 → **월 약 $360**
- 최악(전 건이 finding 상한 + 출력 상한): 건당 $0.157 × 200 → **월 약 $940**

`ai_triage_daily_call_limit`이 거는 것은 **호출 횟수 상한이지 토큰 상한이 아니다.**
하드 실링은 세 번째 줄이며, "상한이 걸려 있다"고 설명할 때 이 구분이 필요하다.

## 6. 안전장치 — 타협하지 않은 3원칙

handoff §5-3 그대로 구현했고, 로컬 테스트로 검증했다.

**① AI에게 억제 권한이 없다.** 판정이 무엇이든 SNS 발행은 항상 일어난다.
Bedrock 장애·상한 초과·스키마 위반·모델 거부 — 어떤 경로로 빠져도 "AI 판정 없음"
으로 통보되고, finding 원본은 GuardDuty에 그대로 남는다. Lambda 자체가 죽는 경우도
`dead_letter_config`로 기존 알림 DLQ에 적재되고, DLQ 알람이 이메일로 직접 간다.

**② 프롬프트 인젝션 방어.** finding 필드는 공격자가 값을 정할 수 있다.
(a) 화이트리스트 투영으로 모델이 보는 필드를 제한하고,
(b) `<finding>` 델리미터로 데이터임을 명시하고,
(c) 구조화 출력(`output_config.format`)으로 판정 스키마를 강제하며,
(d) 인젝션 시도가 감지되면 그 자체를 침해 신호로 삼아 등급을 올리고 Discord에
경고 필드를 띄운다. 그리고 ①이 최대 피해를 원천 차단한다.

**③ API 키가 없다.** Bedrock을 쓰므로 인증은 Lambda 실행 역할의 IAM뿐이다.
state 오염도, 시크릿 로테이션 부담도 발생하지 않는다.

## 7. 롤백

```hcl
# terraform.tfvars
enable_ai_triage = false
```

apply하면 트리아지 Lambda·레이어·테이블이 사라지고 EventBridge target이 SNS 직결로
되돌아간다. **알림 자체는 끊기지 않는다** — 판정만 없어진다.

즉시 멈춰야 하면 EventBridge rule을 disable하는 대신 위 스위치를 쓸 것. rule을
끄면 통보 경로 전체가 죽는다.
