1. javac 인코딩 — x-windows-949 unmappable character

증상

S3Service.java(UTF-8 저장, 한글 주석 포함)를 컴파일하니 unmappable character (0xED) for encoding x-windows-949 경고가 수십 건 쏟아졌다. 방금 손댄 파일이라 내가 넣은 한글이 뭔가 잘못됐나 싶은 착시가 먼저 온다. 

S3Service.java:14: warning: unmappable character (0xED) for encoding x-windows-949
S3Service.java:14: warning: unmappable character (0xED) for encoding x-windows-949
...  (같은 경고 수십 건, 전부 한글 주석 줄)

원인

javac는 -encoding을 안 주면 플랫폼 기본 인코딩으로 소스를 읽는다. Windows에서 그 기본값이 cp949 = x-windows-949다. 파일은 UTF-8인데 javac가 cp949로 해석하니 한글 바이트(0xED 등)가 매핑 불가로 깨진다. Maven 빌드는 project.build.sourceEncoding=UTF-8로 컴파일하므로 이 문제가 안 보이지만, javac를 직접 호출하면 그 설정이 어디에도 실리지 않는다.

해결

javac에 -encoding UTF-8을 붙이자 그 경고가 전부 사라졌다.

판별 근거 — 에러가 코드 로직(타입·심볼·구문)이 아니라 unmappable character 한 종류뿐이면, 그건 인코딩 옵션 문제지 코드 문제가 아니다. 줄 번호가 전부 한글이 들어간 줄에 몰려 있는 것도 같은 신호다.

2. 앱 컴파일 완전검증의 한계 — mvn/mvnw·의존성 부재

증상

인코딩을 넘긴 뒤에도 컴파일이 실패했다. 이번엔 얼굴이 바뀌어 package org.springframework... does not exist, package software.amazon.awssdk... does not exist가 떴다. "그럼 정말 내 코드가 문제인가" 싶어지는 지점이다.

원인

이 PC에는 mvn이 없고, 이 Spring 프로젝트에는 mvnw(래퍼)도 없다. ~/.m2/repository에 이 프로젝트의 의존성(spring / awssdk)이 받아져 있지 않고, target/classes도 없어 로컬에서 한 번도 빌드된 적이 없다. 즉 클래스패스에 라이브러리가 통째로 빠져 있어 import가 전부 "패키지 없음"으로 떨어진다.

확인 지점상태의미
mvn / mvnw둘 다 없음빌드 진입점 없음
~/.m2/repositoryspring · awssdk 의존성 없음클래스패스 공백
target/classes없음로컬 빌드 이력 0

판단 — "완전 컴파일"을 "내 변경 관련 에러 없음"으로 갈음

남은 에러가 전부 "패키지 없음"이고, 내가 추가한 코드(Map.of 사용, 매직바이트 검사, byte 연산)에서 나온 타입·구문 에러는 0건이었다. 이건 환경 제약이지 코드 결함이 아니다. 의존성만 있으면 사라질 에러이므로 CI(GitHub Actions)에서는 통과할 것으로 판단하고, 로컬에서 완전 컴파일을 고집하는 대신 "내 변경 관련 에러 없음"으로 검증을 갈음했다.

판별 근거 — 남은 에러의 종류를 보면 된다. 전부 does not exist(패키지/심볼 부재) 계열이고 내가 만진 심볼의 타입·구문 에러가 0이면, 실패의 원인은 없는 라이브러리지 잘못 짠 코드가 아니다. 로컬 환경 부재를 코드 문제로 오인하기 가장 쉬운 자리다.

3. terraform validate — provider 캐시 부재

증상

log-archive 루트에서 terraform validate가 no package for registry.terraform.io/hashicorp/archive cached in .terraform로 실패했다. 코드가 잘못된 것처럼 보이지만, 실은 검증기 자신이 아직 준비가 안 된 상태다.

원인

매일 init을 도는 건 terraform 루트 하나뿐이다. log-archive를 비롯한 다른 루트들은 이 세션에서 init한 적이 없어 .terraform/providers가 비어 있다. validate는 provider 스키마가 있어야 타입을 검사할 수 있으므로, 캐시가 없으면 코드를 보기도 전에 멈춘다.

해결

# 백엔드 접속 없이 provider만 받아 캐시를 채운 뒤 validate
terraform init -backend=false -input=false
terraform validate   → 통과

-backend=false로 백엔드(원격 state)는 건드리지 않고 provider만 채웠고, 이 방식으로 5개 루트 전부 validate 통과를 확인했다.

판별 근거 — 에러 메시지에 cached in .terraform이 들어 있으면 코드 유효성 문제가 아니라 init을 안 돌린 루트라는 뜻이다. "매일 init하는 루트는 하나뿐"이라는 워크플로를 기억하면 바로 걸러진다.

4. terraform fmt가 정렬을 바꿔 Edit이 "String not found"

증상

변수를 추가하려고 Edit을 걸었더니 String to replace not found가 났다. 방금 읽은 파일 내용 그대로 앵커를 잡았는데도 안 맞는다 — 파일이 유령처럼 바뀐 느낌이다.

원인

앞선 terraform fmt가 = 정렬(공백 개수)을 바꿔 놓았다. 내 old_string은 fmt 이전의 공백을 담고 있어서 현재 파일과 글자 단위로 불일치한다. 내용은 같아 보여도 공백 폭이 달라 exact match가 깨진 것이다.

해결

Grep으로 현재 파일의 실제 텍스트(정렬된 상태)를 다시 읽어 그 앵커로 Edit했다. fmt를 돌린 뒤에는 항상 파일을 재확인하고 앵커를 다시 뜬다.

판별 근거 — "분명히 방금 본 내용인데 not found"가 뜨면, 사이에 포매터(fmt / prettier 등)가 끼어들어 공백·정렬을 바꿨는지를 먼저 의심한다. 기억 속 텍스트가 아니라 지금 디스크의 텍스트가 진실이다.

5. Edit 앵커 오타 — 존재하지 않는 SQL 순서

증상

siem-detection-rules.tf에 룰을 추가하려는데, data-egress 룰 끝을 가리킨 old_string이 불일치했다. §4와 증상이 똑같아 보여서 또 fmt인가 싶지만 원인이 다르다.

원인

이번엔 파일이 바뀐 게 아니라 내 앵커가 틀렸다. 앵커에 ORDER BY total_bytes DESC를 중복으로 잘못 적었다. 실제 SQL의 절 순서는 GROUP BY → HAVING → ORDER BY인데, 기억으로 앵커를 지어내다가 없는 순서를 만들어 낸 것이다.

내가 적은 앵커 (틀림)
GROUP BY→ ORDER BY total_bytes DESC
중복 삽입
파일의 실제 순서
GROUP BY→ HAVING→ ORDER BY total_bytes DESC

해결

파일의 정확한 절 순서를 보고 앵커를 다시 만들어 Edit했다.

판별 근거 · §4와의 구별 — 둘 다 "not found"지만 원인이 반대다. §4는 파일이 바뀐 것(fmt), §5는 내 기억이 틀린 것(앵커 오타)이다. 구별법은 하나 — 기억이 아니라 파일을 보고 앵커를 만든다. Grep으로 현재 텍스트를 뜨면 두 경우 모두 즉시 해결된다.

6. PowerShell 5.1 — BOM 없으면 한글이 깨진다

증상

verify-auto-response.ps1을 Write로 생성하면 UTF-8 no BOM으로 저장된다. PS 5.1이 그 파일을 cp949로 읽어 한글 주석·문자열이 깨진다. 스크립트 로직은 멀쩡한데 실행하면 문법 에러나 문자 깨짐으로 나타나서, 처음엔 스크립트를 잘못 짠 줄 안다.

원인

PS 5.1은 BOM이 없는 파일을 시스템 로캘(cp949)로 디코딩한다. UTF-8로 저장된 한글이 cp949로 읽히니 깨진다. Write 도구의 기본 출력이 no BOM이라 도구의 기본값과 PS 5.1의 기본값이 어긋나는 지점이다.

해결

# Write로 만든 뒤 Python으로 BOM(0xEF 0xBB 0xBF)을 앞에 붙인다
BOM = b'\xef\xbb\xbf'
data = open(path, 'rb').read()
open(path, 'wb').write(BOM + data)

기존 verify-* 스크립트들도 전부 BOM이 붙어 있어, 바이트를 대조해서 같은 상태(EF BB BF로 시작)로 맞췄는지 확인했다.

판별 근거 — 새로 만든 .ps1에서만 한글이 깨지고 기존 스크립트는 멀쩡하면, 차이는 코드가 아니라 BOM 유무다. xxd/hex로 첫 3바이트가 EF BB BF인지 보면 확정된다.

7. cp949 em-dash 사망 — 반복되는 함정 (read_me·AWS CLI)

증상

read_me(visualize)가 돌려준 62KB JSON을 Python으로 파싱·출력하려다 'cp949' codec can't encode character '—' (em-dash)로 죽었다. JSON을 못 다루는 것처럼 보이지만, 실제로는 콘솔에 찍는 순간 죽는 것이다.

원인

Windows 콘솔 기본 인코딩 cp949가 em-dash(—)를 표현하지 못한다. 파싱은 성공하고, print가 그 문자를 콘솔로 내보내는 단계에서 인코딩이 터진다. 이 프로젝트에서 AWS CLI도 같은 이유로 죽어 "리소스 0개"로 오인되는 함정이 반복된다 — 비ASCII가 든 설명 필드 하나 때문에 조회 전체가 실패하고, 화면에는 결과가 없는 것처럼 보인다.

해결

비ASCII가 든 필드를 출력에서 아예 빼고 필요한 것(여기서는 CSS 변수 목록)만 뽑아 찍었다. AWS CLI라면 --query로 설명 필드를 출력에서 제외하는 것과 같은 요령이다.

판별 근거 · 반복 함정 — 조회/파싱이 "0개" 또는 codec 에러로 끝나면 데이터가 없는 게 아니라 콘솔이 특정 문자를 못 찍는 것일 수 있다. cp949 + em-dash(또는 그 외 비ASCII)는 이 프로젝트에서 이미 여러 번 밟은 자리다. "리소스 0개"가 나오면 인코딩부터 배제하고 넘어간다.

8. git checkout main으로 자동대응 코드가 "사라진" 것

증상

WAF 패치용 fix 브랜치를 만들려고 git checkout main을 했더니, 작업트리에서 자동대응 코드(edge.tf·isolation_function.py 등)가 없어졌다. 방금까지 있던 파일이 통째로 사라지니 실수로 날렸나 하고 가슴이 철렁하는 순간이다.

원인

그 파일들은 feat 브랜치 커밋(acaffd8)에만 있고 main에는 없다. checkout main을 하면 작업트리가 main 버전(자동대응 없음)으로 바뀌고, uncommitted였던 WAF 변경만 그대로 따라온다. 사라진 게 아니라 다른 브랜치에 안전하게 커밋되어 있는 것이다.

feat/detection-and-auto-response (acaffd8, origin에 push됨)
edge.tf isolation_function.py …자동대응 일체 ＋ WAF 변경 (uncommitted)
git checkout main 이후 작업트리
자동대응 코드 없음
main엔 애초에 없음 ＋ WAF 변경만 따라옴 (uncommitted라 브랜치 무관)

판단 — 의도된 결과다

이건 두 주제(자동대응 / 보안 패치)를 분리하려는 의도된 동작이다. 자동대응은 feat 브랜치에 커밋되어 있고 origin에도 push되어 있어 안전하다. 자동대응 작업을 이어가려면 git checkout feat/detection-and-auto-response로 돌아가면 된다.

판별 근거 — "파일이 사라졌다"의 첫 확인은 git status와 git branch다. 사라진 파일이 다른 브랜치의 커밋(acaffd8)에 들어 있고 그 브랜치가 origin에 있으면 유실이 아니라 브랜치 전환의 정상 결과다. uncommitted 변경만 브랜치를 따라 이동한다는 규칙을 기억하면 당황할 일이 없다.

9. 아키텍처 결정 3건 — 함정은 아니나 판단 근거 기록

아래 셋은 함정이 아니라 이번에 내린 설계 결정이다. 나중에 "왜 이렇게 배선했나"를 다시 묻지 않도록 근거를 남긴다.

① WAF IP set 위치 — 일일 계층이 아니라 상시 계층에

차단용 WAF IP set은 CLOUDFRONT scope라 us-east-1 전용이다. 그런데 그 IP set을 참조하는 edge WAF는 매일 destroy되는 일일 계층에 있다. 차단된 IP 목록은 매일 사라지면 안 되는 상태값이므로, IP set을 상시 계층 persistent에 두고, 일일 edge가 이를 data source로 참조하게 했다. 참조 방향은 한 방향(일일 → 상시)이라 일일 계층을 밀어도 IP 목록은 살아남는다. IP set의 내용은 Lambda가 관리하므로, terraform은 ignore_changes로 그 내용에서 손을 뗀다(런타임이 채운 값을 terraform이 매번 되돌리지 않도록).

참조 방향 — 한 방향 (일일 → 상시)
edge WAF (일일, 매일 destroy) — data source —> IP set (persistent 상시, us-east-1) ◁ ignore_changes Lambda (내용 관리)

② Lambda → EKS 접근 — VPC 직결 대신 배스천 SSM

자동대응 Lambda가 EKS를 만져야 하는데, 클러스터가 매일 재생성 + 프라이빗 엔드포인트라 Lambda를 VPC에 직결하기 부담스럽다(ENI·서브넷·매일 바뀌는 엔드포인트를 다 물려야 함). 대신 이미 gochuchamchi 네임스페이스 edit 권한이 있는 배스천을 SSM으로 시켜 kubectl을 실행하게 했다. 이건 새 경로가 아니라 기존 DB 프로비저닝과 같은 경로라, 검증된 배선을 재사용하는 셈이다.

Lambda → EKS (기존 DB 프로비저닝과 동일 경로)
자동대응 Lambda— SSM —> 배스천 (gochuchamchi ns edit 권한)— kubectl —> EKS (매일 재생성·프라이빗)

③ SIEM 크로스계정 배선 — 권한은 이미 있고 라우팅만 추가

Log 계정 → Workload 계정으로 이벤트를 put할 권한은 이미 존재했다. 기존 log-account-eventbridge.tf의 event_permission(계정 단위)이 그 권한을 이미 열어 두고 있어서, 권한을 새로 추가할 필요가 없었다. 이번에 필요한 것은 라우팅 rule 하나뿐이라, 그것만 추가했다.

판단 근거 — 크로스계정 배선은 보통 "신뢰/권한"과 "라우팅"이 한 세트인데, 이번엔 권한(계정 단위 event_permission)이 선행 작업으로 이미 깔려 있었다. 기존 log-account-eventbridge.tf를 먼저 읽어 이를 확인했기 때문에 중복 권한을 새로 만들지 않고 rule만 얹을 수 있었다. 기존 코드를 읽는 것이 절약이 된 사례다.
