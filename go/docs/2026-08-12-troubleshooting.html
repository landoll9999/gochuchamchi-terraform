0. 이 문서를 읽는 법

이 기록의 절반은 실제 결함이 아니라 오진이다. 도구가 만든 착시를 문제로 착각하거나, 반대로 진짜 고장을 정상으로 착각한 사례가 섞여 있다. 그래서 결함 목록이 아니라 “무엇을 보고 무엇을 잘못 믿었는가” 기준으로 묶었다.

분류뜻건수
착시도구·환경이 만든 가짜 신호. 코드는 멀쩡했다5
은폐된 고장실제로 실패하고 있었는데 성공처럼 보였다4
설계 구멍동작은 하지만 의도한 보호가 안 되던 것6
경로·이력코드가 아니라 저장소·배포 경로 문제3
관통하는 한 문장. 이날 나온 오진은 거의 전부 “에러를 감춘 것”에서 나왔다. 2>/dev/null, 2>&1, 앱이 반환한 200, 이메일만 오는 알림 — 실패를 삼키는 장치가 하나 끼면 그 뒤의 모든 판단이 틀어졌다.

1. 착시 — 도구가 만든 가짜 신호

1-1. daily-up.ps1이 “init 실패”라고 했지만 terraform은 성공했다

증상
스크립트가 ✖ init 실패로 중단. 그런데 같은 디렉터리에서 terraform init을 직접 돌리면 정상.
원인
PowerShell 5.1에서 네이티브 명령의 출력을 파이프로 흘리며 Select-Object -First 5를 걸면, 필요한 만큼 읽은 뒤 파이프라인을 조기 종료한다. 그러면 terraform이 정상 종료 코드를 돌려줄 기회가 없어 $LASTEXITCODE가 -1이 된다. 스크립트는 그걸 보고 실패로 판정했다.
조치
출력을 먼저 변수로 받고 종료 코드를 즉시 저장한 뒤에 필터링한다. 
$initOut  = terraform init -input=false -no-color
$initCode = $LASTEXITCODE          # 필터링 전에 먼저 잡는다
$initOut | Select-String "Initializing|has been successfully" |
    Select-Object -First 5 | ForEach-Object { Write-Host "   $($_.Line)" }
if ($initCode -ne 0) { ... }
교훈. $LASTEXITCODE는 파이프라인이 끝난 뒤 읽으면 이미 늦다. 같은 함정을 daily-down.ps1에서도 뒤늦게 발견했다(1-5).

1-2. 로컬 python이 Microsoft Store 스텁이었다

증상
파이썬 파일 구문 검사가 가짜 SYNTAX ERROR를 뱉었다. 나중에는 Lambda 레이어 빌드도 막았다.
원인
%LOCALAPPDATA%\Microsoft\WindowsApps\python.exe는 실제 인터프리터가 아니라 Store로 유도하는 스텁이다. pip은 아예 없었다. 이게 PATH에서 앞서 있었다.
조치
실제 Python 3.12.10 설치 후, build-layer.ps1이 PATH를 믿지 않도록 Resolve-Python을 추가했다. 후보를 py 런처 → PATH → 표준 설치 경로 순으로 모으고, WindowsApps 경로는 실행 전에 경로로 걸러낸다. 실행해서 판별하려면 네이티브 stderr 리다이렉션이 필요한데 그게 또 1-1과 같은 함정을 부르기 때문이다.
교훈. “명령이 PATH에 있다”와 “그 명령이 동작한다”는 다르다. 빌드 스크립트는 도구를 찾는 것이 아니라 검증해야 한다.

1-3. Git Bash 경로 변환으로 로그 조회가 전부 실패했고, 그걸 2>/dev/null로 가렸다

증상
구독 필터를 조회하니 전 로그 그룹에서 0건. “Log 계정이 아무 작업도 안 했다”는 결론까지 갔다.
원인
Git Bash(MSYS)는 /aws/...처럼 슬래시로 시작하는 인자를 Windows 경로로 자동 변환한다. AWS API에는 엉뚱한 값이 전달돼 InvalidParameterException이 났는데, 루프에 2>/dev/null이 걸려 있어 그 에러가 “결과 없음”으로 둔갑했다.
조치
export MSYS_NO_PATHCONV=1. 다시 조회하니 application·control-plane·waf 구독이 모두 살아서 Log 계정 destination을 정상으로 가리키고 있었다.
이 오진의 대가가 가장 컸다. 잘못된 근거로 “Log 계정 담당자가 작업을 안 했다”고 판단할 뻔했다. 실제로는 그쪽이 전부 끝내 둔 상태였고, 막혀 있던 것은 우리 쪽이었다(4-2).

1-4. 유령 destroy — 변수를 안 넘기면 실재 리소스가 삭제 대상으로 보인다

증상
cloudwatch-notifications plan에서 이메일 구독이 삭제로, go/terraform plan에서는 엣지 SG와 ACM 인증서가 삭제·교체 대상으로 잡혔다.
원인
기본값이 없는 변수(alert_emails)와 2단계 apply용 변수(enable_edge)를 주입하지 않은 채 plan을 돌렸다. 배포는 그 값이 있는 상태로 되어 있으니 차이가 삭제로 표시된다.
조치
plan·apply 시 항상 같이 넘긴다. daily-up.ps1은 1차(기본값) → 2차(enable_edge=true) 2단계로 apply한다는 점도 이때 파악했다. 
TF_VAR_alert_emails='["where5683@naver.com"]' terraform plan
TF_VAR_enable_edge=true terraform plan   # go/terraform 은 2차 상태가 배포 현실
교훈. plan 결과를 믿기 전에 “이 plan이 배포와 같은 입력으로 돌았는가”를 먼저 묻는다.

1-5. daily-down.ps1의 유출 감지가 정상 리소스를 오탐했다

증상
destroy plan에 상시 계층이 섞였는지 보는 키워드 검사가 log.archive 패턴을 들고 있었다.
원인
정규식의 .가 _에 매칭돼 aws_cloudwatch_log_subscription_filter.cloudwatch_log_archive[*]를 걸어냈다. 이 구독 필터는 일일 스택의 정상 구성원이라 매일 밤 같이 지워지는 게 맞는데, 그걸 “상시 계층 유출”로 판정해 destroy를 막았다. 이날 rds-audit이 추가되며 대상이 3개로 늘었다.
조치
패턴에서 log.archive 제거. 같은 파일의 1-1 함정(2>&1 | Tee-Object)도 함께 수정.

2. 은폐된 고장 — 성공처럼 보이던 실패

2-1. 앱 감사 로그가 400건 중 358건 실패하고 있었다

증상
없었다. 애플리케이션은 200을 반환했고 화면도 정상이었다.
발견 경위
DB 감시 축(QUERY_DML_NO_SELECT)을 켜자마자 감사 로그에 실패한 INSERT가 쏟아졌다. 5분에 266건, 표본 400건 중 358건이 실패였다.
원인
Spring 저장소의 schema.sql에는 있는 audit_logs·user_behavior_logs가 Terraform이 적용하는 사본에 빠져 있었다. 두 사본이 어긋난 것을 아무도 검사하지 않았다.
조치
실제 Spring 파일을 읽어 두 테이블을 추측하지 않고 원문 그대로 복원. 추측한 스키마는 NOT NULL·타입·인덱스가 실제와 달랐다. 재발 방지로 verify-schema-sync.ps1과 CI 워크플로를 추가해 CREATE TABLE 블록을 대조한다.
교훈. 감시를 켜는 행위 자체가 진단이었다. “감사 로그가 비어 있다”와 “감사 로그를 쓰는 데 실패하고 있다”는 화면상 구분되지 않는다.

2-2. IAM 활동 알림이 Discord에서만 조용히 죽고 있었다

증상
이메일로는 알림이 정상 도착. Discord에만 안 옴. DLQ 알람이 뜨지만 원인이 연결되지 않음.
원인
iam-activity.tf의 input_transformer는 이메일 가독성을 위해 평문 여러 줄을 SNS로 보낸다. 그런데 Discord Lambda의 unwrap_events()는 모든 메시지에 json.loads를 걸고 있었다 → JSONDecodeError → SNS 3회 재시도 → DLQ 적재.
조치
파싱 실패 시 평문 전용 렌더러로 넘긴다. 정규식으로 필드를 뽑지 않는다 — 발행자 템플릿이 바뀔 때마다 조용히 깨지기 때문이다.
검증
실제 input_transformer 출력 형태로 합성 SNS 이벤트를 만들어 Lambda를 직접 호출 → {"plaintext": true} + HTTP 200. send_discord_message는 HTTP 오류를 로깅 후 raise하므로 200은 Discord가 수락했다는 뜻이다.
교훈. 다중 구독 알림에서 일부 채널만 죽는 고장이 가장 발견하기 어렵다. 한 채널이라도 오면 사람은 “알림은 온다”고 판단한다.

2-3. 가장 강한 자동대응이 가장 눈에 안 띄는 알림이었다

증상
자동대응 확장으로 새로 생긴 action 5종이 Discord에서 ❓ key-disabled 회색으로 떴다.
원인
isolation_function.py는 recovered / manual-required / key-disabled / stale-quarantine / audit-clean을 내보내는데 렌더러의 action_render 맵이 그대로였다. 탈취 의심 자격증명 무효화 — 가장 강한 대응 — 가 시각적으로 가장 약하게 표시됐다.
조치
5종 전부 전용 문구·색 부여. 자격증명 경로는 대상이 인스턴스가 아니라 키이므로 제목을 사용자 / 액세스키로 바꿨다(instanceId가 없어 -로 뜨던 문제).

2-4. 심각도 숫자 필터가 루트 계정 사용을 버리고 있었다

증상
GuardDuty 통보가 소음은 많은데 정작 중요한 게 안 왔다.
원인
severity 하한만으로 거르고 있었다. 이 환경의 finding은 사실상 전부 severity 2였고, 루트 자격증명 사용(Policy:IAMUser/RootCredentialUsage, severity 2)이 하한에 걸려 버려지는 반면 포트 스캔 같은 소음은 통과했다.
조치
EventBridge 이벤트 패턴을 타입 기반으로 전환. (A) 루트·자격증명·백도어 등은 severity 무관 통과, (B) 그 외는 severity ≥ 4 이면서 소음 타입 제외.
교훈. severity는 벤더가 매긴 맥락 없는 숫자다. “이 환경에서 무엇이 심각한가”는 타입과 주체로 판단해야 한다.

3. 설계 구멍 — 동작하지만 보호가 안 되던 것

3-1. “MariaDB는 IAM DB 인증을 지원하지 않는다”는 저장소 주석이 틀렸다

증상
rds.tf 주석이 “엔진 제약이라 IAM 토큰 인증을 못 켰다”고 적고 있었고, 그대로 믿고 사용자에게 같은 답을 했다.
원인
사실이 아니었다. AWS API로 확인하니 MariaDB 10.11은 IAM DB 인증을 지원한다. 검증 없이 저장소 주석을 재생산한 것이 원인이다.
조치
iam_database_authentication_enabled = true 활성화, AWSAuthenticationPlugin 기반 전용 계정 생성, 15분 토큰 발급용 IAM 정책 부여. 틀린 주석은 취소선으로 원문을 남긴 채 정정했다. 
engine                            mariadb 10.11.18
IAMDatabaseAuthenticationEnabled  True
MARIADB_AUDIT_PLUGIN              CONNECT,QUERY_DDL,QUERY_DCL,QUERY_DML_NO_SELECT
교훈. 코드 주석은 작성 시점의 사실이고 검증된 적이 없을 수 있다. “왜 안 켰나”에 대한 답이 주석에만 근거하면 그 답은 감사 대상이다.

3-2. 환경 설명 문서가 읽기 전용 권한자에게 열려 있었다

증상
AI 트리아지 설계 검토 중 발견. 배포 자체는 하지 않았다.
원인
context.md(계정 ID·네트워크 구조·IAM 주체·배치된 통제·탐지 우선순위, 그리고 스스로 적어 둔 방어 공백 목록)를 Lambda 함수 zip에 넣었다. lambda:GetFunction은 배포 패키지의 presigned URL을 돌려주고, 그 권한은 ReadOnlyAccess 관리형 정책에 포함된다.
조치
S3로 옮기되 그것만으로는 부족하다 — ReadOnlyAccess에는 s3:GetObject도 있다. 실효는 SSE-KMS + 전용 CMK 키 정책에서 나온다. SSE-KMS 객체는 요청자 본인이 kms:Decrypt를 가져야 읽히는데 ReadOnlyAccess에는 그게 없다. 버킷 정책 explicit Deny는 배포 주체까지 잠글 위험이 있어 쓰지 않고, 통제를 키 정책 한 곳에만 뒀다.
교훈. 흩어진 사실은 AWS가 이미 갖고 있지만, 조립된 문서는 이 파이프라인이 처음 만든 것이다. 정보 집약 자체가 새로운 민감도를 만든다.

3-3. 비용 절감 장치가 오히려 25% 더 비쌌다

원인
프롬프트 캐시의 ephemeral 기본 TTL은 5분인데 GuardDuty finding은 몇 시간씩 벌어져 들어온다. 평상시 거의 매번 미스이고, 미스면 캐시 쓰기(정가 1.25배)를 문다 — 캐싱을 안 걸었을 때(1.0배)보다 비싸다.
조치
손익분기가 5분 안에 2건이므로 버스트 보험으로 재정의하고 문서를 정정했다. ttl:"1h"는 쓰기가 2배라 더 나쁘다. 실제 Bedrock 요금표로 배율을 확인했다.
Opus 5   입력 $5 / 출력 $25 / 캐시읽기 $0.5(0.1x) / 캐시쓰기 $6.25(1.25x) / 1h $10(2x)
Sonnet 5 입력 $2 / 출력 $10 / 캐시읽기 $0.2      / 캐시쓰기 $2.5        / 1h $4

3-4. 비용 지표가 실제보다 높게 나오고 있었다

원인
log_usage()가 input + cache_read + cache_write를 그냥 더해 전부 입력 정가로 곱했다. 캐시 토큰은 정가로 과금되지 않는다(읽기 0.1배 / 쓰기 1.25배). 캐시가 맞을 때 입력 비용을 최대 10배 부풀린다.
조치
배율을 반영. 방향이 보수적(항상 실제보다 높게)이라 알람 용도로 위험하진 않았지만, Cost Explorer와 나란히 놓으면 안 맞는 이유가 이것이었다.

3-5. Bedrock 최신 모델은 관문이 3단이었다

증상
AccessDeniedException: anthropic.claude-opus-5 is not available for this account.
원인
세 가지가 순서대로 필요했다. ① 모델 액세스 페이지는 폐지되어 첫 호출 시 자동 활성화되지만, Anthropic 모델은 ② 사용 사례 양식 제출이 선행돼야 하고, 최신 모델은 추가로 ③ Marketplace 구독 계약(create-foundation-model-agreement)이 필요하다.
진단 방법
구형 모델(claude-3-5-sonnet-20240620)로 호출해 보니 성공했다. 계정·IAM·리전·양식은 정상이고 최신 모델만 막혔다는 뜻이라 원인이 구독 계약으로 좁혀졌다.
교훈. “권한 문제”로 보이는 것을 대조군으로 갈라내면 원인 범위가 한 번에 줄어든다.

3-6. 모델 ID가 호출 불가능한 형태였다

원인
anthropic.claude-opus-5는 서울에서 inferenceTypesSupported = INFERENCE_PROFILE 뿐이다(ON_DEMAND 없음). 기반 모델 ID로는 액세스를 켜도 ValidationException이 난다. 게다가 교차 리전 프로파일은 다른 리전에서 실행되므로 IAM의 기반 모델 ARN이 리전 와일드카드여야 한다 — 호출 리전만 박으면 라우팅된 순간 거부된다.
부수 발견
서울에서 ON_DEMAND를 지원하는 Anthropic 모델은 2024년 모델 2개뿐이고, 4.6+ 세대(adaptive thinking·effort·구조화 출력·캐싱을 쓰는 이 코드의 전제)는 전부 global.* 범위뿐이다. 즉 데이터 반출을 피하려면 코드를 재작성해야 한다.

4. 경로·이력 — 코드가 아니라 저장소 문제

4-1. 작업 사본이 둘이었고 양방향으로 갈라져 있었다

증상
저장소에서 go/terraform plan을 돌리면 ACM 인증서 2개를 replace하려 하고 no matching Route 53 Hosted Zone found로 죽었다.
원인
사본이 둘이었다. 비-git 사본에는 실제 운영 도메인(kycj.click)이, 저장소에는 옛 도메인(gochuchamchi.shop)이 있었다. 반대로 그날 만든 신규 기능은 저장소에만 있었다. daily-up.ps1이 $PSScriptRoot/../terraform을 적용하므로 어느 사본의 스크립트를 돌렸느냐로 결과가 갈렸다.
조치
전수 대조 결과 원본에만 있는 실질 내용은 도메인 2줄과 daily-down.ps1 수정뿐이었다 (나머지는 저장소가 앞서거나 CRLF 차이거나 스크립트 산출물). 둘을 가져온 뒤 비-git 사본을 .RETIRED-20260812로 이름 변경해 실행 경로를 하나로 만들었다.
교훈. 줄바꿈 차이를 배제하지 않으면 diff가 실제보다 10배 커 보인다 (diff --strip-trailing-cr). 그것 때문에 “통합 불가능”으로 판단할 뻔했다.

4-2. “Log 계정 대기”는 잘못된 귀속이었다

증상
아키텍처 문서가 중앙 로그와 앱 보안 로그를 “Log 계정 대기 2건”으로 적고 있었다.
원인
Log 계정은 이미 다 해둔 상태였다(Destination 3개 + rds-audit + ALB 버킷 실재 확인). 막힌 쪽은 워크로드였고, 이유는 단순했다 — 그 코드가 그날 아침 apply보다 늦게 커밋됐다. 
Ingress 생성                    09:47 KST
load-balancer-attributes 커밋   10:55 KST   ← 이후
rds-audit 커밋                  12:21 KST   ← 이후
조치
apply하니 두 건 모두 즉시 붙었다. 문서의 상태 표를 정정하고, 기준을 저장소가 아니라 describe-* 실물 조회로 바꿨다.
교훈. “코드에 있음”을 “배포됨”으로 읽으면 없는 의존을 만들어 낸다. 그 결과 남에게 책임을 잘못 귀속시켰다.

4-3. 미해결 account-baseline에 삭제 지뢰가 있다

증상
OAM Link 준비 중 plan에서 발견. 
# aws_cloudwatch_log_group.ssm_sessions will be destroyed
#   (because ... is not in configuration)
# aws_ssm_document.session_manager_prefs will be destroyed
상태
state와 실물은 살아 있는데(/gochuchamchi/ssm-sessions 보존 90일, SSM-SessionManagerRunShell Active) 코드 선언이 어디에도 없다. 전 스택 grep 0건, git 이력에도 0건, 은퇴 사본에도 없다.
위험
이대로 account-baseline을 apply하면 SSM 세션 로깅이 삭제된다. SSH가 없는 이 환경에서 유일한 접속 감사 증적이다. OAM Link도 같은 스택이라 Sink ARN을 받아도 이걸 먼저 풀어야 한다.
다음 조치
두 리소스를 account-baseline에 다시 선언해 IaC 관리로 되돌린다(plan이 no change가 되도록). terraform state rm은 실물을 살리지만 관리 대상 밖으로 밀어내 같은 사고를 반복시킨다.
