# SIEM 구축 — 상관 탐지 + Groq 판정 파이프라인

**작성일** 2026-08-12 · **대상 스택** `go/log-archive` (Security/Log 계정 `564186750363`) · **상태** 코드 완료, `terraform validate` 통과, **apply 전**

---

## 1. 무엇이 없어서 만들었나

로그는 이미 다 모이고 있었다. 없던 것은 **탐지**다.

| 층 | 이전 | 지금 |
|---|---|---|
| 수집 | ✅ CloudTrail·VPC Flow·WAF·ALB·앱 로그 → 중앙 S3 | 그대로 |
| 정규화 | ✅ `security_events` 뷰 (8필드 공통 스키마) | 탐지용 뷰 한 장 추가 |
| **탐지** | ❌ 사람이 콘솔에 들어가야만 뭔가 보임 | ✅ 상관 룰 4종 + 1시간 주기 자동 실행 |
| **판정** | ❌ | ✅ Groq 판정 계층 |
| **알림** | ❌ Log 계정엔 알림 경로 자체가 없었음 | ✅ 전용 SNS → Discord 보안 채널 + 이메일 |
| 조사 | 🟡 저장 쿼리 수동 실행 | 그대로 (알림에서 Athena 링크로 바로 연결) |

핵심은 **소스 간 상관분석**이다. "WAF에서 차단당한 IP가 30분 뒤 CloudTrail에
AccessDenied로 등장" 같은 건 단일 로그로는 절대 안 보인다. 정규화 뷰를 만든
이유가 이 질문을 쿼리 한 장으로 쓸 수 있게 하는 것이었고, 이번 작업이 그걸
실제로 쓰는 층이다.

## 2. 배선

```
CloudTrail / VPC Flow / WAF / ALB / 앱 로그      하루 수십만 건
        │
        │  Athena 상관 룰 4종 — 여기서 볼륨을 잡는다. 모델 관여 없음
        ▼
후보 (rule hit)                                  하루 수십 건
        │
        │  중복 억제 (DynamoDB, 기본 6시간)
        ▼
신규 후보
        │
        │  Groq 판정 — 호출량이 후보 수에 비례한다
        ▼
알림  ──→ SNS ──┬─→ Lambda → Discord 보안 채널
                └─→ 이메일 (Discord가 죽어도 이쪽은 산다)
```

**이 순서가 이 설계의 전부다.** 모델이 앞에 오면 토큰 비용이 트래픽에 비례해
따라 올라가 개인 프로젝트 규모에서 성립하지 않는다. 룰이 앞에서 볼륨을 잡고,
모델은 이미 좁혀진 후보만 본다. **원시 로그가 모델로 가는 경로는 없다.**

부수 효과가 하나 더 있다. 뒤에 판정이 붙으니 **룰 임계값을 재현율 우선으로
낮게** 잡을 수 있다. 룰이 혼자 정확해야 했다면 못 잡았을 경계선 사례까지
후보로 올리고, 소음 제거는 판정이 한다.

### 3-1. 뷰가 두 장이 된 이유

조사와 탐지는 요구가 정반대다.

| | `security_events` (조사용) | `security_events_recent` (탐지용) |
|---|---|---|
| 시간창 | 7일 | 2일 |
| 소스 | 5개 전부 | 4개 (**vpc_flow 제외**) |
| 누가 쓰나 | 사람, 하루 몇 번 | Lambda, 1시간마다 |

7일짜리를 시간마다 훑으면 스캔량이 7배가 되고 워크그룹의 1 GiB 상한에 걸려
**탐지가 조용히 실패한다.** SIEM에서 제일 나쁜 고장이다.

vpc_flow를 뺀 이유: 원시 용량이 압도적으로 크고, flow 레코드에는 인증 주체가
없어 상관 판단에 기여하는 정보가 거의 없다. flow가 실제로 필요한 룰(데이터
반출)은 **원본 테이블을 직접** 본다 — bytes 합계는 어차피 정규화된 `detail`
문자열로는 못 구하므로 이쪽이 기술적으로도 맞다.

창이 1일이 아니라 2일인 건, 파티션 단위가 하루라 UTC 자정 직후 lookback이
어제 파티션을 가리키기 때문이다.

### 3-2. 룰 4종

모든 룰은 첫 컬럼으로 `alert_key`를 반환한다 — 중복 억제 단위이고,
"무엇을 하나의 사건으로 볼 것인가"를 룰이 스스로 정하는 자리다.

| 저장 쿼리 | 심각도 | 잡는 것 | 판정 무시하고 항상 통보 |
|---|---|---|---|
| `20-rule-cross-layer-ip` | HIGH | 한 외부 IP가 2개 이상 계층에 출현 | |
| `21-rule-auth-failure-burst` | HIGH | 인증·인가 실패 폭증 (CloudTrail 권한거부 + 앱 로그인 실패) | |
| `22-rule-privilege-audit-tampering` | CRITICAL | IAM 권한 확대 / 로그·탐지 끄기 시도 | ✅ |
| `23-rule-data-egress` | MEDIUM | 내부→외부 대량 아웃바운드 | |

**룰 1의 함정 하나**: WAF와 ALB는 **같은 요청을 두 번 기록한다.** "2개 계층에
나타남"만으로 조건을 걸면 모든 정상 트래픽이 걸린다. 그래서 CloudTrail 계층이
끼면 계층 수만으로 후보, 아니면 거부가 `siem_cross_layer_denied_threshold`(기본 5)
이상 쌓여야 후보다.

**룰 3만 집계하지 않고 이벤트 하나하나를 올린다.** 건수가 적고 한 건이 곧
사건이기 때문이다. 실패한 시도도 올린다 — "CloudTrail을 끄려다 SCP에 막혔다"는
성공만큼 중요한 신호다.

### 3-3. 룰을 고치는 법

`siem-detection-rules.tf`의 `locals.siem_rules`에 항목 하나를 더하면 끝이다.
Athena 저장 쿼리(콘솔 튜닝용)와 Lambda가 읽는 룰 목록이 **같은 정의에서**
생성되므로, 콘솔에서 손으로 돌려 본 SQL과 매시간 자동 실행되는 SQL이 절대
어긋나지 않는다. Lambda는 저장 쿼리 ID로 SQL을 실행 시점에 읽으므로 **룰만
고칠 때 Lambda 재배포가 필요 없다.**

## 4. 안전장치

### 4-1. 판정이 없어도 알림은 나간다

Groq 장애·타임아웃·일일 한도 초과·스키마 위반·API 키 미주입 — **어느 경로로
빠져도** "판정 없음"을 붙여 발행한다. 모델 가용성이 탐지 가용성을 좌우하면 안 된다.

Discord 알림의 "판정 출처" 필드에 항상 출처(또는 없는 이유)가 찍힌다.
판정 없이 온 알림을 "AI가 정상이라고 했다"로 오해하지 않기 위한 것이다.

### 4-2. benign 판정이 알림을 없애는 구조의 위험과, 그 문 3개

모델 오판이 곧 미탐이 된다. 빠져나가는 문은 셋만 남겼다.

1. **`always_alert` 룰은 판정과 무관하게 통보** — 룰 3(권한 상승·감사 무력화)이
   여기 해당한다. "계획된 apply였는가"는 로그만 봐서는 모델도 사람도 확정할 수 없다.
2. **판정을 못 붙였으면 통보**
3. **benign이어도 확신이 `siem_judge_benign_min_confidence`(기본 0.7) 미만이면 통보**

benign으로 생략된 건도 원본은 Athena에 그대로 있고, `SuppressedByJudge` 지표와
Lambda 로그에 판정 근거가 남는다. **증거가 지워지는 경로는 없다.**

### 4-3. 외부로 나가는 데이터는 가린다

Groq은 AWS 밖이다. 계정 ID(12자리)·사설 IP·이메일은 가명(`ACCT-1`, `INT-1`,
`EMAIL-1`)으로 치환해서 보낸다. 같은 값은 같은 가명이라 "같은 주체인가"는
모델이 여전히 판단할 수 있다. **원본은 Athena에도 Discord 알림에도 그대로 뜬다
— 가려지는 건 외부로 나가는 사본뿐이다.**

> **남는 노출**: IAM 역할 이름·버킷 이름은 가리지 않는다. "이 역할이 CI
> 자동화인가 사람인가"가 판정의 핵심 근거라 가리면 판정이 무의미해지기
> 때문이다. 이름 규칙에 비밀이 들어가는 환경이면 `siem_judge_strict_masking = true`.

### 4-4. 프롬프트 인젝션

버킷 이름·User-Agent·IAM 역할 이름에 "이전 지시를 무시하라"를 심을 수 있다.

- 후보를 `<candidate>` 델리미터로 감싸 **데이터임을 명시**
- `response_format: json_object` + 스키마 검증으로 **자유 텍스트 파싱 제거**.
  계약 위반 출력은 고쳐 쓰지 않고 "판정 없음"으로 떨어뜨린다 —
  인젝션이 들어왔을 때 "고쳐서라도 쓰는" 파서가 가장 위험하다
- 인젝션 시도가 보이면 `injection_suspected`로 올리고, 그때 benign 판정은
  자동으로 suspicious로 승격된다. Discord에도 경고 블록이 뜬다
- 그리고 4-2가 최대 피해를 막는다

### 4-5. 시크릿은 tfstate에 안 들어간다

Groq API 키와 Discord 웹훅 모두 **그릇만 Terraform이 만들고 값은 사람이 넣는다.**
2026-08-05 §4에서 PAT로 배운 것과 같은 원칙이다.

### 4-6. 탐지가 멈춘 것을 알아챈다

실행마다 `DetectionRunSuccess=1`을 찍고, 두 주기 연속 지표가 없으면 알람이
SNS로 통보한다(`treat_missing_data = "breaching"` — 지표가 없는 것이 곧 고장).
**"알릴 게 없는 것"과 "탐지가 멈춘 것"이 구분되지 않는 상태**가 SIEM에서
가장 위험하다.

## 6. 배포 절차

### 6-1. apply

```powershell
cd C:\terraform\go\log-archive
terraform init
terraform plan
terraform apply
```

`hashicorp/archive` 프로바이더가 새로 필요해 `init`이 필수다.

> `data.archive_file.siem_detector`가 plan에서 "known after apply"로 나오는 건
> 정상이다 — 패키지에 넣는 `rules.json`이 Athena 저장 쿼리 ID를 참조하기 때문.

### 6-2. ⚠️ apply 후 반드시: 시크릿 2개 주입

둘 다 Terraform이 그릇만 만든다. 값을 넣지 않으면 조용히 반쪽으로 동작한다.

```powershell
# Discord 웹훅 — 안 넣으면 알림이 DLQ로 가고 DLQ 알람이 이메일로 온다
aws secretsmanager put-secret-value `
  --secret-id gochuchamchi/discord/siem-webhook `
  --secret-string '{\"webhook_url\":\"https://discord.com/api/webhooks/...\"}' `
  --region ap-northeast-2 --profile log-admin

# Groq API 키 — 안 넣어도 탐지·알림은 동작하고 판정만 "판정 없음"이 된다
aws secretsmanager put-secret-value `
  --secret-id gochuchamchi/siem/groq-api-key `
  --secret-string '{\"api_key\":\"gsk_...\"}' `
  --region ap-northeast-2 --profile log-admin
```

이메일 구독도 주입해야 자기 감시 루프의 최종 수신자가 생긴다:

```powershell
$env:TF_VAR_siem_alert_emails = '["someone@example.com"]'
```

apply 후 수신자가 확인 메일의 **Confirm subscription**을 눌러야 활성화된다.

### 6-3. ⚠️ Groq 키·모델 사전 검증

**Groq은 설치할 것이 없다.** HTTP API이고 `judge.py`는 파이썬 표준 라이브러리
`urllib`만 쓴다 — SDK도, Lambda 레이어도 없다. 필요한 건 계정과 API 키뿐이다.

1. `console.groq.com` 가입 → API Keys에서 키 생성 (`gsk_`로 시작)
2. 아래 스크립트로 **apply 전에** 키·모델·판정 경로를 한 번에 검증

```powershell
cd C:\terraform\go\log-archive\siem
$env:GROQ_API_KEY = "gsk_..."
python check-groq.py
```

스크립트가 하는 일: 키 유효성 확인 → 사용 가능한 모델 목록 출력 → 대상 모델이
목록에 있는지 확인 → **실제 `judge.py`를 그대로 태워** 판정 한 건을 받아 본다
(프롬프트 인젝션 문자열을 일부러 심어 방어까지 같이 본다).

여러 후보를 같은 입력으로 비교하려면:

```powershell
$env:GROQ_MODELS = "openai/gpt-oss-120b,openai/gpt-oss-20b"
python check-groq.py
```

**한국어로 답하는지를 자동 검사한다.** 오픈웨이트 모델 중에는 한국어 프롬프트를
받고도 영어로 답하는 것이 흔한데, 그러면 새벽에 알림 받는 사람이 계속 손해를 본다.

### 6-3-1. 모델 선택 근거 (2026-08-12 기준)

Groq 생산 모델 중 텍스트 4종:

| 모델 | 입력/출력 (1M 토큰당) | 속도 | 판단 |
|---|---|---|---|
| **`openai/gpt-oss-120b`** | **$0.15 / $0.60** | 500 tps | **기본값.** llama-3.3-70b보다 싸고 빠르고 크다 |
| `openai/gpt-oss-20b` | $0.075 / $0.30 | 1000 tps | 차선. 120b와 월 $1 미만 차이 |
| `llama-3.3-70b-versatile` | $0.59 / $0.79 | 280 tps | 가장 비싸고 느리다. **공식 지원 언어에 한국어가 없다** |
| `llama-3.1-8b-instant` | $0.05 / $0.08 | 560 tps | 보안 판정·인젝션 저항에 쓰기엔 작다 |

gpt-oss-120b가 llama-3.3-70b 대비 **입력 4배·출력 1.3배 저렴하고 1.8배 빠르다.**

### 6-3-2. 실측 결과 (2026-08-12, check-groq.py 동일 입력)

| | gpt-oss-120b | gpt-oss-20b |
|---|---|---|
| 판정 | suspicious (85%) | suspicious (80%) |
| 한국어 | O | O |
| 인젝션 감지 | O | O |
| 입력 토큰 | 1,875 | 1,875 |
| 출력 토큰 | 402 (사고과정 197) | 463 (사고과정 230) |
| 응답 시간 | 1.24초 | 1.16초 |
| **호출당 비용** | **$0.00052** | **$0.00028** |
| **월 비용 (최악 96회/일)** | **$1.50** | **$0.81** |

**둘 다 합격이고 차이는 월 $0.70다.** 그래서 품질로 고른다 — 120b가 요약이
더 구체적이고(3계층 142건 중 37건 거부를 정확히 짚음), 문체가 알림에 맞는
경어체다. 20b는 평서체(`했다`/`한다`)라 보고서처럼 읽히고 요약이 장황하다.
**결론: `openai/gpt-oss-120b`.**

파기한 Bedrock Opus 5 구성이 월 $75였으니 **50배 차이**다. 비용은 더 이상
모델 선택의 기준이 아니다.

> **입력 1,875 토큰의 대부분은 `context.md`다.** 판정 입력 비용의 주 조절
> 레버가 여기라는 뜻이고, 동시에 판정 정확도의 주 레버이기도 하다.
> 채우는 게 이득이다 — 이 규모에서 토큰 비용은 무시할 수 있다.

레이트리밋은 1000 RPM / 250K TPM인데 이 파이프라인은 **시간당 최대 4회**라
걸릴 일이 없다.

> **`reasoning_effort`는 모델마다 받는 값이 다르다.** gpt-oss는
> `low`/`medium`/`high`, qwen3.6은 `none`/`default`만 받는다. `judge.py`가
> 이 파라미터로 400을 맞으면 **빼고 한 번 자동 재시도**하므로, 모델을
> 갈아끼울 때 이것 하나로 판정이 멈추지는 않는다.

> ### ⚠️ "그록 컴파운드" 계열은 쓰지 말 것
>
> 웹 검색·코드 실행 도구가 내장된 에이전트 시스템이다. 판정 입력에는
> **공격자가 값을 정할 수 있는 문자열**(버킷 이름, User-Agent, IAM 역할 이름)이
> 들어간다. 거기에 도구가 붙으면 프롬프트 인젝션이 단순 오판을 넘어 **실제
> 외부 요청**으로 증폭된다. 판정에는 도구 없는 순수 추론 모델을 쓴다.

통과한 모델 ID를 `terraform.tfvars`의 `siem_groq_model`에 넣는다.

### 6-4. 첫 실행 검증

```powershell
# 스케줄을 기다리지 않고 즉시 실행
aws lambda invoke --function-name gochuchamchi-siem-detector `
  --region ap-northeast-2 --profile log-admin out.json
Get-Content out.json

# 로그 추적
aws logs tail /aws/lambda/gochuchamchi-siem-detector --follow `
  --region ap-northeast-2 --profile log-admin
```

확인 순서:

1. **뷰 재생성이 성공하는가** — 실패하면 Glue 권한 또는 테이블 스키마 문제다.
   `siem-detector.tf`의 `ReadCatalogAndManageViews` 스테이트먼트를 먼저 본다.
   여기서 실패하면 룰이 줄줄이 실패하므로 Lambda가 여기서 끊고 운영 알림을 낸다.
2. **룰 4개가 SUCCEEDED로 끝나는가** — `Query exhausted`/`bytes scanned` 오류면
   스캔 상한에 걸린 것이다. `security_events_detection_window_days`를 줄인다.
3. **`out.json`의 `scanned_bytes`가 얼마인가** — 이 값 × 24 × 30이 월 스캔량이다.
   여기서 실제 비용을 처음으로 확인할 수 있다.
4. **후보가 잡혔다면 Discord에 판정이 붙어 오는가** — "판정 출처"에
   `모델 판정 (모델명)`이 찍혀야 한다. `판정 없음`이면 그 사유가 같이 찍힌다.
5. **한 번 더 실행해 본다** — 같은 후보는 중복 억제로 알림이 안 와야 한다
   (`RuleHits`는 0, `RuleFindings`는 그대로).
6. **후보가 0건이면** Athena 콘솔에서 저장 쿼리 `20`~`23`을 직접 돌려 본다.
   임계값이 높은 건지 데이터가 없는 건지를 여기서 가른다.

## 7. 운영 튜닝 순서

며칠 돌린 뒤 이 순서로 조인다.

1. **`context.md`의 "아직 채워지지 않은 부분"을 먼저 채운다.** 판정 정확도의
   대부분이 여기서 나온다. 비어 있으면 모델이 "모르겠으니 suspicious"로 올린다.
2. **`SuppressedByJudge`가 특정 룰에서 계속 크면** 그 룰의 임계값을 올린다 —
   판정 호출을 태우고 있다는 뜻이다.
3. **룰 3이 apply 때마다 울리면** `siem_trusted_automation_principals`에
   **IaC 파이프라인 역할만** 넣는다. 사람 계정은 절대 넣지 말 것 — 탈취되면
   그게 바로 이 룰이 잡아야 할 사건이다.
4. **룰 4가 정상 목적지로 계속 울리면** 임계값을 올리지 말고
   `siem_egress_ignore_dst_regex`로 그 대역을 뺀다. 임계값을 올리면 조용히
   조금씩 나가는 진짜 반출을 통째로 못 본다.
5. **알림이 반복되면** `siem_alert_dedup_hours`를 늘린다.

> **운영 알림에는 중복 억제가 없다.** 룰 하나가 계속 실패하면 매 주기 알림이
> 온다. 의도된 동작이다 — 탐지 공백은 고칠 때까지 조용해지면 안 된다.
> 시끄러우면 억제를 늘리는 게 아니라 원인을 고치거나 그 룰을 빼야 한다.
